# Debugging Information vs Symbol Table
The debugging information here refers to the debug_* related information; the symbol table refers to symtab and dynsym.

Debugging information is only produced when compiling with the -g option.

The symbol table actually comes in two kinds, symtab and dynsym, which are produced even without -g, because they are needed during relocation.
- symtab includes two kinds of symbols: global symbols and local static symbols.
- dynsym contains only the symbols needed to load dynamic libraries.
#   Stripping the Symbol Table
Stripping the symbol table usually means removing the symbol information contained in a program, to reduce the program's size or for security/privacy reasons. Symbol information typically includes function names, global variable names, and static variable names. This can be done with a tool like strip, which removes all symbol information from executables and object files.

For example, for a C program compiled with gcc, you can strip the symbol table like this:

```bash

gcc -g -o my_program my_program.c
strip --strip-all my_program
 
```

After compiling and stripping symbols with the commands above, my_program loses all symbol information, making debugging much harder. Without a symbol table, gdb cannot set breakpoints or inspect variable values by function name or variable name. When reverse engineering, analyzing a stripped program is also more difficult because symbol information is missing.

Note that strip only removes the symbol table; it does not remove the debugging information generated by the -g option, which is stored in other parts of the program. If you want to remove the debugging information along with the symbol table, you need different strip options or to compile without -g. For example:

```bash
strip --strip-debug my_program
```

 
This command removes the debugging information from the file, not just the symbol table
# If You Compile with -g but Strip the Symbol Table, Can You Still Debug at Source Level (Seeing Which Source Line Corresponds to Each Assembly Instruction Executed)?
When you compile a program with the -g option, debugging information is added to the executable, including line-number information from the source code. If you later use a tool (like strip) to remove the symbol table but not the debugging information in the .debug sections, then in theory you can still do a degree of source-level debugging in gdb. This is because source line-number information is usually stored in the debug sections, not the symbol table.

Even with the symbol table removed, as long as the .debug debugging-information sections remain, gdb should still be able to map assembly instructions to source-code line numbers. This means that in some cases, as you step through the program, you can indeed see which source line each assembly instruction corresponds to.

However, removing the symbol table imposes the following limitations:

- You cannot use function names or variable names to set breakpoints, because that information is normally stored in the symbol table.
- Inspecting and manipulating variables becomes very difficult, especially local and static variables, because resolving them requires data from the symbol table.


# Loading Debug Information in gdb
[Reference link](https://bbs.kanxue.com/thread-254868.htm#msg_header_h1_0)
When debugging with GDB it is not easy to see the various structures in libc, so we need to load symbol tables to make debugging easier.

When Ubuntu's package maintainers compile the corresponding ELF files, they separate the symbol tables from the ELF files and name the symbol packages "*-dbg.deb". This lets us manually download the symbol tables for convenient debugging.

If you use a libc downloaded with "glibc all in one", the libc's symbol table is stored in a ".debug" folder alongside the libc libraries, and gdb can load it automatically. But when you encounter a libc version that "glibc all in one" does not have, you need to download the debug file manually and load it manually.

## Putting the Debug File into a ".debug" Folder
Create a ".debug" folder in the directory where the libc resides and put the debug file into it.

## Using the gdb Command set debug-file-directory directories
We need to put the debug files of libc and other libraries into the corresponding folder, then use the set debug-file-directory $directories command to set that folder as the separate debug-file directory, so gdb can load the debug files.

# [The Difference Between GCC's gcc and g++](https://www.cnblogs.com/samewang/p/4774180.html)
GCC: GNU Compiler Collection, which can compile C, C++, JAV, Fortran, Pascal, Object-C, Ada, and other languages.

gcc is the GNU C Compiler (C compiler) in GCC

g++ is the GNU C++ Compiler (C++ compiler) in GCC

An interesting fact: in essence, gcc and g++ are not compilers, nor collections of compilers; they are just drivers that invoke the corresponding GNU compiler based on the type of file to be compiled given in the arguments. For example, compiling a c file with gcc involves the following steps:

Step1：Call a preprocessor, like cpp.

Step2：Call an actual compiler, like cc or cc1.

Step3：Call an assembler, like as.

Step4：Call a linker, like ld

Since the compiler can be swapped out, gcc can compile more than just C files

So, more precisely: gcc invokes the C compiler, while g++ invokes the C++ compiler


# Compiling with Specified gcc/g++ and glibc Versions
Different versions of GCC implement different versions of the C and C++ standard libraries, which has some impact on code compatibility. The correspondence between each gcc version and the standard library version can be found in the official documentation. Using different versions of the standard library can cause code to compile and behave differently, or even produce errors. Therefore, when writing code you should know which standard library version you are using and avoid deprecated or unmaintained standard libraries.

# The Paths gdb Searches for Separate Debug Files
[Reference link](https://zhuanlan.zhihu.com/p/669022391)

The paths gdb searches for separate debug files are:

1. The directory where the current file resides.
2. The .debug directory under the directory where the current file resides.
3. The directories set by debug-file-directory; the search for the current executable's debugging information combines the file's actual path. (For example, if the debug-file-directory is /usr/lib/debug and the executable is located at /home/test/example, then gdb looks for the example.debug file under /usr/lib/debug/home/test/.) For the debugging information of a shared library (.so), the directory shown by ldd is used. You can directly concatenate the debug-file-directory with the directory shown by ldd. (For example, if the debug-file-directory is /usr/lib/debug and ldd shows liba.so at /home/zy/debuginfo/fff/liba.so, gdb will read the debuginfo file for liba.so under /usr/lib/debug/home/zy/debuginfo/fff.)


```bash
set debug-file-directory directories
Set the directories which GDB searches for separate debugging information files to directory. Multiple path components can be set concatenating them by a path separator.

show debug-file-directory
Show the directories GDB searches for separate debugging information files.
```

> As mentioned earlier, it is also fine to place the debuginfo file directly under /usr/lib/debug (or the root directory set with the set-debug-file-directory command), but the directory structure must mirror the runtime directory structure. One caveat: especially for .so files, when looking up the corresponding debuginfo file under debug-root-directory, the path does not necessarily match the file's actual location — it depends on the path the linker can find, i.e., the path shown by ldd. gdb looks for the corresponding debuginfo file under debug-root-directory/$LDD-shown-directory. The path shown by ldd may be absolute or relative, depending on the .so search paths configured in your operating system — for instance, whether LD_LIBRARY_PATH is set to a relative or an absolute path — and for gdb the path to look up under debug-root-directory differs accordingly. gdb directly concatenates the ldd-shown path with debug-root-directory. For example, if my current LD_LIBRARY_PATH is ./fff, then gdb will read the debuginfo file for liba.so under /usr/lib/debug/./fff, because the path ldd shows for liba.so is ./fff/liba.so.

# Source-Level Debugging of libc in gdb (the Paths Where gdb Searches for Source Code)
When compiling with gcc, if you compile with the -g option, debugging information is attached to the binary so gdb can debug at the source level. `如果二进制中存在调试信息，会去相关目录寻找源码，GDB首先在编译时目录中搜索，如果失败则在当前目录中搜索，即$cdir:$cwd，其中$cdir指的是编译时目录（compilation directory），$cwd指的是当前工作目录（current working directory）。` If the source files are found, you can use gdb's list command to view the source.
By installing a libc with debugging information on Ubuntu and downloading the libc source code, you can configure gdb to step into libc library functions with source-level debugging

> However, if gdb cannot find the source files in the directories it searches by default, source-level debugging is impossible. If the source is in another directory, you can specify it in gdb with the directory or dir command, or with the -d option when starting gdb — either way you can still see the source code.
