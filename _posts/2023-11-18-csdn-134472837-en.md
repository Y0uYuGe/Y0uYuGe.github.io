# Heap off-by-one
off-by-one refers to a single-byte buffer overflow (off-by-one can be based on various buffers, such as the stack, the bss segment, etc.)
Writing one byte more than was requested

 - The loop is set up incorrectly, writing one extra byte
 - The string length is judged incorrectly
   strlen() computes the length of a string without including the null terminator 
   After calling the gets function, the string terminator is automatically appended to the end of the input string    	  
   strcpy also copies the null terminator when copying)

# Exploitation Ideas
 - When the overflowing part can be controlled to arbitrary bytes and the overflowed part is the size field, you can modify the size, thereby leaking data from other chunks or overwriting data of other chunks
 - When the overflowing part is fixed as a NULL byte, and the overflowed part is the size field, and the size is a multiple of 0x100, its low byte will be cleared to 0 and all flag bits will be cleared as well, so the previous chunk will be considered a free chunk
 
   (1) unlink can be exploited
   (2) You can construct both prev_size and the corresponding NULL byte overflow at the same time, then consolidate during unlink; the key to this method is that unlink does not check whether the size of the chunk found via prev_size matches prev_size.

**Note: versions after 2.28 have a check that verifies whether the size of the chunk found via prev_size matches prev_size; versions 2.28 and earlier do not have this check**

```c
/* consolidate backward */
    if (!prev_inuse(p)) {
      prevsize = prev_size (p);
      size += prevsize;
      p = chunk_at_offset(p, -((long) prevsize));
      /* 后两行代码在最新版本中加入，则 2 的第二种方法无法使用，但是 2.28 及之前都没有问题 */
      if (__glibc_unlikely (chunksize(p) != prevsize))
        malloc_printerr ("corrupted size vs. prev_size while consolidating");
      unlink_chunk (av, p);
    }
```

# Approach
Three types of chunks: the first type is for the name, the second type is for the description, and the third type stores information related to the name and description chunks
Two blobs of space: off_202010 and off_202018 store the addresses at offsets 202060 and 202040 respectively; offset 202060 corresponds to the author name, and offset 202040 corresponds to the address of the third type of chunk
![在这里插入图片描述](/images/csdn/2023/csdn-134472837/image-010-e71213a406.png)

mmap is used for allocation only when the size approaches or exceeds the top_chunk size (128KB = 2^17 bytes, i.e., 0x2000).
The offset between certain libc versions and mmap-allocated chunks is fixed.

 - Exploiting the overflowing null byte property: first write a 32-byte name, then creat twice. The chunk corresponding to the first time is allocated by malloc, and when the low byte of this third-type chunk's address is overwritten with \x00 it happens to correspond to the address of the second-type chunk; the chunk corresponding to the second time is larger than the top_chunk size and thus allocated by mmap. Then, using the \x00 truncation property of printf, you can obtain the address of the third-type chunk corresponding to the first time
 - Then rewrite the description of the first chunk (the second-type chunk), constructing it as a chunk whose description part points to the address of the second chunk; then rewrite the name, overwriting a null byte into the pointer array position storing the third-type chunk corresponding to the first chunk, making its lowest byte \x00, thereby pointing to the second-type chunk address of the first chunk, 
 - Then print; at this point it outputs the address of the description chunk corresponding to the second chunk. Since that chunk is mmap-allocated, the distance between this chunk's address and the libc base is fixed for this version, so the libc base address can be computed, and from there the __free_hook address and the system function address
- Then rewrite the description of the current first chunk (which has already been constructed as the description chunk of the original first chunk), thereby modifying the address of the description chunk inside the third-type chunk of the second chunk — write the __free_hook address here; then rewriting the description of the second chunk allows modifying the content of __free_hook to the system function address
- Modify the description of the first chunk again to write /bin/sh into the description part of the third-type chunk of the second chunk; finally, dele the first chunk, which calls the free function with the argument being the address of /bin/sh

## Approach
1. Use the IDA offset plus the base address obtained with the vmmap command (or use the search command in pwngdb to search for the string and thereby learn its location)
2 Learn the printf truncation property and that writing to the original chunk overwrites the low byte of the address with \x00 (not yet)
3 Forge the structure at the position corresponding to the structure pointer that will be overwritten (not overwritten yet, but forged)
4 Overwrite the original structure pointer
5 Use the overwritten structure pointer
7 Set part of the fake chunk to the address of a certain location to obtain the content at that address; use printf again to cause a leak, thereby learning the function address
8 Debug to check whether the offset between the leaked function address and the libc.so base address is fixed, thereby computing its base address
9 Use pwntools to find the offset of _free_hook in the libc.so library and add the base address, etc.
10 Write the address of the _free_hook variable to a certain position (so the content pointed to by the address stored at that position can be modified). You can modify the value of the _free_hook variable to the system function address, then modify the value at the position corresponding to free's argument to the address of /bin/sh; finally, using the free argument gets you a shell
