# uint64_t
uint64_t is an unsigned integer type in C/C++ that represents a 64-bit unsigned integer. In a computer, unsigned integers are stored in two's complement binary form, so its value range is from 0 to 2^64-1 (that is, 18446744073709551615).

The full name of uint64_t is unsigned int 64-bit.

In C, uint64_t is an alias defined via typedef, representing an unsigned 64-bit integer type. This naming style is a standardized representation, where "u" stands for unsigned, "int" stands for integer, and "64" indicates that this is a 64-bit integer type. Using these standard data type aliases improves code readability and maintainability, because they clearly indicate the size and properties of the data type. For example, uint8_t, uint16_t, uint32_t, and uint64_t represent 8-bit, 16-bit, 32-bit, and 64-bit unsigned integer types respectively.

These data types are all defined in the C99 standard. They are not new data types, but aliases of existing data types. The benefit of this is that even though the sizes of these types may differ on different platforms, using these standard aliases ensures code consistency and portability.

# std::array
std::array is a fixed-size array container that provides many features that built-in arrays do not have, while maintaining the same random access capability and efficiency as native arrays. Here are some of the main usages of std::array:

# CPU and CU
The CPU (Central Processing Unit) and the CU (Control Unit) are core components in a computer, and they differ in function. The details are as follows:

CPU: it is the brain of the computer, responsible for executing program instructions and processing data. It consists of multiple components, including the Arithmetic Logic Unit (ALU), the Control Unit (CU), registers, and so on. The CPU uses complex circuits internally to perform various computational and logical operations, and it is also responsible for handling data exchange with memory and input/output devices.
CU: it is a component inside the CPU, with the full name Control Unit. The main function of the CU is to issue various control commands or microinstructions to control the work of the entire computer system, including the various components inside the CPU. The CU coordinates the work of each component to ensure that programs can execute smoothly according to the predetermined flow.

# RISC-V encoding of add and addi
![Image](/images/csdn/2024/csdn-136341332/image-002-719fd7965b.png)
In RISC-V, instruction encoding formats are divided into several types, among which the addi instruction uses the I-type format, while the add instruction uses the R-type format. The machine code of each instruction type is 32 bits wide, and every bit has a specific role.

The I-type format of the addi (Add Immediate) instruction: the RISC-V I-type instruction format is as follows:

```c
┌───────┬───────┬───────┬─────────────┬───────┬───────┐
│ funct7 │  rs2  │  rs1  │    funct3   │   rd  │ opcode│
├───────┼───────┼───────┼─────────────┼───────┼───────┤
│    立即数 (12 bits)    │   rs1 (5 bits)  │  funct3 |   rd (5 bits)   │ opcode (7 bits) │
└────────────────────────┴─────────────┴────────┴─────────────┘ 
```

 
opcode (7 bits): the opcode, which is 0010011 for addi.
rd (5 bits): the number of the destination register.
funct3 (3 bits): the function code, which is 000 for addi.
rs1 (5 bits): the number of source register 1.
Immediate (12 bits): the immediate value to be added; it is signed and is automatically sign-extended to 32 bits or more when executed.
For example, for the instruction addi x5, x10, 15, its binary encoding might look like the following (only the operation-related binary bits are shown, not including the specific immediate value and register numbers):

```c
00000000000011110110000010010011
```

 
The R-type format of the add (Add) instruction: the RISC-V R-type instruction format is as follows:

```c
┌───────┬───────┬───────┬─────────────┬───────┬───────┐
│ funct7 │  rs2  │  rs1  │    funct3   │   rd  │ opcode│
├───────┼───────┼───────┼─────────────┼───────┼───────┤
│ funct7 (7 bits)│ rs2 (5 bits)│ rs1 (5 bits)│ funct3 (3 bits)│rd (5 bits)│opcode (7 bits)│
└───────┴───────┴───────┴─────────────┴───────┴───────┘
```

 
opcode (7 bits): the opcode, which is 0110011 for add.
rd (5 bits): the number of the destination register.
funct3 (3 bits): the function code, which is 000 for add.
rs1 (5 bits): the number of source register 1.
rs2 (5 bits): the number of source register 2.
funct7 (7 bits): for add, this field is 0000000.
For example, for the instruction add x5, x10, x20, its binary encoding might look like the following (only the operation-related binary bits are shown):

```c
00000001010010100000010110110011
```

 
# Simple CPU Workflow

In modern computer architecture, especially in computer systems following the von Neumann architecture, program execution can be broken down into several consecutive stages that together constitute the CPU's instruction cycle. These stages include Instruction Fetch (IF), Instruction Decode (ID), Execute (EX), Memory Access (MEM), and Write Back (WB). This process runs in a loop, with each stage completing a specific task to ensure the smooth execution of computer programs.

```c

+--------+   +--------+   +--------+   +--------+   +--------+
| 取指IF  |-->| 解码ID |-->| 执行EX  |-->| 访存MEM |-->| 写回WB |
+--------+   +--------+   +--------+   +--------+   +--------+
```

In this diagram, each row represents an instruction in the CPU passing through different processing stages over time. Each box represents a stage of the pipeline, and the arrows indicate the flow of an instruction moving from one stage to the next. This design allows up to five instructions to be in different execution stages within any given clock cycle, greatly improving CPU efficiency and performance.

- Instruction Fetch IF: read the instruction from memory.
The CPU reads the instruction from memory using the address pointed to by the program counter (PC). After reading, the PC is updated to the address of the next instruction in preparation for the next cycle.
- Instruction Decode ID: parse the instruction and prepare the necessary operands.
The instruction decoder (ID) parses the fetched instruction and determines the operation to be performed and the operands. This may involve extracting immediates from the instruction, computing addresses, determining register numbers, and so on.
- Execute EX: perform computation or other operations.
The execute stage performs the corresponding arithmetic logic operation (ALU operation), branch decision, or other operations based on the results of the decode stage. This stage may need to use the ALU (Arithmetic Logic Unit).
- Memory Access MEM: perform memory access, such as data load or store.
If the instruction needs to read memory (such as a load operation) or write data to memory (such as a store operation), this stage completes that operation. This step is optional because not all instructions need to access memory.
- Write Back WB: write the execution result back to a register.

Write the result of the execute stage, or the data read from memory in the memory access stage, back to the specified register. This step ensures that the execution result of the instruction can be used by subsequent instructions.
These five stages together constitute the complete execution cycle of an instruction and are the foundation of modern CPU design. By breaking instruction execution down into these stages, the computer can run programs in an efficient and orderly manner. Each stage is handled by a different part of the CPU, allowing the computer to execute different stages of multiple instructions at any given moment. This design is the foundation of pipeline processing and greatly improves CPU execution efficiency.



# Implementation Process
Create add-addi.s and write the following content into it

```bash
.global _start
_start:
    addi x29, x0, 100
    addi x30, x0, 200
    add x31, x30, x29
```

In assembly language, the statements .global _start and _start: define the entry point of the program.

- .global _start: this directive tells the linker that the _start label is a global symbol that can be accessed by other parts of the program or by other linked files. More importantly, it marks _start as the entry point of the program, that is, the starting position of program execution. This is critical for the operating system (OS), because when the program is loaded into memory and executed, the operating system needs to know where to start executing the program.

- _start:: this is a label, and the entry point of the program immediately follows it. The instructions written at this position will be the first batch of instructions executed by the program. In a bare-metal environment or in operating system kernel development, _start is the starting point of the execution flow, with no standard library or runtime environment initialization process.

In summary, .global _start and _start: together define where the program starts executing, giving the operating system a clear starting point to run the program. If you don't write them, an error will be reported.

This code is written in RISC-V assembly language, and it performs a very simple task: compute the sum of two values and store the result. Specifically, the code does the following things:

- Store the number 100 into register x29.
- Store the number 200 into register x30.
- Add the values in registers x29 and x30, and store the result into register x31.

In summary, this code simply computes the sum of 5 and 37, and then stores the result 42 into register x31.

#include<bits/stdc++.h>

class DRAM
{

class CPU    //CPU 从存储器中读取指令，解析指令，然后执行指令
{
    std::array<uint64_t,32> registers={0};
    
    uint64_t pc;
    
    uint32_t ir;

    std::vector<uint8_t> recv_dram_addr;

    public:
    CPU(std::vector<uint8_t>positon)
    {
        pc=0;
        ir=0;
        recv_dram_addr=positon;
    }

    uint32_t get_code()
    {
        
        uint32_t code=static_cast<uint32_t>(recv_dram_addr[pc])
            |static_cast<uint32_t>(recv_dram_addr[pc+1]<<8)
            |static_cast<uint32_t>(recv_dram_addr[pc+2]<<16)
            |static_cast<uint32_t>(recv_dram_addr[pc+3]<<24);
        pc=pc+4;
        return code; //little-endian
    } 
    
    void decode_execute(uint32_t code)
    {
        uint32_t opcode=(code)&0x7f;
        uint32_t rd=(code>>7)&0x1f;
        uint32_t funct3=(code>>12)&0x3;
        uint32_t rs1=(code>>15)&0x1f;
        uint32_t rs2=(code>>20)&0x1f;
        uint32_t funct7=(code>>25)&0x7f;
        uint32_t imm=(code>>20)&0xfff;

        switch(opcode)
        {
            case 0x33: //add
            {
                registers[rd]=registers[rs1]+registers[rs2];
                break;
            }
            case 0x13: //addi
            {
                registers[rd]=registers[rs1]+imm;
                break;
            }
            default:
            {
                std::cout<<"invalid opcode";
                break;
            }
        }
    }

            <<" x"<<std::setw(1)<<std::setfill('0')<<i+2<<"("<<registers_name[i+2]<<") "<<registers[i+2]
            <<" x"<<std::setw(1)<<std::setfill('0')<<i+3<<"("<<registers_name[i+3]<<") "<<registers[i+3]
            <<std::endl;
        }
    }

    void run()
    {
        while(pc<recv_dram_addr.size())
        {
            uint32_t code=get_code();
            decode_execute(code);
        }
    }

};
