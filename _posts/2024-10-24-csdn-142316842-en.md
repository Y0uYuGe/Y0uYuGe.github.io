# pipe

### Overview

`pipe(7)` is the Linux manual page giving an overview of pipes and named pipes (FIFOs). A pipe provides a unidirectional inter-process communication (IPC) channel with a read end and a write end. Data is written to the write end and can be read from the read end.

### Creating pipes

#### Anonymous Pipes

- **Creation**:
  - Created using the `pipe(2)` system call.
  - Calling `pipe(2)` creates a new pipe and returns two file descriptors: one for the read end (usually `pipefd[0]`), and one for the write end (usually `pipefd[1]`).
  - Anonymous pipes are typically used for communication between parent and child processes.

- **Example**:
  ```c
  #include <unistd.h>
  #include <stdio.h>

  int main() {
      int pipefd[2];
      char buf[100] = "Hello, pipe!";
      
      if (pipe(pipefd) == -1) {
          perror("pipe");
          return 1;
      }
      
      // 写入数据
      write(pipefd[1], buf, sizeof(buf));
      
      // 读取数据
      char read_buf[100];
      ssize_t n = read(pipefd[0], read_buf, sizeof(read_buf));
      if (n == -1) {
          perror("read");
          return 1;
      }
      
      read_buf[n] = '\0';
      printf("Read: %s\n", read_buf);
      
      // 关闭文件描述符
      close(pipefd[0]);
      close(pipefd[1]);
      
      return 0;
  }
  ```

#### Named Pipes (FIFOs)

- **Creation**:
  - Has a name in the filesystem, created using the `mkfifo(3)` function.
  - When calling `mkfifo(3)`, you need to specify a path and a permission mode.
  - Opened using the `open(2)` system call, where you can specify the `O_RDONLY` or `O_WRONLY` flag.
  - Any process can open a FIFO, as long as the file permissions allow it.

- **Example**:
  ```c
  #include <sys/types.h>
  #include <sys/stat.h>
  #include <fcntl.h>
  #include <unistd.h>
  #include <stdio.h>

  int main() {
      const char *fifo_path = "/tmp/myfifo";
      
      // 创建 FIFO
      if (mkfifo(fifo_path, 0666) == -1) {
          perror("mkfifo");
          return 1;
      }
      
      // 打开 FIFO 用于写入
      int fd = open(fifo_path, O_WRONLY);
      if (fd == -1) {
          perror("open");
          return 1;
      }
      
      // 写入数据
      const char *msg = "Hello, FIFO!";
      write(fd, msg, strlen(msg));
      
      // 关闭文件描述符
      close(fd);
      
      // 删除 FIFO
      unlink(fifo_path);
      
      return 0;
  }
  ```

### I/O operations

- **Read/write operations**:
  - **Read operations**:
    - If you try to read from an empty pipe, `read(2)` blocks until there is data to read.
    - If all write ends are closed, `read(2)` returns 0, indicating end of file.
  - **Write operations**:
    - If you try to write to a full pipe, `write(2)` blocks until there is enough space.
    - If all read ends are closed, `write(2)` generates a `SIGPIPE` signal, returns -1, and sets `errno` to `EPIPE`.
  - **Non-blocking I/O**:
    - Non-blocking I/O can be achieved by enabling the `O_NONBLOCK` flag via the `F_SETFL` operation of `fcntl(2)`.
    - For a FIFO, if any process has already opened the write end, a read operation returns `EAGAIN`; otherwise, if there is no potential writer, the read succeeds and returns empty.

- **Atomicity**:
  - Writes of data smaller than or equal to `PIPE_BUF` bytes are atomic, i.e. the data is written to the pipe as one contiguous sequence.
  - Writes of data larger than `PIPE_BUF` bytes may be non-atomic; the kernel may split the data into multiple parts written to the pipe, and writes from other processes may be interleaved between these parts.
  - POSIX.1 requires `PIPE_BUF` to be at least 512 bytes; on Linux it is usually 4096 bytes.

### Configuration options

- **/proc filesystem**:
  - `/proc/sys/fs/pipe-max-size`: sets the maximum pipe capacity (in bytes).
  - `/proc/sys/fs/pipe-user-pages-hard`: sets a hard limit on the total number of pages a single unprivileged user can allocate to pipe buffers.
  - `/proc/sys/fs/pipe-user-pages-soft`: sets a soft limit on the total number of pages a single unprivileged user can allocate to pipe buffers.

### Related functions and system calls

- **Creation and management**:
  - `pipe(2)`: create an anonymous pipe.
  - `mkfifo(3)`: create a named pipe.
  - `open(2)`: open a named pipe.
  - `fcntl(2)`: manage file descriptor attributes.
  - `dup(2)`: duplicate a file descriptor.
  - `close(2)`: close a file descriptor.

- **I/O operations**:
  - `read(2)`: read data from a pipe.
  - `write(2)`: write data to a pipe.
  - `poll(2)` and `select(2)`: monitor the status of multiple file descriptors.
  - `splice(2)` and `tee(2)`: transfer data efficiently.
  - `vmsplice(2)`: write the contents of a user-space memory region into a pipe.

- **Others**:
  - `stat(2)`: get file status.
  - `unlink(2)`: delete a file.
  - `epoll(7)`: an efficient I/O multiplexing mechanism.
  - `fifo(7)`: details about named pipes.

### Communication semantics

- **Byte stream**:
  - The communication channel provided by a pipe is a byte stream, with no concept of message boundaries.
  - Data is written and read in order, but there are no explicit message delimiters.

### Example code

#### Anonymous pipe example

```c
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    int pipefd[2];
    pid_t cpid;
    char buf[100];

    if (pipe(pipefd) == -1) {
        perror("pipe");
        exit(EXIT_FAILURE);
    }

    cpid = fork();
    if (cpid == -1) {
        perror("fork");
        exit(EXIT_FAILURE);
    }

    if (cpid == 0) {    // 子进程
        close(pipefd[1]); // 关闭写端
        ssize_t n = read(pipefd[0], buf, sizeof(buf));
        if (n == -1) {
            perror("read");
            exit(EXIT_FAILURE);
        }
        buf[n] = '\0';
        printf("Child: received '%s'\n", buf);
        close(pipefd[0]);
        exit(EXIT_SUCCESS);
    } else {            // 父进程
        close(pipefd[0]); // 关闭读端
        const char *msg = "Hello, child!";
        write(pipefd[1], msg, strlen(msg));
        close(pipefd[1]);
        wait(NULL);     // 等待子进程结束
        exit(EXIT_SUCCESS);
    }
}
```

# The race point
[Arbitrary read-only file vulnerability analysis](https://xie.infoq.cn/article/c2bdf20841b48d407b1485c9a)
It lies in pipe_write

Roughly speaking: after the first process finishes writing to the pipe and releases the lock, the other processes all start writing in turn, but like the first process they all block in wait_event_interruptible_exclusive; only then does the read process get its turn to read. After the read finishes, each process's wait_event_interruptible_exclusive returns, and then they acquire the lock and write again.

So who gets to write first depends on who is faster going from exiting wait_event_interruptible_exclusive to acquiring the lock

Let's go into detail below
## Mutex
Of course, below is a detailed explanation of `mutex_init`, `mutex_lock`, and `mutex_unlock`, including how they work and their internal mechanisms.

### 1. `mutex_init`

#### Definition
```c
#define mutex_init(mutex) \
do {							\
	static struct lock_class_key __key;		\
								\
	__mutex_init((mutex), #mutex, &__key);		\
} while (0)
```

#### Purpose
`mutex_init` is used to initialize a mutex. It ensures the mutex is in an unlocked state and ready to be used.

#### Implementation
```c
void __mutex_init(struct mutex *lock, const char *name, struct lock_class_key *key)
{
	atomic_set(&lock->count, 1); // 将计数器设置为1，表示未锁定
	spin_lock_init(&lock->wait_lock); // 初始化自旋锁，用于保护等待队列
	INIT_LIST_HEAD(&lock->wait_list); // 初始化等待队列
	mutex_clear_owner(lock); // 清除所有者信息
#ifdef CONFIG_MUTEX_SPIN_ON_OWNER
	lock->spin_mlock = NULL; // 初始化自旋锁指针（如果启用了相关配置）
#endif
 
	debug_mutex_init(lock, name, key); // 调试信息初始化
}
```

#### How it works
- **Counter initialization**: `atomic_set(&lock->count, 1)` sets the mutex counter to 1, indicating the mutex is not locked.
- **Spinlock initialization**: `spin_lock_init(&lock->wait_lock)` initializes a spinlock used to protect the wait queue.
- **Wait queue initialization**: `INIT_LIST_HEAD(&lock->wait_list)` initializes a list head used to manage the tasks waiting to acquire the mutex.
- **Clear owner information**: `mutex_clear_owner(lock)` clears the mutex owner information.
- **Debug info initialization**: `debug_mutex_init(lock, name, key)` is used for debugging purposes, recording the mutex name and class key.

### 2. `mutex_lock`

#### Definition
```c
void __sched mutex_lock(struct mutex *lock)
{
	might_sleep(); // 提示编译器该函数可能会睡眠
	/*
	 * The locking fastpath is the 1->0 transition from
	 * 'unlocked' into 'locked' state.
	 */
	__mutex_fastpath_lock(&lock->count, __mutex_lock_slowpath);
	mutex_set_owner(lock);
}
```

#### Purpose
`mutex_lock` is used to acquire a mutex. If the mutex is already held by another task, the current task goes to sleep until the mutex becomes available.

#### Implementation
- **Hint about possible sleep**: `might_sleep()` hints to the compiler that this function may sleep, ensuring the caller does not call this function in a context where sleeping is forbidden.
- **Fast path**: `__mutex_fastpath_lock(&lock->count, __mutex_lock_slowpath)` tries to acquire the mutex quickly. If the mutex is not locked, it directly decrements the counter from 1 to 0, indicating it is locked. If the mutex is already locked, it calls the slow path `__mutex_lock_slowpath`.
- **Set owner**: `mutex_set_owner(lock)` sets the owner of the mutex to the current task.

#### How it works
- **Fast path**: tries to atomically decrement the counter from 1 to 0. If it succeeds, the mutex has been acquired by the current task.
- **Slow path**: if the fast path fails (i.e. the mutex is already held by another task), the slow path `__mutex_lock_slowpath` is called. The slow path adds the current task to the wait queue and puts the current task to sleep until the mutex becomes available.
- **Set owner**: ensures the mutex owner information is correctly set to the current task.

### 3. `mutex_unlock`

#### Definition
```c
void __sched mutex_unlock(struct mutex *lock)
{
	/*
	 * The unlocking fastpath is the 0->1 transition from 'locked'
	 * into 'unlocked' state:
	 */
#ifndef CONFIG_DEBUG_MUTEXES
	/*
	 * When debugging is enabled we must not clear the owner before time,
	 * the slow path will always be taken, and that clears the owner field
	 * after verifying that it was indeed current.
	 */
	mutex_clear_owner(lock); // 清除所有者信息
#endif
	__mutex_fastpath_unlock(&lock->count, __mutex_unlock_slowpath);
}
```

#### Purpose
`mutex_unlock` is used to release a mutex. This function may only be called to release the mutex when the current task holds it.

#### Implementation
- **Clear owner information**: `mutex_clear_owner(lock)` clears the mutex owner information. If debug mode is enabled, this operation is done in the slow path.
- **Fast path**: `__mutex_fastpath_unlock(&lock->count, __mutex_unlock_slowpath)` tries to release the mutex quickly. If the mutex is held by the current task, it directly increments the counter from 0 to 1, indicating the mutex is unlocked. If the mutex is not held by the current task, the slow path `__mutex_unlock_slowpath` is called.

#### How it works
- **Fast path**: tries to atomically increment the counter from 0 to 1. If it succeeds, the mutex has been unlocked.
- **Slow path**: if the fast path fails (i.e. the mutex is not held by the current task), the slow path `__mutex_unlock_slowpath` is called. The slow path verifies the mutex owner information and wakes up the next task in the wait queue.
- **Clear owner information**: ensures the mutex owner information is correctly cleared so that other tasks can acquire the mutex.

### Summary

- **`mutex_init`**: initialize the mutex, ensuring it is in an unlocked state.
- **`mutex_lock`**: acquire the mutex; if the mutex is already held by another task, the current task goes to sleep until the mutex becomes available.
- **`mutex_unlock`**: release the mutex; this function may only be called to release the mutex when the current task holds it.



## pipe_read
The read process starts first, and at this point nothing has been written yet. In the `pipe_read` function, if there is no content to read in the pipe, the execution flow handles this case. The specific execution flow is as follows:

### 1. **Initial state check**
First, the function locks the pipe's mutex (`mutex_lock(&pipe->mutex)`) and checks the pipe's head and tail pointers to determine whether the pipe is empty. The following code snippet performs this check:
```c
unsigned int head = smp_load_acquire(&pipe->head);
unsigned int tail = pipe->tail;
```

The following condition is then evaluated:
```c
if (!pipe_empty(head, tail)) {
    // 管道不为空的情况，处理读取
} else {
    // 管道为空的情况
}
```

If the pipe is empty, `pipe_empty(head, tail)` returns `true`, and the execution flow enters the "pipe is empty" handling logic.

### 2. **Check whether any writers exist**
Next, the code checks whether there are still writers writing to the pipe:
```c
if (!pipe->writers)
    break;
```
- If there are no writers (`pipe->writers == 0`), no more data will be written, so it breaks out of the loop directly and the function returns.
- If writers exist, the function continues executing. (Usually there are.)

### 3. **Handle non-blocking mode**
The behavior differs between blocking and non-blocking modes. Next, the file descriptor flags are checked:
```c
if ((filp->f_flags & O_NONBLOCK) || (iocb->ki_flags & IOCB_NOWAIT)) {
    ret = -EAGAIN;
    break;
}
```
- If the file descriptor has the `O_NONBLOCK` flag set (non-blocking mode), or the `iocb` struct has the `IOCB_NOWAIT` flag set, `pipe_read` immediately returns `-EAGAIN`, indicating there is currently no data to read and it does not wait. (Usually it is blocking.)
- If it is blocking mode, it keeps waiting for data.

### 4. **Unlock and wait for data**
In blocking mode, if the pipe is empty, the program unlocks the mutex and enters the waiting state:
```c
mutex_unlock(&pipe->mutex);
```
Then it calls `wait_event_interruptible_exclusive` to wait for data:
```c
if (wait_event_interruptible_exclusive(pipe->rd_wait, pipe_readable(pipe)) < 0)
    return -ERESTARTSYS;
```
- `wait_event_interruptible_exclusive` puts the current process to sleep until the pipe becomes readable (i.e. data is written), or the process is interrupted by a signal (such as `SIGINT`).
- If it is interrupted by a signal, the function returns `-ERESTARTSYS`, telling the caller that the system call needs to be restarted.
- If the pipe becomes readable (i.e. data was written), the function tries to read data again.

### 5. **Re-acquire the mutex and check again**
After the wait ends, the function re-acquires the pipe's mutex:
```c
mutex_lock(&pipe->mutex);
```
Then it enters the loop, checks the pipe state again, and re-evaluates whether there is data to read. If there is data in the pipe at this point, it enters the read flow.


## Starting multiple pipe_write at the same time
At this point, since only one process can successfully acquire the lock, the others all enter the mutex wait queue, but in an unknown order. Then, when the pipe buffer is filled, the flow enters the following:


Unlocking at this point causes other processes to start acquiring the lock, and sends a signal to the blocked pipe_read read process to wake it up. Then, since the pipe buffer is full, the other pipe_write processes still enter the same flow as described above

But after the first pipe_write process releases the lock, the mutex wait queue contains the other pipe_write processes, so the other pipe_write processes acquire the lock first. At this point the first pipe_write process wakes up the pipe_read read process via `wake_up_interruptible_sync_poll`; the pipe_read read process then tries to lock, but since the lock is taken, it is placed into the mutex wait queue, i.e. behind the pipe_write processes. Then the first pipe_write puts itself into the wait queue until it receives a signal that the pipe is writable


At this point, the other pipe_write processes also reach `wait_event_interruptible_exclusive` in turn and put themselves into the wait queue.

When pipe_write is woken up via `wake_up_interruptible_sync_poll`, the wakeup and wait-queue-joining mechanism is as follows

### Joining the wait queue

1. **Create a wait queue entry**:
   - When `wait_event_interruptible_exclusive()` is called, a `wait_queue_entry` struct is initialized. This is done via `init_wait_entry()`.
   - The `flags` of `wait_queue_entry` mark whether this wait entry is exclusive.
   - The `private` field is usually set to the current process (`current`), indicating which task is waiting.

2. **Insert into the wait queue**:
   - The `prepare_to_wait_event()` function inserts the `wait_queue_entry` into the `wait_queue_head` list.
   - If it is an exclusive wait, the entry is added to the tail of the queue; non-exclusive waits are added to the head.
   - The current task's state is set to `TASK_INTERRUPTIBLE` (if using `wait_event_interruptible_exclusive`) or `TASK_UNINTERRUPTIBLE`.

### Wakeup mechanism
The execution flow of __wake_up_common when wake_up_interruptible_sync_poll(&pipe->wr_wait, EPOLLOUT | EPOLLWRNORM); wakes up wait_event_interruptible_exclusive(pipe->wr_wait, pipe_writable(pipe));

```c
#define wake_up_interruptible_sync_poll(x, m)					\
	__wake_up_sync_key((x), TASK_INTERRUPTIBLE, poll_to_key(m))
	
void __wake_up_sync_key(struct wait_queue_head *wq_head, unsigned int mode,
			void *key)
{
	if (unlikely(!wq_head))
		return;

	__wake_up_common_lock(wq_head, mode, 1, WF_SYNC, key);
}
EXPORT_SYMBOL_GPL(__wake_up_sync_key);

static int __wake_up_common_lock(struct wait_queue_head *wq_head, unsigned int mode,
			int nr_exclusive, int wake_flags, void *key)
{
	unsigned long flags;
	int remaining;

	spin_lock_irqsave(&wq_head->lock, flags);
	remaining = __wake_up_common(wq_head, mode, nr_exclusive, wake_flags,
			key);
	spin_unlock_irqrestore(&wq_head->lock, flags);

	return nr_exclusive - remaining;
}

static int __wake_up_common(struct wait_queue_head *wq_head, unsigned int mode,
			int nr_exclusive, int wake_flags, void *key)
{
	wait_queue_entry_t *curr, *next;

	lockdep_assert_held(&wq_head->lock);

	curr = list_first_entry(&wq_head->head, wait_queue_entry_t, entry);

	if (&curr->entry == &wq_head->head)
		return nr_exclusive;

	list_for_each_entry_safe_from(curr, next, &wq_head->head, entry) {
		unsigned flags = curr->flags;
		int ret;

		ret = curr->func(curr, mode, wake_flags, key);
		if (ret < 0)
			break;
		if (ret && (flags & WQ_FLAG_EXCLUSIVE) && !--nr_exclusive)
			break;
	}

	return nr_exclusive;
}

```
In the Linux kernel, wait queues are used to manage task sleeping and waking. When multiple tasks wait exclusively on the same wait queue (for example, using `wait_event_interruptible_exclusive`), the wakeup mechanism follows certain policies when waking tasks.

### Wakeup policy for exclusive waits

1. **Queue order**:
   - Internally, the wait queue is usually a linked list structure, with tasks arranged in the order they entered. The first task to enter the queue is at the head of the list, and the last to enter is at the tail.

2. **Wakeup order**:
   - When the `__wake_up_common` function traverses the wait queue, it starts checking and waking from the head (i.e. the earliest task to enter). Therefore, under normal circumstances, the first task to be woken is the exclusive task that entered the wait queue first.

3. **Exclusive flag**:
   - Each wait queue entry contains a flag indicating whether the task is exclusive (via the `WQ_FLAG_EXCLUSIVE` flag).
   - In `__wake_up_common`, after an exclusive task is successfully woken, the `nr_exclusive` counter is decremented.
   - Once `nr_exclusive` reaches zero, the wakeup process stops, which means only the specified number of exclusive tasks are woken, rather than all waiting tasks.

### Which task gets woken specifically

- **The first exclusive task**: when multiple tasks are waiting, the wakeup mechanism first wakes the first task in the queue that has the exclusive flag.
- **FIFO order**: because the queue is managed in FIFO (first-in, first-out) order, the first exclusive task to be woken is usually the one that called `wait_event_interruptible_exclusive` and entered the queue earliest.

At this point, which pipe_write process triggers `wait_event_interruptible_exclusive` and joins the wait queue is uncertain, because the trigger order between the pipe_write that unlocked first then triggering `wait_event_interruptible_exclusive`, and the processes that acquire the lock then unlock then trigger `wait_event_interruptible_exclusive`, is uncertain. Naturally, which pipe_write process gets woken first is also uncertain

But if the pipe_write process that triggers `wait_event_interruptible_exclusive` happens before the pipe_write process that unlocked first, then the next process to start writing will not be the one following the original pipe_write process

# Approach
- Multiple processes simultaneously write content larger than the pipe buffer into the pipe, so that one pipe-receive flow is interrupted before receiving everything
- Then wake another process to write to the pipe, causing the remaining received data to come from the other process's pipe write; the next round of received content is then the content we crafted ourselves. However, the leftover chunk of the original data may disrupt the pipe process in later receives. But it is not a big problem — it won't crash the program. We only need one success

Leaking PIE: through the leftover next field being the NULL_MESSAGE variable, which stores a PIE address; it can be leaked via printf_message

Leaking libc: now that we have the PIE, we can still use the pipe race described above so that the received message is the one constructed by destory_buffer. Then we control all fields of the message; we can control next to be near the GOT table, so that the next part of next lands in the GOT table, and then we can leak libc. When writing we need to specify the index; we can first construct a command_flush command struct to clear the index. Then send the message, and only then command_redact. Note: make sure the next of the next corresponding to next is null

Hijacking the program flow: directly write system into the GOT table; construct next so that the destory_buf part of the corresponding next is the GOT table; then redact_message modifies it to the system function — change fwrite in `fwrite(message->destory_buf, 1uLL, (int)message->destroy_buf_len, devnull);` here, then set message->destory_buf to /bin/sh, and finally handle_message triggers fwrite
