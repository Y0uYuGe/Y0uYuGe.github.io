# Abstract Classes, Virtual Functions, and Pure Virtual Functions


### Abstract Class

An abstract class is a class that cannot be instantiated directly; its purpose is to serve as a base class, providing a common interface for derived classes. An abstract class can contain concrete methods (i.e., methods with implementations) and abstract methods (i.e., methods without implementations). Abstract classes are usually used to define an interface specification, forcing subclasses that inherit from them to implement certain methods.

In C++, a class is an abstract class as long as it contains at least one pure virtual function. Instantiation of an abstract class is not allowed; that is, objects of an abstract class cannot be created directly.

### Pure Virtual Function

A pure virtual function is a virtual function declared in a base class that has no concrete implementation in the base class; instead, it is left for derived classes to implement. The declaration syntax for a pure virtual function is to append `= 0` after the function declaration, for example:

```cpp
virtual void func() = 0;
```

A class containing a pure virtual function is called an abstract class. A derived class must implement all pure virtual functions, otherwise that derived class will also become an abstract class.

### Virtual Function

A virtual function is a special type of member function that allows the function from the base class to be overridden in a derived class, thereby achieving dynamic polymorphism. When a virtual function is called through a base class pointer or reference, the version of the function that is actually called is the one belonging to the class of the concrete object being pointed to or referenced.

The declaration of a virtual function does not require `= 0`, for example:

```cpp
virtual void func();
```

The main purpose of using virtual functions is to achieve polymorphism, allowing a base class pointer or reference to call functions in derived classes, so that which function to call can be decided at runtime, increasing the flexibility and extensibility of the program.

### Summary

- **Abstract class**: Cannot be instantiated directly; contains at least one pure virtual function; provides an interface specification for derived classes.
- **Pure virtual function**: A virtual function with no concrete implementation; forces derived classes to implement it; makes a class an abstract class.
- **Virtual function**: Can be overridden in derived classes to achieve dynamic polymorphism, so that when called through a base class pointer or reference, the corresponding function is executed according to the object's actual type.

# Destruction and Construction with Virtual Functions

##  The Reason for Switching the Base Table When Calling the Destructor (Same for Constructors)

>In a subclass constructor, the parent class constructor is called first. The parent class constructor first fills the virtual table in the subclass object with the address of the parent class's virtual table. Inside the parent class constructor, if there is a virtual function call, the parent class's function can be successfully called instead of the subclass's function.

```cpp
class Base {
public:
    Base() { initTable(); }
    virtual ~Base() {
        std::cout << "Before sayHello in Base destructor" << std::endl;
        sayHello(); // 假设这里有个逻辑错误，实际上不应直接调用虚函数
        std::cout << "After sayHello in Base destructor" << std::endl;
    }
    virtual void sayHello() { std::cout << "Hello from Base" << std::endl; }

private:
    void initTable() { /* 假设这里有初始化虚表的操作 */ }
};

class Derived : public Base {
public:
    Derived() { initTable(); }
    ~Derived() override { std::cout << "Derived destructor" << std::endl; }
    void sayHello() override { std::cout << "Hello from Derived" << std::endl; }

private:
    void initTable() { /* 初始化包含 Derived 版本 sayHello 的虚表 */ }
};
```

Now, if we create a `Derived` object and delete it through a base class pointer, what happens?

```cpp
int main() {
    Base* ptr = new Derived();
    delete ptr;
    return 0;
}
```

### Expected Behavior

- First, the destructor of `Derived` is called, cleaning up resources specific to `Derived`.
- Next, control passes to the destructor of `Base`, because after `Derived` is destructed, the base class part still needs to be destroyed.

### The Problem

In the destructor of `Base`, suppose there is a logical error where it directly calls `sayHello()`. If the virtual table were not switched, according to the original object type (i.e., `Derived`), the `Derived` version of `sayHello()` would be called, which contradicts our expectation that only `Base` behavior should be exhibited while destructing the `Base` part.

### Solution: Temporarily Switching the Virtual Table

To ensure that when executing the destructor of `Base`, even virtual function calls reflect `Base` behavior, the compiler temporarily switches the object's virtual table pointer to the `Base` class's virtual table before entering the destructor of `Base`. As a result, when `sayHello()` is called inside the destructor of `Base`, it calls the `Base` version of `sayHello()` rather than the `Derived` version, thereby guaranteeing correct behavior.

This code is a simplified example of how a C++ program handles global constructors and destructors during the startup and shutdown phases after compilation. It is usually generated automatically by the compiler to manage the construction and destruction order of global objects. Several key concepts and variables are involved here; I will explain them one by one and give a conceptual example to help understanding.

### Explanation of Key Concepts and Variables

- `_do_global_ctors`: This function is responsible for calling the constructors of global objects. It is called automatically by the compiler/linker at program startup.
- `_do_global_dtors`: The corresponding function, responsible for calling the destructors of global objects, called when the program ends.
- `refptr___CTOR_LIST__`: This is a pointer to an array of global constructor pointers maintained by the compiler. Each element of the array is a function pointer pointing to the constructor of a global object.
- `refptr___DTOR_LIST__`: Similarly, it points to an array of destructor pointers, but this code does not show it directly.
- `eax`, `ebx`, `rsi`: These are register names under the x86-64 architecture, used to store temporary variables or pointers.

### Function Flow

1. **Initialization check**: First, check whether `refptr___CTOR_LIST__[0]` (i.e., `i`) equals -1. This value usually indicates that the constructor list is uninitialized or empty. If it is -1, the subsequent constructor call steps are skipped.
   
2. **Traversing the constructor list**: If the constructor list is non-empty, calculate the actual length of the list (i.e., the number of constructors), then call each constructor in turn using a two-pointer technique (one pointer moves forward while the other stays put until the first pointer reaches the end).

3. **Registering destructors**: Finally, use the `atexit` function to register `_do_global_dtors`, ensuring that the destructors of global objects are called when the program exits normally.

### Example Explanation

Suppose we have the following two global objects, each with its own constructor and destructor:

```cpp
class ObjA {
public:
    ObjA() { std::cout << "ObjA constructed" << std::endl; }
    ~ObjA() { std::cout << "ObjA destructed" << std::endl; }
};

class ObjB {
public:
    ObjB() { std::cout << "ObjB constructed" << std::endl; }
    ~ObjB() { std::cout << "ObjB destructed" << std::endl; }
};

ObjA globalA;
ObjB globalB;
```

At program startup, `_do_global_ctors` is called, invoking the constructors of `ObjA` and `ObjB` respectively in the order determined by the compiler. The output might be:

```
ObjA constructed
ObjB constructed
```

When the program ends normally, `_do_global_dtors` is called, invoking the destructors in reverse order. The output might be:

```
ObjB destructed
ObjA destructed
```

In this way, C++ ensures that the construction and destruction of global objects proceed in an orderly manner, even when there are dependencies between objects.



# Inheritance

In constructors:
Construction order: first construct the parent class, then construct member objects and members specified in the initializer list in declaration order, and finally execute its own constructor code
Destruction order: first call its own destructor, then call the destructors of member objects, and finally call the parent class's destructor

According to the order of the inheritance relationships, the constructor of parent class Sofa is called first. When calling the other parent class Bed, instead of directly passing the object's starting address as the this pointer, the address is adjusted backward by the length of the parent class Sofa, and the adjusted address value is passed as the this pointer; only then is the constructor of parent class Bed called. Because there are two parent classes, the subclass also inherits their virtual table pointers when inheriting, so it has two virtual table pointers. As can be seen, in multiple inheritance, the number of virtual table pointers in the subclass depends on the number of parent classes inherited; there are as many virtual table pointers as there are parent classes.
When performing polymorphic operations, the pointer is moved forward or backward to point to that location.

#  Virtual Inheritance

### Basic Setup

Suppose we have the following four classes:

1. **Vehicle**: A base class with a member variable `color` representing the color.
   
   ```cpp
   class Vehicle {
   public:
       std::string color;
       Vehicle(std::string c) : color(c) {}
   };
   ```

2. **Car** and **Motorcycle**: Two classes that inherit from `Vehicle`, adding no new members, inheriting directly.
   
   ```cpp
   class Car : public Vehicle {
   public:
       Car(std::string c) : Vehicle(c) {}
   };

   class Motorcycle : public Vehicle {
   public:
       Motorcycle(std::string c) : Vehicle(c) {}
   };
   ```

3. **ConvertibleCar**: A special type of car that is also a kind of motorcycle (imagine a very sci-fi scenario), inheriting directly from `Car` and `Motorcycle`.

   If virtual inheritance is not used and inheritance follows the conventional way, `ConvertibleCar` will have two `color` members, coming from `Car` and `Motorcycle` respectively.

### The Problem Without Virtual Inheritance

```cpp
class ConvertibleCar : public Car, public Motorcycle {
public:
    ConvertibleCar(std::string c) : Car(c), Motorcycle(c) {}
    
    // 这里访问color就会有二义性，因为不清楚是Car的color还是Motorcycle的color
    // std::cout << color; // 错误，编译时会报错
};
```

### Using Virtual Inheritance to Solve the Problem

To make `ConvertibleCar` have only one `color` member, we need `Car` and `Motorcycle` to virtually inherit from `Vehicle`.

```cpp
class Car : virtual public Vehicle { ... };
class Motorcycle : virtual public Vehicle { ... };

class ConvertibleCar : public Car, public Motorcycle {
public:
    ConvertibleCar(std::string c) : Car(c), Motorcycle(c) {}
    
    // 现在访问color是明确的，因为只有一个实例
    std::cout << color; // 正确，输出ConvertibleCar的颜色
};
```

Through virtual inheritance, a `ConvertibleCar` instance has only one shared `Vehicle` base class part, thereby avoiding data redundancy and access ambiguity.

# Virtual Base Class Offset Table (vbtable)
Let's explain the concept of the virtual base class offset table (vbtable) through a concrete example. Suppose we have the following class structure:

```cpp
class Vehicle {
public:
    int wheels;
    virtual void drive() { std::cout << "Driving a vehicle." << std::endl; }
};

class Car : virtual public Vehicle {
public:
    int doors;
    virtual void drive() override { std::cout << "Driving a car." << std::endl; }
    virtual void honk() { std::cout << "Honking the horn." << std::endl; }
};

class Truck : virtual public Vehicle {
public:
    int payloadCapacity;
    virtual void drive() override { std::cout << "Driving a truck." << std::endl; }
    virtual void loadCargo() { std::cout << "Loading cargo." << std::endl; }
};

class SUV : public Car, public Truck {
public:
    int seatingCapacity;
    virtual void drive() override { std::cout << "Driving an SUV." << std::endl; }
};
```

In this example, `Vehicle` is a virtual base class, virtually inherited by the two classes `Car` and `Truck`. Then, the `SUV` class inherits from both `Car` and `Truck`, forming a diamond inheritance structure.

### Memory Layout and the Virtual Base Class Offset Table

In an object of the `SUV` class, the memory layout will include:

1. **Virtual function pointer (vptr)**: For `SUV`, `Car`, `Truck`, and the virtual functions inherited from `Vehicle`, each class with virtual functions has a vptr pointing to its own virtual function table.

2. **Virtual base class pointer (vbptr)**: Since `Vehicle` is virtually inherited, an `SUV` object will have a vbptr pointing to the virtual base class offset table (vbtable).

3. **Data members**: The data members of `SUV`, `Car`, `Truck`, and `Vehicle` are stored in their respective orders.

### The Role of the Virtual Base Class Offset Table

The entries in the virtual base class offset table (vbtable) record the offset from the starting address of the `SUV` object to the actual starting address of the `Vehicle` subobject. When a member of the `Vehicle` class (such as `wheels`) needs to be accessed, the compiler follows these steps:

1. **Get the vbptr**: First, find the virtual base class offset table through the vbptr in the `SUV` object.

2. **Calculate the offset**: Read the offset of the `Vehicle` subobject relative to the vbptr from the virtual base class offset table.

3. **Access the member**: Using this offset plus the address of the vbptr, you can obtain the starting address of the `Vehicle` subobject, and thus correctly access the `wheels` member.

### Example Access

If we want to access the `wheels` member of an `SUV` object, although it directly inherits from `Car` and `Truck`, the compiler actually finds the correct instance of `Vehicle` through the vbptr and vbtable, then calculates the address of `wheels` and accesses it.

In this way, the virtual base class offset table ensures that access to virtual base class members in complex inheritance structures is accurate, avoiding the problem of duplicate data from the same base class caused by multiple inheritance.
