# CPU virtualization

The CPU is the most core component of a computer, directly controlling the operation of the entire system. Meanwhile, memory access (memory virtualization) and I/O operations (I/O virtualization) also depend directly on the CPU, so CPU virtualization is the core of system virtualization technology

# Ring compression
The VMM is at the highest privilege level and the Guest VM is at a lower privilege level. When the Guest VM executes non-sensitive instructions, they run directly on the hardware; when it executes sensitive instructions, it traps into the VMM at the highest privilege level, and the VMM performs the sensitive instruction's behavior

# Privilege levels
The kernel is in ring 0; user processes are in ring 3
![Image](/images/csdn/2023/csdn-134403151/image-001-07339508bb.png)
# System virtualization
In the "Trap & Emulate" architecture of system virtualization, the Guest OS runs entirely in ring 3. When the VM involves a privileged instruction, the VM triggers a General Protection exception, and the VMM steps in to handle it.
But not all sensitive instructions are privileged instructions, so some sensitive instructions that are not privileged do not trigger a General Protection exception to let the VMM intervene — this is dangerous.

# Solutions
## Emulation & interpretation (VMware)
The essence of emulation: achieving the same behavior as the emulated object but on a different platform
Emulation technique: the emulator continuously reads instructions from memory, simulates the effect of each instruction, and then decides whether to change state (i.e. interpretation)

QEMU (Quick Emulator): fully emulates a complete computer system including various hardware

Disadvantages of emulation: extremely poor performance; every instruction must be simulated, and the simulation steps are tedious

## Scan & patch
The instruction sets of the virtual machine and the physical machine are basically the same, so pure emulation is unnecessary.
Only for privileged and sensitive instructions is there a transition to the VMM in some way
Scan & patch: replace all sensitive instructions with jump instructions or other commands that can trap into the VMM
Basic flow:

 1. Before the VM executes each code segment, the VMM scans it, parses each instruction, and looks for sensitive and privileged instructions
 2. The VMM dynamically generates patch code for the corresponding instructions, replacing sensitive and privileged instructions with outward jumps to enter the VMM; the VMM executes the patch code
 3. After executing the patch code, the VMM jumps back to the VM to continue executing the next code

## Binary Translation
Similar to scan & patch, binary translation also dynamically modifies code, but BT uses the basic block (a block of code with only one entry and one exit) as the unit of translation

 1. The emulator then translates the binary code and outputs code consisting of an instruction set that does not contain privileged or sensitive instructions; this code can run safely under the VM
 2. The emulator dynamically allocates a space for the current basic block, called the translation cache, which stores the translated code; each translation cache has a certain mapping relationship with the original code

Translation methods

 1. Simple translation: use other code to achieve equivalent functionality, but the number of instructions increases (a minority)
 2. Equivalent translation: the translated code is the same as the original code (the majority)

## Hardware-assisted virtualization (VT)
This is hardware support Intel provides for virtualization; the one responsible for CPU virtualization is called VT-x.

### VMX operation modes (Virtual Machine eXtensions)
 - VMX Root Operation: the VMM's working mode; can access
all resources and schedules VMs
 - VMX Non-Root Operation: the VM's working mode; in this mode it can only access non-sensitive resources. Accessing sensitive resources causes the CPU to exit Non-Root mode and enter VMX Root Operation mode; after handling is done there, it re-enters VMX Non-Root Operation mode

### **Definition of mode-switching behaviors**

 - VM-Entry: the VMM saves its own state information, switches to VMX Non-Root Operation mode, loads the VM's state information, and resumes the VM's execution flow
 - VM-Exit: the VM stops running and saves its own state information, switches to VMX Root Operation mode, loads the VMM's state information, and executes the corresponding handler
 
### Ring protection
Both VMX Root Operation and VMX Non-Root Operation have their own ring protection. The Host OS and Guest OS can run directly on the hardware in their corresponding modes; switching only occurs when the Guest OS accesses sensitive resources or the Host OS schedules VMs.

### VMCS (Virtual-Machine Control Structure)
The VMCS is a block of memory that stores the state of a virtual machine's virtual CPU. Each virtual CPU has a VMCS; at any given moment a physical CPU can be bound to only one VMCS, i.e. one physical CPU corresponds to one virtual CPU, but at different times a VMCS can be bound to different physical CPUs — a virtual CPU can choose its corresponding physical CPU. This is called VMCS migration

**Binding and unbinding of the VMCS and physical CPUs**
![Image](/images/csdn/2023/csdn-134403151/image-004-62915860f3.png)

**In VT-x, the VMCS structure is defined as a memory block of at most 4KB, aligned to 4KB (i.e. the low three bits of the corresponding hexadecimal address are 0)**
```c
struct VMCS {
    /* 版本号，4字节 */
    uint32_t vmcs_revision_identifier:31, shadow_vmcs_indicator:1;

    /* 中止标识，4字节
     * 当 VM-Exit 失败时便会产生 VMX 中止，并在此处存放原因
     */
    uint32_t    vmx_abort_indicator;

    /* 数据域 */
    struct VMCSData vmcs_data;
};
```

**The data field struct VMCSData vmcs_data stores the main information of the VMCS and can be divided into the following parts**

[Diagram of the data field layout](https://rayanfam.com/assets/files/VMCS.pdf)

 - Guest-state area: stores the VM mode register state; loaded on VM-Entry and saved on VM-Exit
 - Host-state area: stores the VMM mode register state; loaded on VM-Exit and saved on VM-Entry
 - VM-execution control fields: control processor behavior in VM mode
 - VM-entry control fields: control certain behaviors during the VM-Entry process
 - VM-exit control fields: control certain behaviors during the VM-Exit process
 - VM-exit information field: stores the basic reason for the VM-Exit and other detailed information; on some processors this field is read-only

### Overall flow of VMX operation modes
VMX mode is disabled by default; it is only enabled when the VMM needs to use hardware-assisted virtualization, and only after enabling it do the VM-root-operation and VM-non-root-operation modes exist.

> VMXON: enables VMX operation mode
> VMXOFF: disables VMX operation mode

# KVM&QEMU-KVM (Kernel-based Virtual Machine)
Essentially, QEMU acts as the host while the VMM is in the kernel
KVM is responsible for CPU and memory virtualization, while QEMU emulates hardware such as IO devices
In Linux, the ioctl() function can be used for communication between user programs and kernel modules

 - QEMU sends a request via the ioctl system call to enter kernel mode and hand control to KVM, which then runs the VM
 - A VM-Exit occurs while running virtual machine code; KVM then takes over, determines the cause, and after handling decides whether to continue running or hand it over to QEMU
 - If IO operations are needed, it exits KVM and QEMU handles them
