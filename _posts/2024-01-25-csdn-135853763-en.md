# Changes Brought by Introducing the Thread Mechanism

Note that thread concurrency does not require switching the process environment, so overhead is reduced

Lower concurrency overhead: within the same span of time there are fewer process switches, so the system naturally spends less (you can think of it this way: only switching between threads of different processes requires switching the process environment — unlike before, when every switch necessarily switched the process environment; now the switching unit is the thread, and not every switch changes the process environment)

# Thread Attributes

Note that threads of the same process share the process's resources; switching between threads within the same process has very low system overhead

**Threads share the resources of their process because they are different execution paths of the same process and naturally inherit the process's resources. The process resources shared by threads are as follows:**

- Code segment: all threads execute the same program code; this part is read-only and can therefore be safely shared among multiple threads.
- Data segment: global variables and static variables are shared among all threads, which means any thread's modification of these variables affects the others.
- Heap: dynamically allocated memory is shared; any thread can access the data in this memory region through pointers.
- File descriptors, sockets, and ports: open files, network connections, and similar resources can be accessed by all threads, which is especially important for I/O operations.
- Signal handlers: in Unix-like operating systems, signal handling is set at the process scope, so all threads share the same signal-handling behavior.
- Environment variables: environment variables are shared by all threads; they usually contain system-configuration information.
In addition, threads also have some private resources, such as the thread ID, the values of the register set, the thread's stack, and error return codes. These resources are essential for a thread's independent execution and context switching.

In summary, threads are designed to share process resources in order to improve resource utilization and program concurrency. By sharing the memory space, file descriptors, and other resources, threads can communicate and cooperate efficiently without resorting to the more complex IPC (inter-process communication) mechanisms needed between processes. This resource-sharing mechanism is one of the key reasons multithreaded programming improves efficiency.

**Switching threads does not require switching the shared process resources because threads share the resources of their process.**

A thread is the basic unit of CPU scheduling, while a process is the basic unit of resource allocation. Threads in the same process share the process's virtual address space, open file handles, global data, and other resources. Therefore, when the operating system switches threads, it does not need to reallocate or switch these resources; it only needs to save and restore the thread's execution context. Specifically:

1. Virtual address space: because threads share the process's virtual address space, no address-space switch is needed when switching threads.
2. File handles and global data: threads use the process's resources rather than owning them. This means these resources remain unchanged during a thread switch, and threads can access them directly.
3. Context switching: thread switching mainly involves saving the current thread's execution state (such as register values, program counter, etc.) and loading the next thread's state — a relatively lightweight operation.
4. Performance impact: thread switching may affect the performance of the TLB (Translation Lookaside Buffer) cache, but this is usually much smaller than the impact of a process switch, because a process switch involves reallocating far more resources.

In summary, the resource-sharing mechanism between threads makes thread switching more efficient than process switching, because it avoids repeated resource allocation and deallocation. This design improves the running efficiency of multithreaded programs, especially in scenarios where threads are frequently created and destroyed.
