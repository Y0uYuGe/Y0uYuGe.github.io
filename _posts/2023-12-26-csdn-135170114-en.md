# BROP(Blind ROP) 
This is the case where you have neither the source code nor the executable file, and only a provided service port to attack

> BROP (Blind ROP) was proposed in 2014 by Andrea Bittau of Stanford University. The related research was published at Oakland 2014, and the paper is titled Hacking Blind. Below are the author's paper and PPT, along with the author's introduction
> 
- [Paper](http://www.scs.stanford.edu/brop/bittau-brop.pdf)
- [PPT presentation - well worth a look](http://www.scs.stanford.edu/brop/bittau-brop-slides.pdf)

# Attack Requirements

1. A stack overflow vulnerability exists, and you know how to trigger it
2. The server process restarts after crashing, and the restarted process has the same addresses as before (this means that even if the program has ASLR protection, it is only effective when the program first starts). Currently, server applications such as nginx, MySQL, Apache, and OpenSSH all match this characteristic)

# Attack Roadmap
Nowadays, most applications enable ASLR, NX, and Canary protection. What we need to do is figure out how to bypass these defenses
![在这里插入图片描述](/images/csdn/2023/csdn-135170114/image-002-5f67c4bc86.png)

 1. Brute-force to determine the stack overflow length
 2. Brute-force the canary. From requirement 2 above, we know the canary stays the same after each crash and restart, so we can brute-force byte by byte. Each byte has 8 bits, 256 possibilities; we try each possibility one at a time. If there is no error, that byte is correct, and we move on to the next one. So it takes 1024 attempts for 32-bit and 2048 attempts for 64-bit
3. Brute-force the return address to find an address that returns to the main function
4.  First find gadgets; you can use the gadgets in libc_cs_init to control the arguments of the function to be called
5. First use the obtained gadget to construct the arguments, then brute-force addresses as the return address. If the instruction at some address happens to be an output function, then with the previously constructed arguments it will output the corresponding content. If such content appears, it means you have found an output function such as write, puts, or printf
6. Then output the contents of all addresses and write them into a file you create, then disassemble that file to see the program's assembly code. Find the PLT entry of the corresponding output function, locate the instruction `jmp <address of the output function in the GOT table>`, and record the output function's GOT table address
7. Then use the output function's GOT table address as the argument, with the return address being the output function itself, to perform the output. This gives you the address of the output function
8. Use the output function's address to identify the corresponding glibc version, compute the base address, and then obtain the addresses of system and /bin/sh
9. Now send input again, this time constructing the argument as the address of /bin/sh and the return address as the address of system, thereby getting a shell

# The Three Kinds of Gadgets

> PIE (Position-Independent Executables): position-independent executables, similar to the ASLR (Address Space Layout Randomization) mechanism on Windows. PIE enabled means the program has address randomization turned on, meaning the program's addresses change on every run. It mainly solves the problem of the binary's own addresses being known, and can defend against return2elf and other known-address read/write issues.

> By default, when PIE is not enabled, the load base address for x86 is 0x8048000, while for x64 the load base address is 0x400000.

> After PIE is enabled, the relative offsets within the ELF remain unchanged, but the load base changes every time.

probe is the address used for brute-force enumeration, i.e., the address being probed
stop is an address that will not make the program crash
trap is an address that will make the program crash

By arranging different stops and traps starting from the return address on the stack, you can identify the executed instructions, because executing stop means the program does not crash, while trap means the program crashes, so you can determine where the ret of that instruction sequence is

 - probe, stop, traps, traps……
   Keep changing probe to try. The one that does not crash is an instruction sequence that leaves the stack top unchanged and eventually executes a ret instruction
   ret
   xor eax，eax；ret
   push eax；pop ebx；ret
- probe, trap, stop, trap, trap……
   By continuously changing the value of probe, you can find an instruction stream that pops one element off the stack top and then executes another ret without changing the stack top before that ret
   pop rax；ret
   pop rdi；push rax；pop rsi；ret
 - probe, trap, trap, trap, trap, trap, trap, stop, trap, trap……
  At this point you can find an instruction containing ret where, just before the ret, the stack top position has decreased by 6 units
  pop rax；pop rdi；pop rsi；pop rdx；pop rbx；pop r14；ret 


**Note, however, that if probe is the start address of the _start function, it will never crash**

# Using the PLT
When probe is within the range of some function in the PLT, that function will be executed
![在这里插入图片描述](/images/csdn/2023/csdn-135170114/image-009-2f7370c021.png)
## The Gadget for Constructing the rdx Argument
Since the gadget needed here must have pop rdx, and it must also end with ret or some other instruction that can indirectly transfer a value into rdx — but such gadgets are almost nonexistent
However, you can use the characteristic that after calling the strcmp function, rdx holds the string length value, to modify rdx **(debatable)**

> We know that strcmp(para1, para2) can only execute correctly when both para1 and para2 are valid addresses. We already know two usable gadgets: csu_gadget1 + 7 and csu_gadget1 + 9. Therefore, we can use these two addresses as para1 and para2 respectively, then still use probe to determine whether it executed successfully. If it executed successfully, we have found strcmp(). Of course, it is also possible to find strncmp() and strcasecmp(), but they have the same effect as strcmp().

## Finding the PLT of the Output Function
Again, construct the arguments, but this time you can construct rdi, rsi, and rdx. You only need to try probe: if the content corresponding to the argument is output, you have found the PLT location of the output function
## Dumping the Binary File Content
Then construct the arguments and use the output function to output the contents of all addresses of the binary file. At this point it is as if it is no longer blind — you have the source file. Now that you know all the functions in the PLT table, you can call different functions such as read
## Using the Fact That PLT Entries Jump to the Corresponding GOT Address
Once the binary file is obtained, find the PLT entry of the output function, locate the jump instruction inside it that references the output function's GOT entry address, then output again with the parameter being the output function's address in the GOT table. This gives the real address of the output function, from which you get the libc base address and compute the addresses of /bin/sh and system. If that is not possible, you can use the read or write functions to write into writable memory with self-constructed parameters (so the address is known), and then call a syscall or system — except a syscall requires constructing additional parameters
