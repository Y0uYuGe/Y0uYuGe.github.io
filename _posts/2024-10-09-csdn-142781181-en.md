# git@ssh.github.com: Permission denied (publickey)
When you encounter the `git@ssh.github.com: Permission denied (publickey)` error, it usually means that GitHub cannot authenticate you using the SSH key you provided. Here are some troubleshooting steps to help you diagnose and resolve the issue:

### 1. Check Your SSH Keys

Make sure you have generated an SSH key and added it to your GitHub account.

#### Generate a New SSH Key

If you haven't generated an SSH key yet, you can generate one with the following command:

```sh
ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
```

Follow the prompts; this usually generates two files: `id_rsa` (private key) and `id_rsa.pub` (public key).

#### Add the SSH Key to GitHub

1. Open the generated public key file:

   ```sh
   cat ~/.ssh/id_rsa.pub
   ```

2. Copy the public key content.

3. Log in to GitHub, go to account settings, find the "SSH and GPG keys" section, and click "New SSH key".

4. Give the SSH key a descriptive title, paste the public key content into the key field, and click "Add SSH key".

### 2. Configure the SSH Agent

Make sure the SSH agent is running and your private key has been added to the agent.

#### Start the SSH Agent

```sh
eval "$(ssh-agent -s)"
```

#### Add the Private Key to the SSH Agent

```sh
ssh-add ~/.ssh/id_rsa
```

### 3. Check the SSH Config File

Make sure there is no incorrect configuration in your SSH config file `~/.ssh/config`. You can add the following content to ensure the correct key is used:

```sh
Host github.com
  HostName ssh.github.com
  User git
  IdentityFile ~/.ssh/id_rsa
  Port 443
```

### 4. Test the SSH Connection

Test the SSH connection again to make sure you can successfully connect to GitHub:

```sh
ssh -T git@github.com
```

### 5. Check Firewall and Network Settings

Make sure your firewall and network settings are not blocking SSH connections. You can try testing from a different network environment (such as a home network or mobile data).

### 6. Check GitHub Account Settings

Make sure your GitHub account does not have two-factor authentication (2FA) enabled, or if you have enabled 2FA, make sure you have generated an SSH key and added it to GitHub correctly.

### Detailed Steps

1. **Generate a new SSH key**:
   ```sh
   ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
   ```

2. **Add the SSH key to GitHub**:
   - Open the public key file:
     ```sh
     cat ~/.ssh/id_rsa.pub
     ```
   - Copy the public key content.
   - Log in to GitHub, go to account settings, find the "SSH and GPG keys" section, and click "New SSH key".
   - Give the SSH key a descriptive title, paste the public key content into the key field, and click "Add SSH key".

3. **Start the SSH agent and add the private key**:
   ```sh
   eval "$(ssh-agent -s)"
   ssh-add ~/.ssh/id_rsa
   ```

4. **Check the SSH config file**:
   - Edit the `~/.ssh/config` file:
     ```sh
     nano ~/.ssh/config
     ```
   - Add the following content:
     ```sh
     Host github.com
       HostName ssh.github.com
       User git
       IdentityFile ~/.ssh/id_rsa
       Port 443
     ```

5. **Test the SSH connection**:
   ```sh
   ssh -T git@github.com
   ```

With these steps, you should be able to resolve the `Permission denied (publickey)` error and successfully connect to GitHub. If the problem persists, check GitHub's documentation and community support for more help.



# Updates were rejected because the tip of your current branch is behind its remote counterpart

```bash
To github.com:FULLK/glibc-chunk-poc-basic.git
! [rejected] main -> main (non-fast-forward)
error: 无法推送一些引用到 'git@github.com:FULLK/glibc-chunk-poc-basic.git'
提示：更新被拒绝，因为您当前分支的最新提交落后于其对应的远程分支。
提示：再次推送前，先与远程变更合并（如 'git pull ...'）。详见
提示：'git push --help' 中的 'Note about fast-forwards' 小节。
```

The error message you encountered indicates that your local branch `main` is behind the `main` branch of the remote repository. In this case, Git will reject the push because the push might overwrite updates in the remote repository. The correct way to solve this problem is to first synchronize your local code with the remote repository's code.

Here are the detailed steps for several solutions:

### 1. Use `git pull --rebase`

To solve this problem, it is recommended that you first use `git pull --rebase`, which applies your local commits on top of the remote repository's changes without creating an extra merge commit (avoiding unnecessary merge commits).

```bash
git pull --rebase origin main
```

This command performs the following operations:

- Fetches the latest `main` branch from the remote repository.
- Reapplies your local commits on top of the remote branch.
- If there are any conflicts, you need to resolve them manually, then continue with `git rebase --continue`.

Once `git pull --rebase` completes, continue with the push:

```bash
git push -u origin main
```

### 2. Manually Merge the Remote Branch

If you don't want to use `rebase`, you can also resolve it through a manual merge.

First, pull the latest changes from the remote repository:

```bash
git pull origin main
```

If there are no conflicts, Git will automatically merge the remote `main` branch with your local `main` branch.

If there are conflicts, Git will tell you which files have conflicts. You need to edit these files and resolve the conflicts. After resolving them, run the following commands to complete the merge:

```bash
git add <解决了冲突的文件>
git commit
```

Then, you can try pushing again:

```bash
git push -u origin main
```

### 3. Force Push (Not Recommended)

If you are sure that the changes in the remote repository can be overwritten (for example, you are the only contributor, or the updates to the remote `main` branch are unimportant), you can use a force push. However, this approach may lose the remote history, so use it with caution.

```bash
git push -f origin main
```

### Side Effects of Force Pushing:
- **Overwrites the remote history**. If others have done work based on the remote `main` branch, a force push may cause their work to be lost or create conflicts.
- **Cannot be undone**. Once you force push, the remote repository's history is rewritten, and recovering the remote repository's state will be very difficult.

Therefore, unless you are completely sure that the state of the remote branch can be ignored, it is recommended not to use force push.

---

### Summary

1. **Recommended method:** Use `git pull --rebase origin main` to synchronize the remote and local branches, then push.
2. **Merge method:** Use `git pull origin main` to merge the remote changes.
3. **Force push (not recommended):** If the remote changes are unimportant or can be overwritten, you can use `git push -f` to force push.

In general, the first two methods are safer and recommended practices.

# git lfs installError: Failed to call git rev-parse --git-dir: exit status 128 Git LFS initialized.
[https://blog.csdn.net/weixin_44740756/article/details/132103949](https://blog.csdn.net/weixin_44740756/article/details/132103949)

Go to the repository directory

```bash
git lfs install
```


### 1. Track Large Files

Tell Git LFS which files you want to track. For example, you can specify that all `.tar.gz` files are managed by Git LFS:

```sh
git lfs track "*.tar.gz"
```

This will create or update a `.gitattributes` file in the root of your repository with the following content:

```
*.tar.gz filter=lfs diff=lfs merge=lfs -text
```

### 2. Add the `.gitattributes` File

Add the `.gitattributes` file to the Git repository:

```sh
git add .gitattributes
```

### 3. Add the Large File

Add the large file to the Git repository:

```sh
git add glibc/debug_glibc-master.tar.gz
```

### 4. Commit the Changes

Commit these changes:

```sh
git commit -m "Add large file using Git LFS"
```

### 5. Push the Changes

Push the changes to the remote repository:

```sh
git push origin main
```

### 6. Verify

Make sure the file is properly managed by Git LFS instead of being stored directly in the Git repository. You can check the `.gitattributes` file and the `glibc/debug_glibc-master.tar.gz` file in the remote repository to make sure `glibc/debug_glibc-master.tar.gz` has been replaced with a pointer file pointing to Git LFS.

### 7. Other Notes

- **Cloning the repository**: If your repository already uses Git LFS, other users need to install Git LFS and use the `git lfs pull` command to download the large files when cloning the repository.
- **Migrating existing large files**: If your repository already contains large files, you can use the `git lfs migrate` command to migrate these files to Git LFS.

### Migrating Existing Large Files

If your repository already contains large files, you can migrate them to Git LFS with the following command:

```sh
git lfs migrate import --include="*.tar.gz" --include-ref=refs/heads/main
```

This migrates the specified files to Git LFS and rewrites the history to use Git LFS pointer files.

### Example

Suppose your repository already contains a large file `glibc/debug_glibc-master.tar.gz`; you can follow these steps:

1. **Install Git LFS** (you have already completed this step):
    ```sh
    git lfs install
    ```

2. **Track large files**:
    ```sh
    git lfs track "*.tar.gz"
    ```

3. **Add the `.gitattributes` file**:
    ```sh
    git add .gitattributes
    ```

4. **Add the large file**:
    ```sh
    git add glibc/debug_glibc-master.tar.gz
    ```

5. **Commit the changes**:
    ```sh
    git commit -m "Add large file using Git LFS"
    ```

6. **Push the changes**:
    ```sh
    git push origin main
    ```
