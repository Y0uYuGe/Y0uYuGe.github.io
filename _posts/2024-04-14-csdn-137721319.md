#   Export Rules for Imported Packages
In Go, the fields and methods inside structs and interfaces of imported packages also follow the export rules:

1. Structs:
   - Fields inside a struct that are public (exported) must start with an uppercase letter. Public fields can be accessed and modified from outside the package.
   - Methods of a struct (regardless of the receiver) that are public must also start with an uppercase letter so they can be called from outside the package.

```go
// 在 mypackage 包中
package mypackage

type ExportedStruct struct {
    PublicField string // 可以在其他包中访问
    privateField string // 不能在其他包中访问
}

func (s ExportedStruct) PublicMethod() {} // 可以在其他包中调用
func (s ExportedStruct) privateMethod() {} // 不能在其他包中调用
```

2. Interfaces:
   - All methods inside an interface are public, because an interface itself is a contract defining a set of method signatures. Both the interface itself and its methods must start with an uppercase letter to be visible and usable outside the package.

```go
// 在 mypackage 包中
package mypackage

type ExportedInterface interface {
    PublicMethod() // 可以在其他包中实现和调用
}
```

Summary: Whether it's a struct or an interface, its public fields and methods must start with an uppercase letter to be used normally in other packages. For interfaces, since an interface itself is a collection of methods, all methods inside an interface are automatically considered public.

# Mount Information of the Current Process

`/proc/self/mountinfo` is a virtual file in Linux, located in the `/proc` filesystem. This file provides detailed information about the system's current mount points, especially the mount point information visible to the current process (`self`).

Each line represents a detailed description of a mount point, including:

1. Mount ID (unique ID identifying the mount point across all mounts within the system).
2. Parent mount ID (the ID of the parent mount (or of self for the rootfs)).
3. Major and minor device numbers (major and minor numbers of the device mounted).
4. Mount point path (the mount point's pathname).
5. Root directory device ID (root directory ID).
6. Mount options (options used when mounting the filesystem).
7. Filesystem type (filesystem type).
8. Mount source (where the filesystem was mounted from, e.g., device path or NFS server/share).
9. Special mount flags (additional flags specific to the mount).

By reading the `/proc/self/mountinfo` file, you can get detailed knowledge of the filesystem mounts visible to the current process, which is very useful for system administration and troubleshooting. For example, if you want to check the filesystem type, mount source, mount options, etc. of a mounted directory, you can consult the contents of this file.
 
#  defer
In Go, `defer f.Close()` is a statement used to guarantee that a file or resource will definitely be closed before the function finishes executing. Here `f` is an object that implements the `io.Closer` interface, usually a file handle or other resource object that needs to be closed. The `Close` method is used to close the resource and release system resources.

The `defer` keyword in Go is used to delay the execution of a function, meaning the function will be called before the enclosing function finishes executing (whether it returns normally or exits abnormally via a `panic`). The execution order of `defer` statements is LIFO (last in, first out), meaning the last deferred function is executed before the other deferred functions.

For example:

```go
func processFile(filename string) error {
    file, err := os.Open(filename)
    if err != nil {
        return err
    }
    defer file.Close() // 当函数返回时，file.Close()会被调用，确保文件最终会被关闭

    // 对文件进行读写操作...

    return nil // 或者返回其他错误
}
```

In the code above, regardless of whether the `processFile` function executes successfully, and no matter how the function ends (normal return or returning an error), `file.Close()` will be called before the function returns, ensuring the file resource is properly released.

# `for scanner.Scan()`
In Go, `bufio.NewScanner(f)` creates a new scanner (Scanner) that can read data line by line from the given input stream (here `f`). `f` should be an object that implements the `io.Reader` interface, such as a file, network connection, or similar data stream.

The following `for scanner.Scan()` is a loop that keeps executing until the scanner has no more lines to read:

- `scanner.Scan()` is a method call that tries to read the next line of data from the input stream. If a line is successfully read, it returns `true` and stores the read data where methods like `scanner.Text()` or `scanner.Bytes()` can access it.
- If `scanner.Scan()` reaches the end of the stream, or encounters an error during reading, it returns `false`, and the error can be checked via `scanner.Err()`.

The loop body is where each line of data is processed, for example:

```go
f, err := os.Open("example.txt")
if err != nil {
    // 处理错误
}
defer f.Close()

scanner := bufio.NewScanner(f)
for scanner.Scan() {
    line := scanner.Text() // 获取当前行的内容
    // 对line进行处理，如打印、解析或存入数据库等操作
    fmt.Println(line)
}

if err := scanner.Err(); err != nil {
    // 在循环结束后检查是否有读取错误
    fmt.Fprintln(os.Stderr, "Reading standard input:", err)
}
```

In this way, the `for scanner.Scan()` loop completes the process of reading data line by line from the input stream and processing it.


#  Checking String Containment
In Go, to check whether a string (substring) exists within another string, you can use the `strings.Contains` function. Here is an example:

```go
package main

import (
	"fmt"
	"strings"
)

func main() {
	// 主字符串
	mainStr := "Hello, world! This is a test string."

	// 要查找的子字符串
	subStr := "test"

	// 判断子字符串是否存在于主字符串中
	isFound := strings.Contains(mainStr, subStr)

	if isFound {
		fmt.Printf("Substring '%s' found in the main string.\n", subStr)
	} else {
		fmt.Printf("Substring '%s' not found in the main string.\n", subStr)
	}
}
```

In the code above, `strings.Contains(mainStr, subStr)` returns a boolean value: if `subStr` exists in `mainStr`, it returns `true`, otherwise it returns `false`.

# CPU-Related Configuration
Let's use some examples to explain the relationship between cpu.cfs_period_us, cpu.cfs_quota_us, and cpu.shares, and how they work together to control CPU resource allocation:

Suppose we have a system where CPU time can be allocated to different control groups (cgroups):

1. **cpu.shares example**:
   - Suppose we have two cgroups, "A" and "B", and we want "A" to get twice the CPU time of "B".
   - We set "A"'s cpu.shares to 1024 and "B"'s cpu.shares to 512.
   - In this case, cgroup "A" will get twice the CPU time of cgroup "B". If both "A" and "B" are actively using the CPU, "A" will get 2/3 of the CPU time and "B" will get 1/3.

2. **cpu.cfs_period_us and cpu.cfs_quota_us example**:
   - Now, let's use cpu.cfs_period_us and cpu.cfs_quota_us for finer-grained control.
   - Suppose we have a cgroup "C", and we want to limit it to using only 500 milliseconds of CPU time within 1 second.
   - We set "C"'s cpu.cfs_period_us to 1,000,000 (representing 1 second) and cpu.cfs_quota_us to 500,000 (representing 500 milliseconds).
   - In this case, processes in "C" will only get 500 milliseconds of CPU time within a 1-second period. Once they reach the quota, they will be throttled for the remainder of that period.

3. **Combining cpu.shares, cpu.cfs_period_us, and cpu.cfs_quota_us**:
   - Now let's combine these three settings.
   - Suppose we have two cgroups, "D" and "E", and we want "D" to get three times the CPU time of "E", but we also want to limit "D" to using only 1 second of CPU time within 2 seconds.
   - We set "D"'s cpu.shares to 1536 and "E"'s cpu.shares to 512.
   - For "D", we set cpu.cfs_period_us to 2,000,000 (2 seconds) and cpu.cfs_quota_us to 1,000,000 (1 second).
   - For "E", we set cpu.cfs_period_us to 2,000,000 (2 seconds) and cpu.cfs_quota_us to 2,000,000 (2 seconds).

   - In this case, "D" will get three times the CPU time of "E", but is limited by the 1-second CPU time quota. Once "D" reaches its 1-second quota, it will be throttled for the remainder of the current period.

1. `cpuset.cpus`:
This file shows the list of CPUs that the current cgroup can use. If this file is empty, it means the current cgroup can use all CPU resources.

2. `cpuset.cpus.effective`:
This file shows the list of CPUs that the current cgroup can actually use. This list may be more precise than `cpuset.cpus`, because it takes into account the CPU allocation of the parent cgroup.

> In the cgroup system, each cgroup can set its own CPU allocation policy. When a child cgroup is created, it inherits the CPU allocation policy of its parent cgroup.
The cpuset.cpus file represents the list of CPUs that the current cgroup can use. However, this list may not be entirely accurate, because it does not take the parent cgroup's CPU allocation into account.
The cpuset.cpus.effective file, on the other hand, takes the parent cgroup's CPU allocation into account, so the CPU list it shows is more precise. It is actually computed based on the CPU allocation policies of the current cgroup and its parent cgroup.
For example, if the parent cgroup only allows CPU 0 and CPU 1, then even if the child cgroup can use all CPUs, cpuset.cpus.effective will only show CPU 0 and CPU 1.

- `cpuset.cpus` is empty, meaning the current cgroup can use all CPU resources.
- `cpuset.cpus.effective` shows `0-1`, meaning the current cgroup can actually use CPU 0 and CPU 1.

This means that even though the current cgroup can use all CPU resources, due to the parent cgroup's restriction, it can actually only use CPU 0 and CPU 1.

By examining these two files, you can understand the CPU usage of the current cgroup and adjust as needed. If you need to change the CPU allocation, you can modify the contents of these files.

# top
You can use the `top` command to view the CPU usage of processes. The specific steps are as follows:

1. Run the `top` command:

```
top
```

2. Press the `1` key to switch to the CPU information view. You will then see the usage of each CPU core.

3. To view the CPU information used by processes, press the `c` key to switch to command-line display mode. This lets you see the CPU core used by each process.

# Note
If the parent cgroup's `cpuset.cpus.effective` setting is smaller than the child cgroup's `cpuset.cpus.effective` setting, then the processes in the child cgroup can actually only use the CPU range allowed by the parent cgroup.

Specifically:

1. When the parent cgroup's `cpuset.cpus.effective` is set to a certain range (e.g., `0-1`), all child cgroups inherit this CPU range.

2. Even if a child cgroup sets `cpuset.cpus` to a larger range (e.g., `0-3`), the actually usable CPU range is still limited to the parent cgroup's `cpuset.cpus.effective` (i.e., `0-1`).

3. Child cgroup processes can only use the CPU range allowed by the parent cgroup, even if the child cgroup's own settings allow using more CPUs.

4. If the parent cgroup's `cpuset.cpus.effective` is modified, the available CPU range of child cgroups will be updated accordingly.



Also, initially `/sys/fs/cgroup` does not have `cpuset.cpus`, only `cpuset.cpus.effective`, but all currently available CPUs are included in `cpuset.cpus.effective`. Later, newly created cgroups have both `cpuset.cpus` and `cpuset.cpus.effective`, and under the dual constraints of the parent cgroup's `cpuset.cpus.effective` allowed range and `cpuset.cpu`, `cpuset.cpus.effective` will change automatically (when `cpuset.cpus` changes).

# Showing the CPU Number Used by a Process
To see which CPU the current process is using, you can use some extra options in the `top` command.

The steps are as follows:

1. First make sure the `/proc` filesystem is correctly mounted; if it is not mounted, you can mount it with the following command:

   ```
   sudo mount -t proc proc /proc
   ```

2. Run the `top` command and press the `1` key to view the usage of each CPU.

3. To see the specific CPU core used by a process, press the `f` key to enter configuration mode, then select the two fields `%CPU` and `P`.

   - `%CPU` shows the percentage of CPU used by the process
   - `P` shows the CPU number used by the process

4. Press the `d` key to set the refresh frequency, then press `Enter` to confirm.

5. Now the `top` interface will display the specific CPU number used by each process.
