# The real-world pain point

Project address: https://github.com/Narwhal-Lab/MagicSkills



For many teams building multi-agent systems, the first thing to spin out of control is not the model, but skill management.



The same skill directory often needs to serve both Agent applications like Codex, Cursor, and Claude Code, and multiple agents created in frameworks like LangChain and LangGraph.



The result is often not "reuse" but "copying":

The same skill directory gets copied into multiple Agent projects, and once that skill directory needs updating, it has to be maintained repeatedly in multiple places, and soon the copies diverge.



# How MagicSkills solves this

What MagicSkills solves is not "building yet another Agent framework" — instead, it adds a local-first layer of skill infrastructure to multi-agent projects.



To sum it up in one sentence:

Build a skill once, and reuse it for every Agent.



Specifically:



- MagicSkills first aggregates the installed skills into a unified shared skill pool.

- Then it creates a separate `Skills` collection for each Agent, exposing only the capabilities it truly needs.

- Finally, depending on how each runtime integrates, it either syncs to `AGENTS.md` / `CLAUDE.md`, or exposes them as `tool / function`.



Here we can add a more low-level implementation concept:

MagicSkills aggregates the installed skills into a unified `Allskills` view, but when describing how it propagates outward, the easier-to-understand phrasing is "shared skill pool".



# The most extreme example

Suppose you now want to do the most extreme thing — the one that best demonstrates the value of MagicSkills:



You want the same skill directory, without any copying, to simultaneously serve the following Agent applications as well as agents built in Agent frameworks:



- Codex

- Cursor

- Claude Code

- Windsurf

- Aider

- AutoGen

- CrewAI

- LangChain

- LangGraph

- Haystack

- Semantic Kernel

- smolagents

- LlamaIndex



At this point, the whole process can be organized into the following four steps.


## 1. Install MagicSkills first



```bash

git clone https://github.com/Narwhal-Lab/MagicSkills.git

cd MagicSkills

pip install -e .

```



## 2. Install the needed skills into the shared skill pool



```bash

# 方式一：从本地安装 skill

magicskills install skill_template



# 方式二：从 GitHub 安装 skill

magicskills install anthropics/skills

```



Notes:



- The first command installs a skill from the local `skill_template`, for example `c_2_ast`.

- The second command installs more skills from GitHub, for example `pdf`, `docx`, `brand-guidelines`, `doc-coauthoring`, `canvas-design`.

- The installation path can be specified with `-t`, or you can use the default path.

- No matter where they are installed, MagicSkills aggregates these installed skills into the unified shared skill pool.



## 3. Create a separate `Skills` collection for each Agent



This step is the most crucial part of the whole design.



Instead of directly copying a skill directory into the directory where a certain Agent uses skills,

you first create a named `Skills` collection for each Agent, selecting the skills it actually needs to use.



For example:



- For Agent applications like Codex, Cursor, Claude Code, Windsurf, and Aider, each example here corresponds to one Agent by default, so usually you only need to create one `Skills` collection.

- For the following group of `tool / function` framework examples, we uniformly assume that two agents are created inside each agent framework, so each framework corresponds to two `Skills` collections, used by `agent1` and `agent2` respectively.




This step illustrates one extremely crucial thing:



Each skill capability in the shared skill pool can be freely combined into the `Skills` collections of multiple different Agents.

In other words, the same `c_2_ast` skill — without being copied — can simultaneously enter the capability boundaries of different systems such as Codex, Cursor, Claude Code, LangChain, LangGraph, and AutoGen.



## 4. Then adapt according to how each runtime is used



Once you have the individual `Skills` collections, what follows becomes runtime adaptation.



For runtimes like Codex, Cursor, Claude Code, Windsurf, and Aider that read `AGENTS.md` or `CLAUDE.md`, you can use:



```bash

magicskills syncskills <skills_name> --output ./AGENTS.md -y

magicskills syncskills <skills_name> --mode cli_description --output ./AGENTS.md -y

magicskills syncskills <skills_name> --output ./CLAUDE.md -y

```



Where:



- The default mode suits runtimes that can directly consume the `<usage> + <available_skills>` structure in `AGENTS.md`.

- `--mode cli_description` suits runtimes that cannot directly consume that structure and need to use skills through the unified CLI flow `magicskills skill-tool listskill/readskill/execskill --name <skills_name>`.

- `--output` is used to specify the output path, so the target file doesn't have to be `AGENTS.md`; it can also be output as `CLAUDE.md` or other files as required by the runtime.



For `tool / function` frameworks like LangChain, LangGraph, AutoGen, CrewAI, Haystack, Semantic Kernel, smolagents, and LlamaIndex, you directly load in code the `Skills` collection for a specific agent within that framework, and then expose it as a `tool / function`:



```python

from magicskills import REGISTRY



skills = REGISTRY.get_skills("langchain_agent1_skills")

```



Afterwards, through each framework's own `tool / function` mechanism, connect `skills.skill_tool(...)` and `skills.tool_description` to each agent.



## What is the most extreme — and most valuable — part of this?



The most extreme part is:



You are not maintaining a separate copy of skills for each Agent;

instead, you maintain the same underlying shared skill pool for all Agents, carve out each one's `Skills` collection on demand, and finally adapt according to runtime differences.



This means:



- The same skill, without copying, can serve all of the above agent systems.

- The maintenance cost of skills is centralized in one place — you only need to maintain the single copy in the shared skill pool.

- Each Agent only sees the set of capabilities it truly needs.

- Adding a new runtime does not require rewriting the entire set of skills; you only need to create a new collection and connect the corresponding adaptation layer.
