# The purpose and issues of the go compile flags ldflags -w -s
[https://blog.csdn.net/Kevin_Gates/article/details/130107710](https://blog.csdn.net/Kevin_Gates/article/details/130107710)
The -ldflags parameter can be used to pass additional arguments to the compiler. Among them, -w and -s are two commonly used parameters.

- w: strips DWARF debugging information. This reduces the size of the executable.
- s: strips the symbol table information. This further reduces the size of the executable.

After compiling an executable with the `-ldflags "-w -s"` flags, you can check whether the generated executable has had its debugging information and symbol table stripped in the following ways.




### Using the `file` command to check the file type

The `file` command can display basic information about an executable; if debugging information has been stripped, the output of `file` should not mention debugging symbols.

# GOROOT and GOPATH

- **`GOROOT`**: mainly the location of the Go toolchain; usually no manual modification is needed.
- **`GOPATH`**: used to manage and organize the user's Go projects; it can be set and modified as needed, making it easy to manage different workspaces.

### GOROOT

- **Definition**: `GOROOT` is the installation directory of Go. It points to the directory containing the Go toolchain, standard library source code, compiler, and so on.
- **Default value**: when Go is installed, `GOROOT` is usually set automatically to the installation path. For example, if you install Go via the official installer, `GOROOT` might be `/usr/local/go` (on Unix-like systems) or `C:\Go` (on Windows).
- **Purpose**:
  - Stores the Go compiler and toolchain.
  - Contains the standard library source code.
  - Go tools use `GOROOT` to locate the compiler, linker, and other tools, as well as the standard library source code.

### GOPATH

- **Definition**: `GOPATH` is the working directory for Go projects. It points to the developer's workspace and can contain multiple directories.
- **Default value**: if `GOPATH` is not set, the default is usually the `go` directory under the user's home directory (e.g. `$HOME/go`).
- **Structure**: the `GOPATH` directory usually contains three subdirectories:
  - `src`: stores source code.
  - `pkg`: stores compiled package object files.
  - `bin`: stores the executables generated after compilation.
- **Purpose**:
  - Used to store and organize the user's Go code.
  - The `go get` command downloads dependency packages into the `src` directory of `GOPATH`.
  - When compiling, Go tools look up package source code in `GOPATH`.

### The relationship between GOROOT and GOPATH

- `GOROOT` is the installation directory of the Go toolchain and contains the standard library.
- `GOPATH` is the user's workspace directory, containing the user's code and third-party libraries.

### Example

Suppose you are developing a project under `$HOME/go_projects`:

1. You can set `GOPATH` to `$HOME/go_projects`:
   ```sh
   export GOPATH=$HOME/go_projects
   ```

2. Your project directory structure might look like this:
   ```
   $HOME/go_projects/
       src/
           github.com/
               yourusername/
                   yourproject/
                       main.go
       pkg/
       bin/
   ```

3. Build your project:
   ```sh
   cd $HOME/go_projects/src/github.com/yourusername/yourproject
   go build
   ```

The compiled executable will appear in the `$HOME/go_projects/bin` directory.

# pclntab (Program Counter Line Table)

It corresponds to the pcHeader struct in the source code, located at `src/runtime/symtab.go`

```cpp
// pcHeader 包含 pclntab 查找使用的数据。
type pcHeader struct {
        magic          uint32  // 0xFFFFFFF1: 用于识别 pcHeader 结构的魔数。
        pad1, pad2     uint8   // 0,0: 对齐结构在内存中的填充字节。
        minLC          uint8   // 架构的最小指令大小。
        ptrSize        uint8   // 指针的字节大小（取决于 32 位或 64 位架构）。
        nfunc          int     // 模块中的函数数量。
        nfiles         uint    // 文件表中的条目数量（模块中的源文件数量）。
        textStart      uintptr // 功能入口 PC 偏移的基地址，等于 moduledata.text。
        funcnameOffset uintptr // 从 pcHeader 开始到 funcnametab 变量的偏移量，包含函数名。
        cuOffset       uintptr // 从 pcHeader 开始到 cutab 变量的偏移量，用于编译单元信息。
        filetabOffset  uintptr // 从 pcHeader 开始到 filetab 变量的偏移量，包含文件名。
        pctabOffset    uintptr // 从 pcHeader 开始到 pctab 变量的偏移量，用于 PC 数据表。
        pclnOffset     uintptr // 从 pcHeader 开始到 pclntab 变量的偏移量，用于 PC 到行号的映射。
}
```

![在这里插入图片描述](/images/csdn/2024/csdn-138756266/image-003-aa7c929ece.png)

1. **cu_offset**:
   - `cu_offset` is the offset of the compilation unit.
   - In `gopclntab`, a compilation unit is a large block containing function information, line number tables, and so on.
   - `cu_offset` refers to the offset position of the current function within the compilation unit.

2. **pctab**:
   - `pctab` is a table that stores the mapping between program counters (PC) and line numbers.
   - This mapping allows the source code line number to be found from a PC value at runtime, aiding debugging and error handling.

3. **runtime_pclntab**:
   - `runtime_pclntab` is the starting point or base address of the entire `gopclntab`.
   - It is a global table containing the mapping of all functions' PCs to function information.

4. **dq offset cu_offset - offset runtime_pclntab**:
   - This represents the current function's `cu_offset` minus the offset of the global `runtime_pclntab`, yielding a concrete offset value.
   - This offset value is used to locate the current function within the entire `gopclntab` structure.

5. **dq offset pctab - offset runtime_pclntab**:
   - This represents the current function's `pctab` minus the offset of the global `runtime_pclntab`.
   - This offset value is used to locate `pctab` within the entire `gopclntab` structure.

The function address offset is relative to the address of the first function in the function table

# Moduledata 
Module is a higher-level concept than Package: a Module can contain multiple different Packages, and each Package can contain multiple directories and many source files.

Correspondingly, Moduledata is also a higher-level data structure in a Go binary, containing index information for many other structures

According to the definition of Moduledata, the source code path is `src/runtime/symtab.go`

```cpp
type moduledata struct {
        sys.NotInHeap // 仅用于静态数据

        // 指向pcHeader结构的指针，包含程序计数器的头信息
        pcHeader     *pcHeader
        funcnametab  []byte      // 函数名称表
        cutab        []uint32    // 编译单元表
        filetab      []byte      // 文件表
        pctab        []byte      // 程序计数器表
        pclntable    []byte      // PC到行号的映射表
        ftab         []functab   // 函数表
        findfunctab  uintptr     // findfunctab函数的起始地址
        minpc, maxpc uintptr     // 代码段的起始和结束地址

        text, etext           uintptr // 代码段的起始和结束地址
        noptrdata, enoptrdata uintptr // 不包含指针的数据段的起始和结束地址
        data, edata           uintptr // 数据段的起始和结束地址
        bss, ebss             uintptr // BSS段的起始和结束地址
        noptrbss, enoptrbss   uintptr // 不包含指针的BSS段的起始和结束地址
        covctrs, ecovctrs     uintptr // 覆盖计数器的起始和结束地址
        end, gcdata, gcbss    uintptr // 结束地址，GC数据，GC BSS
        types, etypes         uintptr // 类型信息的起始和结束地址
        rodata                uintptr // 只读数据段的起始地址
        gofunc                uintptr // go.func.*

        textsectmap []textsect // 文本段映射
        typelinks   []int32    // 类型链接信息，存储类型偏移
        itablinks   []*itab    // 接口表链接

        ptab []ptabEntry // P 表

        pluginpath string       // 插件路径
        pkghashes  []modulehash // 包哈希信息

        // 这个切片记录了启动程序所需的初始化任务。由链接器构建。
        inittasks []*initTask

        modulename   string       // 模块名
        modulehashes []modulehash // 模块哈希信息

        hasmain uint8 // 如果模块包含main函数，则值为1，否则为0

        gcdatamask, gcbssmask bitvector // GC数据和BSS段的位向量

        typemap map[typeOff]*_type // 前一个模块中从偏移量到*_rtype的映射

        bad bool // 模块加载失败，应被忽略

        next *moduledata // 指向下一个模块的指针
}
```

Moduledata entries can be chained into a linked list, and in a complete executable Go binary, only one firstmoduledata contains the full set of fields shown above

# Program Startup
[Golang Program Startup Process](https://juejin.cn/post/7035633561805783070)

> rt0_amd64_linux->rt0_amd64->runtime_rt0_go
> The rt0_go code is fairly long and can be divided into two parts. The first part handles system parameter acquisition and runtime checks. The second part is the core of Go program startup; the overall startup flow is as follows
![在这里插入图片描述](/images/csdn/2024/csdn-138756266/image-007-a847cfba44.png)
Executing runtime.main mainly performs:
1. Starts the system background monitor sysmon thread
2. Executes init within the runtime package
3. Starts the GC
4. Executes init of user package dependencies
5. Executes the user's main.main method


1. **The `rt0_go` function**
   - When the program starts, the entry point of the Go runtime is the `rt0_go` function. This function is responsible for initializing the runtime environment.

2. **`schedinit`: initializing runtime components**
   - `rt0_go` calls `runtime_schedinit_0` to initialize the scheduler, memory allocator, garbage collector, and so on.
   - **Scheduler initialization**: initializes the scheduler, preparing it to manage the creation, scheduling, and execution of Goroutines.
   - **Memory allocator initialization**: initializes heap memory management to allocate memory for Goroutines and program data.
   - **Garbage collector initialization**: initializes the garbage collector to automatically manage memory allocation and reclamation.

3. **`newproc`: creating the main Goroutine**
   - `rt0_go` calls `runtime_newproc_0` to create the main Goroutine. The entry function of the main Goroutine is `runtime.main`, not the user's `main` function.
   - **Creating a Goroutine**: the `newproc` function is responsible for creating a new Goroutine and adding it to the scheduler's queue. The entry function of this Goroutine is `runtime.main`.

4. **`mstart`: starting the scheduler's scheduling loop**
   - `rt0_go` calls `runtime_mstart` to start the main thread. The main thread executes the `runtime.main` function.
   - **Scheduling loop**: the `mstart` function starts the scheduler's scheduling loop and begins executing the Goroutines in the queue. The first Goroutine executed is the G whose entry method is `runtime.main`.

5. **`runtime.main`: executing initialization and the user's `main` function**
   - The `runtime.main` function first performs some necessary initialization operations, such as setting global variables and initializing the standard library.
   - Then, `runtime.main` calls the user's `main` function.
