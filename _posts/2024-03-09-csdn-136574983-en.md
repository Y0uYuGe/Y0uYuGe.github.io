# The search command

### Example 1: Searching for a specific value

Suppose you want to search memory for the value `0x41414141`, you can do it like this:

```gdb
search 0x41414141
```

### Example 2: Searching for a specific string

If you want to search for the string `"Hello World!"`, you can use the following command:

```gdb
search "Hello World!"
```

### Example 3: Searching for a value of a specific type

Besides simple numeric values and strings, you can also search for values of specific types, such as `byte`, `short`, `word`, `dword`, `qword`, `pointer`, `string`, `bytes`, or `asm`. For example, searching for a `word`-type value `0x12345678`:

```gdb
search word 0x12345678
```

### Parameter Details

- `-a`: Specify the starting address of the search.
- `-l`: Limit the search range.
- `-t`: Specify the search type, such as `byte`, `short`, `word`, `dword`, `qword`, `pointer`, `string`, `bytes`, or `asm`.
- `-r`: Specify the architecture to search.
- `-m`: Specify the mapping name.
- `-x`: Display results in hexadecimal.
- `-e`: Ignore case differences.
- `-w`: Only show printable characters.
- `-s`: Step size.
- `-S`: Search the stack.
- `-L`: Search threads.
- `-A`: Aligned search.
- `-n`: Do not save search results.
- `-N`: Save search results.

# .dynsym and .symtab 
.dynsym and .symtab are both symbol tables, but their purposes differ:

.dynsym (Dynamic Symbol Table)

- dynsym is part of the ELF (Executable and Linkable Format) file format, and it contains the symbols needed during dynamic linking. It is mainly used for runtime dynamic linking (such as linking between shared library .so files), including those symbols handled by the dynamic linker (ld.so).
It usually includes the global symbols that need to be shared or used by other modules (such as other shared libraries or executables).

.symtab (Symbol Table)
- .symtab is also part of the ELF file format, and contains a full set of symbol information that may be used during linking and debugging, including both global symbols and local symbols.
It is usually generated at compile time with the -g option (in gcc), and is used in GDB or other debuggers for symbol resolution and source-level debugging.

When optimizing file size, the strip command (or compiler options) is often used to remove the .symtab section and other debugging information in order to reduce the size of the generated binary file. This usually happens when preparing binaries for a production environment. .dynsym is kept, however, because it is necessary for dynamic linking. This means that even if .symtab is removed, the program can still run normally, because the symbols relied upon for dynamic linking are still provided by .dynsym.

# heaptrace
[https://github.com/Arinerron/heaptrace](https://github.com/Arinerron/heaptrace)

Once you set a breakpoint and enter pwngdb, heap-related content is no longer echoed, which is a bit frustrating.

- heaptrace is a heap debugger used to trace glibc heap operations in ELF64 (x86_64) binaries. Its purpose is to help visualize heap operations when debugging binaries or doing heap pwn.



- Replaces addresses with easy-to-understand symbols

- Detects heap corruption and memory leak issues

- Can be debugged in GDB at any time (--break)

- Supports all ELF64 (x86_64) binaries, regardless of ASLR or compiler settings
- Can create breakpoints so that the tracer is automatically replaced by the GNU debugger (gdb) when specified conditions are met.
