# What is FUZZ (fuzz testing)?
It automatically generates a large number of samples, mutates them by some method, feeds them into the program under test, and determines whether the program has relevant vulnerabilities based on the program's feedback.

## Related tools
![在这里插入图片描述](/images/csdn/2025/csdn-139492836/image-001-e61c4e3ed7.png)




## Basic principles of the two mainstream fuzzing approaches
- Generation-based input fuzzing: 1. random; 2. template-based generation (e.g., HTTP messages, where each field can be classified as fixed, arbitrarily variable, or limited-variable).
- Mutation-based, coverage-guided fuzzing: sample mutation -> triggering new paths, perceiving process feedback -> mutating samples based on feedback and feeding them again.


# AFL principles


## Path information feedback
Feedback flow:
	1. Data generator
	2. Data input
	3. Execute the process (instrumented)
	4. Collect and organize path information
	5. Feed back to the data generator to perform targeted mutation

How to instrument:
1. Assembly level: during the process from assembly language to binary, find conditional jump points such as JNZ adder and insert functions; the instrumentation functions differ for different assembly architectures.
2. llvm pass (official API): clang/llvm IR is universal across different architectures; instrument at the IR level.
  clang: high-level language -> IR
  llvm: IR -> assembly/binary
  
Instrumentation function: coverage information feedback

    1. When fuzzing starts, there is an afl-fuzz main process, which creates a shared memory region and executes the program process.
    2. When the program process triggers different paths during execution, it executes afl-maybe-log (the random_num parameter is a number randomly generated at instrumentation time), generating a hash index for the current path.
    3. The process increments the value at the hash index position in the shared memory by 1.
    4. afl-fuzz accesses the shared memory and learns the path information.

##  Sample mutation
[https://rk700.github.io/2018/01/04/afl-mutations/](https://rk700.github.io/2018/01/04/afl-mutations/)
After obtaining the path information of a sample, it is evaluated; if suitable, the sample is added to the mutation queue, and this sample will continue to be mutated next.
Deterministic mutations:
- bitflip: bitwise flipping
If the path doesn't change, the field is considered worthless.
If the path changes identically, it's considered a fixed token combination.
- arithmetic: integer add/subtract arithmetic operations 
- interest: replacing with special values (boundary values)
- dictionary: replacing/inserting automatically generated (bit-flipped) or user-provided tokens into the original sample
Non-deterministic mutations:
- havoc: random mutation, randomly selecting a mutation method
- splice: sample splicing

## Problems with coverage guidance

For large projects:
1. The hash is simple (XOR-generated index).
2. The array length corresponding to the shared memory is limited.
3. Too many paths lead to hash collisions (multiple paths mapped to the same position; AFL reduces the number of instrumented locations when there are too many paths, but this does not substantially solve the problem).

Countermeasures: afl-fuzz's first execution of the target program turns it into a forkserver, which then forks child processes.
4. Detect afl-fuzz features (such as shared memory environment variables), clear them or directly write to the shared memory to disrupt fuzzing.
5. Detect the existence of the 198/199 pipes or directly read/write those pipes to determine that AFL is fuzzing.

qemu can translate the assembly of the emulated architecture into the corresponding assembly on the host.

qemu knows the address and function (or content) of the instruction to be translated.

When qemu translates an instruction into an assembly instruction on the host, since it knows what the instruction to be translated does, it can identify it and instrument it at that point.

- By setting `AFL_QEMU_PERSISTENT_ADDR` to set the start address and `AFL_QEMU_PERSISTENT_RET` to set the return address, a range is defined, ultimately achieving persistent fuzzing within that range.


# ASAN
## Open-source ASAN
A tool for detecting memory access errors.

Compile with the flag -fsanitize=address; the program crashes when a memory access error occurs during execution.

- Inaccessible memory, such as UAF and double free.
- Out-of-bounds read/write problems.

KASAN and ASAN are essentially the same; both are determined by compiler instrumentation.

Data regions are divided into accessible regions and inaccessible regions (red_zone).

The ratio of shadow memory to normal memory is 1:8, meaning one byte represents the memory access information of eight (aligned) bytes. The two have a mapping relationship and are separate regions (one region is the shadow memory, usually fixed at 0x7FFF8000).

For example, in the kernel:
![在这里插入图片描述](/images/csdn/2025/csdn-139492836/image-005-02df10a672.png)

 Shadow memory values: 1-7 represent how many bytes are accessible; 0 means all are accessible; negative numbers mean none are accessible.

Detecting whether a data region is accessible is roughly as follows; for details, refer to [linux内核（5.4.81）——KASAN](https://www.anquanke.com/post/id/237502).

Main functions of __asan_loadN(addr)/__asan_storeN(addr):
1. Check whether the address to be checked is within the region mapped by the shadow memory.
2. Then check whether the N bytes of memory at addr are usable.


 Setting whether a data region is accessible
 - Heap: inaccessible cases such as UAF and double free
   At malloc time, set the corresponding shadow memory region to 0.
   At free time, set the corresponding shadow region to a negative number or something else (because library functions may need to use the freed region).
- Stack: out-of-bounds read/write problems
  The problem of two consecutive arrays can cause out-of-bounds accesses to go undetected, because overflowing into the next array shows as accessible.
  At the function entry, when space is allocated, a region before and after the array is set to inaccessible (negative) in the shadow memory, and the shadow memory region corresponding to the array is set to 0.


In IDA, I found that heap-related setup operations are integrated into malloc and free; when accessing heap memory, it checks whether the corresponding shadow memory value is 0 or greater than the size being accessed.

IDA shows that the stack allocates a larger space containing the ASAN description information, redzones, and arrays, and the shadow memory values are set.

## Closed-source ASAN
Both only apply to the heap.
Closed-source ASAN for the stack remains unsolved, because setting up regions requires increasing the stack size, and at the assembly level it damages program logic more than inserting code for closed-source ASAN on the heap.

### Binary rewriting
[https://git.zephyr-software.com/opensrc/zafl
](https://git.zephyr-software.com/opensrc/zafl)

[https://github.com/HexHive/retrowrite.git
](https://github.com/HexHive/retrowrite.git)

ASAN's region setup and region detection are mainly implemented through instrumentation.

 
For closed-source, after obtaining the assembly from the binary program, the code section is instrumented.

Because instrumentation is needed at the start and end of functions, such as setting up certain regions,

How to find them?
1. Instrument all instructions in the code section, repeatedly discarding and retrying, until the instrumentation works without crashing. The goal is to instrument the starting points of all functions.
2. Use the function table to instrument directly.

Problems exist when inserting code without breaking the original functionality:
1. Inserting assembly code may change the positions of assembly code; e.g., a jump instruction's target address may remain unchanged, but the corresponding content has changed.
2. inline hook: insert a jump instruction (small instruction length, better than direct insertion, but it still has the consequences of the first approach); the jump instruction jumps to the instrumentation function and then comes back.

Intermediate language instrumentation — instead of instrumenting at the assembly level, because different architectures are troublesome: binary -> assembly -> IR, instrument the IR, smoothing over various architectures.
### Dynamic library hijacking
Suitable for heap UAF/double free.
 1. Hijack the internal implementation of the malloc/free dynamic libraries and instrument them to set memory.
2. UAF: a check is needed at use time, which also requires instrumentation; this can be done via qemu's emulation (instrument a check when encountering a store or load instruction).
3. double free: before free, check whether it has already been set to a negative number (freed).

LD_PRELOAD specifies dynamic libraries; the dynamic library functions here are loaded with priority.
