# ezcanary
**s[i:j] means getting a[i] to a[j-1]
s[:-1] removes the last character
s[:-n] removes the last n characters
s[-2:] takes the last two characters
In the s[i:j:k] format, i and j are the same as above, but k denotes the step, defaulting to 1
s[::-1] copies from the last element to the first element (in reverse)**

## Four Methods
Canary is designed to end with the byte \x00, originally to ensure that the Canary can truncate strings. The idea for leaking the Canary on the stack is to overwrite the low byte of the Canary to print out the remaining Canary part. This exploitation method requires a suitable output function to exist, and may require a first overflow to leak the Canary, followed by another overflow to control the execution flow

For the Canary, although the Canary differs after each process restart (compared to GS, which is the same after restart), the Canaries of different threads in the same process are the same, and the Canary of a child process created via the fork function is also the same, because the fork function directly copies the parent process's memory. We can exploit this characteristic to completely brute-force the Canary byte by byte

It is known that the handling logic for Canary failure enters the __stack_chk_failed function; the __stack_chk_failed function is an ordinary lazily bound function, and this function can be hijacked by modifying the GOT table

It is known that the Canary is stored in TLS, and this value is used for comparison before the function returns. When the overflow size is large, you can overwrite both the Canary stored on the stack and the Canary stored in TLS at the same time to bypass it

> Why modify the libc library
Here libc.so.6 is a symbolic link, indicating that the program depends on a libc.so.2.x.x version of libc; the following path points to the local address of that version of libc, and ld is the address of the linker. But because the libc used locally differs from the target machine's libc version, running the script on different systems causes certain addresses to change and then errors occur. Therefore, you need to download the same libc version as the target machine and make the program's symbolic link point to the libc version matching the target machine, so that local debugging and remote debugging produce correct results.

# leak-env

> write(1,buf,N) and write(0,buf,N)
> Both will print the content of buf on the terminal

> Here is a quote: in libc there is a function called _environ, which stores the current process's environment variables
After obtaining the libc address: libc base address + the offset of _environ = the address of _environ
In the memory layout, they belong to the same segment; after ASLR is enabled, the relative position does not change, and the offset is only related to the libc library
Get the value of _environ through the address of _environ, thereby obtaining the environment variable address; environment variables are stored on the stack, so through offsets within the stack, you can access any variable on the stack

![Image](/images/csdn/2023/csdn-134146384/image-009-b9caf72a9a.png)

> putchar() outputs a character but does not have a built-in newline function.
puts() has a built-in newline function; it replaces the trailing \0 with \n
putchar(10); the reason it achieves a newline:
putchar outputs a character; because 10 is an integer, the system can only convert it to the corresponding ASCII character.
In ASCII, 10 corresponds to the newline character


int main(int argc, char *argv[])
argc is the abbreviation of argument count, representing the number of arguments passed to the main function;
argv is the abbreviation of argument vector, representing the arguments passed to the main function, and the first argument argv[0] is the program name; so strictly speaking, the number of main function arguments we need to input should be argc-1;

In libc there is a symbol environ pointing to the address &argv[argc + 1]; this address is stored on the stack, and the environ address can be obtained by computing with the libc offset. So if conditions permit, by leaking the value of environ to obtain a stack address, then computing and hijacking the stack return address with a pre-arranged ROP chain, you can ultimately achieve the goal of getshell.
![Image](/images/csdn/2023/csdn-134146384/image-010-f6679e6a3b.png)

In libc, environ is environ's address on the stack; through the environ variable's address on the function stack, you can then derive its return address
