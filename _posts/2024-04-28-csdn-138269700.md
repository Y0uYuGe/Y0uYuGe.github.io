# Core Flow
- First, the gethartid function is used in the process
-  The gethartid function saves register a7 as the call number, then ecall makes the system call, and ret returns to the next address after calling the gethartid function
- ecall triggers an interrupt and enters trap_vector; at this time mepc is the ecall address, and mecause is 8
- trap_vector saves the current context, then adds a pointer to the saved context as the third argument of trap_hander; after trap_hander finishes, it writes the return value into mepc, and then mret goes to the position corresponding to mepc, which at this time is the address of ecall+4
- trap_hander executes the syscall function; the argument is the previously saved context passed in, and then the syscall function assigns the hart's id to the a0 register of that context
- At this point, returning to the place where the saved context is finally restored, that is, at trap_vector, after restoring the context, the return value at this time happens to be the hart's id, and mepc has also been set to ecall+4, so it returns to the ret function of the previous level, gethartid, and at this time the return value is also the hart's id, i.e., the hartid is obtained

## Background Explanation

In the RISC-V architecture, PMP (Physical Memory Protection) is a feature used to control the ability of different privilege levels to access memory. It defines the access permissions (read, write, execute) of memory regions and which privilege modes can access these regions through a series of configuration registers (PMP configuration registers such as `pmpcfg0`) and address registers (PMP address registers such as `pmpaddr0`).

## Code Example Analysis

Suppose you are developing a RISC-V operating system and using QEMU as a simulator to test your code. When you upgrade to QEMU 6.0 and above, you encounter a problem related to PMP configuration: if no PMP entry is set, memory accesses from Supervisor (S) or User (U) mode will cause exceptions.

##  Explanation

- **`li t0, 0xffffffff`**: This line of code assigns the value `0xffffffff` to register `t0`. This value represents a very large address in the 32-bit address space (almost close to the maximum value of the address space). According to the standard, this value is intended to set the upper-bound address of a PMP entry, but due to some QEMU implementation details, setting it to all 1s may be interpreted as the special case of covering the entire address space.

- **`csrw pmpaddr0, t0`**: This instruction writes the value of register `t0` into PMP address register 0 (`pmpaddr0`), attempting to set the first PMP entry to cover access permissions for the entire address space.

- **`li t0, 0xf`**: This line of code sets register `t0` to 0xf, which is 1111 in binary form. In PMP configuration, each bit corresponds to an access permission of a PMP entry (read, write, execute), so 0xf means enabling all permissions.

- **`csrw pmpcfg0, t0`**: Finally, this line of code writes the value of register `t0` into PMP configuration register 0 (`pmpcfg0`), activating the first PMP entry and setting read, write, and execute permissions.

## Purpose

The main purpose of this code is to serve as a temporary solution, ensuring that even without detailed configuration of PMP entries, programs in user and supervisor modes can access memory normally, to avoid the exception problems encountered when using QEMU 6.0 and above. It works by configuring one PMP entry to cover the entire address space and granting all access permissions, thereby bypassing the strict checks of unconfigured PMP entries in newer versions of QEMU.

In the RISC-V architecture, the PMP (Physical Memory Protection) mechanism controls access permissions to physical memory through a series of configuration registers, thereby enhancing system security. PMP registers are divided into address registers (such as `pmpaddrN`) and configuration registers (such as `pmpcfgN`), which together define multiple memory access control regions.

When we say "attempting to set the first PMP entry to cover access permissions for the entire address space", this refers to programming the PMP address and configuration registers to create a PMP rule intended to allow read, write, and execute operations on the entire physical address space without any access restrictions. Specifically for the code example:

- `li t0, 0xffffffff`: This line is a load instruction that loads the immediate value 0xffffffff (i.e., the maximum value minus one in the 32-bit address space) into register `t0`. In TOR (Top of Range) matching mode, the value in a PMP address register usually represents the upper-bound address of the range. Theoretically, an upper-bound address of all 1s may be interpreted as an attempt to cover the entire address space, although in practice, due to address alignment and boundary handling, it may not precisely cover the last byte of the address space.

- `csrw pmpaddr0, t0`: This instruction writes the value in register `t0` into PMP address register 0 (`pmpaddr0`), attempting to set the upper-bound address of the first PMP entry.

- `li t0, 0xf` and `csrw pmpcfg0, t0`: These two lines configure the permissions of the PMP entry. `0xf` (hexadecimal) equals 1111 in binary, representing the read (R), write (W), execute (X), and lock (L) permission bits respectively. By writing to `pmpcfg0`, full permissions are set for PMP entry 0.

However, according to the RISC-V PMP specification, a single PMP entry usually cannot directly cover the entire address space. Especially in TOR mode, the `pmpaddr0` register stores the upper 32 bits of the upper-bound physical address of the first range; even if set to all 1s, it cannot perfectly cover the very end of the address space. Moreover, as mentioned in the previous discussion, QEMU's specific implementation may cause `pmpaddr0 = 0xffffffff` to be specially handled in certain situations, seemingly covering the entire address space.
