# Debug Information

Debug information is extra data generated when compiling or building a program, used to help developers understand the execution flow and state of the code during debugging. This information does not directly affect the program's functionality, but it is crucial during the debugging phase. Debug information usually contains the following:

- **Source code line numbers**: Correspond to the source code location of each piece of executable code, allowing the debugger to locate the exact execution point in the source code.
- **Names and types of local variables and function parameters**: Allow viewing and modifying variable values during debugging.
- **Source code paths**: Help the debugger find the original source files in order to display the code context.
- **Compiler macro definitions**: Help understand the conditional compilation parts of the code.
- **Static structure information of the program**: Such as definitions of classes, structs, enums, etc., which helps in understanding data structures.

With this information, the debugger can provide a rich contextual view, enabling developers to step through code, set breakpoints, view and modify variable values, and thereby trace the root cause of errors.

# Symbol Table


A symbol table is a data structure created by the compiler or assembler during compilation. It stores all symbols defined in the program (such as variable names, function names, class names, etc.) and their corresponding addresses or memory locations. The main purposes of the symbol table include:

- **Address resolution**: When generating object code, converting symbol references in the source code into actual addresses in the object code. This is especially important for the linking process, because it helps the linker resolve external references.
- **Debugging assistance**: Provided to the debugger, enabling it to look up the exact memory address of a variable or function based on the symbol name, and then view or modify its value, or jump to the beginning of a specific function to execute.
- **Error reporting**: Compile-time error and warning messages usually reference symbol names from the symbol table, providing more understandable error descriptions.
- **Performance analysis**: In performance analysis tools, the symbol table helps map memory addresses back to symbols in the source code, making it easier to understand which functions or code blocks consume more resources.

#  `.symtab` and `.dynsym`
![在这里插入图片描述](/images/csdn/2024/csdn-138926384/image-001-3bc3536bf0.png)
In the ELF (Executable and Linkable Format) file structure, `.symtab` (symbol table) and `.dynsym` (dynamic symbol table) store symbol information for different purposes. Below, examples are used to explain the differences between these two symbol tables in detail.
### `.symtab` (Symbol Table)

`.symtab` contains all symbol information in the program, whether local (static) symbols or global symbols. This symbol information is used to resolve symbol references during the linking phase, and may be used for debugging purposes at runtime. Here, "local static symbols" refers to symbols visible only within the current compilation unit, while "global symbols" are symbols accessible throughout the entire program.

**Example**:
Suppose there is a C program containing two source files: `main.c` and `helper.c`. A global function `void helper_function()` is defined in `helper.c` and called in `main.c`. In this scenario:

- The symbol information for `helper_function` appears in `.symtab` as a global symbol, because it is visible across compilation units.
- Suppose `main.c` also has a local static variable `static int local_var;`; its symbol information is also added to `.symtab`, but as a local static symbol, it is only visible when compiling `main.c` and is not exposed elsewhere in the linked program.

### `.dynsym` (Dynamic Symbol Table)

In contrast, `.dynsym` only contains symbols needed during dynamic linking, such as functions and global variables exported from dynamic libraries. The dynamic linker (such as `ld.so` on Linux) uses `.dynsym` at program startup to resolve symbols in dynamic libraries that are referenced by the program.

**Example**:
If your program uses the `sin()` function from `libm.so` (the math library), then the symbol information for `sin` appears in `.dynsym` rather than `.symtab`. This is because the `sin` function is provided by a dynamic library, and only at program runtime does the dynamic linker need to know where to find the implementation of this function.

### Summary

- `.symtab` is comprehensive, containing all symbol information in the program, including both local static symbols and global symbols, mainly used for linking and debugging.
- `.dynsym` is more streamlined, recording only those symbols needed during the dynamic linking process; typically these symbols belong to dynamic link libraries or are global symbols that need to be linked by other shared objects.

Indeed, `.symtab` and `.dynsym` are two important sections in ELF (Executable and Linkable Format) files. They each play different roles and together contribute to the program's linking and runtime symbol resolution process. Below is a brief explanation of these two sections and how they help us view the types of variables in libc or other libraries.

- **.symtab (Static Symbol Table)**: This is a complete symbol table containing all symbol definitions and references in the program, whether local symbols, global symbols, or external symbols. It is mainly used for symbol resolution at link time and for debugging purposes. `.symtab` contains the symbol's name, type (such as function, object, TLS, etc.), address in the file, and the symbol's binding attributes (local or global). The static linker uses this information to resolve undefined symbol references. However, at program runtime, `.symtab` is not directly used for dynamic linking, so it is usually removed with the `strip` command when producing the final release version of a program to reduce file size.

- **.dynsym (Dynamic Symbol Table)**: This section only contains the information needed for dynamic linking, i.e., the global symbols and external symbols that may need to be resolved from shared libraries at runtime. `.dynsym` does not include local symbols, because it focuses on symbol lookup across module boundaries. During program execution, the dynamic linker consults this table to locate and load symbols defined in shared objects. `.dynsym` also records the type and address of symbols, which is particularly important for dynamic libraries.

Debugging symbols are a series of pieces of information generated by the compiler when compiling a program and embedded into the executable or library file. They are mainly used to provide source code-level debug information, enabling a debugger (such as GDB) to:

- Show the correspondence between source code line numbers and instructions, letting you know which line of source code each machine instruction corresponds to.
- Show variable names and their locations in memory, including local variables, global variables, and structure members, etc., which is crucial for watching and modifying variable values.
- Provide function names and their addresses in memory, which helps set breakpoints and trace function call stacks.
- Present type information, which is particularly important for understanding complex data structures and correctly displaying the contents of complex types (such as structs and classes).


When debugging symbols are missing, although some debuggers can still load and run the program, many advanced debugging features (such as listing source code, viewing variable values, etc.) will be unavailable or limited, making the debugging process more difficult.

## Importing the Source Code

When GDB or other debuggers report missing debug information, even if you have the source code files, the debugger cannot accurately map the executed instructions to source code lines at runtime. Without debug information, you may only see assembly code (via the `disassemble` command), and cannot directly jump to or view specific C source code lines.
