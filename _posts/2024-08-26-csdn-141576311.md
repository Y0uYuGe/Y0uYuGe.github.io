# Use After Free
Example challenge: `heap bof` 
kaslr, smep, and smap are enabled.

The size of the cred structure is 0xa8. According to the slub allocation mechanism, if you allocate and free a memory block of size 0xa8 (actually 0xe0) and then create a new thread, that thread's cred structure will be exactly the memory block just freed. Using the UAF vulnerability to modify cred achieves privilege escalation.


However, in newer versions, cred_jar is not merged with other slabs of the same size; a freed cred structure is only returned to cred_jar instead of being merged into other slabs.

This is because cred_jar is created with the SLAB_ACCOUNT flag. When CONFIG_MEMCG_KMEM=y (enabled by default), cred_jar is no longer merged with kmalloc-192 of the same size (you can think of it as cred_jar needing to track its memory usage separately, so it is not allowed to merge with other slabs).

It selects the chunk by p_arg.idx, and after kfree the pointer is not cleared, so it can be used again via case 9 and case 8. If the freed chunk is reallocated and stores something related to a kernel address, then `case 9: copy_to_user` can copy that kernel address to user space, leaking a kernel address. Moreover, since case 8 has no length limit — the length is decided by user input — there is also a heap overflow.

## CPU binding
Note: since `-smp cores=2,threads=2 \` is enabled, CPU switching causes the kmalloc-cache-cpu to switch, so a newly allocated object may not be the one just freed by kfree. Therefore we need to bind the process to one CPU core. Without binding there is still some chance of success.

```c
#define __USE_GNU

{
    cpu_set_t cpu_set;

    CPU_ZERO(&cpu_set);
    CPU_SET(core, &cpu_set);
    sched_setaffinity(getpid(), sizeof(cpu_set), &cpu_set);
}
bind_cpu(sched_getcpu());
```

## cred_jar is mergeable
In this case the cred chunk is not distinguished from chunks of the same size, so we can obtain the cred from a same-sized chunk that was just freed.

So we free a heap chunk the same size as cred, then create a child thread; the child's cred will be the chunk that was just freed. Then we use case 8 to modify the previously freed chunk to overwrite the cred structure, setting its uid and gid to 0.

- Leaking the kernel base address
A read primitive is needed. We can use ops = ptm_unix98_ops at offset 0x18: with kaslr disabled, read ptm_unix98_ops from kallsyms; the leaked address minus it gives the kernel base.
![Image](/images/csdn/2024/csdn-141576311/image-002-0d574034b1.png)

- Leaking the kmalloc-1k heap address
A read primitive is needed. We can use a linked-list pointer at offset 0x38, which initially points to itself. Reading it out and subtracting 0x38 gives the address of the current tty_struct, which is also some kmalloc-1k heap address.
![Image](/images/csdn/2024/csdn-141576311/image-003-38b16eec63.png)

- Hijacking the program flow
A write primitive is needed to overwrite ops with a forged tty_operations. Since only one gadget can be written to a given function pointer in the tty_operations structure, besides using pt_regs + ret2dir we can also exploit the characteristics of how tty_struct invokes the function pointers inside tty_operations.

- write (tty_write->do_tty_write->n_tty_write->pty_write)
For example, using write: when jumping to write (with the breakpoint set at pty_write), observe the registers and you will find that rax is tty_struct.ops. We can look for a gadget such as mov rsp, rax to perform stack pivoting, which lets us overwrite the data before tty_struct.ops to ROP. However, this space is a bit small — not enough for ROP — so another stack pivot is needed.
![Image](/images/csdn/2024/csdn-141576311/image-004-514f4e212e.png)
But note that hijacking write triggers a check of the tty magic number.
![Image](/images/csdn/2024/csdn-141576311/image-005-01c5fc8b17.png)


- ioctl （tty_ioctl->pty_unix98_ioctl）
Or use ioctl, which can control the values of some registers via the passed arguments. Note that to use ioctl, the magic number must be correct and driver must be a kernel heap address.
When execution reaches this point, rbp = &tty_struct (sometimes rbp is not &tty_struct). If we set tty->op->ioctl to `leave; ret`, the stack is first pivoted to &tty_struct + 0x8. Set this to `pop rsp; ret`, and set &tty_struct + 0x10 (.driver) to a kernel heap address where the ROP chain is laid out, completing the second stack pivot.

  In addition, at this point rax is the address of the pty_unix98_ioctl function. If we use `xchg eax, esp; ret`, the stack will be pivoted to rax & 0xffffffff, which lands in user space. We can then mmap a ROP chain in user space, but this requires smap to be disabled.
![Image](/images/csdn/2024/csdn-141576311/image-006-38f032de10.png)
- We find that rdi is exactly the address of the tty_struct at this point, which can also be used for exploitation.

Here we overwrite tty_operations with a user-space forged tty_operations, so smap must be disabled.

- What if smap is enabled? Since we can control other parts, we just need to ensure tty_operations is in the kernel. We can overwrite the ops function table pointer with tty_addr + 0x20 - 0x60, so that ioctl points to tty_addr + 0x20, which is a location we control. We put the address of a stack-pivot gadget there; the same applies to other functions.

> For write it is recommended to build the ROP chain on op; for ioctl you can build the ROP chain on tty.

## Overflow via heap layout to modify cred
Overwriting cred by overflow, like the previous UAF cred modification, no longer works on newer versions because they are not in the same cache, so the memory is not necessarily adjacent.

kalloc automatically adjusts the size — you can check /proc/slabinfo; it is usually rounded up.
Here we generally exploit the fact that the allocated size and the cred size fall into the same kmem-cache. We allocate a bunch so that the object addresses in the slub freelist stay contiguous, making the next two contiguous as well to achieve the overflow. The exploitation of this challenge relies on a structure: seq_operations, which is 0x20 in size (the same as queue) and contains 4 pointers:

```c
struct seq_operations {
	void * (*start) (struct seq_file *m, loff_t *pos);
	void (*stop) (struct seq_file *m, void *v);
```

This structure is essential for sequence files; it acts like an iterator that can output certain content in a loop, and is commonly used to export data and records for managing large data files. When an LKM that defines this structure is opened (e.g., with the cat command or read), the kernel creates such a data structure and first calls the start function pointer. Since this structure is 0x20 in size, it is very likely to be allocated close to the queue above. If we can control the start pointer here, we can control the kernel execution flow. The sequence file opened in this challenge is /proc/self/stat.

Here `open("/proc/self/stat", O_RDONLY);` heap-sprays a batch of 0x20-sized chunks, then frees one in the middle. At this point some allocated chunk may be right after the freed one (but it is not), so we try read on all opened descriptors.

However, since what we hijack is a function pointer, there is still a `push rbp` at the beginning, so the leaked address is at rsp+8. We then add the relevant offsets to the leaked address and call functions via `call reg`.

### poll
The `poll` function is a multiplexing technique used to monitor multiple file descriptors (usually sockets or pipes) to determine whether they have data to read, can be written to, or whether an error has occurred.


1. **Monitoring multiple file descriptors**: `poll` can simultaneously monitor state changes of multiple file descriptors, which can be open files, network sockets, etc.

2. **Event detection**: It can detect different event types, such as:
   - **POLLIN**: data is readable.
   - **POLLOUT**: data is writable.
   - **POLLERR**: an error occurred.
   - **POLLHUP**: hang-up event (the peer closed the connection).



The typical steps for using the `poll` function are:

1. Initialize an array of `pollfd` structures (each structure corresponds to one file descriptor).
2. Set the event types to monitor.
3. Call the `poll` function, passing in the `pollfd` array, its size, and a timeout.
4. When `poll` returns, check the `revents` field of each `pollfd` structure to determine which file descriptors had the events of interest.

# Kernel Unlink
When an element is removed from a linked list, unlink is required. The main purpose of kernel unlink is to leverage unlink's mutual pointer-write operation to achieve an arbitrary address write.

unlink is based on the list_del operation. Two addresses are forged to replace prev and next in list_head, so that one address gets written to the memory pointed to by the other address. If we can control the prev / next pointers, we can set the prev pointer to modprobe_path, so that at [2] the next value is written into the memory pointed to by prev.

The problem: at [1], prev is first written to next->prev, which means next must also be a valid pointer; and later next needs to be written to prev->next, so this limits the value we can write to prev. The solution is to use physmap to provide a valid prev value.

```c

static inline void __list_del(struct list_head * prev, struct list_head * next)
{
	next->prev = prev; 				// [1]
	WRITE_ONCE(prev->next, next); 	// [2]
}
```
The range of physmap: 0xffff888000000000-0xffffc87fffffffff

physmap is a region of kernel virtual memory to which physical memory pages are contiguously mapped. So the hijacked prev address can range from 0xffff888000000000 to 0xffffc87fffffffff (there is an offset; the possible values depend on the actual offset). The attacker can control the low 4 bytes of prev, and just needs to ensure the high 4 bytes represent a physmap address.

Since our goal is to modify modprobe_path, we can construct next = 0xffffxxxx2f706d74 (the system memory must be at least 0x2f706d7c bytes, about 760M). If prev = modprobe_path + 1, then via [2], modprobe_path is overwritten with /tmp/(the characters corresponding to 0xffffxxxx)probe (where 0xffffxxxx is the high 4 bytes of prev). Privilege escalation can then proceed as before.

## simple_xattr (any structure with linked-list unlink operations works)
1. setxattr

setxattr is a system call used to set extended attributes of a file. Its basic syntax is:

```c

```

- path: file path
- name: attribute name
- value: attribute value
- size: size of the attribute value
- flags: setting flags

For example:
```c

```
This sets an extended attribute named "user.myattr" with the value "myvalue" on the file.

2. simple_xattr

simple_xattr is a structure in the Linux kernel used to manage extended attributes. It is usually not used directly by user-space programs; instead, the kernel uses it to store and manage extended attributes.

Its structure is roughly as follows:

```c
struct simple_xattr {
    struct list_head list;  // 用于链接多个xattr
    char *name;             // xattr的名称
    size_t size;            // xattr值的大小
    char value[];           // xattr的值,柔性数组成员
};

struct list_head {
	struct list_head *next, *prev;
};
```

- list: used to link multiple xattrs together
- name: attribute name
- size: size of the attribute value
- value: attribute value (flexible array member)

Each file's simple_xattrs are stored in a list_head linked list. The allocation function is simple_xattr_alloc(), the user controls simple_xattr->value, and the allocation size ranges from kmalloc-32 to very large.

> simple_xattr cannot be modified in place; when it is edited, the old simple_xattr is unlinked from the list, then a new simple_xattr is allocated and linked in. Here we can modify simple_xattr via UAF or overflow. Also, unprivileged users cannot set simple_xattr, but it works as long as the system supports user namespaces.


Therefore we can modify simple_xattr to carry out an unlink attack. But this technique requires knowing which simple_xattr object was overwritten; otherwise, removing an arbitrary simple_xattr will cause errors when traversing the list (if a removed normal simple_xattr is adjacent to an abnormal simple_xattr, the abnormal simple_xattr will be linked into the doubly linked list).

Suppose we have a filesystem with a file "secret.txt" that has the following xattrs:

1. user.color = "red"
2. user.size = "large"
3. user.type = "confidential"

These xattrs may be stored in the kernel as a linked list of simple_xattr objects.

Now, an attacker wants to exploit a simple_xattr vulnerability. Their target is to overwrite the simple_xattr object of "user.size".

Steps:

1. The attacker first needs to trigger a heap overflow or UAF vulnerability so they can overwrite the simple_xattr object of "user.size".

2. The attacker modifies the list_head of the "user.size" simple_xattr object.

3. Now the attacker wants to use this modified object for further attacks.

4. If the attacker randomly removes an xattr, such as "user.color":

   ```
   removexattr("secret.txt", "user.color")
   ```

   This may cause the kernel to error while traversing the xattr list, because the list structure has been corrupted.

5. Instead, the attacker should precisely locate and operate on the "user.size" xattr:

   ```
   removexattr("secret.txt", "user.size")
   ```

- If, while modifying simple_xattr, we can also read simple_xattr's value (controlling simple_xattr via UAF), then we can set the value when creating the simple_xattr (the value parameter of setxattr) to determine which simple_xattr object was overwritten.

###  `struct page` pointer, the linear mapping area, and vmemmap

#### 1. The relationship between the linear mapping area and physical addresses

In the Linux kernel, the **linear mapping area** (also called the direct mapping area) is part of the virtual address space that directly maps physical memory addresses. This means that given a physical address, you can obtain its virtual address in the linear mapping area by adding a fixed offset (`PAGE_OFFSET`), and vice versa.

On the x86_64 architecture, `PAGE_OFFSET` is generally `0xffff888000000000`, which is the starting address of the kernel's linear mapping area. Suppose we have a linear mapping area virtual address `0xffff888012345000`; we can get the corresponding physical address by subtracting `PAGE_OFFSET`.

#### 2. Calculating the physical address

Assume `PAGE_OFFSET` is `0xffff888000000000`:
```c
unsigned long linear_address = 0xffff888012345000;
unsigned long physical_address = linear_address - PAGE_OFFSET;
```
The result is:
```c
physical_address = 0xffff888012345000 - 0xffff888000000000
                 = 0x12345000
```
This physical address is `0x12345000`.

#### 3. Converting a physical address to a `struct page` pointer

In the Linux kernel, physical memory pages are managed through `struct page` structures. Each physical page has a corresponding `struct page` structure, and these structures are usually stored contiguously in a kernel array (the `vmemmap` array is a global array that maps the struct page structures of all physical pages. Each element of this array corresponds to the struct page structure of one physical page.) Each element of this array corresponds to one physical page.

To convert a physical address to a `struct page` pointer, the following steps are needed:

1. **Convert the physical address to a page frame number (PFN)**:
   - The page frame number is the physical address divided by the page size (usually 4KB).
   ```c
   unsigned long pfn = physical_address >> PAGE_SHIFT;
   ```
   Here `PAGE_SHIFT` is the shift amount of the page size; for a 4KB page size, `PAGE_SHIFT` is 12.

2. **Convert the page frame number to a `struct page` pointer**:
   - The kernel provides the macro `pfn_to_page(pfn)`, which finds the corresponding `struct page` structure via the page frame number. The result of this macro is the virtual address of the struct page structure corresponding to the PFN in the vmemmap array.
   ```c
   struct page *page = pfn_to_page(pfn);
   ```

#### Example code

Combining the above steps, the code is as follows:
```c
#define PAGE_OFFSET 0xffff888000000000UL
#define PAGE_SHIFT 12

unsigned long linear_address = 0xffff888012345000;
unsigned long physical_address = linear_address - PAGE_OFFSET;
unsigned long pfn = physical_address >> PAGE_SHIFT;
struct page *page = pfn_to_page(pfn);
```

### pipebuffer
[https://www.51cto.com/article/684282.html](https://www.51cto.com/article/684282.html)

When fcntl reallocates the size, it first does a kcalloc, then copies the contents of the original pipebuffer (for pages that have data) into the kcalloc-allocated pipebuffer.

Read: pipebuffer reads via pipebuffer->offset, pipebuffer->len, and page; after reading, `pipebuffer->offset = pipebuffer->offset + pipebuffer->len`
Write: pipebuffer writes starting at `pipebuffer->offset + pipebuffer->len`, and `pipebuffer->len = pipebuffer->len + number of bytes written`

In addition, physical pages are allocated for page only when writing to the pipe.


### Exploitation
The vulnerability lies in command 1300 (append data to an existing cache): there is an off-by-null vulnerability.

Since it is a standalone cache, no other structures share a cache with it. But structures whose caches come from the same buddy order can be adjacent, so we can only consider page-level heap fengshui to cause a cross-cache condition.

### Privilege escalation
#### Privilege escalation via init_cred
Follow the real_parent of the current task_struct — the virtual address of the parent process's task_struct — upwards until real_parent points to itself, which is `init_task`. Then write init_task's init_cred into the current task_struct's cred pointer so it points to init_cred.
####  Writing ROP onto the kernel stack
The page table address can be obtained via mm_struct; the mm_struct address can be obtained via task_struct; the kernel stack address can likewise be obtained via task_struct.

Through the stack pointer of task_struct we can obtain the kernel stack address. Then, via page table translation, we get the stack's physical address and thereby the corresponding page. Afterwards we can spray ROP into the corresponding page to achieve privilege escalation.


####  USMA
- mmap a region of memory, and modify the page tables so that the mmap'ed virtual memory maps to the physical address corresponding to the ns_capable_setid function. Then write shellcode into the mmap region to modify the ns_capable_setid function. Here, the code segment containing ns_capable_setid is a 2M huge page rather than a 4K memory page, so it is resolved through 3-level page tables instead of 4-level page tables. Therefore, the page table entry in the fourth-level page table that the mmap'ed virtual memory ultimately maps to is the address of a 2M huge page.
- The shellcode can make the return value of ns_capable_setid always 1. When calling setresuid(0, 0, 0) to elevate privileges, ns_capable_setid is consulted to decide whether it is allowed. After modifying the ns_capable_setid function, we can use setresuid(0, 0, 0) to escalate privileges.
