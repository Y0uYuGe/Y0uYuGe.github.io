## Approach
Since the region allocated by mmap is at some offset between the main thread's heap and the stack, in between there are anonymous mappings allocated by mmap and the file mappings of libc and ld.

- First allocate the space of the current heap_info (leaving a residual topchunk, but with a size such that the topchunk can neither satisfy the request nor be extended, so a new heap_info is requested), then make the requested size plus the current heap->size greater than max_size so that the original topchunk is freed, and then obtain a new heap_info
-  Allocate something larger than `0x20000 ` so that mmap allocations fill the part between the heap and libc
-  Allocate a portion of the chunk that previously went into the unsortedbin, then overflow to modify its size, so that when splitting, the fd of the unsortedbin lands exactly on the first eight bytes of the new page (i.e., the ar_ptr of the heap_info corresponding to libc, because every chunk obtained is checked to see whether its arena matches ar_ptr, and at this point the fd points into the mstate corresponding to ar_ptr), then allocate it out and partially write it to obtain `ar_ptr `

## moudle function basic_block
Of course, I will use a C language example to explain the relationship between Module, Function, and Basic Block. These concepts are the core components of LLVM IR.

First, let's look at a simple C program:

```c
#include <stdio.h>

int add(int a, int b) {
    return a + b;
}

int max(int a, int b) {
    if (a > b) {
        return a;
    } else {
        return b;
    }
}

int main() {
    int x = 5, y = 10;
    int sum = add(x, y);
    int maximum = max(x, y);
    printf("Sum: %d, Max: %d\n", sum, maximum);
    return 0;
}
```

Now, let's explain how this program is organized in the context of LLVM:

1. Module:
   - The entire C file is treated as one Module.
   - A Module is the top-level container of LLVM IR.
   - It contains all function definitions, global variables, and other top-level entities.

2. Function:
   - In this example, we have three functions: `add`, `max`, and `main`.
   - Each function is represented as a Function in LLVM IR.
   - A Function contains the function's parameters, return type, and function body.

3. Basic Block:
   - Each function consists of one or more Basic Blocks.
   - A Basic Block is a series of consecutive instructions with only one entry (the first instruction) and one exit (the last instruction).
   - In our example:
     - The `add` function may have only one Basic Block.
     - The `max` function may have three Basic Blocks: one for the condition check, one for the `if` branch, and one for the `else` branch.
     - The `main` function may have one or more Basic Blocks, depending on compiler optimizations.

Let's take a closer look at the `max` function, since it demonstrates multiple Basic Blocks:

```llvm
define i32 @max(i32 %a, i32 %b) {
entry:
  %cmp = icmp sgt i32 %a, %b
  br i1 %cmp, label %if.then, label %if.else

if.then:                                          ; preds = %entry
  ret i32 %a

if.else:                                          ; preds = %entry
  ret i32 %b
}
```

In this LLVM IR representation:
- The entire `max` function is one Function.
- It contains three Basic Blocks: `entry`, `if.then`, and `if.else`.
- The `entry` Block contains the comparison instruction and the conditional branch.
- The `if.then` and `if.else` Blocks each contain a return instruction.

Relationship summary:
1. A Module contains multiple Functions.
2. Each Function contains one or more Basic Blocks.
3. A Basic Block contains the actual instruction sequence.

## BYTE1
Damn, I always thought BYTE1 was the low byte, but it turns out it is not

In IDA, the effect of the line `result = (BYTE1(code) >> 4) & 7;` can be understood through step-by-step analysis. Suppose `code` is a variable of integer type, and `BYTE1(code)` is a macro or function used to extract the second byte of `code` (counting from the low bits, the low byte is byte 0).

### Analysis Steps:

1. **`BYTE1(code)`**:
   - `BYTE1(code)` is typically used to extract the second byte of `code` (i.e., the 1st byte counting from the low bits). For example, if `code` is a 32-bit integer, then `BYTE1(code)` extracts the 8 bits from bit 8 to bit 15 of `code`.
   - A concrete implementation might be `#define BYTE1(x) ((x >> 8) & 0xFF)`, which means it shifts `code` right by 8 bits and then takes the lowest 8 bits.

2. **`BYTE1(code) >> 4`**:
   - This step shifts the extracted second byte right by another 4 bits. Shifting right by 4 bits keeps the high 4 bits of that byte, while the low 4 bits are discarded.

3. **`& 7`**:
   - The binary representation of `7` is `00000111`, which keeps only the lowest 3 bits. The `& 7` operation performs a bitwise AND between the shifted result and `7`, thereby keeping only the lowest 3 bits of the result.

### Summary:
The effect of the line `result = (BYTE1(code) >> 4) & 7;` is:

- Extract the second byte (bits 8 through 15) from `code`.
- Shift that byte right by 4 bits, keeping its high 4 bits.
- Then, through the `& 7` operation, only the lowest 3 bits of the shifted result are kept.

In the end, the value of `result` is the lowest 3 bits of the high 4 bits of the second byte of `code`. This kind of operation is typically used to extract a specific bit field from a byte, possibly for parsing some encoding format or protocol.
