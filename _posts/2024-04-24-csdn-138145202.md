# Concurrency and Synchronization
Control flow: can be understood as a task or process

An interrupt can also be understood as switching to another task (the interrupt handler), so macroscopically they are considered to execute simultaneously

Synchronization: can be understood as requiring a certain ordering between a certain operation of one task and a certain operation of another task

# Critical Sections and Locks

![Image](/images/csdn/2024/csdn-138145202/image-002-de84baa411.png)
In concurrent execution, when a process accesses a critical section, unless the access ends, other processes (even if switched to that process) cannot enter the critical section, i.e., they are blocked. Otherwise, it would affect that process's use of the critical section resources.

> A critical section refers to a section of code or a resource area in a multithreaded environment that only allows one thread to access at a time. To ensure safe access to critical sections and avoid data inconsistency or other race conditions caused by multiple threads accessing simultaneously, we need to take synchronization measures to protect critical sections


# Locks
- When a thread tries to acquire a sleepable lock held by another thread, if the lock is unavailable, the thread will be suspended by the operating system and placed in the waiting queue, thus stopping execution (entering the sleep state). Once the thread holding the lock releases it, the operating system will select an appropriate thread to wake up and grant it ownership of the lock. In this way, the thread can continue executing the protected code segment.
- For non-sleepable locks, when trying to acquire the lock, if the lock is occupied, the current thread is not suspended, but instead spins in place, constantly checking whether the lock has been released. This approach avoids the overhead of thread context switching, but may cause the thread to consume a large amount of CPU resources, especially when the lock is held for a long time.
![Image](/images/csdn/2024/csdn-138145202/image-003-bcc6514406.png)

Locking causes another process that also wants to lock to block and keep looping, until the lock is finally released

# Deadlock
Accessing multiple critical sections may involve multiple locks

When A executes and acquires lock A, then B executes and acquires lock B, then A acquires lock B, and B acquires lock A
This will cause blocking. That is, switching to A again to prepare to acquire lock B, and then switching to B to acquire lock A, will block. Both get stuck
![Image](/images/csdn/2024/csdn-138145202/image-004-d45238e90c.png)
# Solving Deadlock
In addition to the three points, you can also implement acquiring multiple locks in one go, without interruption. This can solve it

Adjust the order of acquiring locks, because the inconsistent order of requesting locks in the previous example is also a cause of deadlock
To prevent requesting other locks while holding one lock, try to make sure all locks requested before requesting a lock are released

# Atomicity Problem
The interrupt granularity is at the assembly instruction level

That is to say, the locking operation may not be completed before an interrupt occurs and jumps to another control flow, causing that other control flow to find the lock is not locked at this time, resulting in both entering the critical section (the first executed the assembly and entered the if but did not set locked, causing the second to also enter the if and lock at this time)

# Atomic Operation Implementation
amoswap.w.aq stores the locked value into a register, and at the same time the value of locked is updated to the register's value, which is 1. It cannot be interrupted

Here the value change is completed in one go, so that there won't be a situation where the lock hasn't been updated in time before switching to another process, making it also think it's not locked. (You can also think of it as making the value update happen before judging whether to enter the critical section)

If it is not atomic, then suppose it is divided into several parts to implement updating the value and saving the original value, then you might get deadlock or the result of both entering the critical section

It is found that only the execution flow executing this instruction will lock; others won't, even an execution flow that is about to reach this instruction

## amoswap.w.aq
In the RISC-V architecture, the amoswap.w.aq instruction is one of the atomic memory operation instructions, mainly used for atomic read-modify-write memory operations in concurrent environments. The name of this instruction comes from a combination of several keywords:

- **amo**: Atomic Memory Operation, indicating that this instruction is indivisible during execution, ensuring atomicity of the operation even in multithreaded or multiprocessor environments.
- **swap**: indicates that this instruction performs a swap operation, i.e., exchanging the value in a register with the contents of a memory location.
- **w**: indicates that the data width of the operation is 32 bits (word size).
- **aq**: is part of the Atomicity Qualifier. The RISC-V architecture uses the two atomic ordering tags aq and rl to cooperate in implementing the memory ordering model. Among them, aq (Acquire) ensures that the execution of the instruction is not reordered with previous memory operations, and that write operations from other cores can be observed after the instruction executes.

The specific function of the amoswap.w.aq instruction is as follows:

- It simultaneously reads the original value of a memory location (through the specified address) and writes the value in a register to that memory location.
- Finally, the instruction stores the read original memory value into another specified register.

This series of operations is completed as a single atomic step, which is crucial for maintaining data consistency, especially when multiple threads concurrently access shared memory regions.

For example, in the amoswap.w.aq rs2, rs1, (ra) instruction format:
- rs1 is the source register of the new value to be written to memory.
- rs2 is the destination register that holds the original value of memory.
- ra is the register containing the memory address to operate on.


1. **aq (Acquire)**:
   - When an instruction with the "aq" tag is executed, it acts as an "acquire" memory barrier, ensuring that memory read and write operations before this instruction have all completed, and that these operations are visible to subsequent operations (including this core and other cores).
   - That is, the amoswap.w.aq instruction is not only atomic itself, but also guarantees that after executing this instruction, any read operation of shared variables can see the effects of all write operations that occurred before the instruction, effectively preventing instruction reordering.

2. **rl (Release)**:
   - Correspondingly, an instruction with the "rl" tag means it is a "release" memory barrier, ensuring that when this instruction executes, it and all memory operations before it have all completed, and write operations after this instruction will be invisible to other cores until the next instruction with the "aq" tag executes.
   - That is to say, after the amoswap.w.rl instruction writes to shared memory, other cores can only see the result of this write after executing their own "aq" instruction.


## Example

Suppose there are two cores, Core A and Core B, which share a memory region, and Core A is modifying a variable `shared_var`, while Core B needs to read the latest value of `shared_var`. Without control, the following situation may occur:

1. Core A first modifies the value of `shared_var`, but due to factors such as cache coherence, this modification has not yet been flushed to main memory;
2. Core B reads `shared_var` at this time; since there is no memory ordering guarantee, it may read the old value instead of the new value just modified by Core A.

To ensure Core B can see Core A's write operation, we can use an atomic instruction with the `aq` tag. For example, in the RISC-V architecture, if we have an amoswap.w.aq instruction:

```assembly
amoswap.w.aq t1, t2, (a0)
```

This instruction atomically writes the value of register `t2` to the memory location pointed to by address `a0`, and returns the original value of the memory location to `t1`. More importantly, the `aq` marker here ensures that before executing this atomic operation, all memory operations have completed and are visible to external cores, that is, before Core B executes the amoswap.w.aq instruction, it can definitely observe Core A's previous writes to this shared memory.

# Other Synchronization Techniques
![Image](/images/csdn/2024/csdn-138145202/image-011-a80ee015e4.png)
In operating systems and multithreaded programming, a completion variable is a synchronization primitive, mainly used to achieve synchronization between threads or processes, especially in scenarios where one task notifies another task after completing specific work. Its core role is to simplify the collaboration process in concurrent environments.

Specifically, the main functions of completion variables include:

1. **Task marking**: After a task completes an operation, it can set (or increment the count of) a completion variable, indicating that a key phase has ended.

2. **Blocking and waking up**: Other tasks can wait on this completion variable; when they detect that the variable is set or the wait count reaches the expected value, they are automatically woken up and resume execution. In this way, a task can safely wait for the previous task to complete its work before starting to execute the next phase.

3. **Replacing semaphores**: In some cases, completion variables can serve as lightweight replacements for semaphores, especially when only one-time notification is needed rather than multiple signal controls. Compared with traditional semaphores, completion variables are usually easier to understand and use, because they are directly associated with whether a specific operation is completed.

For example, in the Linux kernel, completion variables (`completion`) are a built-in data structure and API that allow synchronization between kernel threads or other concurrent entities. A typical use case is that when a kernel thread initiates an I/O operation, it can suspend itself and wait on a completion variable until the I/O completes; the device driver or other related parts will trigger this completion variable to wake up the waiting thread.
