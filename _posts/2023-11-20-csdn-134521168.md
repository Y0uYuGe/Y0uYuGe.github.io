# overflow
Assumption: char buf[40] and signed int num are defined
## scanf 
 -  scanf("%s", buf)
    %s has no bounds checking and can overflow
 - scanf("%39s", buf)
   %39 only takes 39 bytes from the input and places a NULL byte at the end of the input; cannot overflow
 - scanf("%40s", buf)
   Takes 40 bytes from the input, but also places a NULL byte at the end position of the input; there is a single-byte NULL overflow
 - scanf("%d", &num)
   When used in combination with alloca(num), if num is set to a negative value, the memory allocated from the stack will overlap with the original stack frame
 Most of the time, the program only checks the upper bound and forgets that num may be negative (or forgets to declare num as unsigned); in this case, entering num as a negative number may have unexpected
effects
  > alloca() allocates space on the stack
## get
 - gets(buf)
   No bounds checking; can overflow
 - fgets(buf,40,stdin)
  Takes 39 bytes from the input and places a NULL byte at the end of the input; useless
## read
 - read(stdin, buf, 40)  fread(buf, 1, 40, stdin)
   Takes 40 bytes from the input and does not place a NULL byte at the end; there may be an information leak
 For example
 `0x7fffffffdd00: 0x4141414141414141      0x4141414141414141
0x7fffffffdd10: 0x4141414141414141      0x4141414141414141
0x7fffffffdd20: 0x4141414141414141      0x00007fffffffe1cd`
At this point, if printf or puts is used to output buf, it will keep outputting until a NULL byte
At this point you can get 'A'*40 + '\xcd\xe1\xff\xff\xff\x7f', thus the information leak succeeds
## strcpy
Assumption: char buf2[60] is defined
 - strcpy(buf,buf2)
   The strcpy() function copies every byte of the source string buf2 into the destination string buf until reaching a NULL byte; the NULL byte at the end of buf2 is also copied over. buf2 may be longer than buf, so it may overflow
 - stncpy(buf,buf2,40) memcpy(buf,buf2,40)
  Copies 40 bytes from buf2 to buf, but does not place a NULL byte at the end; since there is no NULL byte, there may be an information leak, e.g., when printf or puts outputs this content — same as the read information leak above
## strcat
 - strcat(buf,buf2)
  Appends the string pointed to by buf2 to the end of the string pointed to by buf. If buf is not large enough, it may cause an overflow
  It places a NULL byte at the end, which may cause a one-byte overflow
  In some cases, this NULL byte can be used to exactly overwrite the lowest byte of a stored stack address
 - strncat(buf, buf2, n)
   strncat() adds a third parameter on top of strcat(), where the third parameter limits the maximum number of characters to append; everything else is the same as strcat(): the concatenated string becomes the new first string and a NULL byte is also placed at the end; the second string's value is unchanged; the return value is the address of the first argument
   There may also be a single-byte NULL overflow
# Find string in gdb
> Exploiting environ
After finding the environ address via libc, leaking the value at the environ address yields the environment variable address; environment variables are stored on the stack, and through offsets you can get the address of any variable on the stack.
SSP (Stack Smashing Protector) attack
 When a stack smash is detected, the __stack_chk_fail function prints the value of libc_argv[0] in the error message, and libc_argv[0] points to the program name.
If we can overflow the stack with sufficient length to overwrite the position of __libc_argv[0], we can make the program print data from any address, causing arbitrary address data leaks. This is the SSP attack.

In an SSP attack, we need to find the distance between argv[0] and the address where output starts

# Binary Service
> ncat converts a binary file into an IP address and port


> The loading order is LD_PRELOAD > LD_LIBRARY_PATH > /etc/ld.so.cache > /lib>/usr/lib 
> LD_PRELOAD (not LD_PRELOAD_PATH) is a list of specific libraries (files) to be loaded before any other libraries, regardless of whether the program needs them. LD_LIBRARY_PATH is a list of directories to search when loading libraries that will be loaded anyway.

 - ncat -vc ./binary_filename -kl 127.0.0.1 port_number
 
When you need to modify the dynamic link library
 -  ncat -vc  'LD_PRELOAD=/path/to/libc.so ./binary' ./binary_filename -kl 127.0.0.1 port_number
 -  ncat -vc 'LD_LIBRARY_PATH=/path/of/libc.so ./binary' ./binary_filename -kl 127.0.0.1 port_number

Then you can run the program via nc 127.0.0.1 port_number

# Fork problem in gdb

 - You can use set follow-fork-mode mode to set the fork following mode.
 - After entering gdb, we can use show follow-fork-mode to view the current follow mode.
show follow-fork-mode
 - set follow-fork-mode parent
      gdb only follows the parent process, not the child process; this is the default mode.
 - set follow-fork-mode child
      After the child process is created, gdb only follows the child process and abandons following the parent process.

 If you want to debug both the parent and child processes simultaneously, the above methods are insufficient. Linux provides the set detach-on-fork mode command for us to use
 - show detach-on-fork
      show detach-on-fork displays the current detach-on-fork mode

 -  set detach-on-fork on
      Only debug one of the parent or child processes (determined by follow-fork-mode); this is the default mode. The other process runs independently

 -  set detach-on-fork off
       Both parent and child processes are under gdb's control; one process is debugged normally (determined by follow-fork-mode), and the other process is set to a paused state. The other process blocks at the fork position


After using the 'set detach-on-fork off' command, use 'i inferiors' (i is short for the info command) to view process status; you can see that both parent and child processes are in a state of being debugged by gdb, and the one marked with '*' is the process currently being debugged. We can use inferior x (where x is the num of the process shown by i inferiors) to switch to the corresponding process to debug
# Secret of a mysterious section - .tls

 - malloc is available and can allocate any size
 - Able to read the contents of any address

Generally, when malloc allocates a size greater than 0x21000, mmap is used for allocation, and the allocated memory region happens to be right before the .tls segment

The .tls segment stores some useful information, such as the address of main_arena, the canary address, and a stack address that always has a fixed offset to a location pointing onto the stack
# Predictable RNG(Random Number Generator)
When a program uses values generated by an RNG as addresses of certain important information, we can use ctypes to call functions in dynamic link libraries or shared libraries
ctypes is a Python library that provides data types compatible with C and can directly call exported functions in dynamic link libraries.

For example, the following code

```c
srand(time(NULL));
while(addr <= 0x10000){
    addr = rand() & 0xfffff000;
}
secret = mmap(addr,0x1000,PROT_READ|PROT_WRITE,MAP_PRIVATE|MAP_ANONYMOUS ,-1,0);
if(secret == -1){
    puts("mmap error");
    exit(0);
}
```
We can obtain the same addr through the following means

```python
import ctypes
LIBC = ctypes.cdll.LoadLibrary('libc.so.6')
LIBC.srand(LIBC.time(0))
addr = LIBC.rand() & 0xfffff000
```
 ctypes.cdll.LoadLibrary(dynamic_link_library) loads a dynamic library, after which you can call the functions in it.

# Use printf to trigger malloc and free
printf sometimes triggers malloc, and of course triggering malloc will eventually also trigger free

```c
#define EXTSIZ 32
enum { WORK_BUFFER_SIZE = 1000 };

if (width >= WORK_BUFFER_SIZE - EXTSIZ)
{
    /* We have to use a special buffer.  */
    size_t needed = ((size_t) width + EXTSIZ) * sizeof (CHAR_T);
    if (__libc_use_alloca (needed))
        workend = (CHAR_T *) alloca (needed) + width + EXTSIZ;
    else
    {
        workstart = (CHAR_T *) malloc (needed);
        if (workstart == NULL)
        {
            done = -1;
            goto all_done;
        }
        workend = workstart + width + EXTSIZ;
    }
}
```
Conditions for triggering malloc

 - width >= WORK_BUFFER_SIZE - EXTSIZ
 - __libc_use_alloca (needed)==0

Let's look at the functions related to __libc_use_alloca()

```c

/* Minimum size for a thread.  We are free to choose a reasonable value.  */
#define PTHREAD_STACK_MIN        16384

#define __MAX_ALLOCA_CUTOFF        65536

int __libc_use_alloca (size_t size)
{
    return (__builtin_expect (size <= PTHREAD_STACK_MIN / 4, 1)
        || __builtin_expect (__libc_alloca_cutoff (size), 1));
}

int __libc_alloca_cutoff (size_t size)
{
	return size <= (MIN (__MAX_ALLOCA_CUTOFF,
					THREAD_GETMEM (THREAD_SELF, stackblock_size) / 4
					/* The main thread, before the thread library is
						initialized, has zero in the stackblock_size
						element.  Since it is the main thread we can
						assume the maximum available stack space.  */
					?: __MAX_ALLOCA_CUTOFF * 4));
}
```
To make the return value 0, the following must be satisfied

 - __builtin_expect (size <= PTHREAD_STACK_MIN / 4, 1)==0
 - __builtin_expect (__libc_alloca_cutoff (size), 1)==0
 
> __builtin_expect is usually used in if-else branches; first make it clear that if (exp) is equivalent to if (__builtin_expert(exp, x)), regardless of the value of x.

> In the ternary operator "?:", the omitted part in the middle is exactly the same as the number or expression before the "?".

That is, satisfy

 - size > PTHREAD_STACK_MIN / 4
 - size > MIN(__MAX_ALLOCA_CUTOFF, THREAD_GETMEM(THREAD_SELF, stackblock_size) / 4 ?: __MAX_ALLOCA_CUTOFF * 4)

At this point THREAD_GETMEM usually returns 0, so the final result of the MIN function is __MAX_ALLOCA_CUTOFF, i.e., 65536; therefore size > 65536 also satisfies PTHREAD_STACK_MIN / 4

So a size of 65537 can trigger malloc and free: first hijack by writing onegadget to the position of __malloc_hook or __free_hook and determine an appropriate width, then exploit the printf format string vulnerability (printf(buf)), and finally get a shell
# Use execveat to open a shell
execveat can play a role similar to execve

```c
int execveat(int dirfd, const char *pathname,
             char *const argv[], char *const envp[],
             int flags);
```
When the pathname parameter points to /bin/sh, and the argv, envp, and flags parameters are 0, then regardless of the value of dirfd, you can get a shell

Explanation of execveat parameters
```c
If pathname is absolute, then dirfd is ignored.
```
