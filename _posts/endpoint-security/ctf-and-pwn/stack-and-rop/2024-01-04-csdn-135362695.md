SROP (Sigreturn Oriented Programming) was proposed in 2014 by Erik Bosman of Vrije Universiteit Amsterdam. His related research, Framing Signals — A Return to Portable Shellcode, was published at the top security conference Oakland 2014 and was selected as one of that year's Best Student Papers. # Linux Signal Handling
1. When an interrupt or exception is sent, the kernel delivers a signal to the relevant process
2. The system then switches to kernel mode, and the kernel executes the setup_fram() function to set up the user stack. The main job of setup_frame is to push onto the user stack a data structure holding the values of all registers and other important information (this varies by architecture), and also to push a return address for the signal function — the address of sigruturn().
3. Next, hand_signal executes; this function jumps to user mode to run the signal handler function
4. After the signal handler runs in user mode, because the return address was set to the address of the sigreturn() system call, the system traps back into the kernel to execute the sigreturn() system call. The main job of this system call is to restore the register values and related content from what was previously pushed onto the stack. When the system call finishes, program execution resumes.

# Approach
To build a ROP chain from the overflow: there is no dynamically linked library, and the program itself has pitifully few gadgets. With insufficient gadgets, if you want ret2syscall, the syscall argument rax must be 59, rdi must be the address of /bin/sh, and rsi and rdx must be zero,
but the relevant pop gadgets do not exist, so a syscall via ROP is not possible. At this point SROP can be used, because the sigreturn system call executes a series of pop instructions, giving us a chance to set up the arguments for execve
1. First, rax is easy to set — just set it to the syscall number for execve
2. Second, rdi must be the address of /bin/sh; /bin/sh cannot be found, so we have to input it onto the stack and then obtain its address on the stack
3. Then rsi and rdx — these are also easy, both just set to 0

So how do we input /bin/sh and get its address?
First we need to obtain the starting address of the input area on the stack; then on the next input we can input /bin/sh and invoke the execve system call

1. First get the write function to output the stack base address
The system call corresponding to write needs rax to be 1, rdi to be 1, rsi to be the stack base address, and rdx greater than 8. The only way to modify rax is that after read executes, it stores the input length into rax. So input one byte, and if the return address starts from 0x4000B3, then the write function will end up outputting the stack base address. We must lay out the return address in advance, so that when read executes the second time we can input one byte, and after modifying one byte of the return address it becomes exactly 0x4000b3,
2. The write function then outputs the value of rsp. Since we can only output at this point, the return address must have been laid out during the first input. Now that we have the rsp value, we can set it as the input function, input the corresponding sigframe, and at the same time input the return address as the address of the system call. Because to reach the sigreturn function the length read inputs must equal 15, we have to wait for two inputs. So in one input we send the sigfram and /bin/sh, with the return address set to the address that inputs again; on the next input we only input the system call address and seven other bytes that do not affect the sigfram. Then sigreturn is called first, followed by execve

constants.SYS_read is the constant syscall number of read
After the write function, the program accepts one more input. This input first changes the return address to 0x4000b0 so that yet another input is possible, and at the same time inputs the reserved return address for the next input and the sigfram

# System Call Recap

> A system call is very similar to an ordinary library function call, except that a system call is provided by the operating system kernel and runs in kernel mode, while an ordinary library function call is provided by a function library or the user and runs in user mode.
```c
int execve(const char *filename, char *const argv[], char *const envp[]);
```

> filename specifies the name of the program file to run; argv and envp specify the program's run arguments and environment variables respectively.

> !! The system function is NOT a system call
