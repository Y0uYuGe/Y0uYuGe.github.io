# busybox
A simple UNIX filesystem with many files inside; you can think of busybox as a folder
We use it as the filesystem running inside the first container.

# `docker run -d busybox top`

The command `docker run -d busybox top` is used to start a new container in Docker and perform a specific operation. Below is a detailed explanation of each part of the command:

- `docker run`: This is one of Docker's main commands, used to start a new container from a specified image.

- `-d`: This is a flag that tells Docker to run the container in detached mode. This means the container will run in the background instead of connecting directly to the user's terminal. When a container runs this way, Docker immediately returns the container ID, and the user can continue executing other commands on the command line without affecting the running container.

- `busybox`: This is the name of the image. BusyBox is a lightweight collection of Unix-like tools, packing a large number of commonly used command-line tools into a small image.

- `top`: This is the command to be executed inside the container. On Linux systems, the `top` command provides a real-time system status report, showing the resource usage of each process in the system, such as CPU and memory usage.

In summary, when you execute `docker run -d busybox top`, Docker creates a new container from the BusyBox image and starts the `top` command inside that container, making it a long-running process so the container keeps running in the background. This approach is often used for testing or monitoring purposes, letting the `top` command inside the container continuously display the system state inside the container.

# `containerId=(docker ps --filter "ancestor=busybox:latest"|grep -v IMAGE|awk '{print $1}')` 
The purpose of the Shell command `containerId=(docker ps --filter "ancestor=busybox:latest"|grep -v IMAGE|awk '{print $1}')` is to obtain the ID of the latest container started from the `busybox:latest` image and assign it to the variable `containerId`. Let's break it down one by one:

- `docker ps`: This is a Docker command used to list all running containers and their related information.
  
- `--filter "ancestor=busybox:latest"`: This is a filter parameter that filters out containers derived from the `busybox:latest` image.

- `|` (pipe symbol): used to pass the output of the preceding command as the input of the following command.

- `grep -v IMAGE`: The `grep` command is used to find matches in a text stream; the `-v` parameter means invert selection, i.e., exclude lines containing the specified pattern. Here it filters out the line describing the image in the output, because we only need the container ID.

- `awk '{print $1}'`: `awk` is a powerful text analysis tool; here it is used to extract the first column of each line, i.e., the container ID column.

`awk '{print $1}'` is a command-line expression based on the `awk` tool, used to process and manipulate text data streams. In this command:

- It reads a file or input stream (in this case, the output of `docker ps` passed through the pipe) and processes each line of data according to the specified pattern.

- The `{}` braces contain the action the awk command is to perform.

- `print` is a built-in awk command used to output the specified field or variable.

- `$1` is a special variable in awk representing the first field of each line of records (fields are separated by whitespace characters such as spaces or tabs by default). In the output format of many UNIX/Linux commands, the first column often contains key information; for example, in the output of `docker ps`, the first column is usually the container ID.



Combining the above commands, it actually finds the most recently started container based on the `busybox:latest` image from the list of running containers and extracts its ID. Then this ID value is assigned to the variable `containerId` in the shell script.

The final `echo "containerId" $containerId` is used to output the value of the variable `containerId`, so you can see the actually obtained container ID.


# `docker export -o busybox.tar $containerId` or `sudo docker export 09bbf421d93f > ./busybox.tar `
`docker export -o busybox.tar $containerId` is a Docker command used to export the filesystem contents of a specified container into a tar archive file.

- `docker export`: This is a Docker command used to export a snapshot of a container's filesystem. This command only exports the filesystem hierarchy inside the container, not including the container's metadata, configuration information, or runtime state.

- `-o busybox.tar`: The `-o` option is followed by the name of the output file; here it specifies saving the exported content to a tar file named `busybox.tar`.

- `$containerId`: This is a variable representing the container ID obtained earlier by the command. In this command, it specifies the specific instance of the container to export.

So the meaning of the entire command is: export the filesystem contents of the BusyBox container previously created and run via the `docker run` command in the form of a tar file, and name the exported file `busybox.tar`. This tar file contains all the files and directory structure inside the container, and can be used for backup or to re-import this filesystem in another environment.

# `tar -xvf busybox.tar -C busybox/`
The command `tar -xvf busybox.tar -C busybox/` is used to decompress and extract the contents of the `busybox.tar` file to the specified directory. The meaning of each part of the command is as follows:

- **tar**: This is a tool in Unix/Linux systems for handling archive files (usually *.tar files); it can be used to pack, compress, decompress, and list files within archives.

- **-x**: This option means perform an extract operation. It tells the tar tool to extract files from the specified tar archive.

- **-v**: This is verbose mode; detailed information is displayed during the extraction process, including the names of files being extracted, making it easy for the user to understand the extraction progress.

- **-f**: This option is followed by the name of the tar file to operate on, i.e., `busybox.tar`. This parameter is required to specify the tar archive you want to extract.

- **-C**: This option allows you to specify the directory where the extracted files are stored; it is followed by the target directory path `busybox/`. This means all files and directories extracted from `busybox.tar` will be placed in the directory named `busybox`.

In summary, the overall effect of this command is to extract all files from `busybox.tar` and decompress them into the `busybox/` subdirectory under the current directory. If the `busybox/` directory does not yet exist, `tar` will create this directory before extracting.

#  The Shareability of mount namespace

Whether mounting a filesystem in a Linux `mount namespace` will affect the host's filesystem depends on the specific situation.

- **By default (before systemd was introduced or when the MS_SHARED propagation type is set)**:
  If you mount a filesystem in a new `mount namespace`, and the mount point is shared (i.e., the mount propagation type is `MS_SHARED`), then mount operations in the new `mount namespace` will propagate back to the host and other `mount namespace`s that share this mount point. This means the host's filesystem view will change accordingly.

- **Set as private mount (MS_PRIVATE)**:
  If when creating a `mount namespace`, the mount point is set to private (via the `syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, "")` command), then any filesystem mounted in this new `mount namespace` will not affect the host or other `mount namespace`s that are not set to private. This means mount and unmount operations on the filesystem in the new `mount namespace` only affect that namespace, and the host's filesystem view will remain unchanged.

In container technologies such as Docker, a new `mount namespace` is usually created and its internal mount points are set to private to ensure that filesystem operations inside the container do not affect the host or other containers. This achieves container-level filesystem isolation.


# Self Mount

Imagine you have a big tree: the trunk represents the host's root filesystem, and the branches represent the various directories mounted on it. When you want to create an independent branch (such as `/newroot`) as the new root directory of a container, if no measures are taken, this branch will still be affected by other changes on the entire tree (the host).

**Example**:
Suppose there is a directory structure on the host as follows:
```
/
├── bin
├── etc
├── home
├── newroot
│   ├── bin
│   ├── etc
│   └── var
└── var
```

You want `/newroot` to become the container's independent root directory, but if you don't perform a self bind-mount on `/newroot`, then mount operations made under `/newroot` will affect other parts of the host. For example, if a temporary filesystem is mounted under `/newroot/var`, this mount will also propagate to the host's `/var` directory.

However, by performing a self bind-mount (`mount --bind /newroot /newroot` or `syscall.Mount("/newroot", "/newroot", "", syscall.MS_BIND|syscall.MS_REC, "")`), you actually create a "mirror" branch that is independent of the rest of the host in terms of mount behavior. Thereafter, any mount operations made under `/newroot`, such as mounting a temporary filesystem to `/newroot/var`, will only affect the `/newroot` "mirror" branch, and will not affect the host's original `/var` directory.

In this way, when executing `pivot_root` to switch `/newroot` to the container's new root directory, the new root directory (`/newroot`) is a clean and independent filesystem view that does not affect the rest of the host, thereby achieving the isolation required by the container.

# `syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, "")` 
`syscall.Mount("", "/", "", syscall.MS_PRIVATE|syscall.MS_REC, "")` is a code snippet in the Go programming language that calls the Linux kernel `mount()` system call, with the purpose of changing the mount flags of the current process's root directory mount point. Specifically:

- The first parameter `""` represents the current mount point; here an empty string means the current process's root directory `/`.
- The second parameter is also `"/"`, referring to the target mount point, which is also the root directory here.
- The third parameter `""` represents the filesystem type; since this is not mounting a new filesystem but modifying the attributes of an existing mount point, it is also left empty here.
- The fourth parameter is the mount flags, `syscall.MS_PRIVATE|syscall.MS_REC`:
  - `syscall.MS_PRIVATE`: sets the current mount point and all its sub-mount points as private mounts. This means any mount, unmount, or remount operations performed on this mount point will not propagate to other mount namespaces, thereby achieving isolation of mount events, which is crucial for creating independent container environments or other scenarios requiring filesystem isolation.
  - `syscall.MS_REC`: This is a recursive flag, meaning this private mount attribute is applied not only to the root directory `/`, but also to all sub-mount points under the root directory, ensuring the entire mount tree becomes private mounts.
- The fifth parameter `""` represents additional mount option parameters; here it is an empty string, indicating no additional mount options need to be set.

In summary, the effect of this command is to set the entire filesystem mount tree of the current process (including the root directory and all subdirectories) as private mounts, ensuring that mount operations performed within the mount namespace of the current process and its descendant processes do not affect the host or the namespaces of other processes.

#  bind mount
This is because the "bind mount" operation creates a new filesystem mount point on the host that has the same content as the original `/container_root` directory but resides in a different filesystem.

Specifically:

1. In the container, `/container_root` is the container's root filesystem.
2. When we execute `mount --bind /container_root /container_root`, a new filesystem mount point is created on the host that points to the `/container_root` directory.
3. This new filesystem mount point is a different filesystem from the host's root filesystem `/host_root`.

That is, from the host's perspective, `/container_root` is now an independent filesystem, not in the same filesystem as the host's root filesystem `/host_root`.

This process can be explained with an example:

Suppose on the host, `/container_root` was originally a subdirectory of the host's root filesystem `/host_root`. But after executing `mount --bind`, `/container_root` becomes an independent filesystem mount point, no longer in the same filesystem as `/host_root`.

The purpose of doing this is to satisfy the requirement of the `syscall.PivotRoot` function, namely that the new root filesystem and the old root filesystem cannot be under the same filesystem. Through the "bind mount" operation, we can achieve this requirement.

# Private Mount Points vs. Private mount namespace

The attributes of a Mount Namespace mainly refer to the propagation attributes of mount points in the Namespace (Mount Propagation). The following example explains this:

**Example scenario**:
Suppose there are two directories `/mnt/shared` and `/mnt/private` on the host, and the mount propagation attribute of the host's root directory `/` is the default value.

1. **Create a new Mount Namespace and set mount point propagation attributes**:
   We can use the `unshare` command to create a new Mount Namespace, and set `/mnt/shared` as a shared mount attribute and `/mnt/private` as a private mount attribute.

   ```bash
   sudo unshare -m bash            # 创建一个新的Mount Namespace
   sudo mount --make-shared /mnt/shared    # 设置/mnt/shared为共享挂载
   sudo mount --make-private /mnt/private  # 设置/mnt/private为私有挂载
   ```

2. **Operations inside the Namespace**:
   - **Shared mount (/mnt/shared)**: In the new Namespace, if a new filesystem is mounted to `/mnt/shared/subdir`, since `/mnt/shared` is a shared mount, this newly added mount point can also be seen on the host or in other Mount Namespaces.
   - **Private mount (/mnt/private)**: If any mount or unmount operations are performed on `/mnt/private` in the new Namespace, these operations will not affect the host or other Mount Namespaces. In other words, any changes made to `/mnt/private` in the new Namespace are transparent to external Namespaces.

3. **Effect**:
   - For `/mnt/shared`, mount operations inside and outside the Namespace affect each other, while for `/mnt/private`, they are completely isolated.

Through this example, we can see how the attributes of a Mount Namespace affect the visibility of mount points between different Namespaces and the effects of operations. In container technology, these attributes of Mount Namespaces provide containers with independent filesystem views, which helps achieve resource isolation and security.
