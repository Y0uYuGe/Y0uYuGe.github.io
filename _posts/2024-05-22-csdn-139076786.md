# The difference between Docker and Kata Containers

### Docker containers share the host kernel

Docker containers are implemented based on the Linux kernel's namespaces and control groups (cgroups) technologies. Simply put, Docker gives containers what appears to be an independent filesystem, network, process space, user ID space, and so on, but in reality, all containers as well as the Docker daemon on the host share the same Linux kernel. This means that although containers are logically isolated, at the physical level they share the host's CPU, memory, and operating system kernel. If the kernel has a security vulnerability or a program inside a container tries to access unauthorized system resources, there is theoretically a security risk.

### Each container instance runs in a lightweight virtual machine (MicroVM)

Technologies such as Kata Containers take a different approach: they create a very lightweight virtual machine (MicroVM) for each container instance. In this model, each container no longer directly shares the host's operating system kernel, but instead has its own miniature virtualization environment, including an independent kernel. This is usually implemented through technologies like QEMU-KVM, providing each container with an isolated hardware abstraction layer — including CPU, memory, I/O devices, etc. — plus an independent kernel.

This means that even if a program inside a container tries to break through its security boundary, it cannot directly affect the host or other containers, because every container runs inside its own micro virtual machine with stricter hardware-level isolation. This design significantly improves security, especially when running untrusted code or in scenarios requiring strong isolation. The trade-off is that it may slightly increase resource consumption and startup time, since each container needs to boot its own kernel and virtualization environment.

### Summary

- Docker containers provide logical isolation through namespaces and control groups, sharing the host's kernel. They use resources efficiently, but their degree of isolation is relatively low.
- Kata Containers and similar technologies use MicroVM technology to give each container an independent kernel and hardware abstraction layer. Isolation is high and security is enhanced, but this may sacrifice a bit of startup speed and resource efficiency.

#  An intuitive example of the Kata Containers architecture
![Image](/images/csdn/2024/csdn-139076786/image-001-62e02373fb.png)


This diagram shows how Kubernetes (kubelet) interacts with Containerd and Kata Containers through the CRI interface.


- **Kubernetes (kubelet)** is our smart butler.
- **Containerd** is the property manager.
- **Kata Containers** provides a more secure way to run containers — like adding a small house (a lightweight virtual machine) outside each room, so that different rooms are better isolated from each other.

Now, suppose the landlord (the user) wants to run his software in a more secure environment. So he tells the butler (Kubernetes): "I need a special room with an independent little house inside, to make sure my software is completely isolated from everything else."

1. **The butler (Kubernetes) receives the order**: Knowing the landlord's needs, the butler decides to use the service provided by Kata Containers. Through the CRI interface, he tells Containerd that this time a special room is needed — that is, a container with a lightweight virtual machine.

2. **Containerd calls Kata Containers**: To satisfy this requirement, Containerd invokes something called "containerd-shim-kata-v2", an agent program dedicated to handling Kata Containers requests. This agent program further communicates with the hypervisor (virtual machine manager), telling it that a lightweight virtual machine needs to be created to hold the new container.

3. **The hypervisor creates a lightweight virtual machine**: After receiving the request, the hypervisor creates a lightweight virtual machine on the host system. This virtual machine has its own guest operating system (guest kernel). Inside this virtual machine, the hypervisor also creates a separate space for the new container.

4. **The container runs inside the lightweight virtual machine**: Finally, the hypervisor starts the new container in the space inside the lightweight virtual machine. This container gets better isolation protection from other containers and other processes.

Once the whole process is complete, the butler (Kubernetes) can tell the landlord (the user) that his software is already running in a very secure environment. Also, thanks to Kata Containers, even if something goes wrong in other rooms, this special room will not be affected.


# The actual Kata Containers architecture
![Image](/images/csdn/2024/csdn-139076786/image-002-402a21e328.png)

### A walkthrough of the container technology stack

1. **Top layer: application management platform (e.g. Kubernetes)**
   - This layer is where users or administrators interact with the system to deploy, manage, and orchestrate containerized applications. It sends commands to the layer below, such as creating, stopping, or restarting containers.

2. **Container runtime manager (Containerd)**
   - Containerd is operating-system-level software responsible for container lifecycle management. It receives commands from the layer above (such as commands passed through Kubernetes' CRI interface) and then performs operations like creating, starting, and stopping containers.

3. **Shim layer (containerd-shim-kata-v2)**
   - The shim layer is a lightweight process that acts as a bridge between Containerd and the lower-level container runtime technology. `containerd-shim-kata-v2` is designed specifically for Kata Containers: its job is to convert Containerd's standardized API into a format that Kata Containers can understand, and to manage the lifecycle of Kata Containers instances. The shim layer ensures that Containerd does not need to know the implementation details of Kata Containers directly.

4. **Kata Containers**
   - Kata Containers is a container runtime that provides stronger isolation for each container through lightweight virtualization. Compared with traditional containers, Kata uses a miniature virtual machine (VM) to run each container, achieving security isolation close to the virtual-machine level while trying to preserve container startup speed and resource efficiency.

5. **Hypervisor**
   - In the Kata Containers architecture, the Hypervisor is one of the core components. It is software running on the physical host that can create and run virtual machines. The Hypervisor is responsible for allocating physical resources (CPU, memory, I/O devices) to each micro virtual machine and ensuring isolation between them. For Kata Containers, QEMU is a commonly used Hypervisor; it creates and manages the micro VMs that run the containers.

### Summary
This diagram may show the entire flow from the application management layer down to the underlying virtualization layer in detail, emphasizing the flow of information and division of responsibilities between the layers. As the core of the container runtime, Containerd indirectly controls Kata Containers and the Hypervisor it depends on through the shim layer; together they provide a highly secure and isolated runtime environment for containers.


# agent and shim
Imagine you are a busy parent (the shim process) who needs to take care of children (containers) living in different rooms, and each room has a caring nanny (agent). You want to make sure the children's needs are met while also supervising their activities, but you cannot enter every room directly and disturb them.

### The role of the parent (shim process)

As a parent, you are responsible for coordinating everything in the house, including the children's requests and daily schedules. However, talking directly with every child would be time-consuming and inefficient. So you decide to communicate with each nanny through the intercom system in the rooms (the agent protocol).

### The duties of the nanny (agent)

The nanny lives in the child's room and knows the child's needs inside out. They listen for the parent's instructions over the room's intercom, such as "prepare dinner for little Ming" or "let little Hong take a break". After receiving a message, the nanny immediately takes care of the child as requested, and also reports the children's status back to the parent through the intercom, such as "little Ming has finished dinner and is reading a book".

### The role of the "agent protocol"

The "agent protocol" here is like that intercom system: it defines the language and rules for communication between the parent and the nanny. For example, it specifies how to express instructions like "mealtime" and "rest", and how to report feedback like "done" or "need help". In this way, the parent can efficiently manage the daily life of the whole family without entering the rooms directly, while ensuring that each child's (container's) needs receive personalized attention and are met.

### Mapping to real technology

Back to the Kata Containers scenario: the shim process is like that attentive parent, communicating through the "agent protocol" with the agent running inside the virtual machine (guest). This protocol ensures that the management process on the host can safely send control commands and obtain status information without directly interfering with the internal workings of the virtual machine, thereby maintaining container isolation and security. In this way, Kata Containers can provide virtual-machine-level security isolation while ensuring high performance.

Imagine you are running a virtual game world made up of countless mini-games (tasks), each with its own rules and lifecycle. `Shimv2` is like the administrator of this virtual world, responsible for creating, managing, and ending these mini-games (tasks).

### Shim Interface

- **shimapi.TaskService**: This part of the interface is like a detailed "game guide", covering how to start a new game (`Create`), how to set the game running (`Start`), how to pause or resume a game (`Pause` and `Resume`), and even how to adjust the rules mid-game (`Update`), and so on. - **Cleanup**: When a game (task) ends, someone needs to clean up the venue to prepare for the next game. `Cleanup` is this cleaner: it ensures that even if the game administrator (the shimv2 process) leaves early for some reason, leftover resources can still be cleaned up by other means, keeping the game world neat and tidy.

- **StartShim**: Imagine you open a new game area and need to assign a new administrator to be in charge of it. `StartShim` is this process: it is responsible for starting a new administrator (shimv2 process) and telling him the entrance to the game world (containerdBinary and containerdAddress) and the number of the area he is responsible for (id), so that he can start work smoothly.

### Containers and tasks

In the game world, a "container" can be compared to a game kit: it contains all the props and rule instructions needed before the game starts, but only when you actually start playing the game (running the container) does it become a living "task" — a running game instance with its own life course and player interactions.

### A concrete example

Suppose you decide to add a "treasure hunt task" (container) to your virtual world. First, you need to prepare the task package (create the container configuration), containing the map, treasure locations, and other information (static resources). Then, through the `StartShim` command, you assign an administrator (start the shimv2 process) and tell him the rules of the task and how to coordinate with other systems (containerd).

Once the task (treasure hunt game) officially starts (the task runs), it becomes an active process (Task), and the administrator manages all aspects of this task through the `TaskService` interface — for example, adjusting the difficulty (resource limit adjustment), checking player progress (status query), and ending the task (deleting the task).

If one day this administrator suddenly disappears (the shimv2 process exits unexpectedly), you can also clean up leftover issues through `Cleanup`, ensuring that the game world continues to run smoothly and is ready for the next task.

6. Once the competition starts, the chief director can view the competition status in real time through the console (containerd's API), adjust resource allocation, and even terminate certain competition events if necessary.

## create_container/do_create_container

### Preparations before creating the container

1. **rescan_pci_bus**: Imagine you are tidying up your storage room at home and find some new devices (such as new USB devices). This step rescans the hardware in the virtualized environment, ensuring that the system can recognize and prepare these new devices for the container to use.

2. **add_devices** and **add_storages**: Just like buying furniture for a new house, you need to select and arrange furniture (device configuration) according to the decoration blueprint (the OCI Spec). These two steps ensure that the container can access the required physical or virtual devices and mount the necessary storage volumes to meet the application's runtime requirements.

3. **update_container_namespaces** and **update_device_cgroup**: A container is like an independent apartment with its own exclusive address (namespace) and property management rules (cgroup). These two operations adjust the container's isolated environment, ensuring that it has an independent network, filesystem view, and resource limits.

4. **append_guest_hooks**: Similar to setting up automation scripts for a smart home system before moving in, this step adds some custom scripts or hooks before and after the container starts, used to perform specific initialization or cleanup tasks.

5. **setup_bundle**: Create the container's "living space" (the bundle directory), including the configuration file (config.json) — just like preparing a move-in guide for a new house, it contains all the configuration information needed to start the container.

- **ctr.start(p）**: Although the name says "start", this stage is mostly about doing final preparation and initialization.

2. **Establishing the pipes**

   - Use `unistd::pipe()` to create two anonymous pipes. This is like building two bridges: one for the parent process (the current Kata Agent) to send information to the child process (`crfd` to `pwfd`), and the other for the child process to send messages back to the parent process (`prfd` to `cwfd`).
   - `PipeStream::from_fd` converts raw file descriptors into stream objects that are more convenient to operate on, making reads and writes easier.

### Starting the container process

3. **Starting the Kata Agent child process and passing the PID**

   - `child.spawn()?` starts the new Agent process. At this point, the new process executes the `do_init_child` function and begins the container initialization work.
   - Once the container's init process (the process with PID 1) starts successfully in the child Agent (it needs to execute `do_init_child`), it sends its PID to the parent process through one of the previously established pipes (`cwfd`).
   - The parent process waits for and receives this PID through `read_async`, thus learning the exact identifier of the container process.

### Namespaces and process management

4. **Joining namespaces**

   - `join_namespaces` is a key step inside the Kata Agent. It is responsible for setting up namespaces on the newly created container process, including the PID namespace, network namespace, and so on, ensuring that the container process runs in a completely isolated environment — just like carrying out activities in an independent room without outside interference. (One of the last important functions executed by ctr.start() is join_namespaces)
   - This process may involve the `clone` system call, which allows the new process to inherit certain attributes of the parent process while separating from the parent in certain aspects (such as namespaces), creating a brand-new execution environment.

### Execution of the container process

5. **Executing `do_init_child` in the new Agent process**

   - At this step, the child Agent (acting as the container's daemon process) begins executing the `do_init_child` function, completing the remaining initialization operations such as mounting the filesystem, configuring the network, and executing the user-specified application.
   - Through the previously passed environment variables and file descriptors — such as the `exec.fifo` file pointed to by `FIFO_FD` — the timing and manner of the container process's startup can be controlled, ensuring everything proceeds as planned.


##  do_init_child

```rust
fn do_init_child(cwfd: RawFd) -> Result<()> {
    match fork() {
        Ok(ForkResult::Parent { child, .. }) => {
            let _ = write_sync(cwfd, SYNC_DATA, format!("{}", pid_t::from(child)).as_str());
            // parent return
            return Ok(());
        }
        Ok(ForkResult::Child) => (),
        Err(e) => {
        }
    }

}
```

### The role of the `do_init_child` function

- **Fork and division of roles**: The `do_init_child` function executes in the child process started after the Kata Agent is launched with the `init` argument. It first performs the `fork()` system call, producing two processes. The parent process (the process where `do_init_child` runs here) is mainly responsible for writing the PID of the newly created child process (the real container process) to `cwfd`, and then exiting. The child process continues executing and becomes the first process inside the container.

- **PID synchronization**: The parent process writes the PID of the just-created child process into the pipe via `write_sync(cwfd, SYNC_DATA, format!("{}", pid_t::from(child)).as_str())`, so that the parent process (actually the main Kata Agent process) can learn the real PID of the container process by reading the other end of the pipe (`crfd`).

- **Reading `exec.fifo`**: When the startup arguments include `init`, it means the container's main process needs to be initialized. The `do_init_child` function finds the descriptor of the `exec.fifo` file according to the environment variable `FIFO_FD`, and then reads the `exec.fifo` file through a series of file operations (`fcntl::open`, `unistd::close`, `unistd::read`). - **`do_exec` and process replacement**: After reading `exec.fifo`, `do_exec(&args)` is called. ### Synchronization between container startup and RPC requests


- **Waiting for the `start_container` RPC**: Although `do_exec` has been called, because the earlier `read` operation is waiting for the `exec.fifo` signal, the container process is actually blocked here until a `start_container` RPC request arrives from the outside (such as one sent through the shim). This request usually triggers a write to the `exec.fifo` file, unblocking the read so that `do_exec` can continue and the container process begins execution.

## start_container/do_start_container (starting the container)
### The `exec` function

The main task of this function is to trigger the startup of the process inside the container by writing data to a FIFO (named pipe) file called `exec.fifo`. The specific steps are as follows:

1. **Constructing the FIFO file path**: First, it constructs the full path of the FIFO file by formatting a string. This FIFO file is usually located in the container's root directory and has a fixed name (as defined by `EXEC_FIFO_FILENAME`).

2. **Opening the FIFO file**: Use the `fcntl::open` function to open the FIFO file at the above path in write mode (`O_WRONLY`). The mode is also set to 0, meaning existing permissions are not changed.

3. **Writing data and notifying**: Write one byte of data (in this example, `[0]`) to the just-opened FIFO file. This step is actually a signaling mechanism, used to notify the process waiting at the other end of this FIFO (the read end) that it can continue executing. This is because during container initialization, there is usually a process blocked here waiting for this signal, so that it knows when to start executing the actual application inside the container.

4. **Recording the startup time and state change**: Record the time the container process started and update the container state to `RUNNING`.

5. **Closing the file descriptor**: Finally, close the file descriptor of the previously opened FIFO file.

```rust
start_container 最终会执行到这个函数：

// kata-containers/src/agent/rustjail/src/container.rs
fn exec(&mut self) -> Result<()> {
    let fifo = format!("{}/{}", &self.root, EXEC_FIFO_FILENAME);
    let fd = fcntl::open(fifo.as_str(), OFlag::O_WRONLY, Mode::from_bits_truncate(0))?;
    let data: &[u8] = &[0];
    unistd::write(fd, &data)?;
    info!(self.logger, "container started");
    self.init_process_start_time = SystemTime::now()
        .duration_since(SystemTime::UNIX_EPOCH)
        .unwrap()
        .as_secs();

    self.status.transition(ContainerState::RUNNING);
    unistd::close(fd)?;

    Ok(())
}
```

The core logic is simply writing some data into the exec.fifo file. At this point, the place in the do_init_child function we saw above that blocks on reading exec.fifo will continue executing, and then execute the do_exec method that follows

```rust
fn do_exec(args: &[String]) -> ! {
    let path = &args[0];
    let p = CString::new(path.to_string()).unwrap();
    let sa: Vec<CString> = args
        .iter()
        .map(|s| CString::new(s.to_string()).unwrap_or_default())
        .collect();
    let a: Vec<&CStr> = sa.iter().map(|s| s.as_c_str()).collect();

    let _ = unistd::execvp(p.as_c_str(), a.as_slice()).map_err(|e| match e {
        nix::Error::Sys(errno) => {
            std::process::exit(errno as i32);
        }
        _ => std::process::exit(-2),
    });

    unreachable!()
}
```
Finally, the specified process in the container is started through the execvp system call.
### The `do_exec` function

This function is responsible for actually executing the command or program inside the container. Its workflow is as follows:

1. **Preparing arguments**: Take the first element from the incoming argument slice as the program path and convert it to the `CString` type, because the `execvp` system call requires arguments in C string format. At the same time, convert all arguments into a `CString` array, ready to be passed to `execvp`.

2. **Executing the `execvp` call**:
   - Use `execvp` to attempt to replace the current process image with the specified program. It takes two arguments: one is the path of the program (in C string format), and the other is the argument list (an array of pointers to C strings).
   - If `execvp` succeeds, the current function will not return, because the process has already been replaced by the new program.
   - If it fails, the exit code is determined by the error type. If it is a system error, the error number is directly used as the exit code; for other types of errors, -2 is used as the exit code by default.

3. **`unreachable!()`**: This statement indicates that if execution flow reaches here, it is theoretically impossible, because `execvp` does not return on success and directly exits the process on failure. This is a logical assertion that helps static analysis tools understand the expected execution flow of the code.

Imagine you are a director preparing to shoot a movie. You can compare this process to the `create_container` and `start_container` processes.

### The create_container phase

1. **The director (kata-agent service) plans the scene**: As the director (equivalent to the `kata-agent service`), you decide to start shooting a new movie (create a container). To begin work, you first need to arrange for an assistant (`kata-agent init`) to prepare the shooting site.

2. **The assistant prepares the filming crew**: The assistant starts a film crew (the container's temporary process), which includes the assistant director, cameraman, lighting technician, and so on (various initialization work). After arranging everything, the assistant (parent process) leaves the contact information (pid) of the assistant director (child process) who actually does the filming work with the director (kata-agent service), and then can leave.

3. **The assistant director waits for instructions**: The assistant director (child process) is now at the shooting site with everything ready, but is still waiting for the director's specific shooting instructions. So he sits in the director's chair, staring at a specific signal light (blocked on reading `exec.fifo`).

### The start_container phase

4. **The director gives the shooting signal**: The director (kata-agent service) feels everything is ready, so he presses the button (writes data to `exec.fifo`), lighting up that signal light.

5. **Filming officially begins**: As soon as the assistant director (child process) sees the signal light come on, he immediately gets up and starts executing the shooting plan (starting the container's real process through `execvp`, such as starting to record the first scene). This marks the official start of the movie shoot — that is, the application inside the container begins running.

6. **Behind-the-scenes communication**: Throughout the filming process, the director (parent process) and the assistant director (child process) need to keep communicating (synchronizing data through pipe file handles) — for example, the director needs to tell the assistant to adjust camera angles or actor positioning, ensuring the filming goes smoothly.
