# System V IPC and POSIX
Let's understand System V IPC and POSIX message queues and the differences between them through a simple restaurant order-processing analogy.

Suppose a restaurant has a front kitchen and a back kitchen. The front kitchen is responsible for receiving customers' orders and then needs to pass the orders to the back kitchen for cooking.

**System V IPC Message Queues**

System V IPC is like using a special ordering system. In this system:

- The front kitchen writes down orders and gives each order a specified type label, such as "appetizer", "main course", "dessert", etc.
- The back kitchen has a list containing all order types.
The back kitchen can choose to view orders of a specific type; for example, right now the back kitchen only wants to see "main course" orders.
- These orders are placed on a special counter, and the back kitchen staff must follow specific rules to check the counter, such as using a special key. (Here the "key" refers to the key value key_t in System V IPC message queues.)
- Once an order is written down, even if the front kitchen staff leaves, the order stays on the counter until someone in the back kitchen explicitly handles it.

**POSIX Message Queues**

And if this restaurant uses POSIX message queues to process orders:

- The front kitchen uses a more modern system to write orders, and each order can be marked with an urgency level.
- The back kitchen has a display that automatically sorts the most urgent orders to the front.
- The back kitchen can keep checking this display and take orders in order of urgency.
- The display also has a light indicator; if the back kitchen is too busy to look, the light tells them whether there are new orders waiting to be processed. (Here the "light indicator" can be thought of as the non-blocking feature of POSIX message queues.)
- Once an order is completed, the display updates automatically, without requiring a special key or operation.
Differences

Now let's summarize the main differences between them:

- Naming and access method: SysV IPC uses an integer key value (key_t) to access a message queue, which requires a special method to generate and obtain the key value. POSIX message queues, on the other hand, are accessed through a string name like files, which makes them look more like part of the operating system rather than a separate service.
- Message priority: POSIX allows messages to be prioritized, ensuring that the most important messages are processed first. SysV message queues can achieve similar functionality, but usually not as intuitively or simply.
- Interface and functionality: The POSIX API is generally considered more modern and consistent, with better error handling and a more complete feature set. SysV IPC may be less intuitive or less reliable in certain versions of certain operating systems.

These differences make POSIX message queues possibly a better choice in new systems or scenarios requiring more features, while SysV IPC may be used in older systems for compatibility.

# IPC Namespace

Imagine that inter-process communication (IPC) is like a post office system. Within this system, the residents of a city (the various processes) want to send letters or packages (data) to each other. To accomplish this task, they use the services provided by the post office, such as mailboxes, package conveyor belts, or mail carriers (these correspond to IPC communication methods such as message queues, semaphores, shared memory, etc.).

Now let's talk about "ipcnamespace". This term can be understood as an independent small community or small district. Within each small community, residents have their own small post office, their own mailboxes and package conveyor belts. People outside the community cannot directly use the mailboxes and post office services of other communities. In this way, communication within each community is independent and private.

In computers, IPC namespaces serve a similar purpose. When you create a new IPC namespace, you are actually creating an isolated small community within the existing operating system, where processes can freely pass messages inside this community while outside processes cannot interfere. This is particularly useful when you don't want certain programs to be affected by the outside world, such as when using container technologies like Docker to isolate and manage different applications. Each container runs in its own IPC namespace, ensuring the independence and security of internal process communication. It's like giving an application a "private post office" that only serves the inside of the container, without mutual interference.

# What is a Message Queue
A message queue is a method of inter-process communication (IPC) or inter-application communication (between different applications or services) that allows processes to communicate by reading from/writing to a queue without needing to directly know about each other. A queue is an ordered collection of messages, which can be data, commands, or any information that can be converted into a byte string.

Message queues work similarly to a real-life post office system:

- Sending a message (sending a letter): A process (or thread) acts as the sender of the message (just like people sending letters) and places the message into a message queue.

- Storing messages (the post office holds letters): The queue temporarily stores these messages until the receiver is ready to receive them. The message queue can guarantee the order of messages and ensure that messages are not lost.

- Receiving a message (picking up a letter): Another process (or thread) acts as the receiver of the message and takes messages out of the queue in order for processing.

# Message Queue Related Structures
The basic structure of a message queue is simple but crucial, and can effectively coordinate message producers (senders) and consumers (receivers). Here are some main components of a message queue:

- Message: A message is the basic unit of data in the message queue structure. It can contain data in any form, such as strings, objects, or byte streams. Typically, a message consists of two parts: a message header (containing metadata such as message ID, timestamp, priority, etc.) and a message body (containing the actual data being sent).

- Queue: A queue is an ordered collection of messages that operates on the first-in-first-out (FIFO) principle. In other words, the first message sent to the queue will be the first to be received and processed. The queue provides a buffer between message producers and consumers, allowing them to work at different rates.

- Producer (sender): The producer is the entity that creates and sends messages to the queue. The producer sends messages to the queue, and once sending is complete, it usually no longer cares whether the message is consumed.

- Consumer (receiver): The consumer reads and processes messages from the queue. The consumer can be a process that directly listens to the queue and processes messages immediately when they arrive, or a process that periodically checks for new messages. In some cases, the consumer sends a response or result after processing a message.

# ipcs -q
The ipcs command is a tool in the Linux operating system used to report the status of Inter-Process Communication (IPC) facilities. ipc stands for inter-process communication, which can include message queues, semaphores, and shared memory segments. The ipcs command can display the current status of each type of IPC object, which is useful for diagnosis or system monitoring.

When the ipcs command is used with the -q option (i.e., ipcs -q), it specifically reports information about message queues. The output will include the key, msqid, and other additional information for each message queue.

Here is a typical output example of the ipcs -q command:

```bash
------ Message Queues --------
key        msqid      owner      perms      used-bytes   messages    
0x12345678 0          myuser     644        0            0           
0xaabbccdd 1          anotherusr 644        16384        4
 
```

An explanation of what each column in the above example represents:

- key: The key value used to uniquely identify the message queue.
- msqid: The kernel-internal unique identifier of the message queue.
- owner: The user who created the message queue.
- perms: The permissions of the message queue, usually displayed in octal form.
- used-bytes: The total number of bytes occupied by all messages currently in the queue.
- messages: The number of messages currently in the queue.



# ipcmk -Q
ipcmk is a command on Linux used to create IPC (Inter-Process Communication) resources; it can create message queues, shared memory, and semaphores. When you use ipcmk -Q (note that the parameter Q is uppercase), it creates a new message queue.

Here is a simple usage and output of ipcmk -Q:

```bash
$ ipcmk -Q
Message queue id: 32768
 
```

In this example, the ipcmk -Q command created a new message queue and output its message queue ID (msqid). This ID is the key identifier used to access and manage the message queue. If you need to use this message queue in your program, you will need this ID.
#  The Difference Between msqid and key
Imagine we have a post office with many mailboxes, and each mailbox has a unique mailbox number (this is like the msqid). If you want to put a letter into a certain mailbox, you need to know that mailbox's number.

However, to get a mailbox number, you first need to tell the post office a password or code so that they can assign a mailbox to you based on this password (this password is like the key). This password may be shared, meaning that other people may also know this password and use it to request the same mailbox number.


For example, suppose a school wants to set up an information publishing system. They decide to use a message queue to publish notifications, and they choose to use the school's identification code "123" and a specific project identifier 'A' to generate this key.

First, they generate a key for this purpose:

```go
// 学校使用识别码（例如123）和项目标识符（例如 'A'）生成key
key_t key = ftok("/path/to/somefile", 'A');  
```

 
After obtaining this key, the school can use it to get its own mailbox number (msqid):

```go

// 学校通过提供key来请求（如果不存在，则创建）一个邮箱号码（msqid）
int msqid = msgget(key, IPC_CREAT | 0666); 
 
```

If the request succeeds, the post office (the operating system) assigns a unique mailbox number (msqid) to the school's information publishing system.

At that point, the school's information publishing department can use this mailbox number (msqid) to send notifications, and other school departments or services that know this mailbox number can also go to the "post office" with this mailbox number to receive notifications. They don't need to know the original password (key); as long as they have the mailbox number (msqid), they can access that mailbox (message queue).
# Code
Compared to before, the only difference is **Cloneflags:CLONE_NEWUTS|CLONE_NEWIPC**
```go
package main

import
(
	
	"os/exec"
	"syscall"
	"os"
	"log"
)
func main(){
	cmd:=exec.Command("sh")
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Cloneflags: syscall.CLONE_NEWUTS | syscall.CLONE_NEWIPC ,
	}
	cmd.Stdin=os.Stdin
	cmd.Stdout=os.Stdout
	cmd.Stderr=os.Stderr

	if err:=cmd.Run();err!=nil{
		log.Fatal(err)
	}
}
```
