# Interrupt Classification
Local interrupts: software interrupts (0-3) and timer interrupts (4-7)
Global interrupts: external interrupts (8-10)

The three types of interrupts correspond to three pins on the CPU
![Image](/images/csdn/2024/csdn-137630897/image-001-40731b9e39.png)
# mie mip
The interrupt register in mstatus is global, while the mie interrupt register is at the second level, equivalent to a refinement

mie: enables a certain type of interrupt in a certain mode
mip: indicates whether a certain type of interrupt in a certain mode is currently occurring
![Image](/images/csdn/2024/csdn-137630897/image-002-b880fcebc5.png)
#  Interrupt Handling Flow
Similar to the exception handling flow, the difference is that mepc is set to save the address of the instruction following the current pc. Because an interrupt is considered to be taken after the current instruction finishes executing, after the interrupt is handled, execution should return to the instruction following the previous one.

# External Interrupts
Peripheral devices generate interrupts to the CPU, the CPU responds and handles the interrupt
Each CPU has only one pin corresponding to external interrupts, but there are many peripheral devices
![Image](/images/csdn/2024/csdn-137630897/image-003-fba636b273.png)
Managed through the PLIC interrupt controller: after a peripheral generates an interrupt source, the PLIC processes it and then passes it to a certain CPU for handling
![Image](/images/csdn/2024/csdn-137630897/image-004-42b982d52e.png)
# Interrupt Sources
0 has no fixed corresponding interrupt source; it is reserved
![Image](/images/csdn/2024/csdn-137630897/image-005-f2b92b9053.png)
#  PLIC
The PLIC is also a peripheral device. The CPU accesses the PLIC by mapping it into memory, so that accessing memory means accessing the PLIC registers
![Image](/images/csdn/2024/csdn-137630897/image-006-60004cc117.png)

#  Priority
Each interrupt source corresponds to its Priority register according to its interrupt source ID. The value in each register ranges from 0 to 7, where 0 represents the lowest priority for that interrupt source
![Image](/images/csdn/2024/csdn-137630897/image-007-ae772d7e9a.png)
#  Pending
The PLIC is readable and writable, and indicates whether a certain interrupt source has occurred. Each PLIC has two of these registers because 64 bits are needed to represent all interrupt sources
![Image](/images/csdn/2024/csdn-137630897/image-008-e64bb00893.png)
#  Enable
Corresponds to the hart; there are also two, again because 64 bits are needed to represent all interrupt sources

# PLIC Workflow

 Interrupt sources 1 and 2 have priorities 1 and 2 respectively. Enable is turned on for all devices of hart0 and turned off for hart1. hart0's threshold is set to zero
 1. When interrupt sources 1 and 2 occur simultaneously, the interrupt priorities of the interrupt sources are compared with each other first, and the higher priority one enters first
2. At this point, hart0's Enable allows entry, while hart1 does not
3. Then, since hart0's threshold is zero, entry is allowed
4. The pending bit corresponding to the interrupt source is set to 1, and at this point it is passed to the CPU, so the CPU knows that a certain interrupt has occurred
5. Then Claim can learn the ID number of the current interrupt source and clear the pending bit, then proceed to the interrupt handler
6. Then complete, notifying the PLIC that the current interrupt has been handled, then handle interrupt source 1, and the process is the same as above

# asm volatile("mv %0, tp" : "=r" (x) );
This code is an inline assembly statement on the RISC-V architecture, used in a C or C++ programming environment. It has the following meanings:

```c
asm volatile("mv %0, tp" : "=r" (x) );
```

1. `asm volatile`: This indicates that this is an inline assembly instruction, marked as `volatile`. This means the compiler will not optimize this piece of code; it will be executed literally every time, and the result of execution may affect the program's state.

2. `"mv %0, tp"`: This is an assembly instruction of the RISC-V architecture. `mv` is the move instruction, used to copy a value from a source register to a destination register. Here, `tp` represents the thread pointer register, and `%0` is a placeholder representing the C/C++ variable specified in the output constraint.

3. `: "=r" (x)`: This is an output constraint describing how the assembly instruction interacts with C/C++ variables. `=r` means a register is required as output, and the value of that register is assigned to the variable `x`.
# Header Files Cannot Define Functions, Otherwise Each Import Defines Them Once

```bash
/usr/lib/riscv64-unknown-elf/bin/ld: plic.o: in function read_mie': /home/llk/Desktop/risllkos/github/Fullkenerl6/trap.h:14: multiple definition of read_mie'; Trap.o:/home/llk/Desktop/risllkos/github/Fullkenerl6/trap.h:14: first defined here /usr/lib/riscv64-unknown-elf/bin/ld: plic.o: in function write_mie': /home/llk/Desktop/risllkos/github/Fullkenerl6/trap.h:19: multiple definition of write_mie'; Trap.o:/home/llk/Desktop/risllkos/github/Fullkenerl6/trap.h:19: first defined here 
```

This link error indicates that two object files in the project (`plic.o` and `Trap.o`) are both trying to define the same functions `read_mie` and `write_mie`, and these function definitions are located at lines 14 and 19 of the header file `/home/llk/Desktop/risllkos/github/Fullkenerl6/trap.h`.

In C/C++, functions should not be defined directly in header files; only function prototypes should be declared. Otherwise, when source files that include this header are compiled, each source file will generate a definition of the function, causing duplicate definition errors at link time.

The solution is as follows:

1. Move the definitions of the `read_mie` and `write_mie` functions to a separate source file (such as `trap.c` or `trap.s`, depending on whether they are C functions or assembly functions).

2. Keep only the function declarations (prototypes) in the header file `trap.h`:

```c
#ifndef _TRAP_H_
#define _TRAP_H_

// 声明函数，而不是定义
extern uint32_t read_mie(void);
extern void write_mie(uint32_t value);

#endif // _TRAP_H_
```

3. Make sure the actual implementations of these two functions are defined in only one source file in the project, then compile and link all the source files of the project normally.

4. If these functions are very low-level assembly functions and you really want to place the definitions in the header file, then you need to make sure to declare them with the `static inline` keywords to avoid multiple definition errors at link time. But note that this approach is suitable for very small functions that are suitable for inlining. For larger functions or functions involving special register access, this is generally not recommended.


# static inline
In C or C++, when you define a regular (non-inline) function in a header file and include that header in multiple source files (.c or .cpp), the compiler generates the machine code for this function in every source file that includes the header. When the linker tries to link all the object files into an executable, it finds the same function defined in multiple places, triggering a multiple definition link error.

However, for `static inline` functions, the situation is different:

1. **Static**: The `static` keyword here is used to limit the scope of the function. For functions, this means the function has "internal linkage", that is, it is only visible within the compilation unit that contains it (usually the source file containing the function definition). Although the function is defined in a header file here, because it is `static`, each source file that includes this header gets an independent copy of the function. These copies do not affect each other and are each valid within their own scope.

2. **Inline**: The `inline` keyword is used to request the compiler to try to embed the function body directly into each place where the function is called, like a macro, instead of generating a separate function call. In this way, theoretically there is no need to handle external references to this function at link time.

Combining the two, a `static inline` function both limits the scope (each source file is treated as an independent scope) and asks the compiler to inline it as much as possible. Even if the compiler cannot inline it for some reason, due to the effect of `static`, the function copies generated in each source file are still independent and only valid within their own compilation units, so no multiple definition errors occur at link time.

For example:

```c
// trap.h
#ifndef TRAP_H
#define TRAP_H

static inline void handle_trap() {
    // 函数体...
}

#endif // TRAP_H

// file1.c
#include "trap.h"
void some_function() {
    handle_trap(); // 调用
}

// file2.c
#include "trap.h"
void another_function() {
    handle_trap(); // 另一处调用
}
```

In this example, although the `handle_trap()` function has its definition included in both `file1.c` and `file2.c`, because it is `static inline`, each source file has an independent inline version (ideally the compiler inlines it; if not, each compilation unit has an independent non-inline copy), and ultimately no multiple definition problem occurs at link time.
