# Introduction to VMware Escape
1. The virtual machine operating system sends a sensitive request, causing the OS to trap into kernel mode
2. Certain privileged instructions enter a state below ring 0, meaning they are handed over to the Hypervisor
3. Exploit a vulnerability in the Hypervisor so that after the Hypervisor executes the privileged instruction, no instruction-state return occurs, leaving the system in kernel mode even after the instruction completes
4. Once privilege escalation is achieved, you can penetrate the Hypervisor and other regions of the virtual machine, breaking the virtualization isolation mechanism and completing the escape.

(In other words, when the virtual machine performs certain operations it sends requests to the host vmx, which then handles the requests; exploiting vulnerabilities in vmx achieves privilege escalation.)
![Image](/images/csdn/2024/csdn-139836466/image-001-4f38aa1a6e.png)


For example, suppose we discover a vulnerability in the Hypervisor that can be exploited to prevent the normal state transition after a privileged instruction executes.

1. Normal case:

```
Guest OS 执行特权指令 -> Trap 到 Hypervisor -> Hypervisor 执行指令 -> 返回 Guest OS 用户态
```

2. After exploiting the vulnerability:

```
Guest OS 执行特权指令 -> Trap 到 Hypervisor -> Hypervisor 执行指令 
-> 漏洞阻止状态转换 -> Guest OS 保持在内核态
```

The concrete implementation might look like this:

1. The attacker discovers that the Hypervisor has a buffer overflow vulnerability when handling certain privileged instructions.

2. The attacker crafts a special input that triggers this buffer overflow.

3. The overflowing data overwrites the code or data structures in the Hypervisor responsible for the state transition.

4. When the Hypervisor finishes executing the privileged instruction and prepares to return to the Guest OS, it cannot correctly perform the state transition because the critical code has been overwritten.

5. As a result, the Guest OS remains in kernel mode after the privileged instruction executes, instead of switching back to user mode as normal.

This kind of attack can lead to serious security problems, because it breaks the isolation between user mode and kernel mode and can be further exploited to escalate privileges or perform other malicious operations.

How it works:

1. Use special I/O instructions:
   VMware intercepts specific I/O instructions (the 'in' instruction in this example) and interprets them as backdoor calls.

2. Magic number and commands:
   A predefined magic number (BDOOR_MAGIC) and command codes are used to specify the type of operation.

3. Passing parameters via registers:
   Parameters are passed and results are received through specific registers.

4. Executes the 'in' instruction, which is intercepted and handled in VMware.
5. The result is returned in eax.

##  Message_Send and Message_Recv
The Message-related functions are the second layer of the internal communication channel between guest applications and VMware, and they are also implemented in open-vm-tools. Message_Send, Message_Recv, and others are higher-level abstractions built on top of the backdoor mechanism. They use the backdoor as the underlying communication channel, but provide a more usable and more flexible interface.


1. Message_OpenAllocated (simplified version):

```c
Bool Message_OpenAllocated(uint32 proto, Message_Channel *chan, char *receiveBuffer, size_t receiveBufferSize)
{
    Backdoor_proto bp;
    
    bp.in.cx.halfs.high = MESSAGE_TYPE_OPEN;
    bp.in.size = proto | GUESTMSG_FLAG_COOKIE;
    bp.in.cx.halfs.low = BDOOR_CMD_MESSAGE;
    
    Backdoor(&bp);
    
    if (!(bp.in.cx.halfs.high & MESSAGE_STATUS_SUCCESS)) {
        return FALSE;
    }
    
    chan->id = bp.in.dx.halfs.high;
    chan->cookieHigh = bp.out.si.word;
    chan->cookieLow = bp.out.di.word;
    
    chan->in = (unsigned char *)receiveBuffer;
    chan->inAlloc = receiveBufferSize;
    chan->inPreallocated = receiveBuffer != NULL;
    
    return TRUE;
}
```
 Message_OpenAllocated:
   - Function: opens a preallocated communication channel.
   - Parameters: protocol type, channel structure pointer, receive buffer and its size.
   - Process:
     * Uses the Backdoor mechanism to send an open-channel request.
     * On success, sets the channel ID and cookies.
     * Initializes the receive buffer information.
   - Returns: TRUE on success, FALSE on failure.

## GuestRPC 
A more flexible communication method implemented on top of the backdoor and Message_Send/Receive

Backdoor -> Message_Send/Receive -> GuestRPC
Each layer is built on top of the layer below it, providing higher-level abstractions and functionality.

When a GuestRPC call is executed, the data flow is typically:
GuestRPC command -> Message_Send processing -> Backdoor, e.g. RpcOut_start->Message_OpenAllocated->Backdoor

Executing a single GuestRPC call consists of a series of requests:

- Open the GuestRPC channel
- Send the command length
- Send the command data
- Receive the reply size
- Receive the reply data
- Signal the end of reception
- Close the GuestRPC channel

The process for each request is as follows

This code defines the interface of the RpcOut module, which is used to send RPC (Remote Procedure Call) requests from inside the virtual machine to the VMware virtualization layer.

1. Communication mechanism:
   RpcOut provides a mechanism that allows programs inside the virtual machine to communicate with the VMware virtualization layer.

2. Sending requests:
   The virtual machine can use this interface to send various requests to VMware, such as retrieving information, executing operations, and so on.

3. Receiving responses:
   RpcOut can not only send requests, but also receive responses from VMware.

4. Flexibility:
   It provides multiple methods to construct and send RPC requests, adapting to different use cases.

5. Main functions:
   - RpcOut_sendOne: the most commonly used method, used to send a single RPC request and receive the response.
   - RpcOut_SendOneRaw: handles UTF-8 strings and other data that could be corrupted by the Win32 FormatMessage function.
   - RpcOut_SendOneRawPreallocated: allows the caller to supply the receive buffer, avoiding an internal malloc call.

6. Lifecycle management:
   Provides a constructor (RpcOut_Construct) and a destructor (RpcOut_Destruct) to manage the lifecycle of RpcOut objects.

7. Session control:
   Includes the RpcOut_start and RpcOut_stop methods, used to begin and end RPC sessions.

The main purpose of the RpcIn module is to handle RPC (Remote Procedure Call) requests from the VMware virtualization layer into the virtual machine. The RpcIn module provides a framework for programs inside the virtual machine to receive and process RPC requests from the VMware virtualization layer.

1. Receiving requests:
   RpcIn allows programs inside the virtual machine to receive RPC requests from the VMware virtualization layer.

2. Callback mechanism:
   Provides a mechanism for registering callback functions (RpcIn_RegisterCallback) to handle specific types of RPC requests.

3. Event-driven:
   Uses an event queue (DblLnkLst_Links *eventQueue) to handle asynchronous RPC requests.

4. Lifecycle management:
   Provides a constructor (RpcIn_Construct) and a destructor (RpcIn_Destruct) to manage the lifecycle of RpcIn objects.

5. Start and stop:
   Includes the RpcIn_start and RpcIn_stop methods, used to start and stop RPC listening.

6. Error handling:
   Supports an error handling function (RpcIn_ErrorFunc) and a clear-error function (RpcIn_ClearErrorFunc).

7. Flexibility:
   Allows setting a delay (delay) and a reset callback (resetCallback) to adapt to different use cases.

8. Response setup:
   Provides the RpcIn_SetRetVals function to set the return values of an RPC call.

9. Backward compatibility:
   Retains some old interfaces (such as the old version of RpcIn_RegisterCallback) to maintain backward compatibility.

10. Multi-platform support:
    Through conditional compilation (#ifdef __cplusplus), it supports use in both C and C++ environments.

11. Custom handling:
    Allows registering custom callback functions to handle RPC requests with specific names.

### Example: `RpcOutSendOneRawWork`

```c

/*
 *-----------------------------------------------------------------------------
 *
 * RpcOutSendOneRawWork --
 *
 *    Helper function to make VMware execute a RPCI command.  See
 *    RpcOut_SendOneRaw and RpcOut_SendOneRawPreallocated.
 *
 *-----------------------------------------------------------------------------
 */

static Bool
RpcOutSendOneRawWork(void *request,         // IN: RPCI command
                     size_t reqLen,         // IN: Size of request buffer
                     char *callerReply,     // IN: caller supplied reply buffer
                     size_t callerReplyLen, // IN: size of caller supplied buf
                     char **reply,          // OUT: Result
                     size_t *repLen)        // OUT: Length of the result
{
   Bool status;
   Bool rpcStatus;
   /* Stack allocate so this can be used in kernel logging.  See 1389199. */
   RpcOut out;
   char const *myReply;
   size_t myRepLen;

   Debug("Rpci: Sending request='%s'\n", (char *)request);
   RpcOutInitialize(&out);
   if (!RpcOut_startWithReceiveBuffer(&out, callerReply, callerReplyLen)) {
      myReply = "RpcOut: Unable to open the communication channel";
      myRepLen = strlen(myReply);

      if (callerReply != NULL) {
         unsigned s = MIN(callerReplyLen - 1, myRepLen);
         ASSERT(reply == NULL);
         memcpy(callerReply, myReply, s);
         callerReply[s] = '\0';
      }
      if (reply != NULL) {
         *reply = NULL;
      }
      return FALSE;
   }

   status = RpcOut_send(&out, request, reqLen,
                        &rpcStatus, &myReply, &myRepLen);
   /* On failure, we already have the description of the error */

   Debug("Rpci: Sent request='%s', reply='%s', len=%"FMTSZ"u, "
         "status=%d, rpcStatus=%d\n",
         (char *)request, myReply, myRepLen, status, rpcStatus);

   if (reply != NULL) {
      /*
       * If we got a non-NULL reply, make a copy of it, because the reply
       * we got back is inside the channel buffer, which will get destroyed
       * at the end of this function.
       */
      if (myReply != NULL) {
         /*
          * We previously used strdup to duplicate myReply, but that
          * breaks if you are sending binary (not string) data over the
          * backdoor. Don't assume the data is a string.
          */
         *reply = malloc(myRepLen + 1);
         if (*reply != NULL) {
            memcpy(*reply, myReply, myRepLen);
            /*
             * The message layer already writes a trailing NUL but we might
             * change that someday, so do it again here.
             */
            (*reply)[myRepLen] = 0;
         }
      } else {
         /*
          * Our reply was NULL, so just pass the NULL back up to the caller.
          */
         *reply = NULL;
      }

      /*
       * Only set the length if the caller wanted it and if we got a good
       * reply.
       */
      if (repLen != NULL && *reply != NULL) {
         *repLen = myRepLen;
      }
   }

   if (RpcOut_stop(&out) == FALSE) {
      /*
       * We couldn't stop the channel. Free anything we allocated, give our
       * client a reply of NULL, and return FALSE.
       */

      if (reply != NULL) {
         free(*reply);
         *reply = NULL;
      }
      Debug("Rpci: unable to close the communication channel\n");
      status = FALSE;
   }

   return status && rpcStatus;
}
```

This process is embodied in the RpcOutSendOneRawWork function. The role of the RpcOutSendOneRawWork function is to package a piece of raw data into a message and send it via VMware's RPC protocol to another virtual machine or the host. This function mainly calls three functions:

- RpcOut_startWithReceiveBuffer: ultimately calls the Message_OpenAllocated function to perform the MESSAGE_TYPE_OPEN process.
- RpcOut_send: ultimately calls the two functions Message_Send and Message_Receive.
Message_Send: first performs the MESSAGE_TYPE_SENDSIZE process to send the message length, then loops through the MESSAGE_TYPE_SENDPAYLOAD process until the entire message has been sent.
Message_Receive: first performs the MESSAGE_TYPE_RECVSIZE process to obtain the length of the message to receive, then loops through the MESSAGE_TYPE_RECVPAYLOAD process until the entire message has been received.
- RpcOut_stop: ultimately calls the Message_CloseAllocated function to perform the MESSAGE_TYPE_CLOSE process.

## The VMWareRPCChannel and BufferedRPCChannel Classes

The vmx also provides a convenient, object-oriented way to execute GuestRPC commands: the VMWareRPCChannel and BufferedRPCChannel classes. By using the VMWareRPCChannel class, you can execute any GuestRPC request supported by VMware

VMWareRPCChannel and BufferedRPCChannel are classes through which VMware implements communication between the virtual machine and the host. They are used to manage and optimize the data transfer of remote procedure calls (RPC). They are wrappers around the series of mechanisms described earlier

BufferedRPCChannel is an enhanced class implemented on top of VMWareRPCChannel, mainly adding a buffering mechanism to optimize data transfer

vmmon and vmnet are two important modules in VMware virtual machines, each responsible for different functions:

1. vmmon (VMware Monitor):
   - This is a kernel module responsible for the core functions of the virtual machine, such as the virtualization of CPU, memory, and hardware devices.
   - It emulates a complete computer system, including hardware devices such as CPU, memory, disk, and network card, allowing the virtual machine to run operating systems and applications as if it were running on physical hardware.
   - For example, when you run the Windows operating system in a VMware virtual machine, the vmmon module is responsible for virtualizing your physical CPU and memory resources, making Windows feel as if it is running on dedicated hardware.

2. vmnet (VMware Network):
   - This is a kernel module for virtual networking.
   - It is responsible for creating and managing virtual network devices, such as virtual switches and virtual routers, as well as the network connections between virtual machines.
   - For example, when you set a "bridged" network mode in a VMware virtual machine, the vmnet module creates a virtual switch that connects the virtual machine's network card to the physical network, allowing the virtual machine to access external networks just like a physical machine.
