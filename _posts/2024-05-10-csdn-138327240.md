# The browser access process
Yes, when you visit a web page in a browser, the general flow is as follows:

1. **Request initiation**: After you type a URL or click a link, the browser generates an HTTP request containing the URL of the page you want to visit plus other information, such as the browser type and accepted content types.

2. **Server reception**: This HTTP request is sent to the server corresponding to the website. The server can be a web server such as Apache or Nginx, which listens on a specific port (usually port 80, or port 443 for HTTPS) and receives requests from clients.

3. **Request processing**: After receiving the request, the server determines which file to execute based on the URL path. In a PHP environment, if the URL points to a .php file, the server (via the PHP handler module) executes that file. During execution, the code in the PHP file is parsed, which may include database queries, business logic processing, file reading/writing, and other operations.

4. **Response generation**: After the PHP file finishes executing, it usually produces some output, which can be HTML, CSS, JavaScript code, or data formats such as JSON or XML. This output is the response body to the original HTTP request.

5. **Sending the response**: The server wraps the generated response content into an HTTP response message, including a status code (such as 200 for success), response headers (describing the response type, encoding, caching settings, etc.), and the response body (the content generated above). This response is then sent back to the browser.

6. **Browser rendering**: After receiving the server's response, the browser parses the HTML and CSS, executes the JavaScript, and finally renders the content into a web page visible to the user.

## cookie
A cookie is a way to pass data between a web browser and a server. It lets the server identify specific information about a user, enabling features like user session tracking and staying logged in. The example you gave, `Cookie: PHPSESSID=t2mqaq10tusne8c7p7o5j1ch25`, describes a concrete cookie instance. Below I use a simplified scenario to explain what this example means and does:

### Simplified scenario

Imagine that Zhang San visits an online shopping site, example.com, developed in PHP. When Zhang San visits the site for the first time, the server creates a unique session identifier (Session ID) in order to recognize and track Zhang San's visit, and sends this identifier to Zhang San's browser via the Set-Cookie HTTP response header. In this example, `PHPSESSID` is the name of this session identifier, and `t2mqaq10tusne8c7p7o5j1ch25` is the actual session ID value.

### Explanation of each part

- **Cookie**: This is a header field keyword in the HTTP protocol, indicating that the following information is about a cookie.
  
- **PHPSESSID**: This is the name of the cookie, indicating that it is related to a PHP session. In PHP, `PHPSESSID` is the default key name of the session identifier, used to store the unique ID of the session data.

- **=**: The separator between the cookie's name and value.

- **t2mqaq10tusne8c7p7o5j1ch25**: This is the actual value of the cookie, i.e., the unique identifier of Zhang San's session. This string is randomly generated to ensure that each user's session is not confused with others.

### How it works

1. **First visit**: The server generates a session ID and sends it to the browser, which stores this cookie (usually in local storage).

2. **Subsequent requests**: Whenever Zhang San's browser sends a request to the site (e.g., clicking a link or submitting a form), it automatically includes `Cookie: PHPSESSID=t2mqaq10tusne8c7p7o5j1ch25` in the HTTP request header.

3. **Server processing**: After the server receives a request carrying this cookie, it looks up the session data corresponding to this `PHPSESSID` and knows this is Zhang San's session, thereby restoring his login state, shopping cart contents, and so on.

In this way, stateful user interaction is achieved even on top of the stateless HTTP protocol, improving user experience and security. However, note that cookie security and privacy protection are also key concerns in development, such as using HTTPS to encrypt cookie transmission and setting cookie lifetimes reasonably.

## Can tokens prevent brute force?
[https://blog.csdn.net/a987329381/article/details/130917886](https://blog.csdn.net/a987329381/article/details/130917886)

> Note that the token in the fetch response applies to the current request message, i.e., you must set the token of the current request message to the token from the response.

In brute forcing, request 0 is the currently sent packet; the first request is the one that starts brute forcing from the dictionary.

The role of the token in this example
- The information the server responds to the client with contains a server-generated token to be used for the next request.

Burp Suite's "Intruder" module is a powerful tool for performing various types of automated attacks, including password cracking, parameter fuzzing, and token brute forcing. The role of the `Recursive Grep` feature in token brute forcing is mainly reflected in the following aspects:

1. **Dynamic token extraction**: During token brute forcing, target websites often generate a new token for each request as a security measure to prevent replay attacks. `Recursive Grep` can automatically extract the latest token value from the server's response, ensuring that each attack request uses the newest, valid token.

2. **Automatic payload updating**: By setting the `Payload type` to `Recursive Grep`, you can configure Intruder to use the `Grep Extractor` on each attack iteration to extract text matching a specific pattern (such as a token value) from the previous response, and dynamically insert the extracted value into the corresponding position in the next request. This way, even if the token changes with each request, the attack can continue, improving the effectiveness of the brute force.

3. **Multithreading compatibility note**: It is worth noting that when using `Recursive Grep` to extract payloads, since it relies on each request's response to dynamically generate the next request's payload, it usually cannot be used together with multithreaded (concurrent request) attacks, as this could cause logical confusion, extract the wrong token values, or make requests fail.

### The `domxss` function
This function is intended to get the text the user enters in an input box on the page (with ID "text") and dynamically insert it as part of a link into another element on the page (with ID "dom").

```javascript
function domxss(){
    var str = document.getElementById("text").value;
    document.getElementById("dom").innerHTML = "<a href='"+str+"'>what do you see?</a>";
}
```

1. **Getting user input**: `var str = document.getElementById("text").value;` This line gets the value of the HTML element with ID "text" (assumed to be a text input box), i.e., the text entered by the user.

2. **Constructing and inserting the link**: `document.getElementById("dom").innerHTML = "<a href='"+str+"'>what do you see?</a>";` This line concatenates the user input `str` into the `href` attribute of an `<a>` tag, then uses `innerHTML` to set it as the content of the element with ID "dom". This means the text entered by the user directly becomes part of the link.

### Attack attempt examples
The next two commented lines show inputs an attacker might try in order to exploit the DOM-based XSS vulnerability:

- `'><img src="#" onmouseover="alert('xss')">`
  This input attempts to close the original `<a>` tag and add an `<img>` tag with an `onmouseover` event. When the mouse hovers over this link, it triggers JavaScript's `alert('xss')`, popping up an alert box showing "xss", proving the XSS attack succeeded.

- `onclick="alert('xss')">`
  This is a more concise attempt: by adding an `onclick` event to the input, when the link is clicked, `alert('xss')` is likewise executed, demonstrating the effect of the XSS attack.

## XSS and htmlspecialchars
`htmlspecialchars` is a widely used function in PHP whose main purpose is to convert certain predefined characters into HTML entities, ensuring these characters are displayed correctly and safely on web pages rather than being interpreted by the browser as part of HTML tags or scripts. This is especially important for preventing cross-site scripting (XSS) attacks, because it can stop malicious users from injecting HTML or JavaScript code to manipulate page content or steal user data.

### Conversion rules
The `htmlspecialchars` function converts the following five predefined characters into their corresponding HTML entities:
- Less-than sign (`<`) is converted to `&lt;`
- Greater-than sign (`>`) is converted to `&gt;`
- Ampersand (`&`) is converted to `&amp;`
- Double quote (`"`) is converted to `&quot;` (when the `ENT_COMPAT` or `ENT_QUOTES` flag is specified)
- Single quote (`'`) is converted to `&#039;` (when the `ENT_QUOTES` flag is specified)

### Usage
The basic syntax is as follows:
```php
htmlspecialchars(string $string, int $flags = ENT_COMPAT | ENT_HTML401, string $encoding = 'UTF-8', bool $double_encode = false): string
```
- `$string`: The original string to be converted.
- `$flags`: Defines the type and level of conversion; e.g., `ENT_QUOTES` converts both double and single quotes.
- `$encoding`: Specifies the character encoding, defaulting to `UTF-8`.
- `$double_encode`: When set to `false`, if HTML entities already exist in the string, they will not be converted again, avoiding double-encoding of already-encoded entities.

### Example
```php
$text = "<script>alert('XSS Attack');</script>";
$safe_text = htmlspecialchars($text, ENT_QUOTES, 'UTF-8');
echo $safe_text;
```
The output will be:
```html
&lt;script&gt;alert(&#039;XSS Attack&#039;);&lt;/script&gt;
```
In this example, the script that could have triggered an XSS attack is converted into safely displayed HTML entities; the browser directly displays the text content without executing the script, thereby protecting the website and its users.

# CSRF (Cross-site request forgery)
- The attacker forges a request (this request is usually a link)
- Then tricks the target user into clicking it
- The user clicks the request, launching the attack

> CSRF completes the attack by borrowing the user's privileges; the attacker does not obtain the user's privileges, whereas XSS directly steals the user's privileges and then carries out the damage.

## Fuzzy (LIKE) injection
Pay attention to quotes and punctuation
### Usage example

Suppose we have a table named `products` with a column `product_name` storing product names, and we want to find all records whose product name contains "phone". We can use the following SQL statement:

```sql
SELECT * FROM products WHERE product_name LIKE '%phone%';
```

This query returns all records where `product_name` contains the string "phone" at any position, e.g., "SmartPhone X10", "iPhone 13 Pro", and "Headphone Stand" would all be matched.

### Other pattern-matching examples

- `'%input_'`: Find records that start with "input" followed by exactly one arbitrary character.
- `'_input%'`: Find records that end with "input" preceded by one arbitrary character.
- `'%input'`: Find all records ending with "input".
- `'input%'`: Find all records starting with "input".

`%df` represents a specific byte in percent-encoding (also called URL encoding). In this context, `%df` decodes to the byte with hexadecimal value `df`, i.e., 223 in decimal. In different character encoding standards, this byte represents different characters:

In PHP, `$_FILES` is a predefined global array used to store information about files uploaded via HTTP POST requests. When a user uploads a file through a form, PHP automatically populates this array, allowing developers to easily access detailed information about the uploaded file.

Regarding the array element structure, `$_FILES[$key]`, the `$key` here corresponds to the value of the `name` attribute of the file input field in the form. For example, if the file upload part of your HTML form looks like this:

```html
<input type="file" name="uploadfile">
```

Then in PHP, you can access the related information of this uploaded file through `$_FILES['uploadfile']`.

Explanation of `$_FILES[$key]['tmp_name']`:

- This key contains the temporary storage path of the uploaded file on the server. When a file is uploaded, PHP first stores it in a temporary directory until your script decides what to do with the file (such as moving it to a permanent location or deleting it). The name of this temporary file is generated by PHP; you usually don't need to care what it is exactly, but you need to use this temporary filename to perform the file move operation.

Explanation of `$save_path.$_FILES[$key]['name']`:

- This constructs a complete save path for the target file. `$save_path` is the directory path where you want to save the file, and `$_FILES[$key]['name']` is the original name of the uploaded file. Through the string concatenation operator `.`, these two parts are merged into a complete path. For example, if `$save_path` is `/var/www/uploads/` and the uploaded file is named `example.txt`, then the final path is `/var/www/uploads/example.txt`. This path is used by the `move_uploaded_file` function to move the uploaded temporary file to this specified permanent location.

# File Inclusion (file inclusion vulnerability)
### include()

- **Function**: `include()` is used to include the content of a specified file at a specified location. If the included file does not exist or the path is wrong, `include()` produces a warning (E_WARNING), but the script continues to execute.


### include_once()

- **Function**: Similar to `include()`, but with the characteristic that the file is included only once. If the file has already been included, it will not be included again, which helps avoid errors from redefining functions or classes.


### require()

- **Function**: `require()` is functionally similar to `include()`, but handles errors differently. If `require()` fails (file not found or unreadable), it produces a fatal error (E_COMPILE_ERROR), which causes the script to stop executing.

### require_once()

- **Function**: Combines the characteristics of `require()` and `include_once()`, ensuring the file is included once, and if the file does not exist or is unreadable, it causes a fatal error that terminates script execution.

2. **Generating the XML file**: The bookstore's backend system writes a script or program that extracts this information from the database and converts it into XML format. Below is a simplified XML example showing information for two books:

    ```xml
    <?xml version="1.0" encoding="UTF-8"?>
    <inventory>
        <book>
            <title>哈利·波特与魔法石</title>
            <author>J.K.罗琳</author>
            <isbn>978-7-5399-3665-1</isbn>
            <category>Fantasy</category>
            <quantity>25</quantity>
            <price>59.99</price>
        </book>
        <book>
            <title>百年孤独</title>
            <author>加西亚·马尔克斯</author>
            <isbn>978-7-5442-4560-3</isbn>
            <category>Literary Fiction</category>
            <quantity>100</quantity>
            <price>39.99</price>
        </book>
    </inventory>
    ```

3. **Data transmission**: This XML file can be securely sent to the data analytics company via an HTTP POST request, FTP upload, email attachment, etc.

4. **Data parsing and analysis**: After the data analytics company's system receives the XML file, it uses an XML parser (such as Python's xml.etree.ElementTree library, Java's DOM/SAX parsers, etc.) to parse the file, converting the XML data into data structures the company's system can process (such as dictionaries, lists, objects, etc.). The data is then used for further analysis and report generation.

Through this example, we can see the flexibility and convenience of XML as a data exchange format: it makes data sharing between different systems standardized and efficient. In addition, because XML is self-describing, the receiver can roughly understand the structure and meaning of the data from the XML tags even without extra documentation.

The `simplexml_load_string` function together with the `LIBXML_NOENT` flag is used to parse XML strings containing entities and to manipulate the resulting SimpleXMLElement object.

### Example XML string

Suppose we have a simple XML string containing entity references:

```xml
$xmlString = <<<XML
<?xml version="1.0"?>
<books>
    <book title="PHP与MySQL Web开发">
        <author>&lt;first&gt;Luke&lt;/first&gt; &lt;last&gt;Welling&lt;/last&gt;</author>
        <year>2016</year>
    </book>
</books>
XML;
```
In this example, the text inside the `<author>` tag uses the entity references `&lt;` and `&gt;` to represent angle brackets, preventing them from being mistaken for XML tags.

### Parsing with `simplexml_load_string`

We will use the `simplexml_load_string` function to parse this string, and use the `LIBXML_NOENT` parameter to replace entities with their corresponding characters:

```php
$bookData = @simplexml_load_string($xmlString, 'SimpleXMLElement', LIBXML_NOENT);
```

### Manipulating the parse result

After successful parsing, we can traverse and retrieve the XML data just like working with a normal PHP object:

```php
foreach ($bookData->book as $book) {
    echo "书名: " . (string)$book['title'] . "\n";
    echo "作者: " . str_replace(array('<first>', '</first>', '<last>', '</last>'), '', (string)$book->author) . "\n"; // 简单处理作者名字展示
    echo "出版年份: " . (string)$book->year . "\n";
}
```

### Output

This code outputs the following information:

```
书名: PHP与MySQL Web开发
作者: Luke Welling
出版年份: 2016
```


When using `simplexml_load_string` or similar XML parsing functions in PHP, adding the `LIBXML_NOENT` flag actually instructs the `libxml` parser to enable parsing support for external entities. This allows an XML document to reference external resources, such as data in other files or URIs. However, this can also introduce security risks, especially when processing untrusted XML input, potentially leading to XXE (XML External Entity) attacks.


Suppose we have an XML string containing an external entity declaration and reference (an entity whose content requires accessing something external is an external entity):

```xml
$xmlString = <<<XML
<!DOCTYPE test [
    <!ENTITY secret SYSTEM "file:///etc/passwd">
]>
   <content>&secret;</content>

XML;
```

In this example, the XML document defines an external entity `&secret;` that points to the `/etc/passwd` file on the server, a sensitive file containing system user information.

Without `LIBXML_NOENT`, many modern `libxml` versions by default forbid parsing external entities, thereby protecting the application from XXE attacks. But if `LIBXML_NOENT` is explicitly set, like this:

```php
$doc = simplexml_load_string($xmlString, 'SimpleXMLElement', LIBXML_NOENT);
```

The parser will try to resolve external entities, which means that if the XML comes from an untrusted source, it can potentially read arbitrary files on the server, causing serious security problems. After the above code executes, if parsing succeeds and external entity resolution is not blocked by other means, `$doc->content` may contain part or all of the `/etc/passwd` file.

So enter

```xml
<!DOCTYPE test [
    <!ENTITY secret SYSTEM "file:///etc/passwd">
]>
   <content>&secret;</content>
```

# URL redirection
- The client sends a piece of data to the server
- The server processes the received data and then performs a redirect-related operation


Phishing attacks caused by URL redirection vulnerabilities, simply put, are when attackers exploit users' trust in well-known or trusted websites and, through an insecure URL redirection feature, guide users to a malicious phishing site. Below is a concrete example to help understand this process:

**Scenario assumption**:
Suppose there is a well-known online bank with the domain `trustedbank.com`. Users frequently visit this site for various financial operations and have a high degree of trust in this domain.

**Attack process**:
1. **Constructing the malicious link**: The attacker creates a malicious link that looks like a page from `trustedbank.com`. The link might look like this: `https://trustedbank.com/login?redirect=https://evilphishingsite.com/login`. Here, the `redirect` parameter is followed by the address of the phishing site controlled by the attacker.

2. **Inducing clicks**: The attacker tricks users into clicking this link via email, social media, text messages, etc. The email or message may be disguised as an official notice from the bank, reminding the user that their account information needs updating or that a transaction needs confirmation.

3. **Exploiting the URL redirection vulnerability**: After the user clicks the link, the browser first loads the `trustedbank.com/login` page. However, because the bank's website has a URL redirection vulnerability and does not properly verify the safety of the `redirect` parameter, it directly redirects the user to `https://evilphishingsite.com/login`.

4. **The phishing site**: The user is redirected to a phishing site that looks almost identical to the `trustedbank.com` login page. Since the address bar showed the real bank's address before the redirect, and given the user's trust in the bank, they may not immediately realize they are no longer in a safe environment.

5. **Information theft**: On this forged login page, the user enters their bank account username and password, and possibly other sensitive information such as security question answers or verification codes. Once submitted, this information is sent directly to the attacker.

If the protocol prefix (such as http:// or https://) is not included, then resolving the redirect target URL depends on the current page's protocol and context. In many modern browsers and server configurations, such a URL is likely to be treated as a path relative to the current page or to default to the current page's protocol. This means that if the current page is accessed over HTTPS, the browser may try to access "www.baidu.com/" over HTTPS, but if the current page is HTTP, it may try HTTP instead, which can lead to inconsistent behavior or security warnings, especially when the target site enforces HTTPS.

# SSRF (Server-Side Request Forgery)
[https://blog.csdn.net/angry_program/article/details/104451155](https://blog.csdn.net/angry_program/article/details/104451155)
- Data flow: the attacker sends data -----> the server receives the data ----> the server accesses the target address the attacker sent to it

Improper use of the following functions in PHP can lead to SSRF:
1. **file_get_contents()**:
   This function is usually used to read file contents, but if what is provided is a URL rather than a local file path, PHP will try to initiate an HTTP or FTP request to that URL to fetch content. Attackers can carefully craft a URL to make the server access internal systems, perform unauthorized API calls, or access external malicious servers, thereby causing information disclosure or triggering other security issues.

2. **fsockopen()**:
   This function is used to open a network connection and is commonly used for TCP/IP communication. It allows directly establishing a connection with any IP address and port, sending and receiving data. If an attacker can control the parameters passed to this function, they can force the server to establish connections with internal systems or malicious servers and perform the requests the attacker wants, such as scanning the intranet or attacking other services.

3. **curl_exec()**:
   cURL is a powerful library for downloading data from servers of various protocols (HTTP, FTP, SMTP, etc.). The `curl_exec()` function executes a cURL session; likewise, if an attacker can manipulate the requested URL or other parameters, they can induce the server to send requests to arbitrary addresses, resulting in an SSRF vulnerability.
## SSRF (curl)
- The backend server accesses the passed-in url parameter
- Since the visitor is the server, the access happens from the server's perspective, so it can access content on the intranet or on this server itself

```php
if(isset($_GET['url']) && $_GET['url'] != null){

    //接收前端URL没问题,但是要做好过滤,如果不做过滤,就会导致SSRF
    $URL = $_GET['url'];
    $CH = curl_init($URL);
    curl_setopt($CH, CURLOPT_HEADER, FALSE);
    curl_setopt($CH, CURLOPT_SSL_VERIFYPEER, FALSE);
    $RES = curl_exec($CH);
    curl_close($CH) ;
//ssrf的问是:前端传进来的url被后台使用curl_exec()进行了请求,然后将请求的结果又返回给了前端。
//除了http/https外,curl还支持一些其他的协议curl --version 可以查看其支持的协议,telnet
//curl支持很多协议，有FTP, FTPS, HTTP, HTTPS, GOPHER, TELNET, DICT, FILE以及LDAP
    echo $RES;

}
```
