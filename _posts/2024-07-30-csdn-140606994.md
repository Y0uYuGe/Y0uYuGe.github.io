This diff file contains the following main changes:

1. In the `bootstrapper.cc` file, a new built-in function `ArrayOob` was added to the prototype of `JSGlobalObject`. This function can be used to read and write out-of-bounds elements of an array.

2. In the `builtins-array.cc` file, the logic of the `ArrayOob` function is implemented.
		                        
	
	1. `BUILTIN(ArrayOob)` is a macro definition used to define built-in functions in the V8 engine. This function is named `ArrayOob`.
	
	2. The first line of the function gets the number of arguments of the function, stored in the variable `len`.
	
	3. Next, a simple argument check is performed: if the number of arguments is greater than 2, it directly returns `undefined`.
	
	4. Uses `Object::ToObject` to convert the function caller into a `JSReceiver` object, then forcibly casts it to a `JSArray` object, stored in the `array` variable.
	
	5. Obtains the array's underlying storage structure `FixedDoubleArray` via `array->elements()`, stored in the `elements` variable.
	
	6. Gets the length of the array, stored in the `length` variable.
	
	7. Next, it determines whether to read or write based on the argument count `len`:
	   - If `len` equals 1, it indicates a read operation. It gets the value of the array's last element via `elements.get_scalar(length)` and returns it after converting it to a `Number` type. There is an off-by-one error here, because array indices start from 0, but we use `length` as the index, causing an out-of-bounds element of the array to be read.
	   - If `len` equals 2, it indicates a write operation. First, the second argument is converted to a `Number` type, stored in the `value` variable. Then `elements.set(length, value->Number())` is used to write that value to the array's last element. There is also an off-by-one error here, because we use `length` as the index, causing an out-of-bounds element of the array to be written.



4. In the `builtins-definitions.h` file, the definition of the `ArrayOob` function was added, specifying it as a C++ implementation.

5. In the `typer.cc` file, type inference logic was added for the `ArrayOob` function, with the return type being `Type::Receiver()`.

![Image](/images/csdn/2024/csdn-140606994/image-001-b06ba70a8d.png)
In the case of a.oob(1), two arguments are passed:

- The first argument is the array a itself, which is the implicitly passed this argument.
- The second argument is the number 1.

a.oob(0) prints the out-of-bounds a[4] of the array


It was found that the elements of an array object is actually also an object. These elements are distributed in memory right above the array object, i.e., at lower addresses. In other words, in terms of memory allocation, v8 first allocates a block of memory to store the element contents, then allocates a block of memory to store the object structure of this array; the elements pointer in the object points to the memory address storing the element contents

```bash
  elements  ----> +------------------------+
                   |          MAP           +<---------+
                   +------------------------+          |
                   |      element 1         |          |
                   +------------------------+          |
                   |      element 2         |          |
                   |      ......            |          |
                   |      element n         |          |
 ArrayObject  ---->-------------------------+          |
                   |      map               |          |
                   +------------------------+          |
                   |      prototype         |          |
                   +------------------------+          |
                   |      elements          |          |
                   |                        +----------+
                   +------------------------+
                   |      length            |
                   +------------------------+
                   |      properties        |
                   +------------------------+
```

So actually the out-of-bounds read can read out the map's address, and the write can modify the map's address, i.e., the object type Map can be modified (type confusion)
For example, if we define a FloatArray floating-point array A, then define an object array B. Under normal circumstances, accessing A[0] returns a floating-point number, and accessing B[0] returns an object element. If B's type is changed to A's type, then accessing B[0] again no longer returns the object element B[0], but rather the B[0] object element converted to a floating-point number, i.e., the memory address of the B[0] object; if A's type is changed to B's type, then accessing A[0] again no longer returns the floating-point number A[0], but rather a JavaScript object with A[0] as its memory address.


> Calculating an object's address, addressOf: store the object whose memory address needs to be calculated into A[0] of an object array, then use the above type confusion vulnerability to change the object array's Map type to the float array type; accessing A[0] then yields the memory address of the target object represented as a floating-point number.

> Forging a memory address into an object, fakeObject: store the memory address to be forged into B[0] of a float array, then use the above type confusion vulnerability to change the float array's Map type to the object array type; B[0] then represents a JS object with this memory address as its starting address.

# Arbitrary Address Read/Write
Use the contents of an array's elements to forge the memory of an array object; after leaking the array's address, obtain the address of the array's element contents, use the type confusion vulnerability to write it into a float array, then change it to an object array to get a fake object at the element content address. Then, by modifying the element within the array's element contents and reading/writing the fake object, arbitrary address read/write can be achieved


Since forging a DoubleArray in an array for arbitrary read/write has some tricky problems
- When the array performs element access, it performs a mask operation with the base address of the heap, ensuring that the memory segment pointed to by the elements pointer belongs to the scope of the v8 heap. (Writing to high addresses via the FloatArray approach will fail.)
- When operating on the forged float array, the function that collects Inline Cache is triggered, causing a SIGTRAP.
- The arbitrary address read/write constructed with DoubleArray can only read/write elements + 0x10, and it also accesses data in the range [elements, elements + 0x10). If writing shellcode in an rwx segment, you need to write from the starting position, so the arbitrary read/write constructed with DoubleArray cannot be used to accomplish this.

After that, each arbitrary address read/write can first use one ArrayBuffer to change the other ArrayBuffer's BackingStore, and then use the other ArrayBuffer to perform arbitrary address read/write. (Or directly change an ArrayBuffer's BackingStore to point to the address to be written, then write via dataview)

##  Traditional Method
Through constructors such as Array, the ELF load base address can be leaked, and then the libc load base address can be leaked through the GOT table.

> View the Array object structure --> view the object's Map property --> view the constructor structure specified in the Map --> view the code property --> the instruction address in the v8 binary is stored at a fixed offset from the code memory address

> When v8 generates an array object, it correspondingly generates a code object. This code object stores the constructor instructions related to that array object, and these constructor instructions in turn call instruction addresses in the d8 binary to complete the construction of the array object.

> Note that the release version must be used here to inspect this, otherwise the debug version does not show PIE-related addresses
