#  Overview
QEMU can provide an environment for CPU emulation of user processes
One QEMU process provides an environment that can boot one virtual machine

KVM runs in the kernel; it allows the virtual machines started by QEMU to execute guest code directly on the host CPU safely. Its role is to be responsible for creating virtual machines, allocating virtual memory, and virtual CPUs

```c
// 第一步，获取到 KVM 句柄
kvmfd = open("/dev/kvm", O_RDWR);
// 第二步，创建虚拟机，获取到虚拟机句柄。
vmfd = ioctl(kvmfd, KVM_CREATE_VM, 0);
// 第三步，为虚拟机映射内存，还有其他的 PCI，信号处理的初始化。
ioctl(kvmfd, KVM_SET_USER_MEMORY_REGION, &mem);
// 第四步，将虚拟机镜像映射到内存，相当于物理机的 boot 过程，把镜像映射到内存。
// 第五步，创建 vCPU，并为 vCPU 分配内存空间。
ioctl(kvmfd, KVM_CREATE_VCPU, vcpuid);
vcpu->kvm_run_mmap_size = ioctl(kvm->dev_fd, KVM_GET_VCPU_MMAP_SIZE, 0);
// 第五步，创建 vCPU 个数的线程并运行虚拟机。
ioctl(kvm->vcpus->vcpu_fd, KVM_RUN, 0);
// 第六步，线程进入循环，并捕获虚拟机退出原因，做相应的处理。
for (;;) {
  ioctl(KVM_RUN)
  switch (exit_reason) {
      case KVM_EXIT_IO:  /* ... */
      case KVM_EXIT_HLT: /* ... */
  }
}
// 这里的退出并不一定是虚拟机关机，
// 虚拟机如果遇到 I/O 操作，访问硬件设备，缺页中断等都会退出执行，
// 退出执行可以理解为将 CPU 执行上下文返回到 Qemu。
```
On exit, the reason is checked; it may be handled by KVM or by QEMU
# Memory
It can be understood this way: the physical memory used by the guest is actually part of the virtual memory of the QEMU process that started it. That is, this part may correspond to the guest's physical memory starting from 0 (from the guest's perspective)

Two layers of translation

 1. From the guest's virtual address to the guest's physical address
     Equivalent to obtaining the physical address from the page table
 2. From the guest's physical address to the virtual address in the host's QEMU process
     This physical address plus the starting address of the guest in the virtual address space of the host's QEMU process gives the corresponding host virtual address


First layer of translation: use the pagemap page mapping file for the translation

 1. The offset in pagemap corresponding to the virtual address (i.e., which entry it is in pagemap) multiplied by 8 gives the offset in pagemap (i.e., the corresponding address in pagemap)

![Image](/images/csdn/2023/csdn-134742868/image-001-4acbc5978a.png) 

 2. After reading, check whether the content exists and whether the highest bit is 1; if it is 1, the page is present. Then shift the read content left by 12 bits to get the lower 52 bits (the address of the physical page), and OR it with the lower 12 bits (page offset) of the original virtual address to get the guest's physical address


Run the following code with QEMU

#include <string.h>

#include <stdlib.h>

#define PFN_PRESENT (1ull << 63)

int fd;
// 获取页内偏移
uint32_t page_offset(uint32_t addr)
{
	// addr & 0xfff
    return addr & ((1 << PAGE_SHIFT) - 1);
}

uint64_t gva_to_gfn(void *addr)
{
    uint64_t pme, gfn;
    size_t offset;

    printf("pfn_item_offset : %p\n", (uintptr_t)addr >> 9);
    offset = ((uintptr_t)addr >> 9) & ~7;

    ////下面是网上其他人的代码，只是为了理解上面的代码
    //一开始除以 0x1000  （getpagesize=0x1000，4k对齐，而且本来低12位就是页内索引，需要去掉），即除以2**12, 这就获取了页号了，
    //pagemap中一个地址64位，即8字节，也即sizeof(uint64_t)，所以有了页号后，我们需要乘以8去找到对应的偏移从而获得对应的物理地址
    //最终  vir/2^12 * 8 = (vir / 2^9) & ~7 
    //这跟上面的右移9正好对应，但是为什么要 & ~7 ,因为你  vir >> 12 << 3 , 跟vir >> 9 是有区别的，vir >> 12 << 3低3位肯定是0，所以通过& ~7将低3位置0
    // int page_size=getpagesize();
    // unsigned long vir_page_idx = vir/page_size;
    // unsigned long pfn_item_offset = vir_page_idx*sizeof(uint64_t);

    lseek(fd, offset, SEEK_SET);
    read(fd, &pme, 8);
    // 确保页面存在——page is present.

        return -1;
    // physical frame number 
    gfn = pme & PFN_PFN; //取低52位
    return gfn;
}

uint64_t gva_to_gpa(void *addr)
{
    uint64_t gfn = gva_to_gfn(addr);
    assert(gfn != -1);
    return (gfn << PAGE_SHIFT) | page_offset((uint64_t)addr);//合并
}

int main()
{
    uint8_t *ptr;
    uint64_t ptr_mem;

        exit(1);
    }
    
    ptr = malloc(256);

    printf("Your physical address is at 0x%"PRIx64"\n", ptr_mem);

# PCI Devices
PCI is a Peripheral Component Interconnect standard; PCI devices are devices that conform to this standard and are connected to the PCI bus. The PCI bus is the bridge between the CPU and external devices.

Devices that conform to the PCI bus standard are called PCI devices
PCI devices are divided into master devices and target devices; the master device is the initiator of an access operation, while the target device is the one being accessed.

Each PCI device has a corresponding PCI Configuration Space, which records information about the device. The PCI configuration space is at most 256 bytes, of which the first 64 bytes are a predefined standard.

Bit 1 being 0 indicates a 32-bit address; being 1 indicates a 64-bit address

# MMIO
Memory-mapped IO shares an address space with memory. Its contents can be read and written just like reading and writing memory.
Accessing device I/O through the Memory space is called memory mapped I/O, i.e., MMIO. In this case, the CPU can access device I/O directly using ordinary memory access instructions.
# PMIO
Port-mapped IO: memory and IO devices have their own independent address spaces, and the CPU needs dedicated instructions to access them. In Intel microprocessors, the instructions used are IN and OUT.

Accessing device I/O through the I/O space is called port mapped I/O, i.e., PMIO. In this case, the CPU needs dedicated I/O instructions such as IN/OUT to access I/O ports
# Ispci
PCI peripheral addresses look like 0000:00:1f.1. The first part, 16 bits, represents the domain; the second part, 8 bits, represents the bus number; the third part, 5 bits, represents the device number; the last part, 3 bits, represents the function number.

# Accessing the Memory Space and IO Space in the PCI Device Configuration Space
## MMIO

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>
#include <errno.h>
#include <signal.h>
#include <fcntl.h>
#include <ctype.h>
#include <termios.h>
#include <assert.h>
#include <sys/types.h>
#include <sys/mman.h>
#include <sys/io.h>

#define MAP_SIZE 4096UL
#define MAP_MASK (MAP_SIZE - 1)

char* pci_device_name = "/sys/devices/pci0000:00/0000:00:04.0/resource0";

unsigned char* mmio_base;

unsigned char* getMMIOBase(){
    
    int fd;
    if((fd = open(pci_device_name, O_RDWR | O_SYNC)) == -1) {
        perror("open pci device");
        exit(-1);
    }
    mmio_base = mmap(0, MAP_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);//根据resource0中的文件内容来分配Memory空间
    if(mmio_base == (void *) -1) {
        perror("mmap");
        exit(-1);
    }
    return mmio_base;
}

void mmio_write(uint64_t addr, uint64_t value)
{
    *((uint64_t*)(mmio_base + addr)) = value;
}

uint64_t mmio_read(uint64_t addr)
{
    return *((uint64_t*)(mmio_base + addr));
}

int main(int argc, char const *argv[])
{
    getMMIOBase();
    printf("mmio_base Resource0Base: %p\n", mmio_base);

    mmio_write(144, val);
    mmio_read(144);
    
    return 0;
}
```
## PMIO
Permissions are required to access ports
Ports 0x000-0x3ff can be accessed with ioperm(from, num, turn_on)
For example, ioperm(0x300,5,1); obtains access permission for ports 0x300 to 0x304
Higher ports require iopl(3) to obtain permission, which grants access to all ports in the range
The in and out series of functions are as follows: write/read one byte (ending in b), two bytes (ending in w), and four bytes (ending in l) respectively

```c
#include <sys/io.h >

iopl(3); 
inb(port); 
inw(port); 
inl(port);

outb(val,port); 
outw(val,port); 
outl(val,port);
```

# QQM (qemu object model)
QEMU provides an object-oriented programming model — QOM, i.e., QEMU Object Module. Almost all devices such as CPUs, memory, and buses are implemented using this object-oriented model.
Object initialization is divided into four steps:

 1. Register TypeInfo as TypeImpl
 2. Instantiate ObjectClass
 3. Instantiate Object
 4. Add Property

ObjectClass: the base class of all class objects; it only stores an integer type.
Object: the Base Object of all objects; its first member variable is a pointer to ObjectClass.
TypeInfo: a utility data structure used by users to define a Type.
TypeImpl: an abstract data structure for data types; the attributes of TypeInfo correspond to those of TypeImpl.

# Concise Summary

## Registering TypeInfo as TypeImpl:

1. First, the __attribute__((constructor)) modifier makes type_init execute before main. The parameter of type_init is the XXX_register_types function pointer, which is passed to the init function pointer of ModuleEntry. Finally, this ModuleEntry is inserted into ModuleTypeList
2. module_call_init(MODULE_INIT_QOM); in the main function calls the init() functions of all ModuleEntry of type MODULE_INIT_QOM in ModuleTypeList, which is exactly the XXX_register_types function pointer passed as the first parameter of type_init in step one
3. Next comes the operation of the XXX_register_types function, which is to create the TypeImpl hash table

## Initialization of ObjectClass:

Call chain: main->select_machine->object_class_get_list->object_class_foreach->object_class_foreach_tramp->type_initialize

Some information from parent->class->interfaces is added to the ti->class->interfaces list, and the information of the type corresponding to ti->interfaces[i].typename is also added to the ti->class->interfaces list. Finally, and most importantly, the parent's class_base_init is called for initialization, and then its own ti->class_init is called for initialization.

## Instantiating Instance (Object)

Call chain: qemu_opts_foreach->device_init_func->qdev_device_add->object_new->object_new_with_type

The object_new_with_type function initializes some members of Object, and calls the ti->instance_init function through the object_init_with_type function (if there is a parent, object_init_with_type is called recursively first, then its own ti->instance_init function is called). Finally, object_post_init_with_type is similar, except that it first calls its own ti->instance_post_init, then recursively calls the parent's ti->instance_post_init
