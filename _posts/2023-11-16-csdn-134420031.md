# IO virtualization
Since peripheral devices are limited, we still want to provide peripheral functionality to VMs. (Also, since the interaction between the processor and peripherals is mainly IO interaction, peripheral virtualization is called IO virtualization.) So the VMM is needed to provide IO device functionality to VMs through IO virtualization.

**Tasks of IO virtualization:**
 - Access interception: when a VM accesses a peripheral, the VMM needs to be able to intercept it
 - Provide device interfaces: the VMM must provide VMs with virtual device interfaces or physical device interfaces
 - Implement device functionality: the VMM needs to implement the functionality of virtual devices
# Basic models
## Platform device emulation
That is, the VMM is responsible for emulating device functionality
The VMM emulates devices for Guest OSes to share

## User space device emulation
That is, the host's user space emulates device functionality; the emulated virtual devices can be invoked by other VMs through interfaces provided by the VMM. And device emulation is independent of the VMM.
## Device passthrough
That is, directly assigning a physical device exclusively to a specified VM, which then uses the physical device's functionality directly. This provides near-native device performance (often imitated, never surpassed)

# Software paravirtualization — virtio
Establish a connection with virtualized devices through virtio drivers, thereby gaining access
1. Full virtualization

It can run on such a VMM without any modification to the GuestOS operating system software source code

In a fully virtualized platform, the GuestOS does not know it is a virtual machine; it believes it is the HostOS running on the computer's physical hardware. This is because a fully virtualizing VMM logically abstracts the physical devices an OS can operate — CPU, memory, peripherals — into virtual devices such as virtual CPUs, virtual memory, and virtual peripherals, and then hands them to the GuestOS to use. Such a GuestOS regards the underlying hardware platform as its own, but in fact this illusion is created by the VMM for the GuestOS.

2. Paravirtualization

The GuestOS kernel code must be modified to some extent for the GuestOS to run on a paravirtualizing VMM.

Paravirtualization avoids the aforementioned virtualization holes by modifying privileged instructions at the GuestOS source code level.

A GuestOS with a modified kernel also knows it is a virtual machine, so it can recognize and handle kernel-mode instructions and sensitive instructions well; the downside is that the GuestOS image file is not generic.

Paravirtualization adds dedicated API interfaces to optimize guest instructions and share system hardware drivers, maximizing computer performance, using software interfaces to replace computer hardware functions, and solving the performance waste caused by binary translation in full virtualization.
## Drivers
A driver is essentially software code whose main role is to carry out data transfer between the computer system and hardware devices; only with a driver can the two communicate and perform specific functions. Without a driver, a hardware device cannot perform its specific functions with only the operating system. In other words, a driver is the intermediary between the operating system and the hardware, achieving bidirectional communication — conveying the hardware device's own functions to the operating system, and conveying the operating system's standard instructions to the hardware device — thus achieving a seamless connection between the two.
## VirtQueue: transport layer abstraction
The virtqueue is the key structure in virtio for data transfer; it itself represents a data queue: one side adds buffers to the queue, and the other side takes buffers from the queue — this implements the basic data transfer model between Guest and Host.

To reduce model complexity, we use two virtqueues for bidirectional communication between Guest and Host: one virtqueue from Guest to Host, and one from Host to Guest

### Data structures used

This is the descriptor structure
```c
struct vring_desc
{
    __u64 addr;     // 描述符对应的起始地址
    __u32 len;      // 从起始地址开始占的大小空间
    __u16 flags;    // 该描述符的属性
    __u16 next;     // 对应的下一个描述符的下标
};
```
This is the Avail structure
```c
struct vring_avail
{
    __u16 flags; //该结构内所有描述符的附加属性
    __u16 idx;  // 下一次要加描述符对应在ring数组中的下标
    __u16 ring[NUM]; //存储描述符的
};
```
This is the Used structure
```c
struct vring_used_elem 
{
    __u32 id;  //描述符的值

{
    __u16 flags; //该结构内所有描述符的附加属性
    __u16 idx; //下一次要加描述符对应在ring数组中的下标
    struct vring_used_elem ring[];//存储描述符的

```

# IOMMU
The IOMMU, or Input/Output Memory Management Unit, has functionality similar to the CPU's MMU; it is a unit that provides address translation on the device side.
**Differences between the IOMMU and the MMU**
![Image](/images/csdn/2023/csdn-134420031/image-002-6dbcab5c9b.png)
**IOMMU functions**
LAPIC (Local Advanced Programmable Interrupt Controller) 

 - DMA remapping: DMA-capable devices can use virtual addresses, converted by the IOMMU into physical addresses for direct memory access.
 - Interrupt remapping: the IOMMU intercepts interrupts generated by devices and generates new interrupt requests according to the interrupt remapping table, sending them to the LAPIC.
## DMA remapping
DMA remapping is address-access re-translation on the device side. As shown in the figure below, the left side is the CPU's virtualization of memory: the MMU uses the process page table to translate the virtual addresses the process wants to access into physical addresses, and because different processes have different page tables, accessing the same virtual address in two processes actually accesses different physical addresses — DMA remapping works on a similar principle. As shown on the right side of the figure, when a peripheral wants to perform DMA, the IOMMU translates addresses according to the "device page table"; different devices have different page tables, so two devices each perceive that they are accessing the same address while actually accessing different physical addresses.
![Image](/images/csdn/2023/csdn-134420031/image-003-9e4318fdb1.png)


Paravirtualized devices do not know the GPA-to-HPA translation, so they may access incorrectly; therefore the IOMMU needs to perform DMA mapping according to the GPA-to-HPA address translation table provided by the Host, so that peripherals can correctly access the Guest's physical memory
