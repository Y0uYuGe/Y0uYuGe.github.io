# SLAM
SLAM (Simultaneous Localization and Mapping) is one of the core technologies in robotics and autonomous driving. It uses sensor data (such as lidar, cameras, etc.) to estimate the pose (position and orientation) of a robot or unmanned system in real time while building a map of the environment.


#  hector_mapping 
hector_mapping is a lidar (LIDAR)-based SLAM (Simultaneous Localization and Mapping) node, suitable for scenarios without odometry and with limited computing resources.
- Subscribed topics
scan (sensor_msgs/LaserScan)
Lidar scan data used by the SLAM system.
syscommand (std_msgs/String)
System command. If the string equals "reset", the map and robot pose will be reset to their initial state.
- Published topics
map_metadata (nav_msgs/MapMetaData)
Map data can be obtained from this topic; the data is latched and updated periodically.
map (nav_msgs/OccupancyGrid)
Map data can be obtained from this topic; the data is latched and updated periodically.
slam_out_pose (geometry_msgs/PoseStamped)
Estimated robot pose, without covariance.
poseupdate (geometry_msgs/PoseWithCovarianceStamped)
Estimated robot pose, with Gaussian-estimated uncertainty.

# Hector_Mapping parameter settings
1. ~map_update_distance_thresh
Type: double (floating point)
Default value: 0.4
Unit: meters (m)
Purpose:
This is the distance threshold for map updates. The robot must move at least 0.4 meters (default value) to trigger a map update.
Details:
If the distance the robot moves is smaller than this threshold, the map will not be updated.
This parameter works together with ~map_update_angle_thresh; meeting either condition triggers a map update.

2. ~map_update_angle_thresh
Type: double (floating point)
Default value: 0.9
Unit: radians (rad)
Purpose:
This is the angular threshold for map updates. The robot must rotate at least 0.9 radians (default value) to trigger a map update.
Details:
If the robot's rotation angle is smaller than this threshold, the map will not be updated.
This parameter works together with ~map_update_distance_thresh; meeting either condition triggers a map update.
3. ~map_pub_period
Type: double (floating point)
Default value: 2.0
Unit: seconds (s)
Purpose:
This is the time interval for publishing the map. The map data is published once every 2.0 seconds (default value).
Details:
Even if the robot does not move or rotate, the map is still published periodically at this interval.
This parameter is unrelated to ~map_update_distance_thresh and ~map_update_angle_thresh; it only controls the frequency of map publishing.

# The ROS TF system (localization)

The **TF (Transform) system** in ROS (Robot Operating System) is a core tool for managing coordinate frame transforms. It allows users to define and query the relationships between different coordinate frames in a robot system, such as the relative positions and orientations among the robot chassis, sensors, manipulators, etc. The TF system plays a vital role in robot navigation, perception, and control.

---

1. **Basic concepts of the TF system**
  1.1 Coordinate frames (Frame)
- In a robot system, each component (such as a sensor, manipulator, chassis, etc.) has its own coordinate frame.
- Coordinate frames are usually expressed in a **parent-child relationship**. For example, the lidar's coordinate frame may be a child frame of the robot chassis coordinate frame.

  1.2 Transforms (Transform)
- A **transform** describes the conversion relationship from one coordinate frame to another, including translation (position) and rotation (orientation).
- A transform can be represented by a **4x4 transformation matrix** or a **translation vector + quaternion (Quaternion)**.

  1.3 Timestamps (Timestamp)
- Transforms change over time (e.g., a moving robot), so each transform has a timestamp indicating the time at which the transform is valid.

---

 2. **Core functions of the TF system**
 2.1 Publishing transforms (Publish Transform)
- Publish transform relationships between coordinate frames via `tf::TransformBroadcaster`.
- For example, publish the transform from the robot chassis to the lidar.

 2.2 Looking up transforms (Lookup Transform)
- Query the transform relationship between two coordinate frames via `tf::TransformListener`.
- For example, look up the transform from the lidar frame to the map frame.

 2.3 Managing the transform tree (Transform Tree)
- The TF system maintains a **transform tree**, in which each node is a coordinate frame and each edge is a transform relationship between frames.
- The transform tree must be a directed acyclic graph (DAG); that is, no circular dependencies are allowed.

---

 3. **Using the TF system**
 3.1 Publishing transforms
Here is an example of publishing a transform:
```cpp
#include <ros/ros.h>
#include <tf/transform_broadcaster.h>

int main(int argc, char** argv) {
    ros::init(argc, argv, "tf_broadcaster");
    ros::NodeHandle nh;

    tf::TransformBroadcaster broadcaster;

    ros::Rate rate(10); // 10 Hz
    while (ros::ok()) {
        // 定义变换：从 "base_link" 到 "laser"
        tf::Transform transform;
        transform.setOrigin(tf::Vector3(0.1, 0.0, 0.2)); // 平移 (x, y, z)
        transform.setRotation(tf::Quaternion(0, 0, 0, 1)); // 旋转 (x, y, z, w)

        // 发布变换
        broadcaster.sendTransform(
            tf::StampedTransform(transform, ros::Time::now(), "base_link", "laser"));

        rate.sleep();
    }

    return 0;
}
```
   Simulation
  - Publishes the transform from `base_link` (robot chassis) to `laser` (lidar).
  - The transform includes a translation of `(0.1, 0.0, 0.2)` and a rotation of `(0, 0, 0, 1)` (no rotation).

 3.2 Looking up transforms
Here is an example of looking up a transform:
```cpp
#include <ros/ros.h>
#include <tf/transform_listener.h>

int main(int argc, char** argv) {
    ros::init(argc, argv, "tf_listener");
    ros::NodeHandle nh;

    tf::TransformListener listener;

    ros::Rate rate(10); // 10 Hz
    while (ros::ok()) {
        tf::StampedTransform transform;
        try {
            // 查询从 "base_link" 到 "laser" 的变换
            listener.lookupTransform("base_link", "laser", ros::Time(0), transform);

            // 打印变换信息
            ROS_INFO("Translation: [%f, %f, %f]",
                     transform.getOrigin().x(),
                     transform.getOrigin().y(),
                     transform.getOrigin().z());
            ROS_INFO("Rotation: [%f, %f, %f, %f]",
                     transform.getRotation().x(),
                     transform.getRotation().y(),
                     transform.getRotation().z(),
                     transform.getRotation().w());
        } catch (tf::TransformException &ex) {
            ROS_ERROR("%s", ex.what());
        }

        rate.sleep();
    }

    return 0;
}
```
- **Explanation**:
  - Looks up the transform from `base_link` to `laser`.
  - Prints the translation and rotation information of the transform.

tf2_msgs/TFMessage is a message type used in ROS (Robot Operating System) to convey multiple coordinate transform information.
transforms: This is an array containing multiple geometry_msgs/TransformStamped messages. Each TransformStamped message represents a transform relationship between coordinate frames.
Purpose: TFMessage is typically used to pass multiple coordinate transform data between ROS nodes. For example, one node can publish a TFMessage containing the transform relationships between multiple coordinate frames, and other nodes can subscribe to that message to obtain the transform information.



geometry_msgs/TransformStamped is a message type used to represent a coordinate transform with a timestamp.
1. header: This is a std_msgs/Header message containing the timestamp and coordinate frame information.
header.stamp: The timestamp, indicating the time of the transform.
header.frame_id: The name of the parent coordinate frame.
2. child_frame_id: The name of the child coordinate frame, indicating that the transform goes from the parent frame to the child frame.
3. transform: This is a geometry_msgs/Transform message containing translation and rotation information.
transform.translation: The translation vector, containing the x, y, z components. It is the position of the child frame's origin in the parent frame.
transform.rotation: The rotation quaternion, containing the x, y, z, w components. It describes the rotation of the child frame's x, y, z axes, or the rotation angle and orientation of the object relative to another coordinate frame.

# What is odometry




Motor odometry plays an important role in lidar SLAM (Simultaneous Localization and Mapping). It computes the robot's displacement by recording motor rotation data, thereby estimating the robot's current position.

This displacement information is published to the /tf topic in the form of TF messages. The motor odometry outputs the TF from odom to base_footprint, while lidar SLAM outputs the TF from map to base_footprint.


The advantage of motor odometry is that it does not depend on the features of external reference objects, so it will not be misled by the features of reference objects.

However, motor odometry has errors. For example, when the robot's wheels slip, the odometry's localization information may not match the actual position. Moreover, such errors accumulate continuously, making the localization error larger and larger. Therefore, an obstacle point-cloud registration algorithm is needed to correct the odometry error.


```bash
roslaunch wpr_simulation wpb_corridor_hector.launch 
```


Hector Mapping is a lidar-based SLAM algorithm whose core idea is to localize by registering the lidar point cloud against obstacles. In Hector Mapping, the robot's displacement is mainly computed by the lidar point-cloud registration algorithm, without using odometry data. In order to display the map and the robot model in RViz, Hector Mapping outputs a TF from map to odom to counteract the ever-growing odometry TF, so that the position of base_footprint always stays consistent with scanmatcher_frame.

When running Hector Mapping, if the robot enters a corridor with smooth walls on both sides, the lidar can only scan the walls on both sides, causing the obstacle point-cloud registration to conclude that the robot has not moved forward, mistakenly attributing it to noise in the lidar data so that the localization jitters within a small range. At this point, Hector Mapping outputs a TF in the direction opposite to the robot's motion to counteract the change in odometry, keeping the position of base_footprint consistent with scanmatcher_frame.

![Radar](/images/csdn/2025/csdn-145568423/image-003-031a19d855.png)
The displacement obtained directly from lidar point-cloud matching is scanmatcher_frame.
```bash
roslaunch wpr_simulation wpb_corridor_hector.launch 
```

Gmapping is another commonly used SLAM algorithm. Its core idea is to first use odometry to estimate the robot's displacement, then fit the lidar point cloud to obstacle contours to correct the odometry error. In Gmapping, the robot's displacement is mainly estimated by odometry, and the lidar point-cloud registration algorithm only serves to correct the odometry error. Gmapping outputs the TF from map to odom and then to base_footprint.

When running Gmapping, as the robot enters a corridor with smooth walls on both sides, the positions of map and odom begin to diverge, with obvious jumps. This is caused by the localization jumps from lidar point-cloud registration against obstacles. Even so, since the odometry is still running, the robot's localization continues to advance, and the final mapping result basically matches the actual site.


The position from map to odom is the offset from obstacle point-cloud matching.
The position from odom to base_footprint is the odometry offset.

slam_gmapping is a ROS (Robot Operating System) node for simultaneous localization and mapping (SLAM). It receives laser scan data (sensor_msgs/LaserScan) and builds a map (nav_msgs/OccupancyGrid). The map can be obtained via ROS topics or services.
- Subscribed topics
tf (tf/tfMessage)
Purpose: Provides the coordinate transforms between the laser, the base, and the odometry.
Note: These transforms are necessary for building the map and localizing the robot.
scan (sensor_msgs/LaserScan)
Purpose: Receives laser scan data used to create the map.
Note: Laser scan data is the primary input for building the map.
- Published topics
map_metadata (nav_msgs/MapMetaData)
Purpose: Obtain the map metadata.
Note: This topic publishes the map's metadata, including the map's resolution, dimensions, etc. The data is latched and updated periodically.
map (nav_msgs/OccupancyGrid)
Purpose: Obtain the map data.
Note: This topic publishes the map data, represented as an occupancy grid. The data is latched and updated periodically.
~entropy (std_msgs/Float64)
Purpose: Estimate the entropy of the robot's pose distribution.
Note: A higher entropy value indicates greater uncertainty in the robot's pose. This is a feature added since version 1.1.0.
- Required transforms
<frame of incoming scans> → base_link
Purpose: Converts laser scan data from the laser frame to the robot base frame.
Note: This is usually a fixed transform, broadcast periodically by robot_state_publisher or tf static_transform_publisher.
base_link → odom
Purpose: Associates the robot base frame with the odometry frame.
Note: This is usually provided by the odometry system, such as the driver of the mobile base.
- Provided transforms
map → odom
Purpose: Provides the current pose estimate of the robot in the map frame.
Note: This transform represents the robot's position and orientation in the map.

#  Saving and loading maps

`map_server` is an important package in ROS (Robot Operating System) mainly used for handling map data. It provides two main functions: the `map_server` node and the `map_saver` command-line tool. The following is a detailed explanation of its functions:

 1. **map_server node**
The `map_server` node reads map files from disk and provides map data through ROS services. Map data is usually stored in two file formats:
- **YAML file**: Describes the map's metadata, including the map's resolution, origin, thresholds, and other information.
- **Image file**: Usually in `.pgm` or `.png` format, representing the occupancy of the map. Each pixel in the image corresponds to a cell in the map, and the pixel's color value indicates the occupancy state of that cell (free, occupied, or unknown).

 Main functions:
- **Publishing map data**: The `map_server` node publishes two topics:
  - `map_metadata`: Publishes the map's metadata (such as resolution, origin, etc.).
  - `map`: Publishes the map's occupancy grid data (`OccupancyGrid`).
- **Providing services**: `map_server` also provides a `static_map` service, allowing other nodes to obtain map data via service calls.

 Usage example:
```bash
rosrun map_server map_server mymap.yaml
```
This command starts the `map_server` node and loads the map specified in the `mymap.yaml` file.

 2. **map_saver tool**
`map_saver` is a command-line tool used to save a map to disk. It is typically used to save maps generated by SLAM (Simultaneous Localization and Mapping).

Main functions:
- **Saving the map**: `map_saver` reads map data from the specified ROS topic and saves it as `.pgm` and `.yaml` files.
Default topic: /map (message type: nav_msgs/OccupancyGrid)
Custom topic: another topic can be specified via map:=<topic_name>.
- **Custom thresholds**: The thresholds for occupied and free areas can be set via the `--occ` and `--free` parameters.

 Usage example:
```bash
rosrun map_server map_saver -f mymap
```
This command saves the map as `mymap.pgm` and `mymap.yaml` files.

 3. **Map format**
A map consists of two files:
- **YAML file**: Contains the map's metadata, such as resolution, origin, thresholds, etc.
- **Image file**: Contains the map's occupancy data, usually a grayscale image where white represents free areas, black represents occupied areas, and gray represents unknown areas.

 YAML file example:
```yaml
image: testmap.png
resolution: 0.1
origin: [0.0, 0.0, 0.0]
occupied_thresh: 0.65
free_thresh: 0.196
negate: 0
```
- `image`: The path to the image file.
- `resolution`: The resolution of the map, in meters/pixel.
- `origin`: The 2D pose of the lower-left pixel in the map, in the format (x, y, yaw), where yaw represents counterclockwise rotation (yaw=0 means no rotation). Many parts of the current system ignore yaw.
![Image](/images/csdn/2025/csdn-145568423/image-007-b21de046f1.png)

- `occupied_thresh` and `free_thresh`: The thresholds for occupied and free areas, respectively.
- `negate`: Whether to invert the semantics of the image (black/white inversion).

 4. **Value interpretation**
Pixel values in the map can be interpreted as three states:
- **Trinary**: Pixel values are interpreted as free (0), occupied (100), or unknown (-1).
- **Scale**: Pixel values are interpreted as a gradient between free and occupied.
- **Raw**: The raw pixel values are used directly.
