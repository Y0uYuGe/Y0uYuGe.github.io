# move_base

![Image](/images/csdn/2025/csdn-145595623/image-002-91701d6ddb.png)
Main components
- Global Planner:
Responsible for generating the global path from the start point to the goal point.
Common implementations include navfn and global_planner.
- Local Planner:
Responsible for generating concrete motion commands based on the global path and local environment information (such as obstacles).
Common implementations include base_local_planner and dwa_local_planner.
- Costmap:
Used to represent the cost information of the robot's surrounding environment, helping the planner avoid obstacles.
Includes the global costmap and the local costmap.
- Recovery Behaviors
When the robot encounters problems during navigation (such as getting stuck), move_base executes recovery behaviors.
The default recovery behaviors include:
Clearing obstacles from the costmap.
Rotating in place to re-plan the path.

# AMCL localization algorithm

1. rviz splits into various particles, i.e., possible robot positions at different locations and orientations.
2. Then the robot actually moves a distance and the lidar scans to obtain the odometry distance + lidar scan features.
3. Then the odometry distance is superimposed onto each particle, and the least-matching particles are eliminated via lidar feature matching.
4. Repeat the above three steps.
- Function: amcl is a probabilistic localization system for robots in 2D. It implements the adaptive (or KLD-sampling) Monte Carlo localization approach, using a particle filter to track the robot's pose in a known map.
- Algorithms: uses multiple algorithms, including sample_motion_model_odometry, beam_range_finder_model, likelihood_field_range_finder_model, Augmented_MCL, and KLD_Sampling_MCL.
- Sensor support: currently only supports laser scans and laser maps, but can be extended to other sensor data.


- Node: the amcl node receives laser maps, laser scans, and transform messages, and outputs pose estimates.
- Subscribed topics:
scan (sensor_msgs/LaserScan): laser scan data.
tf (tf/tfMessage): transform messages.
initialpose (geometry_msgs/PoseWithCovarianceStamped): used to initialize the mean and covariance of the particle filter.
map (nav_msgs/OccupancyGrid): when the use_map_topic parameter is set, subscribes to this topic to get the map used for laser localization.
- Published topics:
amcl_pose (geometry_msgs/PoseWithCovarianceStamped): the robot's estimated pose in the map, with covariance.
particlecloud (geometry_msgs/PoseArray): the set of pose estimates maintained by the filter.
tf (tf/tfMessage): publishes the transform from odom to map.

The different layers of the costmap:
Static Map Layer: the static map layer, a basically unchanging map layer, usually the static map built by SLAM.
Obstacle Map Layer: the obstacle map layer, used to dynamically record obstacle information perceived by sensors.
Inflation Layer: the inflation layer, which inflates (expands outward) on the above two map layers to prevent the robot from hitting obstacles.
Master Layer: the combination layer, which integrates the information of the above layers to generate the final costmap.

# Costmap parameter settings
- Function: the costmap_2d package provides a 2D costmap implementation for robot navigation. It takes in sensor data, builds a 2D or 3D occupancy grid (depending on whether the voxel implementation is used), and inflates costs in the 2D costmap based on the occupancy grid and a user-specified inflation radius.

- Marking and Clearing:
The costmap automatically subscribes to sensor topics and updates itself based on sensor data.
Each sensor is used to mark (insert obstacle information into) or clear (remove obstacle information from) the costmap, or both.
Occupied, Free, and Unknown Space:
Each cell in the costmap can have 255 different cost values, but the underlying structure can only represent three states: free, occupied, or unknown.
Each state has a special cost value when projected into the costmap.
- Map Updates:
The costmap performs map update cycles at the specified update frequency (update_frequency).
In each cycle, sensor data is processed, marking and clearing operations are performed in the underlying occupancy structure, and then projected into the costmap.
- Transforms (tf):
The costmap uses tf (transforms) to insert sensor data. It assumes that all transforms between the global frame (global_frame), the robot base frame (robot_base_frame), and the sensor sources are connected and up to date.
The transform_tolerance parameter sets the maximum allowable delay between these transforms.
- Inflation:
Inflation is the process of propagating cost values outward from occupied cells, with cost values decreasing as distance increases.
Five specific cost value symbols are defined to represent the robot's relationship to obstacles.

- Static Map:
Initialize the costmap using a user-generated static map (such as a map built via the map_server package).
The costmap's width, height, and obstacle information match the static map.
- Rolling Window:
Set the rolling_window parameter to true to keep the robot at the center of the costmap while it moves; as the robot moves away from an area, obstacle information is removed from the map.
This configuration is typically used when the robot only cares about obstacles in a local area.


- Coordinate frame and transform parameters:
global_frame: the global frame of the costmap (default is /map).
robot_base_frame: the robot base frame (default is base_link).
transform_tolerance: the tolerance delay for transform data (default is 0.2 seconds).
- Frequency parameters:
update_frequency: map update frequency (default is 5.0 Hz).
publish_frequency: map publish frequency (default is 0.0 Hz, meaning only the updated parts are published).
- Map management parameters:
rolling_window: whether to use a rolling window (default is false).
always_send_full_costmap: whether to publish the full costmap on every update (default is false).
width, height, resolution, origin_x, origin_y: the map's width, height, resolution, and origin coordinates.

# Recovery behaviors



![Image](/images/csdn/2025/csdn-145595623/image-011-97112cbf1a.png)
1. Conservative Reset:
Description: The robot attempts to clear obstacle information from the map beyond a specified area.
Transitions:
If obstacles are successfully cleared and navigation continues, it enters the Navigating (normal navigation) state.
If clearing fails or it is still stuck, it enters the Clearing Rotation state.
2. Clearing Rotation:
Description: The robot performs an in-place rotation to try to clear local obstacle information.
Transitions:
If obstacles are successfully cleared after rotation and navigation continues, it enters the Navigating (normal navigation) state.
If it is still stuck after rotation, it enters the Aggressive Reset state.
3. Aggressive Reset:
Description: The robot clears obstacle information from the map more aggressively, including all obstacles beyond the specified area.
Transitions:
If obstacles are successfully cleared and navigation continues, it enters the Navigating (normal navigation) state.
If clearing fails or it is still stuck, it enters the Clearing Rotation state.
4. Navigating (normal navigation):
Description: The robot is in the normal navigation state, moving along the planned path.
Transitions:
If it encounters an obstacle or gets stuck, it enters the Conservative Reset state.
5. Aborted:
Description: If all recovery behaviors fail, the robot considers the goal unreachable and abandons the navigation task.
Transitions:
No further transitions; the task ends.


# Recovery behavior parameter settings

```bash
recovery_behaviors:
  - name: 'rotate_recovery'
    type: 'rotate_recovery/RotateRecovery'
  - name: 'reset_recovery'
    type: 'clear_costmap_recovery/ClearCostmapRecovery'

```

The clear_costmap_recovery package provides a recovery behavior used during robot navigation to clear obstacle information from the costmap, helping the robot get out of trouble and continue navigating.

This recovery behavior clears obstacle information in the costmap beyond a specified area, allowing the robot to re-plan its path.
The cleared area is a square region centered on the robot, whose side length is determined by the reset_distance parameter.

```bash
rotate_recovery:
  reset_distance: 2.0
  layer_names: ["obstacle_layer"]
```

- ~<name>/reset_distance (double, default: 3.0):
Specifies the side length of the area in which obstacles are cleared (a square region centered on the robot), in meters.
For example, reset_distance: 3.0 means clearing obstacle information within 3 meters around the robot.
- ~<name>/invert_area_to_clear (bool, default: false):
If set to false, obstacle information outside the specified area is cleared; if set to true, obstacle information inside the specified area is cleared.
- ~<name>/layer_names (list, default: ["obstacles"]):
Specifies the names of the layers to clear. By default, only the obstacles layer is cleared.





The rotate_recovery package provides a recovery behavior used during robot navigation to clear obstacle information from the costmap by performing a 360-degree rotation, thereby helping the robot get out of trouble and continue navigating.
Performing a 360-degree rotation:
This recovery behavior rotates the robot 360 degrees in place, updating sensor data, thereby clearing obstacle information from the costmap.
During the rotation, the robot rescans the surrounding environment and updates the obstacle information in the costmap.

```bash
reset_recovery:
  reset_distance: 0.0
  layer_names: ["obstacle_layer"]
```

- ~<name>/sim_granularity (double, default: 0.017):
The angular interval (in radians) of each check when checking whether an in-place rotation is safe. The default is 0.017 radians (about 1 degree).
- ~<name>/frequency (double, default: 20.0):
The frequency (in Hz) at which velocity commands are sent to the mobile base. The default is 20.0 Hz.
- ~TrajectoryPlannerROS/yaw_goal_tolerance (double, default: 0.05):
The yaw tolerance (in radians) of the controller when achieving the goal. The default is 0.05 radians.
- ~TrajectoryPlannerROS/acc_lim_th (double, default: 3.2):
The robot's rotational acceleration limit (in rad/s²). The default is 3.2 rad/s².
- ~TrajectoryPlannerROS/max_rotational_vel (double, default: 1.0):
The maximum rotational velocity allowed for the base (in rad/s). The default is 1.0 rad/s.
- ~TrajectoryPlannerROS/min_in_place_rotational_vel (double, default: 0.4):
The minimum rotational velocity allowed for the base when rotating in place (in rad/s). The default is 0.4 rad/s.

# DWA
Dynamic Window Approach (DWA)
1. State space sampling: at the current moment, based on the robot's velocity and acceleration limits, compute the possible velocity combinations (linear velocity v and angular velocity ω), forming a dynamic velocity window.
The dynamic window can be represented as a velocity range containing the velocity combinations (linear velocity v and angular velocity ω) that the robot can safely take at the current moment.
3. Trajectory generation: for each pair (v, ω), predict the future trajectory via a motion model, usually over a certain time span.
4. Evaluate trajectories: score each trajectory according to a trajectory quality evaluation function (usually including the distance to the goal point, the safe distance from obstacles, etc.).
5. Select the best velocity: select the velocity command with the highest score, so that the robot can both reach the goal and effectively avoid obstacles during motion.

# TEB

teb_local_planner is a local trajectory planner plugin in the ROS navigation stack, based on the Timed-Elastic-Bands method. It can optimize the robot's trajectory at runtime while considering trajectory execution time, distance from obstacles, and kinematic and dynamic constraints.

teb_local_planner is based on nonlinear optimization and generates smooth, safe, and efficient local trajectories for the robot in real time. Its core method is "Timed-Elastic-Bands", which stretches or compresses the trajectory by introducing virtual forces to adapt to environmental constraints and robot dynamics.


1. The TEB algorithm first selects a segment from the global route provided by the global planner as the initial trajectory.

2. Based on the start and end points of this trajectory segment, a connecting line (timed elastic band) is generated. This line consists of multiple discrete time points, each corresponding to a pose (position and orientation) of the robot.

3. The global route has an attractive force on the TEB band, i.e., the algorithm tries to keep the band close to the global route. This is achieved by imposing an objective function during optimization that makes the points on the band as close as possible to the points on the global route.

4. Obstacles have a repulsive force on the TEB band, i.e., the algorithm tries to keep the band away from obstacles. This is achieved by imposing another objective function during optimization that makes the points on the band as far away from obstacles as possible.


The TEB algorithm adjusts the shape of the band through multi-objective optimization. The optimization objectives include:
Path length: minimize the path length.
Trajectory execution time: minimize the trajectory's execution time.
Distance from obstacles: maintain a safe distance from obstacles.
Passing through intermediate waypoints: try to pass through key points on the global route.
Robot dynamic and kinematic constraints: ensure the trajectory conforms to the robot's motion capabilities.

# Navigation Action programming interface
Action communication is a bidirectional message-passing mechanism. Unlike traditional Topic communication, Actions can provide continuous feedback information.
Navigation Action communication includes three main parts:
1. Goal Request: the goal request sent by the client to the server, containing the coordinates and orientation of the navigation goal point.
2. Result: the result returned by the server after completing the navigation task, indicating whether navigation succeeded.
3. Feedback: feedback information sent periodically by the server to the client during navigation, used to monitor the navigation progress in real time.

    while(!ac.waitForServer(ros::Duration(5.0))){
        ROS_INFO("Waiting for the move_base action server to come up");
    }

    move_base_msgs::MoveBaseGoal goal;
    goal.target_pose.header.frame_id = "map";
    goal.target_pose.header.stamp = ros::Time::now();
    goal.target_pose.pose.position.x = -3.0;
    goal.target_pose.pose.position.y = 1.0;

    goal.target_pose.pose.orientation.w = 1;

    ROS_INFO("Sending goal");
    ac.sendGoal(goal);
    ac.waitForResult();
    if(ac.getState() == actionlib::SimpleClientGoalState::SUCCEEDED)
        ROS_INFO("complete mission");
    else
        ROS_INFO("failed mission");

}

- wp_manager:
Function: the wp_manager node is responsible for managing waypoints. It reads waypoint data from the waypoints.xml file and sends it to wp_navi_server. wp_navi_server stores the waypoint information but does not start navigation; it waits for waypoint information to appear on the goal navigation topic, then compares it with the waypoint information that wp_manager sent and wp_navi_server stored, to perform navigation.
- wp_navi_server:
Function: the wp_navi_server node is responsible for handling navigation tasks. It subscribes to the "goal waypoint topic", receives goal waypoint information, then passes it to move_base for navigation, and publishes the navigation result via the "navigation result topic".
