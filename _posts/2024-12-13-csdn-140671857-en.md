# unlink
After free, before a chunk is placed into the unsorted bin, related checks are performed to see whether it needs to be merged with the chunks before and after it — first checking the lower-address chunk for merging, then checking the higher-address one.
```c
P是要从链表中脱下来的chunk   

static void
unlink_chunk (mstate av, mchunkptr p)
{
  if (chunksize (p) != prev_size (next_chunk (p)))
    malloc_printerr ("corrupted size vs. prev_size");

  mchunkptr fd = p->fd;
  mchunkptr bk = p->bk;

  if (__builtin_expect (fd->bk != p || bk->fd != p, 0))
    malloc_printerr ("corrupted double-linked list");

  fd->bk = bk;
  bk->fd = fd;
  if (!in_smallbin_range (chunksize_nomask (p)) && p->fd_nextsize != NULL)
    {
      if (p->fd_nextsize->bk_nextsize != p
	  || p->bk_nextsize->fd_nextsize != p)
	malloc_printerr ("corrupted double-linked list (not small)");

      if (fd->fd_nextsize == NULL)
	{
	  if (p->fd_nextsize == p)
	    fd->fd_nextsize = fd->bk_nextsize = fd;
	  else
	    {
	      fd->fd_nextsize = p->fd_nextsize;
	      fd->bk_nextsize = p->bk_nextsize;
	      p->fd_nextsize->bk_nextsize = fd;
	      p->bk_nextsize->fd_nextsize = fd;
	    }
	}
      else
	{
	  p->fd_nextsize->bk_nextsize = p->bk_nextsize;
	  p->bk_nextsize->fd_nextsize = p->fd_nextsize;
	}
    }
}
```
Conditions
- FD->bk = P and BK->fd = P
-  chunk2's prev_size is modified to the fake chunk's size
- chunk2's size has the PREV_INUSE bit set to 0, and chunk2's size must not be in the fast bin range.

Effect
 - FD->bk = BK   BK->fd = FD

## Alloc to Stack & Arbitrary Alloc

Hijack the fd pointer of a chunk in the fastbin list, pointing the fd pointer to the address we want to allocate, thereby gaining control of some critical data, such as the return address.

The prerequisite for being able to allocate the memory pointed to by an fd in a fastbin is that the value at the size field of that memory matches the size corresponding to that fast bin.

```c
 if (victim != 0)
        {
          if (__builtin_expect (fastbin_index (chunksize (victim)) != idx, 0))
            {
              errstr = "malloc(): memory corruption (fast)";
            errout:
              malloc_printerr (check_action, errstr, chunk2mem (victim), av);
              return NULL;
            }
            …………
        }
```
Usually you first use house of spirit or double free to hijack the fd. Generally only `if (__builtin_expect (victim_idx != idx, 0))` and `fastbin_index` are checked — they check whether the size after shifting right by 4 bits (on 64-bit systems) matches the size corresponding to the current fastbin (0x7f is equivalent to 0x70). Address alignment and size alignment are not checked.

For example, modify the fd pointer to point to a suitable offset before __realloc_hook (usually the offset 0x23 before __malloc_hook), then two malloc(0x60) calls allocate the fake chunk at that address, achieving control over __realloc_hook and __malloc_hook.

Since one_gadget may fail because the stack layout does not satisfy its constraints, you can modify __malloc_hook to realloc+offset and modify __realloc_hook to one_gadget to change the stack layout and get a shell.
Besides realloc + offset, you can also change the stack layout by triggering a malloc error that executes malloc.

# Unsorted Bin Attack

## Unsorted Bin Leak
 The unsorted bin is a doubly linked list, so in the unsorted bin list there must be a node whose fd pointer points inside the main_arena structure. If we can leak the correct fd pointer, we can obtain an address with a fixed offset from main_arena, and this offset can be determined through debugging.
 
main_arena is a global variable of type struct malloc_state, the only instance through which ptmalloc manages the main arena. Speaking of global variables, one can immediately think that it will be placed in a segment such as .data or .bss. So if we have the .so file of the libc used by the process, we can obtain the offset between main_arena and the libc base address, thereby obtaining the libc base address.

The address difference between main_arena and __malloc_hook is 0x10: `main_arena_offset = ELF("libc.so.6").symbols["__malloc_hook"] + 0x10`

## Unsorted Bin Attack
When an unsorted bin chunk is taken out (first in, first out), the address of this unsorted bin chunk is written to the location bck->fd. (This applies when there is more than one chunk in the unsorted bin before the removal; otherwise it is handled as last_remainder.) Here the chunk is first removed from the list, then it is judged whether the size of the removed chunk equals the requested size. If it matches, it is returned; if not, it is placed into the smallbin or largebin according to its size.

```c
  while ((victim = unsorted_chunks (av)->bk) != unsorted_chunks (av))
        {
        ……
			bck = victim->bk;
          /* remove from unsorted list */
          unsorted_chunks (av)->bk = bck;
          bck->fd = unsorted_chunks (av);
          ……
          }
```

In other words, if we control the bk value of the last chunk, i.e. bck, we can write unsorted_chunks (av) to an arbitrary address (the address of bck). This method is usually used to write a large value to global_max_fast, thereby expanding the fast bin range, and even overflowing the fastbinsY array to achieve an arbitrary address write.

# Large Bin Attack
Large Bin Attack works by modifying the bk or bk_nextsize of a chunk located in the large bin, then letting another chunk enter the large bin, using the linked-list operations to write a heap address at the target address.

Before glibc-2.30, because the process of linking a chunk into the large bin lacked checks on the bk and bk_nextsize pointers, you could modify the bk and bk_nextsize pointers to perform two arbitrary address writes.

- If the large chunk being added is smaller than the smallest one, it enters the following processing flow
```c
			  bck = bin_at (av, victim_index);
              fwd = bck->fd;
               assert ((bck->bk->size & NON_MAIN_ARENA) == 0);
if ((unsigned long) (size) < (unsigned long) (bck->bk->size))
                    {
                      fwd = bck;
                      bck = bck->bk;

                      victim->fd_nextsize = fwd->fd;
                      victim->bk_nextsize = fwd->fd->bk_nextsize;
                      fwd->fd->bk_nextsize = victim->bk_nextsize->fd_nextsize = victim;
                    }
          victim->bk = bck;
          victim->fd = fwd;
          fwd->bk = victim;
          bck->fd = victim;
```
 Here, modifying bk at `  bck = bck->bk;` is not easy, because it is inside main_arena, so instead we modify `fwd->fd->bk_nextsize `. Then `  victim->bk_nextsize = fwd->fd->bk_nextsize;
                      fwd->fd->bk_nextsize = victim->bk_nextsize->fd_nextsize = victim;` will write a heap address at the location pointed to by `bk_nextsize`.

# Tcache attack
Tcache was introduced in Glibc 2.26. Its next pointer points to the memory region of the next chunk, not the chunk header. It has fewer checks than the fast bin, and has a count limit.
##  bypass tcache to bin
If you want a freed chunk to bypass the tcache, here are the methods:

- Free a chunk that is not within the tcache size range.
- Free 7 chunks of the same size to fill the tcache bin at the corresponding position.
- If the challenge limits the number of free calls, you need to satisfy `tcache->entries[tc_idx] != NULL` and then malloc multiple times to ` --(tcache->counts[tc_idx])`, setting the counts at the corresponding position to -1 to bypass the tcache. Here you just need to make sure the size parameter of malloc maps to the same idx, and the fd you set must be an accessible address: `tcache->entries[tc_idx] = e->next;`, because `e->next;` will be accessed.

## tcache key
Starting from glibc 2.29, tcache added a key field. This field is located in the bk field of the chunk, and its value is the address of the tcache structure. If free() detects chunk->bk == tcache, it will traverse the tcache to check whether the corresponding list contains this chunk. Some older glibcs of the latest versions (such as the newer 2.27) have also introduced this protection mechanism.

### tcache key bypass
If there is a key-based double free check, before performing a tcache double free you also need to find a way to bypass the tcache key protection.
Common tcache key bypass methods are as follows:

- Clearing the tcache key: use some UAF method to clear the tcache key recorded in the freed chunk, thereby bypassing this check.
- house of kauri: by modifying the size, the same memory freed twice enters different entries.
- tcache stash with fastbin double free: there is no strict double free detection in the fastbin. We can complete a double free in the fastbin after filling the corresponding tcache chain, then pour the fastbin chunks back into the tcache through the stash mechanism. At this point, the fast bin double free becomes a tcache double free. (That is, for the double free on higher versions, note that the fastbin contains 1->2->1->2->1... After 1 is allocated away, since 1 is taken, the fastbin becomes 2->1->2, and then what enters the tcache is 2->1->2.)
- House of Botcake
Free the same chunk into both the tcache and the unsorted bin. The chunk freed into the unsorted bin changes size through heap consolidation. Compared with the previous method, the advantage of this method is that one double free can be used multiple times, because the chunks controlling the same memory belong to different structures (one holds chunkB of the unsorted bin, the other holds chunkB in the tcache bin; you can use the unsorted bin chunkB to modify the chunkB that entered the tcache bin, then malloc out the chunkB in the tcache bin, malloc out the chunk corresponding to fd, then free again to put chunkB into the tcache bin, and then the unsorted bin chunkB can continue to modify it).
  1. Allocate 7 chunks of the same size (larger than 0x80), then allocate three more: chunk A, chunk B, and chunk C (C prevents consolidation). chunk A and B have the same size as the previous 7.
  2. Free the first 7 and chunk A. The first 7 all enter the tcache bin; chunk A enters the unsorted bin.
  3. Free chunk B; chunk B will merge with chunk A.
  4. Allocate one chunk out of the tcache bin.
  5. Free chunk B again; now B exists in both the unsorted bin and the tcache bin.
  6. Then malloc once or multiple times with a size no larger than the merged chunkAB size, and you can get a chunk that controls chunkB.

# Heap Overlapping

The heap overlapping here refers to making one heap chunk able to control the header of another heap chunk, rather than only controlling the memory region. This condition is much stronger than an ordinary UAF, because an ordinary UAF controls the memory region but cannot control the header.
## UAF to Heap Overlapping
In the fastbin, forge a chunk (forge the size) in the memory region of a controllable heap chunk, then use a UAF partial address write to modify the fd to the header of the forged chunk. After that, allocating the fake chunk out lets you control part of the next heap chunk (the start address is inside the original chunk, but the size is the same — of course, it overflows), causing heap overlapping. (But a UAF can actually be understood as a heap_overlap in a sense. In the tcache you don't need to forge a chunk — just modify the fd.)

### Brute-force method (brute-forcing four bits)
Through heap layout, make the address of chunk p (i.e. the chunk used for unlink) be 0x?????0??. Then brute-force it to 0x????00?? with a probability of 1/16. This makes it easy to write p when doing a partial write.

### Improved direct method (no special restrictions)
Through backward consolidation, the constructed fd and bk pointers are preserved. This way, when they are taken out of the unsorted bin, this fd will not be destroyed. And the fd exists inside the chunk rather than immediately after the chunk metadata, so you can partially write a single 0 byte into fd — unlike before, where at least two bytes had to be written into fd.

The goal is to let H1 merge with C0:

- C0 satisfies the unlink condition construction. That is, a D->C0->A doubly linked list (no need to set D->bk and A->fd)

- C0. size == H1.prev_size

The general process:
1. Free A, C0, D. Now unsortedbin: D->C0->A. By freeing B0, B0 and C0 merge into BC, thereby preserving the constructed fake chunk pointers: C0->fd, C0->bk. (Here C0 is the chunk p to be forged, with address aligned to 0x????00 (the last two digits are 0), no brute-forcing needed.)
2. Allocate B1, splitting BC. B1.size = B0.size+0x20. At this point you can change C0's size to 0x551. Then allocate the remaining C1, D, A back.

#  HOOK
To finally obtain a shell, besides overwriting the GOT table, the other way is overwriting function pointers. There are many hook structures in glibc that can be exploited.
## malloc_hook / realloc_hook
- The argument of the function called by malloc_hook is size; realloc

Modify the fd pointer to point to a suitable offset before __realloc_hook (usually the offset 0x23 before __malloc_hook), then two malloc(0x60) calls allocate the fake chunk at that address, achieving control over __realloc_hook and __malloc_hook.

Since one_gadget may fail because the stack layout does not satisfy its constraints, you can modify __malloc_hook to realloc+offset and modify __realloc_hook to one_gadget to change the stack layout and get a shell.

[RoarCtf - pwn](https://n0va-scy.github.io/2022/02/14/RoarCTF/)
[SUCTF Freshman Competition PWN_Beginner-friendly WP](https://xz.aliyun.com/t/3383?time__1311=n4%2bxnii=G=0Q0=DODgD0x05DIdrFuoraT=eOeC4D)
Besides realloc + offset, you can also change the stack layout by triggering a malloc error that executes malloc.

> Freeing the same chunk twice will trigger a malloc_printer error, which will then also call malloc_hook. If the content of malloc_hook is onegadget, the error-reporting process will change the program's execution flow and go on to execute onegadget, getshell.   
> You can free the same heap chunk twice in a row to trigger malloc_hook. The benefit of doing this is that malloc_printer is called before malloc_hook, so the stack structure is changed, and then using realloc to adjust the offset has a greater chance of satisfying the onegadget conditions.

# mmap leak
When the glibc heap is initialized, 132KB of memory is carved out at once for the program to use. That is to say, the tcache/fast/small/unsorted/large we mentioned are all produced on the basis of this 132KB (0x21000). So if you directly malloc more than 132KB, the system will call mmap to allocate memory near libc. After testing, although a size greater than 132KB can make it allocated near libc, if it does not reach a certain size, the offset between the allocated memory address and libc is not very certain. Here we draw on the experience of predecessors: allocating 0x200000 of memory can make the offset fixed. ## Shellcode on the heap
[Detailed explanation of using the mprotect function in pwn](https://xz.aliyun.com/t/12717?time__1311=GqGxu7i=itdeqGN4nxU2BFm3GKvdh7hbD)

```cpp
int mprotect(void * addr, size_t len, int prot)

其中变量addr代表对应内存块的指针，len代表内存块的大小，而prot代表内存块所拥有的权限

对于prot来说，对应权限依照以下规则改变值

无法访问 即PROT_NONE：不允许访问，值为 0
可读权限 即PROT_READ：可读，值加 1
可写权限 即PROT_WRITE：可读， 值加 2
可执行权限 即PROT_EXEC：可执行，值加 4
```
From the above poc we can know that the length of the ROP chain is greater than that of shellcode.
When there is a layout length limit, you can solve it by arranging a ROP call to the mprotect function and then + shellcode, or directly shellcode (no mprotect needed).

When calling a libc function, some of them internally call functions in the libc GOT table. You can put the libc into IDA to view the functions called by that libc function. If there are functions starting with j such as j_strlen, then it is possible that a function in the libc GOT table is called (~~or just set breakpoints on all libcgot functions :) then you'd know for sure~~).

- 2.35: write GOT0 to the rsp for stack pivoting, GOT1 to `pop rsp ret`, modify the libcgot that will be called to plt0, and then write the ROP chain at the corresponding pivot destination.

```cpp

#include <unistd.h>
#include <string.h>
int main() {
    char *addr = 0;
    size_t len = 0;
    printf("printf %p\n", printf);
    char* libc_got=printf+0x195dc0+0x8;
    printf("libc got %p\n",libc_got);
    char* plt0=printf-0x30240;
    char* pop_rsp=printf-0x2eae5;
    char* pop_rdi=printf-0x2e7be;
    char* pop_rsi=printf-0x24686;
    char* pop_rax=printf-0x17b70;
    char* pop_rsp_jmp_rax=printf+0xe1da5;
    *(unsigned long long *)libc_got=libc_got+0x10;
    *(unsigned long long *)(libc_got+0x8)=pop_rsp;
    *(unsigned long long *)(libc_got+0x10)=pop_rdi;
    *(unsigned long long *)(libc_got+0x18)=printf+0x1582a7;  ///bin/sh  addr
```

- 2.36-2.38: GOT0 and GOT1 are both no longer writable, but the following libc.got entries are all writable.
![在这里插入图片描述](/images/csdn/2024/csdn-140671857/image-041-3a9abe52a4.png)
The idea is: one control-flow hijack gadget -> set the rsp-related value to rdi -> call the gets function to write the ROP chain at the return address.

Refer to the regular expression given by master veritas for finding suitable gadgets in IDA.
```cpp
.*lea\s+rdi,\s+\[rsp\+.*\n(?:.*\n){0,9}.*call\s+j_.*
```
Conditions: leak libc + write 3 libc.got entries + have gadgets for pairwise jumps between the corresponding three libcgot functions.
