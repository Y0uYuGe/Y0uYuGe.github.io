# make_pair
This function parses the login information entered by the user. The `make_pair` used here is a function in the C++ standard library that creates a `std::pair` object. `std::pair` is a template class that can store two related values at the same time, and these two values can usually be of different types.

Specifically, in this line of code:

```cpp
return make_pair(tok_ring[0], tok_ring[1]);
```

- `tok_ring` is a `std::vector<std::string_view>` returned by the `splitToken` function, which stores the string fragments separated by a specific delimiter (a colon `:` in this case). `tok_ring[0]` represents the first fragment (usually the username), and `tok_ring[1]` represents the second fragment (usually the password).

- The `make_pair` function takes these two string fragments as arguments and creates a new `std::pair` object, where the first element is `tok_ring[0]` (the username) and the second element is `tok_ring[1]` (the password).

The line `return make_pair(tok_ring[0], tok_ring[1]);` packages the parsed username and password into a `std::pair` object and returns it as the return value of the `parseUser` function.


# string_view and string


### Internal implementation and characteristics of `std::string`

`std::string` is a class that encapsulates a dynamic array for storing and manipulating strings. Its internal structure usually contains the following components:

1. **Character pointer**: a pointer to a dynamically allocated character array that stores the actual content of the string.
2. **Length**: a member variable that records the current actual length of the string (the number of characters, excluding the terminating null character).
3. **Capacity**: usually another member variable that records the total amount of memory currently allocated, reserved for when the string grows, avoiding frequent memory reallocation.
4. **Management mechanism**: `std::string` is responsible for allocating and freeing dynamic memory, including automatic growth strategies (automatically expanding memory capacity when the string grows) and deep copying (copying the content when copied or assigned).

### Internal implementation and characteristics of `std::string_view`

In contrast, `std::string_view` is a lightweight string view class that does not own the string's memory but is a reference to an existing string. Its internal structure is relatively simple:

1. **Character pointer**: a `const char*` or `const CharT*` pointer to the string data, pointing to the start of the externally stored string.
2. **Length**: a member variable that records the length of the string referenced by the `string_view`.
   
The design philosophy of `string_view` is a zero-cost string reference: it involves no memory management, does not copy strings, and only provides a view of an existing string. It improves efficiency, especially when string operations are frequent or unnecessary string copying needs to be avoided.

### Example

Suppose we have a function that needs to count how many times a character appears in a string:

- **Using `std::string`**:
  ``cpp
std::string str = "Hello, World!";
std::size_t count = std::count(str.begin(), str.end(), 'o');
  ``
  Here, even if a temporary string literal is passed in, str still creates a copy on the stack.

- **Using `std::string_view`**:
  ``cpp
std::string_view view = "Hello, View!";
std::size_t count = std::count(view.begin(), view.end(), 'e');
  ``
string_view` directly references the original string data, with no extra memory allocation or copy operations, so it is more efficient.

In summary, `std::string` provides complete string management, including memory allocation and ownership, making it suitable for scenarios where you need to modify strings or store string data independently. `std::string_view`, as an efficient read-only view, is suitable for situations where you do not need to modify the string and want to avoid copy overhead.


#  SSO (Short String Optimization) and Heap Allocation
The following is a basic, conceptual diagram of the internal structure of string:

```cpp
template<typename CharT, typename Traits, typename Allocator>
class basic_string {
private:
    union {
        struct {
            // 指向堆上分配的字符串数据的指针（如果未使用SSO）
            CharT* ptr;
            // 字符串长度（不包括终止的空字符）
            size_t length;
            // 总容量（包括已使用的和未使用的，仅当在堆上分配时有意义）
            size_t capacity;
        };
        // 内部缓冲区，用于SSO（假设大小为N，N通常由实现决定，例如15或22）
        CharT small_buffer[N];
    };

    // 一个或几个比特位用于标记是否使用SSO
    bool is_short_string : 1;

    // 其他成员和方法...
};
```

The `basic_string` class implements SSO through a union. A union allows the same memory region to be interpreted as different data types. When the string is short enough to satisfy the SSO condition, the string data is stored directly in `small_buffer`, and the `ptr`, `length`, and `capacity` fields are not used. The `is_short_string` flag indicates whether the current `std::string` object uses SSO. If the string exceeds the SSO length limit, `ptr` points to the string data allocated on the heap, while `length` and `capacity` record the actual length of the string and the total allocated capacity.

# The mechanisms of `std::basic_string`, `std::string`, and `std::string_view`
In C++, memory allocation can happen on the heap and on the stack. For `std::string`, `std::string_view`, and `std::basic_string`, the memory allocation mechanisms differ, as follows:

### `std::string`

- **Memory allocation**: the `std::string` object itself (i.e., the control block, including the pointer to the character data, the size, and other information) is usually allocated on the stack. However, the actual character data of the string is usually dynamically allocated, i.e., on the heap. This is because the length of a string is not fixed and may change at runtime.
  
- **Small String Optimization (SSO)**: many implementations (such as libstdc++ and libc++) use a technique called Small String Optimization (SSO). In this case, if the length of the string is below a certain threshold, the character data may be stored inside the object itself on the stack instead of being allocated on the heap. This optimization reduces the heap allocation overhead for small strings.

- **How it allocates**: it uses the standard library's allocator mechanism to manage memory. By default, `std::allocator<char>` is used for heap memory allocation.

```cpp
#include <string>

int main() {
    std::string str = "Hello, World!"; // 可能使用SSO
    str += " More text."; // 可能触发堆分配
    return 0;
}
```

### `std::string_view`

- **Memory allocation**: `std::string_view` does not own the string data; it is just a view of existing character data, so it does not perform heap memory allocation. The `std::string_view` object itself is usually allocated on the stack. It holds a pointer to the character data and size information representing the length.

- **How it allocates**: no dynamic memory allocation is needed because it does not manage memory. `std::string_view` only stores a pointer and length information and is usually created on the stack.

```cpp
#include <string_view>
#include <iostream>

int main() {
    const char* text = "Hello, World!"; // 字符数据在常量区
    std::string_view view(text); // view在栈上，不分配堆内存
    std::cout << view << std::endl;
    return 0;
}
```

### `std::basic_string`

- **Memory allocation**: the allocation mechanism of `std::basic_string` is similar to that of `std::string`, because `std::string` is a specialization of `std::basic_string<char>`. For different character types (such as `wchar_t`), the allocation mechanism is still the same: the object itself is on the stack, and the character data is usually on the heap.

- **Small String Optimization (SSO)**: like `std::string`, `std::basic_string` can also use SSO to optimize the storage of small strings and reduce heap allocations.

- **How it allocates**: it uses the allocator specified by the template parameter (default is `std::allocator<CharT>`) to manage dynamic memory.

```cpp
#include <string>
#include <iostream>

int main() {
    std::basic_string<wchar_t> wide_str = L"Hello, World!"; // 可能在栈上用SSO，否则在堆上
    wide_str += L" More text."; // 可能触发堆分配
    std::wcout << wide_str << std::endl;
    return 0;
}
```

# allocator Allocation
In C++, `std::allocator` is the default allocator used by the standard library for dynamic memory management. It provides a simple and effective memory allocation and deallocation mechanism for standard library containers (such as `std::vector`, `std::string`, `std::basic_string`, etc.).

### Default behavior of `std::allocator`

`std::allocator` is a template class that provides the basic functionality of allocating and freeing memory. Its behavior is similar to the `new` and `delete` operators. The key member functions of `std::allocator` and their purposes are as follows:

1. **`allocate(size_t n)`**: allocates enough uninitialized storage to hold `n` objects of type `T`. It returns a pointer to the allocated storage.

2. **`deallocate(T* p, size_t n)`**: frees the previously allocated memory block `p`, where `n` is the number of objects allocated in `allocate`.

3. **`construct(T* p, Args&&... args)`**: constructs an object at the memory pointed to by `p` using the passed arguments. Since C++17, standard library containers no longer explicitly call `construct` and `destroy`; instead, they directly use placement new and explicitly call destructors.

4. **`destroy(T* p)`**: destroys the object at the memory pointed to by `p`.

### Allocator usage in `std::basic_string`

`std::basic_string` is a template class, and `std::string` is a specialization of it (i.e., `std::basic_string<char>`). `std::basic_string` uses an allocator to manage the memory of its character data. By default, `std::basic_string` uses `std::allocator` for memory management.

#### Memory allocation process

1. **Object creation**: when a `std::string` or `std::basic_string` object is created, the string object itself is usually allocated on the stack (if created inside a function). This object contains metadata such as a pointer to the character data, the size, and the capacity of the string.

2. **Character data allocation**: the character data is usually allocated on the heap. The `allocate` method of `std::allocator` is used to allocate enough memory on the heap to store the string characters.

3. **Small String Optimization (SSO)**: many implementations use Small String Optimization (SSO), i.e., when the string is short, the character data is stored in an internal buffer of the string object instead of on the heap. This reduces heap allocation overhead for small strings.

4. **Memory deallocation**: when a `std::string` or `std::basic_string` object is destroyed, the allocator's `deallocate` method is called to free the memory of the character data.

# Approach
1. In parseUser, a string_view is used to reference the string object obtained from getInput. If the string object holds enough characters when created, heap allocation is used to store the string. When parseUser finishes, the string object's destructor is called and frees the heap chunk, but the string_view still stores the pointer to the corresponding string on the heap.
2. What parseUser ultimately returns are two string_view objects, and their pointers both point to heap chunks that have already been freed.
3. getInput is called again next; if the input is too long, it will also be allocated on the heap. If the size is right, it can overlap with the heap chunk freed by the previous destructor, allowing us to modify the previous content on the heap — and the string_view objects' pointers happen to point to that freed heap chunk.
4. Because of the earlier splitting in parseUser, the two string_view objects' pointers point to the corresponding content on the heap (username: password). So if the new input has the same length and format as before, the username portion of the input will be recognized as admin, bypassing the earlier admin check.
